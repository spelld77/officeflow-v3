# 후속 개선 전체 공통설계

작성일: 2026-10-08. 상태: 공통설계와 1차 구현/검증·사용 확인 완료. 전체 기능 구현 완료가 아님.

진행 기록: [1차 상세설계](25-follow-up-phase-1-design.md)는 작성 완료(2026-10-08).
[1차 구현·검증 보고](26-follow-up-phase-1-results.md)에 실제 반영 범위와 검증을 기록한다.
2026-10-08 사용자 사용 확인과 로컬 커밋 후 2차 상세설계 진행 승인을 받았다.
2·3차 구현은 아직 하지 않았다. 아래 공통 원칙은 계속 적용한다.

이 문서는 [후속 개선 목록](23-follow-up-improvements.md)의 승인된 방향을 연결하는
데이터·파일 보존·변경 이력·삭제·백업·조회 계약이다. 기능이 구현되었다는 뜻이 아니다.
공통설계 작성 당시에는 프로그램 코드/DB를 변경하지 않았다. 후속 1차 작업에서는 코드와
격리 테스트 DB만 변경하며 실제 사용자 DB/첨부, 버전, 배포물, GitHub는 변경하지 않는다.

진행 방식은 전체 공통설계 후 `1차 상세설계/구현/검증 → 사용 확인 → 2차 상세설계/구현/검증
→ 사용 확인 → 3차 상세설계/구현/검증`이다. 상세설계는 해당 차수의 구현 **전에** 한다.
공통 계약을 변경할 필요가 생기면 먼저 이 문서와 영향받는 차수의 설계를 함께 갱신한다.

## 1. 목표와 범위

### 1.1 목표

- 현재 첨부를 편집하면서도 중요한 원본과 특정 시점 파일을 별도로 보존한다.
- Windows 탐색기에서 사용할 사본을 익숙한 저장 대화상자로 내보낸다.
- 업무의 변경 과정과 사용자가 지정한 중요 시점을 한 곳에서 확인한다.
- 목록에서 항목을 없애는 것과 실제 파일을 없애는 것을 구분한다.
- 원본·작업본·보관본·업무 묶음이 같은 파일 보존/백업 기반을 사용한다.
- 기능을 나눠 구현해도 앞 단계의 데이터와 동작을 뒤 단계에서 다시 갈아엎지 않게 한다.

### 1.2 유지할 기존 동작

- 일반 업무, 반복 회차, 다중 알림, 업무일지, 체크리스트의 역할을 유지한다.
- 알림 `확인`은 해당 알림 처리, `업무 완료`는 업무/선택 회차 완료다.
  미래 알림을 중단하는 기존 완료 규칙을 바꾸지 않고 표시와 갱신을 고친다.
- 기존 첨부는 수정 가능한 일반 첨부로 이행한다. 자동으로 원본을 지정하지 않는다.
- 휴지통에 넣은 업무의 기록·첨부·보관 자료는 그대로 남는다.
- Python 실행 방식과 로컬 데이터 저장을 유지한다. Git 설치나 외부 계정은 필요 없다.

### 1.3 이번 공통설계에 자동 포함하지 않는 것

- U1 업무/알림 중복 표시 개선: 기존 보류 유지. 관련 식별 계약만 호환되게 마련한다.
- 실제 Git 연동, 클라우드 동기화, 시간대 목록 파일 제외.
- 업무일지 편집 이력, 체크리스트 항목별 자동 이력, 문서 내용 자체의 자동 버전 관리.
- 외부 저장 파일 자동 추적/재가져오기, 자동 보관·업무자료 자동 파일 삭제.
  보기용 임시 캐시의 안전한 자동 정리는 7.4절의 별도 정책을 따른다.
- 원본 덮어쓰기/보호 해제, 첨부 메모 검색·상속, 설명 TXT 동봉,
  여러 업무의 검색 결과를 한 번에 저장하는 기능.

## 2. 사용자 용어와 역할

| 용어 | 의미 | 편집/보관 원칙 |
| --- | --- | --- |
| 일반 첨부 | 지금처럼 업무에 첨부한 파일 | 편집 가능. 기존 파일은 이 상태로 유지 |
| 원본 | 사용자가 기준 자료로 지정한 파일 | 지정 당시 저장된 내용으로 고정 |
| 작업본 | 원본·작업본·보관본에서 새로 만든 내부 편집 파일 | 다른 파일과 독립적으로 수정 가능 |
| 보관본 | 사용자가 이름을 붙여 남긴 특정 시점의 파일 | 내용 고정. 이름은 `v2.0`, `검토 반영` 등 자유롭게 지정 |
| 다른 이름으로 저장 | 선택 파일을 사용자 폴더로 복사 | 외부의 독립 파일. 자동으로 열거나 재연결하지 않음 |
| 업무 변경 이력 | 저장에 성공한 업무 필드의 변화 | 자동 기록, 과거 값 조회/비교 |
| 중요 시점 보관(묶음) | 당시 업무 정보와 선택 파일을 함께 남긴 자료 | 사용자 수동 기록, 내용 고정 |

`사본`은 설명에서 복사된 파일을 뜻할 수 있지만, 내부 항목의 역할 이름으로 추가하지 않는다.
파일의 표시 이름, 보관 이름, 실제 저장 경로는 서로 다르다. 표시 이름을 바꿔도 파일 식별자는 유지한다.
보관 이름의 `v2.0`에 특별한 프로그램 의미를 부여하지 않는다. 생성 시각과 내부 ID로 구분하며
이름이 같아도 서로 다른 보관본이다. 기본 제안 이름은 `보관본 1`, `보관본 2`와 같은 순번이다.

### 2.1 기존 설명·결과메모·업무일지와의 구분

- 설명: 현재 수행해야 할 업무의 내용. 수정하면 현재 내용이 바뀐다.
- 체크리스트: 현재 실행할 세부 항목과 완료 여부.
- 결과메모: 업무 또는 반복 회차의 현재 결과 요약.
- 업무일지: 날짜별로 남기는 사용자의 업무 기록. 기존 작성/검색 기능을 유지한다.
- 자동 이력: 위에서 승인한 업무 필드가 **어떻게 바뀌었는지** 보여준다.
- 중요 시점 보관: **그때 어떤 내용과 파일이 있었는지** 보여준다.

이력/보관 때문에 설명·결과메모를 두 번 입력하게 하지 않는다. 전체 업무일지를 묶음에 복제하지 않는다.
현재 체크리스트는 업무 공통 자료다. 이 기능을 계기로 회차별 체크리스트 시스템을 새로 만들지 않는다.

## 3. 공통 불변 조건

1. 편집 가능한 파일과 고정 보관 파일은 같은 물리 파일을 공유하지 않는다.
   단순 읽기 전용 속성이나 하드링크를 원본/보관본의 보호 수단으로 삼지 않는다.
2. 고정 파일은 생성 후 프로그램이 내용을 덮어쓰지 않는다. 새 내용은 새 파일/새 ID로 만든다.
3. 파일을 사용하는 모든 DB 연결을 확인한 뒤에만 물리 삭제 후보로 판정한다.
   첨부 목록에서 사라졌다는 이유만으로 묶음의 파일을 삭제하지 않는다.
4. 실패한 복사, 취소된 보관, 저장 실패는 완료 항목/성공 이력을 만들지 않는다.
5. DB 커밋과 파일시스템 변경은 하나의 원자적 트랜잭션이 아니므로 준비·확정·복구 절차를 둔다.
6. 업무 변경과 그 자동 이력은 같은 DB 트랜잭션으로 저장한다.
7. 파일 전체를 메모리에 읽지 않는다. 복사·해시는 작업 스레드에서 제한된 크기로 처리한다.
8. 실제 파일의 변경 확인 결과와 최초 첨부 시 정보, 보관 시 검증값을 구분한다.
9. 원본/보관본 열기, 삭제, 내보내기, 백업은 모든 화면에서 같은 서비스 계약을 사용한다.
10. 외부 저장과 내부 삭제는 독립 작업이다. 저장 성공을 자동 삭제 허가로 해석하지 않는다.
11. 반복 회차의 식별자는 원래 발생 시각이다. 이동된 표시 날짜를 회차 ID로 사용하지 않는다.
12. 미저장 입력과 실제 실행 상태를 분리한다. 갱신 알림이 편집 중인 값을 덮어쓰지 않는다.

프로그램을 통한 실수는 이 규칙으로 줄인다. 탐색기/관리자에 의한 직접 변경, 회사 보안 제품,
저장 장치 고장까지 완전히 막는다는 보장은 하지 않는다. 같은 디스크의 내부 보관본은 외부 백업의 대체물이 아니다.

## 4. 현재 코드에서 바뀌어야 할 경계

| 현재 구조 | 공통설계에서의 보완 |
| --- | --- |
| `attachments` 한 행이 파일 경로·크기·해시를 직접 보유 | 사용자 항목과 실제 파일 자산을 분리 |
| 편집 시 최초 해시/크기와 실제 내용이 달라질 수 있음 | 최초 기준과 최근 관측 정보를 분리, 중복 판단 전 실제 내용 확인 |
| 일반 열기가 관리 파일 경로를 외부 편집기에 전달 | 일반/작업본은 유지, 고정 파일은 보기용 복사본으로만 열기 |
| 업무 영구 삭제 후 첨부 경로 목록을 제거 | 참조와 보관 자료를 포함한 삭제 계획을 먼저 생성 |
| 삭제 복구·백업이 주로 기존 첨부 경로를 조회 | 모든 자산 참조와 미확정 작업을 고려하는 공통 목록 사용 |
| 업무 편집의 저장은 알림 변경과 한 DB 트랜잭션 | 이력도 포함. 목록/알림/결과메모 등 다른 변경 경로까지 같은 원칙 적용 |
| 프로세스 안의 파일 게이트 | 외부 편집 잠금을 별도로 처리. 게이트만으로 문서 고정을 보장하지 않음 |

기존 Presentation → Application → Domain / Infrastructure 구조를 유지한다.
화면에서 새 SQL, 경로 삭제, 보호 파일 직접 열기를 구현하지 않는다.
공통 서비스는 필요한 경계를 추가하는 것이며 전체 프로그램을 새 프레임워크로 교체하는 작업이 아니다.

## 5. 공통 데이터 모델

아래 이름은 설계상의 논리 이름이다. 실제 컬럼/클래스 이름과 Alembic revision은 차수별 상세설계에서 확정한다.
필요 없는 차수의 테이블을 미리 설치하지 않는다. ID는 내용 해시가 아니라 독립 식별자다.

### 5.1 파일 계층

| 모델 | 핵심 정보 | 소유·참조 규칙 |
| --- | --- | --- |
| `file_assets` | ID, mutable/frozen, 상대 경로, 생성 시각, 최근 관측 정보; frozen은 고정 크기/SHA-256/확정 시각 | 실제 파일의 유일한 경로 원장. 자산은 업무 삭제 CASCADE 대상이 아님 |
| 기존 `attachments` 확장 | 업무 ID, 자산 ID, 표시 이름, 역할, 문서 계열 ID, 순서, 메모, 최초 첨부 정보 | mutable 자산의 소유자는 한 첨부뿐. original 역할은 frozen을 참조 |
| `attachment_versions` | 업무/문서 계열 ID, frozen 자산 ID, 보관 이름·메모·시각, 출처 정보 | 작업본이 삭제되어도 유지. 같은 계열의 작업본/보관본을 연결 |
| `snapshot_files` | 묶음 ID, frozen 자산 ID, 당시 이름·역할·메모·순서·검증값·출처 | 현재 첨부 이름이나 메모를 JOIN해서 과거 표시를 바꾸지 않음 |

문서 계열 ID는 원본 → 작업본 → 보관본 → 새 작업본의 관계를 묶는 단순 식별자다.
독립적인 문서관리/프로젝트 시스템을 추가하지 않는다. 계열에 속한 항목이 일부 삭제되어도
남은 보관본을 조회할 수 있다. `첨부 수`는 현재 연결된 첨부 수이며 보관본 수와 혼동하지 않는다.

출처 첨부/보관본 ID는 추적용으로만 사용한다. 출처 항목 삭제 시 이 링크는 비울 수 있지만,
보관 당시 출처 이름·시각·식별 정보는 남긴다. **출처 링크와 파일 보존 참조는 다르다.**
자산 ID에 대한 참조는 삭제 제한을 적용한다. 참조 수 캐시만 믿지 않고 실제 연결을 조회한다.

동일 내용이어도 새 작업본에는 반드시 독립적인 파일을 만든다. 일반 파일 추가의 중복 방지와
명시적인 `작업본 만들기`를 구분한다. 해시가 같다는 이유로 기존 작업본을 재사용하지 않는다.
이미 고정된 자산을 묶음에서 사용하는 경우에만 같은 frozen 자산을 참조할 수 있다.
mutable 자산을 묶음에 직접 연결하지 않으며, 전체 파일의 자동 해시 중복 제거는 범위 밖이다.

### 5.2 현재 파일 정보와 무결성

- 첨부의 최초 크기/해시: 최초 가져오기 기준. 기존 값을 그대로 보존한다.
  과거 기준 해시가 없으면 `최초 정보 없음`으로 다루고 새 관측값을 과거의 검증값처럼 만들지 않는다.
- mutable 자산의 관측 크기/해시/시각/파일 특성: 마지막으로 확인한 실제 파일 정보.
- frozen 자산의 고정 크기/해시: 보관을 확정한 내용의 기준. 변경 발견 시 덮어쓰지 않는다.
- 파일 크기/수정 시각은 해시 재검사 후보를 고르는 힌트이지 내용 동일성의 증명이 아니다.
- 일반 첨부/작업본의 해시 변화는 `수정됨`이다. 그것만으로 `손상`이라고 단정하지 않는다.
- frozen 변화는 `보관 후 변경됨`, 읽기 실패는 `확인 불가`, 파일 없음은 `누락`으로 구분한다.
  frozen의 보기/내보내기/재사용도 고정 검증값을 확인한다. 불일치하면 정상 보관본으로 전달하지 않고
  원장·실제 파일을 보존한 채 경고한다. 일반 첨부의 정상 편집과 같은 자동 갱신을 하지 않는다.
- 중복이라고 판단하여 가져오기를 생략하기 전 후보 파일의 현재 내용을 다시 확인한다.
  오래된 최초 해시만으로 새 파일을 버리지 않는다. 목록을 열 때 모든 파일을 재해시하지 않는다.
- 내보내기/보관은 현재 디스크 내용을 읽는다. 외부 편집기의 미저장 내용은 읽을 수 없다.

### 5.3 이력·업무 묶음 계층

| 모델 | 핵심 정보 | 원칙 |
| --- | --- | --- |
| `task_history` | 업무 ID, 범위(task/occurrence), 원래 회차 시각, 명령 ID, 변경 시각/순서, 변경 필드, before/after, payload 버전 | 성공한 의미 있는 변경을 append-only로 저장 |
| `task_snapshots` | 업무 ID, 범위/회차, 보관 이름, 캡처/확정 시각, 고정 payload, 작업 ID | 당시 기본 정보·결과메모·체크리스트 상태를 저장 |
| `snapshot_files` | 위 파일 계층의 항목 | 선택 파일 전부 확정되어야 묶음 완료 |
| `file_operation_receipts` | 작업 ID, 종류, 커밋 시각 | 파일 작업의 DB 확정 여부를 재시작 때 판별 |

payload는 형식 버전을 포함한 JSON 등 명시적 데이터로 저장한다. 객체 pickle을 저장하지 않는다.
큰 문서 바이너리는 SQLite BLOB으로 넣지 않고 파일 자산으로 보관한다.
자동 이력의 before/after는 해당 시점의 승인된 여섯 필드 그룹 전체를 가진다.
변경 필드 목록은 별도로 둔다. 두 시점 비교에 이전 이력 수천 건을 처음부터 재생할 필요가 없게 한다.
텍스트 중복 저장의 비용은 허용하되 바이너리/전체 업무일지를 복제하지 않는다.
조회 인덱스는 업무/회차/시각/고유 ID, 문서 계열/보관 시각, 자산 참조 FK를 중심으로 둔다.
시간은 기존 UTC 저장 원칙을 따르고, 화면은 사용자 시간대와 요일을 포함해 표시한다.

## 6. 서비스·동시성 공통 계약

### 6.1 책임 분리

- 파일 참조 해석: 첨부/개별 보관본/묶음 항목을 받아 실제 자산과 열기 정책을 반환한다.
- 파일 캡처: 안정적으로 읽기, 스트리밍 복사/해시, 취소, 준비 파일 검증을 담당한다.
- 첨부 명령: 원본 지정, 작업본 생성, 보관본 생성, 메모/순서 변경을 담당한다.
- 외부 저장: 단일 저장/여러 파일 저장과 이름 충돌 결과를 담당한다.
- 삭제 계획: 논리 연결, 살아 있는 참조, 물리 삭제 후보, 확인 범위를 계산한다.
- 업무 변경: 기존 저장/알림 트랜잭션과 자동 이력을 조정한다.
- 업무 보관: 일관된 정보 캡처와 선택 파일 전부의 확정을 조정한다.
- 이력 조회: 자동 변경/수동 묶음을 공통 타임라인으로 투영한다.

실패 결과는 취소·잠금·내용 변경·누락·권한·공간 부족·DB 충돌을 구분한다.
오류에는 해당 표시 이름과 재시도 방법을 포함하되 문서 내용 자체를 로그에 남기지 않는다.

### 6.2 잠금 순서와 작업 스레드

- 파일 게이트는 새 파일 공개/삭제 계획 확정 등 짧은 구간에 사용한다.
- DB 쓰기 트랜잭션을 잡은 채 파일 복사, 해시 계산, 사용자 응답, 파일 잠금을 기다리지 않는다.
- 파일 게이트와 DB 쓰기를 함께 쓰는 구간의 순서는 `파일 게이트 → DB 트랜잭션`으로 통일한다.
- 자산 참조의 생성/이동/제거도 이 계약을 사용한다. 삭제 확인 뒤 다른 참조가 생기는 경쟁을
  화면별 코드가 우회하지 않게 한다. 사용 예약 조회와 최종 삭제 판단 역시 같은 게이트에서 한다.
- 캡처 중 자산에 사용 예약(pin)을 걸어 앱의 삭제/교체를 막는다. 사용 중이면 삭제는
  기다리며 UI를 멈추지 않고 `사용 중, 잠시 후 다시 시도`로 반환한다.
- 여러 파일의 읽기 핸들은 자산 ID 순으로 확보한다. 일부 실패 시 확보한 핸들을 모두 닫는다.
- 장시간 작업은 worker에서 진행한다. DB session은 worker가 따로 만들고 닫는다.
  GUI 스레드와 session/열린 ORM 객체를 공유하지 않는다.
- 복사 동시 실행은 제한된 작업 큐로 제어한다. 취소 시 준비 파일만 처리하고 원본은 보존한다.
- 알림 스케줄러는 계속 작동한다. 작업 중 전체 주 창이나 알림 처리까지 비활성화하지 않는다.

### 6.3 외부 편집 중인 파일

고정 보관에는 Windows의 읽기 공유만 허용하고 쓰기/삭제 공유를 허용하지 않는 읽기 핸들을 사용한다.
호환되지 않는 기존 핸들이 있으면 공유 위반으로 실패하므로 `문서를 저장하고 닫은 뒤 다시 시도`를 안내한다.
확보한 핸들이 유지되는 동안의 공유 규칙을 이용하는 설계이며 앱 내부 게이트와 별개다.
근거: [Microsoft CreateFileW 공유 모드 문서](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew).

보안 제품/파일시스템 때문에 안정적인 캡처를 확보할 수 없으면 보관 성공으로 처리하지 않는다.
파일 특성의 전후 비교만으로 같은 보호를 제공했다고 주장하지 않는다. 보안 정책을 우회하지 않는다.
전원 장애나 저장 장치/필터 드라이버 문제까지 위 공유 모드가 보장하는 것은 아니다.

## 7. 파일 생성·확정·복구

### 7.1 관리 위치

- 기존 첨부 경로는 이행 시 이동하지 않는다.
- 새 편집 파일은 기존 UUID 기반 저장 규칙을 재사용한다.
- 새 고정 파일은 첨부 루트의 구분된 `frozen/` 영역에 독립 ID로 저장한다.
- 준비 파일/작업 저널은 첨부 루트의 `.operations/` 아래에 둔다.
- 보기용 사본은 데이터 루트의 별도 캐시 영역에 둔다. 고정 원장 파일과 분리한다.
- 모든 관리 상대 경로는 루트 포함 여부를 검사한다. `..`, 절대 경로,
  junction/symlink 등으로 관리 루트를 벗어나는 파일 공개/삭제는 허용하지 않는다.

### 7.2 내부 생성 절차

1. 작업 ID를 발급하고 검증된 출처/예정 자산 ID/준비 경로를 작업 저널에 기록한다.
2. 현재 내용을 안정적으로 읽어 `.part` 파일에 복사한다. 크기·해시를 계산하고 flush/fsync 한다.
3. 복사가 모두 성공했는지 확인한다. 사용자 취소나 읽기 실패는 이 단계에서 중단한다.
4. 짧은 파일 게이트 안에서 예상 출처/DB 상태를 다시 확인한다. 미등록 새 경로에 파일을 공개한다.
5. 게이트를 유지한 짧은 DB 트랜잭션에서 예상 출처/캡처 토큰을 최종 확인하고
   자산·사용자 항목·참조·작업 확정 영수증을 함께 저장한다. 중간에 상태가 바뀌면 확정하지 않는다.
6. DB 커밋 후에만 성공과 화면 갱신을 알리고 저널/불필요한 준비 파일을 정리한다.

새 ID의 파일은 기존 관리 파일을 덮어쓰지 않는다. 파일 공개 후 DB 실패 시 새 파일만 복구 대상으로 남긴다.
복구 과정에서 다른 작업의 파일이나 출처를 지우지 않는다. OS 수준 flush를 하더라도 모든 하드웨어의
정전 내구성을 절대 보장하지는 않는다.

| 중단 지점 | 재시작 시 처리 |
| --- | --- |
| 준비 복사 도중 | 유효한 저널과 미확정 상태를 확인하여 해당 준비 파일만 정리/실패 표시 |
| 파일 공개 후 DB 커밋 전 | 확정 영수증과 참조가 모두 없음을 확인한 해당 새 파일만 복구 대상으로 처리 |
| DB 커밋 후 완료 통지 전 | 영수증·자산·참조를 확인하여 이미 완료로 인식. 재시도 시 중복 생성 금지 |
| 삭제 격리 후 DB 실패/중단 | DB 참조가 남으면 원래 위치로 복구. 복구 불가 시 파일을 보존하고 경고 |
| DB 삭제 커밋 후 물리 정리 실패 | 다시 참조/저널을 확인해 재시도. 실패를 기록하고 사용 중인 파일은 삭제하지 않음 |
| 저널 손상/경로 불명/상태 충돌 | 보존하고 점검 대상으로 표시. 파일명 추측으로 삭제하지 않음 |

같은 작업 ID의 재시도는 이미 확정된 결과를 반환한다. 실패 후 새 선택으로 보관하면 새 작업 ID를 사용한다.
저널 복구는 자산 목록을 읽을 수 있는 스키마 준비 후, 자동 정리보다 먼저 수행한다.
기존 `.trash` 삭제 저널도 계속 인식하고 모든 새 참조를 확인한다.

### 7.3 원본 지정·열기·작업본

- 원본 지정은 **지정 시각의 저장된 파일을 새 frozen 자산으로 복사**하는 명령이다.
  최초 첨부 당시 내용으로 되돌리지 않는다. 성공한 뒤 첨부 역할/자산 연결을 변경한다.
- 기존 편집 파일을 제자리에서 원본으로 바꾸지 않는다. 따라서 예전 편집 경로에 저장하더라도
  새 기준 파일은 바뀌지 않는다. 이전 편집 파일은 해제 첨부로 남겨 업무 소유와 확인/정리 동선을 유지한다.
  원본 지정 성공과 동시에 자동 삭제하지 않는다. 이후 명시적인 정리는 사용 예약/참조/잠금 규칙을 따른다.
- 원본/보관본 열기는 보기용 사본을 만들어 전달한다. 이 사본에서 저장한 내용은 보관 자료에 반영되지 않는다.
- 보기용 사본임을 안내한다. 만료 캐시는 잠금과 수정 여부를 확인하며, 편집 중이거나 수정된 사본을
  종료 시 무조건 삭제하지 않는다. 수정된 사본은 별도 저장 후 명시적으로 다시 첨부하도록 안내한다.
  보기 캐시는 정식 보관/백업 대상이 아니며 원본에 자동 반영하지 않는다.
- 작업본은 일반 첨부, 원본, 다른 작업본, 보관본의 현재 저장 내용에서 생성할 수 있다.
  외부 파일을 저장한 뒤 자동으로 열지 않는다. 작업본 생성도 기본적으로 자동 열지 않는다.
- v3 이후 v2부터 다시 시작하면 `v2 보관본 → 새 작업본`으로 만든다.
  v3나 기존 작업본을 자동으로 되돌리거나 덮어쓰지 않는다.
- 보호 파일의 관리 경로를 일반 열기/탐색기 선택 기능으로 편집용 경로처럼 노출하지 않는다.
  고정 자료의 사용 동선은 보기용 사본 또는 외부 저장이다.

### 7.4 보기용 캐시 재사용·정리

2026-10-08 추가 합의: 보기용 사본은 관리가 필요한 임시 캐시이며, 반복 열람만으로 계속 쌓이지 않게 한다.
이 원칙은 2차 첨부 역할 기능과 함께 구현한다. 구현 후의 별도 과제로 미루지 않는다.

- 같은 고정 자산을 다시 볼 때는 출처 검증과 캐시 상태 확인 후 수정되지 않은 사본을 재사용한다.
  캐시가 정리되었으면 다시 만든다. 매 열람마다 첨부/작업본 항목을 추가하지 않는다.
- 출처 자산 ID·생성 시 검증값·마지막 사용 시각 등 캐시 관리 정보를 남겨 재시작 후에도 구분한다.
- 만료/용량·개수 기준에 따라 앱이 만든 미수정·미사용 캐시만 제한된 작업으로 자동 정리한다.
  실행/종료 때 전체 파일을 무조건 삭제하거나 GUI 스레드에서 대량 검사하지 않는다.
- 사용 중·수정됨·상태 판정 불가인 사본은 자동 삭제하거나 원본 내용으로 덮어쓰지 않는다.
  수정된 사본은 별도 저장 안내 대상으로 유지한다. 정리 실패는 보류/재시도하며 알림을 중단시키지 않는다.
- 캐시 상한에 도달해도 보호 대상 사본을 강제로 삭제하지 않는다. 안전하게 정리할 수 없는 자료가 남으면 안내한다.
- 캐시 정리는 전용 관리 영역과 등록된 캐시만 대상으로 한다. 원본·작업본·보관본·외부 저장 파일에는 적용하지 않는다.
- 재사용, 수정/사용 중 정리 방지, 재시작 후 정리, 정리된 캐시 재생성, 삭제 실패를 2차 검증에 포함한다.

정리 시점·유효기간·용량/개수 기준·사용 중 판정 방법은 2차 상세설계에서 확정한다.
캐시는 정식 보관/백업 대상이 아니므로 수정 자료를 캐시에만 장기 보관하도록 유도하지 않는다.

## 8. 외부 저장 공통 계약

### 8.1 단일 파일

- 오른쪽 메뉴의 `다른 이름으로 저장…`에서 표준 저장 대화상자를 연다.
- 기본 이름은 목록의 파일 이름이다. 마지막 저장 폴더를 기억하되 없거나 접근 불가하면 안전한 기본 폴더를 쓴다.
- 확장자를 보존하며 Windows 금지 이름/문자/경로 길이 오류는 실제 쓰기 전에 안내한다.
- 관리 루트/보기 캐시로 다시 저장하거나 현재 출처와 같은 파일을 덮어쓰는 선택은 거절한다.
- 기존 외부 파일은 명시적 덮어쓰기 확인 후에만 교체한다. 확인 후 대상이 바뀌면 다시 확인한다.
- 대상 폴더 안의 임시 파일로 먼저 복사·검증한 뒤 공개한다. 실패/취소 시 기존 대상은 유지한다.
  대상 존재 확인과 공개 사이의 경쟁도 처리하며, 임의 `os.replace`로 새로 생긴 파일을 덮어쓰지 않는다.
- 플랫폼의 부분 교체 오류/동시 외부 변경으로 원경로 자동 복구가 안전하지 않으면,
  이전 내용과 새 준비 자료를 복구 파일로 보존하고 위치/확인 필요를 안내한다.
  상세 동작은 1차 설계 7.3절에 둔다. 불확실한 교체를 정상 성공으로 처리하지 않는다.
- 성공하면 저장 위치와 `폴더 열기`를 제공한다. 저장한 문서를 자동으로 열지 않는다.

### 8.2 여러 파일

- 선택한 현재 첨부/보관본을 표준 폴더 선택 후 한 번에 저장한다. 초기에는 한 업무 안의 선택이다.
- 같은 이름은 기존 파일과 이번 선택 모두를 고려해 `이름 (1).확장자` 등으로 자동 번호를 붙인다.
  공개 직전에 충돌해도 덮어쓰지 않고 새 이름을 예약한다. 원본 파일 이름은 변경하지 않는다.
- 묶음 보관과 달리 외부 저장은 파일별 완료를 허용한다. 실패/취소 시 완료 파일을 되지우지 않는다.
- `완료/실패/미처리`, 실제 저장 이름과 위치를 보여준다. 재시도는 실패/미처리 파일을 대상으로 한다.
- 외부 임시 파일은 앱이 만들었다고 확인되는 것만 정리한다. 재시작 시 사용자 폴더를 임의 청소하지 않는다.
- 출력 파일은 앱 백업/정리 대상이 아니다. 앱 삭제 이후에도 해당 폴더에 남지만
  같은 디스크라면 장치 고장에 대한 별도 백업 효과까지 있다고 안내하지 않는다.

파일을 정리하기 전 `열기 → 선택 → 외부 저장 → 저장 결과/폴더 확인 → 필요하면 내부 삭제`를 제공한다.
오래됨/완료 업무/큰 용량만으로 정리할 파일을 자동 결정하지 않는다.

## 9. 삭제·해제 공통 계약

### 9.1 참조와 삭제 계획

파일의 살아 있는 보존 참조는 현재/해제 첨부, 원본, 개별 보관본, 업무 묶음의 파일 항목이다.
휴지통 업무의 참조도 살아 있다. 사용 예약과 진행 중 작업도 물리 삭제를 막는다.
단순 출처 정보는 내용 보존 참조가 아니다.

삭제 전 계획에는 대상 논리 항목 수, 업무/회차, 보관 자료 수, 물리 삭제 가능 파일 수,
다른 항목이 사용하므로 유지되는 파일 수, 사용 중/확인 불가 항목을 넣는다.
확인 화면을 띄운 뒤 상태가 바뀌면 계획을 다시 계산한다. UI에 표시한 예전 경로 목록만 지우지 않는다.
DB 연결 해제와 파일 격리/물리 정리는 7절의 저널 복구 규칙을 사용한다.

### 9.2 명령별 정책

| 명령 | 남는 것/없애는 것 |
| --- | --- |
| 첨부 해제 | 현재 첨부 표시에서 제외. 기존 해제 파일 보존 정책 유지, 정리 화면에서 확인 가능 |
| 첨부 항목 삭제 | 해당 항목과 내용 보존 연결을 삭제. 다른 보관 참조가 있으면 그 파일은 유지 |
| 개별 보관본 삭제 | 보관본 항목을 명시적으로 삭제. 묶음 등이 같은 자산을 사용하면 물리 파일 유지 |
| 중요 시점 묶음 삭제 | 묶음과 그 파일 참조를 명시적으로 삭제. 다른 항목의 파일은 유지 |
| 업무 휴지통 이동/복원 | 첨부·해제 파일·보관본·이력·묶음을 전부 보존/재표시 |
| 업무 영구 삭제 | 휴지통에서만 허용. 아래 보관 자료 확인 절차까지 통과한 범위만 삭제 |

업무 영구 삭제는 업무/첨부 삭제 확인과 **보관본·이력·묶음까지 삭제하는 범위 확인**을 구분한다.
초기에는 보관 자료를 남기려면 영구 삭제를 취소하고 휴지통 상태로 보존한다.
`업무는 지웠지만 주인 없는 보관함으로 이전` 기능은 새로 만들지 않는다.
다른 업무/자료가 자산을 참조한다면 전체 삭제를 승인해도 그 자산은 유지한다.
기존 업무일지의 연결 해제/보존 규칙은 변경하지 않고 삭제 계획에 함께 안내한다.

정리 화면의 고아 판정도 이 참조 계산을 재사용한다. `.part`/저널/캐시/격리 파일을
일반 고아 첨부로 묶어 삭제하지 않는다. 미분류 파일은 보존하고 검토 대상으로 둔다.
정상 완료한 업무에 대해서도 첨부나 이력을 자동으로 삭제하지 않는다.

## 10. 자동 이력과 중요 시점 보관

### 10.1 자동 이력

초기 자동 이력 필드는 제목·설명·일정·중요도·상태·결과메모다.
일정은 종일 여부, 시작/종료, 시간대, 반복 규칙/종료 조건, 해당 회차 예외를 한 변경 그룹으로 다룬다.
알림 발생/확인/재알림, 내부 갱신 시각, 파일 관측 정보만의 변화는 이력에 넣지 않는다.
고정/첨부 순서/메모/체크리스트 세부 편집/업무일지 편집의 자동 이력은 초기 범위에 추가하지 않는다.

- 편집 저장, 목록의 완료/대기, 알림 창의 업무 완료, 결과메모 수정 등 모든 의미 있는 변경 경로를 포함한다.
- 한 사용자 명령은 범위별 바뀐 필드를 묶어 기록한다. 여러 repository 호출마다 중복 기록하지 않는다.
  여러 범위를 함께 바꾸는 명령은 같은 명령 ID로 묶고 조회 화면에서 관계를 표시한다.
- 동일 값 저장, 취소, 실패는 기록하지 않는다. 회차 캐시 생성만으로 사용자 변경을 기록하지 않는다.
- 새 업무는 생성 시 기준 정보를 남긴다. 기존 업무는 첫 의미 있는 변경 때 이전 값의
  `이력 시작 기준`과 변경 결과를 기록한다. 실제 과거 생성 이력처럼 위장하지 않는다.
- before/after는 저장에 성공한 실제 값을 담는다. 저장 전 UI 임시 문자열은 기록하지 않는다.
- 현재 업무/회차 변경, 관련 알림 상태 변경, 이력 추가를 한 DB 트랜잭션으로 확정한다.
- 초기에는 자동 이력을 기간/개수로 잘라 삭제하지 않는다. 명시적인 업무 영구 삭제는 위 정책을 따른다.

반복 업무의 공통 필드 변경은 업무 범위, 회차의 완료/결과/이동은 해당 원래 회차 시각 범위로 기록한다.
회차 조회에서는 `업무 공통 변경`과 `이 회차 변경`을 구분한다. 미래 회차를 전부 생성해 같은 이력을 복제하지 않는다.

### 10.2 중요 시점 묶음

사용자가 보관 이름과 첨부 선택만 지정하면 현재 저장된 기본 정보·결과메모·체크리스트 상태를 캡처한다.
반복 업무는 공통 정보와 선택 회차를 함께 기록하고 공통 체크리스트임을 표시한다.
현재 첨부 메모/순서/이름도 선택 파일의 당시 정보로 보관한다. 원래 업무의 메모나 체크 상태를 바꾸지 않는다.

1. 선택 출처를 확인하고 파일 사용 예약을 확보한다. 모든 선택 파일의 안정적인 읽기 핸들을 확보한다.
2. 짧은 DB 읽기 스냅샷에서 업무/회차/체크리스트/선택 파일 정보를 읽어 캡처 토큰과 시각을 만든다.
3. worker에서 mutable 파일을 새 frozen으로 복사하고, 기존 frozen은 무결성을 확인해 참조한다.
4. 확정 전 짧은 DB 쓰기 구간에서 캡처 대상 정보/참조가 여전히 같음을 확인한다.
   내용이 바뀌었으면 확정하지 않고 `자료가 변경됨, 다시 보관`을 안내한다.
5. 4번과 같은 DB 트랜잭션에서 묶음·모든 파일 참조·새 자산·확정 영수증을 저장한다.
   선택 파일의 읽기 핸들과 사용 예약은 이 확정까지 유지하고 성공/실패/취소 모두에서 해제한다.

캡처 토큰은 관련 값과 항목 ID/연결의 정규화된 지문이다. `task.updated_at`만 비교하지 않는다.
체크리스트, 첨부 이름·메모·순서·역할·선택 자산, 회차 결과의 변화도 확인한다.
UI 전체/모든 이력을 토큰에 넣지 않으며 파일 내용은 확보된 읽기 핸들/검증값으로 보호한다.
표시할 기준 시각은 캡처 시각이고, 긴 복사의 완료 시각도 별도로 가진다.

선택 파일 하나라도 누락·잠금·변경·복사 실패하면 전체 묶음을 완료로 만들지 않는다.
파일 없이 보관하는 것은 처음부터 그렇게 선택한 경우에만 허용한다. 실패 항목을 조용히 빼지 않는다.
과거 묶음은 읽기 전용이다. 텍스트 복사/파일 외부 저장/파일에서 새 작업본 생성은 가능하지만,
과거 상태·일정·알림까지 통째로 되돌리는 복원 버튼은 초기 범위가 아니다.
과거 설명을 현재에 활용하려면 복사해 일반 편집 흐름에서 명시적으로 저장한다.
이때의 변경도 새 이력으로 남고 이후 시점의 기존 이력을 없애지 않는다.

### 10.3 타임라인·비교

- 자동 변경과 수동 보관을 시간순으로 조회한다. 별도의 중복 타임라인 저장 테이블을 만들지 않는다.
- 항목 종류, 시각, 이름/변경 필드, 업무/회차 범위를 표시한다. 좁은 창에서는 세로 목록을 사용한다.
- 최신 일부부터 페이지 조회하며 시각+안정적인 ID로 다음 페이지를 구분한다.
  상세 설명/파일 목록은 항목을 열 때 가져온다. 표시용 이력 전체를 메모리에 누적하지 않는다.
- 두 시점을 고르면 호환되는 범위의 before/after 또는 묶음 값을 비교한다.
  공통 업무와 서로 다른 회차를 설명 없이 같은 대상으로 비교하지 않는다.
- 설명은 긴 문장을 실제 문구 그대로 비교하고 줄/단어 변경을 표시한다.
  `예산 100만원`과 `예산 100(천원)`의 의미가 같다는 식으로 추론하지 않는다.
- 파일 비교는 묶음의 선택/제외·이름·보관 식별/검증값을 보여준다.
  HWP/Excel 바이너리의 내부 편집 내용 비교나 매 저장 자동 파일 이력을 약속하지 않는다.
- 과거 이력의 이름/텍스트는 현재 업무 수정에 의해 바뀌지 않는다. 내용 열람만으로 업무일지를 새로 작성하지 않는다.

## 11. 알림 표시와 화면 갱신

- 조회 모델에 업무/회차 상태와 알림 처리 상태를 따로 둔다.
  `업무 완료 · 알림 확인함`, `업무 완료 · 이후 알림 중단`처럼 구분한다.
- 이미 확인한 알림 이력을 업무 완료 때문에 전부 `완료`로 다시 쓰지 않는다.
- 열린 편집창은 편집 초안과 실제 실행 상태를 분리한다. 완료 이후 미래 예약을 여전히 예정처럼 표시하지 않는다.
- 저장/완료 커밋 후 영향받은 업무/회차/첨부/이력 ID를 UI에 전달한다.
  목록·달력·오늘 알림·열린 기록/첨부창은 필요한 부분만 재조회한다.
- worker 결과는 Qt의 queued 연결 등으로 GUI 스레드에 전달한다.
  늦게 도착한 조회 결과가 더 최신 화면을 덮어쓰지 않도록 요청 토큰을 확인한다.
- 반복 회차 완료는 다른 회차의 미래 알림을 중단시키지 않는다.
- U1을 진행할 때 사용할 묶기 키는 `(업무 ID, 원래 회차 시각 또는 업무 범위)`다.
  일정만/알림만 있는 날짜를 모두 표현하고 업무 수와 알림 수를 분리할 수 있게 한다.
  이번 차수에서는 그 키가 있다는 이유로 중복 표시 UI를 자동 구현하지 않는다.

## 12. 백업·복원·이행

### 12.1 백업의 완전성

백업 파일 목록은 첨부 행만 조회하지 않고 자산과 모든 보존 참조를 함께 해석한다.
원본·작업본·해제 파일·개별 보관본·업무 묶음·이력·메모·순서·출처·작업 확정 정보를 포함한다.
같은 frozen 자산을 여러 항목이 참조하면 백업에 한 번 넣고 모든 연결을 보존한다.
DB 파일만 복사한 것은 전체 첨부 백업이 아니다.

- DB는 SQLite의 일관된 복사 방식을 사용한다. 실행 중 DB 파일의 단순 복사로 대체하지 않는다.
  근거: [SQLite Online Backup API](https://www.sqlite.org/backup.html).
- DB 캡처의 파일 목록에 사용 예약을 걸고 파일별 안정적인 독립 복사를 만든다.
  mutable 파일의 하드링크를 백업/고정본의 독립 사본이라고 간주하지 않는다.
- 각 파일의 실제 복사 크기/해시를 manifest에 기록한다. mutable 최초 해시 변화 때문에 실패시키지 않는다.
- 필요한 파일이 없거나 안정적으로 읽히지 않으면 완전한 백업 성공으로 알리지 않는다.
  자동 백업은 기존 정상 백업을 유지하고 실패/재시도 상태를 알린다. 프로그램/알림은 계속 작동한다.
- 백업은 DB의 한 시점과 각 파일의 안정적인 캡처를 보존한다. 외부 편집 가능한 모든 문서의 내용을
  정확히 한 순간으로 동결했다는 의미는 아니다. 그 보장이 필요한 작업은 10절의 수동 묶음이다.
- 보기 캐시/미완성 복사는 정상 첨부로 포함하지 않는다. 미분류 기존 파일/격리 자료는
  함부로 버리지 않고 별도 복구 목록에 구분하여 보존한다. 참조 자산으로 위장하지 않는다.
- 파일 수가 많아도 전체 ZIP 구성/해시는 worker에서 제한 메모리로 처리하고 긴 전역 게이트를 피한다.

### 12.2 복원·호환

- 백업 형식 버전과 DB 스키마 버전을 검사한다. 참조 자산이 모두 존재하고 manifest와 일치하는지 확인한다.
- 별도 준비 위치에서 DB FK/스키마/파일 참조를 검사한 뒤 데이터 루트를 교체한다.
  복원 실패 시 현재 데이터를 그대로 사용한다. 이전 루트의 복구 가능성도 유지한다.
- 복원한 미분류/격리 파일은 복구 영역으로 유지하고 정상 첨부인 것처럼 자동 연결하지 않는다.
- 이전 백업은 지원되는 이행 경로로 읽는다. 새 스키마를 모르는 구버전 실행은 시작 전에 차단한다.
- 구버전 실행 파일만 덮어써서 다운그레이드하지 않는다. 필요하면 업그레이드 전 전체 백업과
  그 스키마를 지원하는 프로그램을 함께 별도 데이터 루트에 복원한다.
- 새 schema/full backup fixture를 배포 게이트에 추가한다. 실제 사용자 데이터를 테스트에 쓰지 않는다.

### 12.3 차수별 이행

- 1차: 최초/관측 메타데이터 분리 등 필요한 최소 변경만 한다. 파일 참조 서비스는 기존 첨부를 어댑터로 지원한다.
  2차의 역할/자산 연결이 추가되어도 외부 저장 API는 파일 참조를 받아 동일하게 동작하도록 한다.
- 2차: 파일 자산·역할·문서 계열·보관본·메모·확정 영수증을 도입한다.
  기존 첨부 ID/순서/이름/경로를 유지하여 mutable 자산과 연결한다. 파일을 대량 이동/복사하지 않는다.
  기존 해시/크기는 최초 정보로 보존하고 최근 관측은 실제 확인 때 채운다.
- 3차: 자동 이력·업무 묶음·묶음 파일 참조를 추가한다. 2차 자산/파일 캡처 기반을 재사용한다.
- 파일 경로의 권위는 2차 이후 자산 원장 하나로 통일한다.
  이전 컬럼을 잠시 호환용으로 남겨도 두 원장을 독립 수정하는 구조로 유지하지 않는다.
- DB 이행 전 스키마 백업/검증을 수행한다. 파일 내용을 바꾸는 작업은 별도 확정 프로토콜을 사용한다.
  대량 파일 이동이 필요해지는 설계 변경은 전체 백업/복구 계획부터 다시 검토한다.
- 기존 데이터로 자동 원본/보관본을 만들거나 이력의 과거를 재구성하지 않는다.
  제거한 v2.6 가져오기 기능을 다시 도입하지 않는다.

## 13. UI·성능 공통 기준

- 주 화면에 새 관리 탭/버튼을 계속 늘리지 않는다. 첨부 관련 행동은 기존 첨부 목록/오른쪽 메뉴,
  업무 이력/중요 시점 보관은 기존 업무 상세/기록 동선을 중심으로 상세설계한다.
- 원본/작업본 표시, 보관본 개수, 짧은 첨부 메모를 필요할 때 보여준다. 메모가 없으면 빈 영역을 만들지 않는다.
- 보관 이름·파일 이름·전체 경로를 동시에 늘어놓지 않는다. 긴 이름은 잘림 대신 상세/툴팁으로 확인 가능하게 한다.
- 기본 Tab 이동에 드문 관리 옵션을 과하게 끼워 넣지 않는다. 좁은 창에서도 저장/취소와 핵심 동선은 접근 가능해야 한다.
- [개발 및 품질 지침](06-development-process.md)의 밝은 테마를 명시적으로 적용한다.
  viewport, 선택/비활성 상태, 메뉴/드롭다운/연결 창도 글자색·배경색을 함께 확인한다.
- 조회는 페이지 단위, 상세는 지연 조회한다. 목록에는 파일 바이너리/전체 설명을 적재하지 않는다.
- 파일 관측/해시는 요청 항목·유효하지 않은 후보부터 작업 큐로 처리한다.
  타이머마다 모든 첨부를 스캔하거나 타임라인을 위해 모든 파일을 재검사하지 않는다.
- 이력 건수 증가와 큰 파일 처리의 메모리 비용을 분리한다. 파일 크기에 비례하여 메모리가 증가하지 않게 한다.
- 이력/보관 조회와 파일 작업에 실패해도 알림 프로세스가 종료되지 않도록 예외 경계를 유지한다.

이는 이미 승인된 보존/범위 정책을 구현하기 위한 상세 결정이다. 승인된 1~6번을 다시 묻지 않는다.
보관자료 유지 정책 변경, 자동 삭제, 새 외부 연동처럼 목적·위험이 달라지는 확장은 별도로 확인한다.

## 15. 대표 사용 흐름으로 설계 확인

1. 서식 첨부 → 원본 지정: 지금 저장된 내용이 고정된다. 이미 수정한 내용도 지정 시 기준으로 포함된다.
2. 원본 → 작업본 A 생성 → 외부 편집/저장: 원본은 바뀌지 않는다.
3. 작업본 A → `검토 반영 v2` 보관 → 작업본 A 계속 수정 → `제출 전 v3` 보관:
   v2/v3는 고정되고 A는 계속 편집 가능하다.
4. v2부터 다시 시작 → 작업본 B 생성: A/v3는 유지된다. 전 업무 상태/알림을 되돌리지 않는다.
5. 중요 시점 보관에 v2와 B 선택: v2는 고정 자산 참조, B는 캡처한 고정 파일로 묶음에 들어간다.
   B가 잠겨 읽히지 않으면 묶음 전체는 완료로 남지 않는다.
6. B를 첨부 목록에서 삭제: 묶음의 고정 파일은 계속 열린다. 출처 표시가 없어져도 내용은 남는다.
7. 원본/v2/v3/선택 작업 파일을 함께 외부 저장: 폴더 선택 한 번, 동명은 번호 처리,
   자동 문서 열기 없음. 결과 폴더 확인 후 필요한 내부 자료만 별도로 정리한다.
8. 업무 휴지통 이동: 모든 자료/이력은 남는다. 영구 삭제하려면 보관 자료까지의 범위를 확인한다.
9. 새 PC에서 전체 백업 복원: 원본·작업본·보관본·메모·묶음·이력·참조가 함께 복원되어야 한다.

## 16. 설계 근거와 관리

검토한 현재 코드: `infrastructure/database/models.py`, `database/attachment_repository.py`,
`database/task_repository.py`, `database/task_saving.py`, `database/session.py`,
`application/attachments.py`, `application/tasks.py`, `application/task_saving.py`,
`infrastructure/attachments/storage.py`, `attachments/coordination.py`, `infrastructure/backup.py`,
`bootstrap/paths.py`, `presentation/record_dialog.py` 등 (`src/officeflow/` 기준).

이 문서는 현재 코드를 확인한 **목표 설계**다. 원장/타임라인/파일 캡처 모델이 지금 코드에 존재하는 것으로
읽지 않는다. 기존 [전체 아키텍처](03-architecture.md)와 [초기 데이터 모델](04-data-model.md)의
역사적 범위는 유지하며, 여기의 후속 기능을 구현할 때 관련 항목과 도움말을 함께 갱신한다.

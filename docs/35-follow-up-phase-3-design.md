# 후속 개선 3차 상세설계 — 업무 변경 이력·중요 시점 보관

작성일: 2026-10-09. 상태: **3차 소스 구현·격리 검증 완료, 사용자 사용 확인 전**.
기준 소스: 로컬 중간 커밋 `3be8a61bc830345df05a6a87de301f05682b391e`.
2차 최종 검사: [페이지·다중 삭제 보고](34-document-paging-and-multiple-delete.md) 5절.
공통 계약: [전체 공통설계](24-follow-up-common-design.md), 범위: [후속 목록](23-follow-up-improvements.md) U12/U13/U14.

설계 작성 요청에서는 문서만 변경했다. 이후 `3차 구현 및 테스트 진행해` 요청으로
3A/3B를 구현했다. 실제 범위·검사 결과·제한은 [3차 구현·검증 보고](36-follow-up-phase-3-results.md)를 따른다.
아래 미래형 문구는 구현 전에 정한 계약을 보존한 것이다. 코드와 격리 테스트 DB의
0014/0015 이행을 검증했으며 운영 DB·첨부와 프로그램 버전은 변경하지 않았다.
EXE/ZIP/설치 파일 재생성, GitHub 업로드, 실제 Git 내장 기능은 포함하지 않는다.
새 설계는 위 중간 커밋 **이후**의 검토 자료이며 2차 기능 커밋에 섞지 않는다.

## 1. 사용자가 얻는 것과 범위

- **자동 변경 이력:** 업무 내용을 바꾸고 저장하면 이전/이후 내용을 따로 입력하지 않아도 확인한다.
- **중요 시점 보관:** `팀장 검토 전`, `최종 제출 자료`처럼 이름과 선택 파일만 지정한다.
  그때의 저장된 업무 정보·결과메모·체크리스트와 선택 파일 내용을 고정한다.
- **이력·보관:** 두 종류를 같은 업무의 시간순 목록에서 찾고, 항목 하나의 변경 전후 또는 두 시점을 비교한다.

설명은 현재 지시사항, 체크리스트는 현재 실행 상태, 업무일지는 날짜별 사용 기록이다.
이력은 변경 과정, 중요 보관은 당시 자료다. 보관 때문에 일지를 자동 작성하거나 완료를 요구하지 않는다.
기존 완료 목록의 `completed_history_page`는 완료 업무/회차 조회이며 새 변경 이력 원장이 아니다.

제외: 글자마다 저장, 첨부 편집기의 매 저장 자동 버전, 체크리스트/업무일지의 세부 자동 이력,
HWP/Excel 내부 내용 비교, 과거 상태·알림의 통째 되돌리기, 자동 자료 삭제, 외부 동기화.
U1 일정/알림 중복 표시 개선은 계속 보류한다. 다른 업무까지 아우르는 이력 검색은 추가하지 않는다.

## 2. 자동 이력의 정확한 범위

### 2.1 여섯 필드 그룹

| 그룹 | 업무 공통 범위 | 특정 반복 회차 범위 |
| --- | --- | --- |
| 제목 | 저장된 title | 당시 공통 제목을 문맥으로 보존 |
| 설명 | 저장된 description | 당시 공통 설명을 문맥으로 보존 |
| 일정 | all_day, starts_at, ends_at, timezone, recurrence_rule 및 계산된 종료 조건 | 원래 occurrence_start/end와 이동된 effective_start/end |
| 중요도 | priority | 당시 공통 중요도를 문맥으로 보존 |
| 상태 | status와 완료 시각 | occurrence.status와 해당 회차 완료 시각 |
| 결과메모 | task.result_note | occurrence.result_note |

공통 변경은 미래 회차마다 복제하지 않는다. 회차의 before/after에는 당시 공통 문맥과
해당 회차의 여섯 그룹을 함께 저장하되 changed_fields에는 실제로 바꾼 회차 그룹만 넣는다.
일정/중요도/상태는 값 그대로, 설명/메모는 도메인의 기존 저장 정규화가 끝난 실제 문구를 저장한다.
이력 기능만을 위해 문구·단위·시간을 새롭게 정규화하지 않는다.

- `확인/다시 알림`, 알림 발생/예약 재계산, 첨부 관측, updated_at만의 변화는 제외한다.
- 알림의 `업무 완료/대기`는 실제 업무 상태를 바꾸므로 포함한다.
- 고정, 첨부 이름/메모/순서, 체크리스트 편집과 업무일지 편집은 자동 이력에 넣지 않는다.
- 같은 값을 저장하거나 pending 회차를 조회용으로 생성했을 뿐이면 기록하지 않는다.
- 하나의 완료+결과메모 저장은 상태·결과메모가 같이 바뀐 **한 변경**이다.
- 업무 휴지통 이동/복원은 보존 상태 변경이지 위 여섯 그룹의 변경은 아니다. 이력·묶음은 그대로 유지한다.

### 2.2 시작 기준과 반복 회차

- 새 업무는 생성 성공 트랜잭션에 `created`와 최초 상태를 저장한다.
- 기존 업무/기존 회차는 첫 의미 있는 변경 때 `baseline`(변경 직전 실제 상태)과 `change`를 같이 저장한다.
  `이력 기록 시작`이라고 표시하며 이전 생성일·과거 변경을 재구성하지 않는다.
- 변경 전 조회만으로 baseline을 만들지 않는다. 실패/취소된 첫 변경에도 만들지 않는다.
- 새 회차 첫 처리도 기본 pending/원래 일정/빈 결과에서의 변화를 기록한다.
  `ensure_occurrence` 자체가 생성 기록이나 완료 기록을 만들지는 않는다.
- 범위 키는 `task` 또는 `occ:<원래 발생 시각 UTC, 마이크로초 포함>`이다.
  이동된 표시 날짜와 occurrence 행 ID를 회차의 영구 식별자로 사용하지 않는다.
- 반복 규칙 수정 후 더는 발생하지 않는 과거 회차도 기존 저장 이력/묶음으로 조회할 수 있다.
  조회하려고 현행 반복 규칙에 맞는 새 회차를 생성하지 않는다.

## 3. 저장 경로·원자성

### 3.1 현재 코드에서 연결할 경로

| 진입점 | 이력과 같이 확정할 값 |
| --- | --- |
| TaskSaveService.save / 새 업무·편집 | 업무 생성/수정, 알림 규칙·예약, 실제 여섯 그룹 변경 |
| TaskService.quick_add/create/update | 생성 기준 또는 저장된 변경 |
| TaskService.transition/complete | 상태·완료 시각·선택 결과메모, 관련 알림 처리 |
| TaskService.update_result_note | 업무 또는 해당 회차 결과메모 |
| transition_occurrence / 회차 이동·건너뛰기·재개 | 해당 원래 회차의 상태·일정·결과, 회차 알림 처리 |
| ReminderService.complete/defer | 업무/회차 변경, 해당 delivery 처리, 이력 |

TaskSaveService는 이미 scoped SessionFactory의 write_unit_of_work를 사용한다.
다른 TaskService 경로와 ReminderService.complete/defer는 현 상태에서 별도 저장 호출이 있을 수 있다.
따라서 이력 INSERT만 뒤에 덧붙이지 않고 이 명령 경계를 함께 조정한다.

### 3.2 명령 단위 설계

- Application에 `TaskMutationContext`와 명령 실행 경계를 둔다.
  command_id(UUID), 명령 종류, now, 요청 출처, 예상 상태 토큰과 범위별 수집기를 가진다.
- DB 어댑터가 한 write_unit_of_work 안에서 scoped task/reminder repository와 이력 writer를 만든다.
  중첩 저장 호출은 **명시적으로 전달받은 같은 context**를 사용한다. 전역/thread-local collector는 쓰지 않는다.
- 실제 쓰기 직전 DB 상태를 before로 수집하고 명령의 모든 저장/알림 검증이 끝난 상태를 after로 수집한다.
  호출자가 먼저 읽었던 오래된 Task 객체를 현재 DB의 before로 간주하지 않는다.
- 편집/결과메모 저장은 열 때의 예상 값 토큰을 전달해 다른 창의 저장을 덮지 않게 한다.
  충돌하면 초안을 유지한다. 목록 상태 변경은 트랜잭션 안에서 읽은 실제 대상/범위를 사용한다.
- 바뀐 범위별로 여섯 그룹 전체 before/after와 changed_fields를 기록한다.
  같은 command_id/범위의 중간 repository 호출을 따로 사용자 변경으로 기록하지 않는다.
- 의미 있는 변경과 필요한 baseline, 알림 결과를 같은 트랜잭션에서 확정한다.
  이력 저장 실패/유효성 실패/경쟁 충돌이면 업무·알림도 롤백하고 입력을 보존한다.
- 순수 알림 확인/재알림과 스케줄러 cache 갱신은 기존 경계를 유지한다. 이력 수집기를 호출하지 않는다.
- 모든 프로덕션 변경 진입점을 연결한 뒤 완료 판정한다. SQLite trigger/ORM flush만으로
  사용자 명령과 내부 cache 변경을 추측하는 자동 감시는 도입하지 않는다.

command_id는 한 사용자 처리마다 발급하고 재시도하는 동안 유지한다.
성공한 명령을 같은 ID/요청으로 다시 실행하면 저장된 결과를 반환한다. ID만 같고 입력이 다르면 거절한다.
무변경 명령도 별도 `task_mutation_receipts`에 요청 지문/결과를 저장해 이후 새 입력의 재실행과 구분한다.
이 영수증은 타임라인에 표시하지 않으며 명령 재시도로 알림이 다시 처리되지 않게 한다.
결과는 업무/회차 ID·이력 ID·처리 종류로 보존한다. 재시도 시 `이미 처리됨`과 필요한 현재 재조회 값을
구분하여 과거 결과를 현재 상태로 위장하지 않는다. 모든 설명을 영수증에 또 복제하지 않는다.
작업 확정 전 UI 성공/이력 갱신 신호를 보내지 않는다.

## 4. 데이터 모델·이행 계획

아래는 설계 당시 **추가할 모델**이었다. 현재 개발 소스에는 0014/0015로 구현됐으며,
기존 공개 실행 파일이나 실제 사용자 DB에 이미 적용됐다는 뜻은 아니다.

### 4.1 3A — 자동 이력

예정 revision `0014_task_history`(구현 시 선행 revision/중복 번호 재확인):

- `task_history`: INTEGER PK AUTOINCREMENT, task_id FK(CASCADE), scope, scope_key,
  occurrence_start(NULL 허용), command_id, event_type(created/baseline/change), recorded_at,
  changed_fields JSON, before_payload(NULL 가능), after_payload, payload_version=1,
  짧은 summary(최대 200자). 바이너리는 넣지 않는다.
- UNIQUE(task_id, command_id, scope_key, event_type), 범위별 최초 created/baseline 중복 방지 partial index.
  scope/발생 시각/키의 대응과 payload 버전을 검증한다.
- 인덱스 `(task_id, recorded_at DESC, id DESC)`,
  `(task_id, scope_key, recorded_at DESC, id DESC)`, `(task_id, scope_key, id DESC)`.
- `task_mutation_receipts`: command_id PK, task_id FK(CASCADE), request_fingerprint,
  command_kind, committed_at, payload_version, 결과 식별자/반환 값 JSON.
  첨부의 `file_operation_receipts`와 섞어 파일 확정 기록으로 해석하지 않는다.

before/after는 승인된 여섯 그룹 **전체 값**을 담는다. 두 시점 비교에 처음부터 이력을 재생하지 않는다.
SQL 날짜는 기존 UTCDateTime, JSON 시각은 UTC ISO 형식의 마이크로초와 Z를 포함한다.
직렬화는 필드/enum/None/시간 형식을 고정하고 정렬 JSON의 SHA-256을 요청/상태 지문으로 사용한다.
scope별 최신 이력 ID는 인덱스 조회로 얻고 보관 캡처의 동시 변경 감지에도 사용한다.

### 4.2 3B — 중요 시점 보관

예정 revision `0015_task_snapshots`:

- `task_snapshots`: INTEGER PK AUTOINCREMENT, task_id FK(CASCADE), scope/scope_key,
  occurrence_start, label(1~200자), ordinal, captured_at, committed_at, job_id UNIQUE,
  request_fingerprint, payload_version=1, 정보 payload, file_count, 짧은 summary.
  UNIQUE(task_id, ordinal), 인덱스는 task/범위 + captured_at + id를 사용한다.
  ordinal은 확정 트랜잭션에서 해당 업무의 보관 순번으로 정한다. 삭제 뒤 기본 제안 번호가 다시
  사용될 수 있어도 보관의 식별자는 id/job_id다. 사용자 label을 순번/버전 숫자로 파싱하지 않는다.
- `snapshot_files`: INTEGER PK AUTOINCREMENT, snapshot_id FK(CASCADE), asset_id FK(RESTRICT),
  position, 당시 파일명/최초 이름/역할/메모, family_id, source_kind/source 정보,
  fixed_size_bytes/fixed_checksum, payload_version.
  UNIQUE(snapshot_id, position), UNIQUE(snapshot_id, source_kind, source 식별자), asset_id 인덱스.
- 출처 ID/이름/계열은 provenance다. 현재 출처가 없어져도 당시 이름/식별 정보를 유지한다.
  삭제로 비워질 수 있는 현재 출처 FK와 당시 payload를 구분한다. family 삭제 CASCADE로 파일 행을 없애지 않는다.
- snapshot_files는 active frozen 자산만 참조한다. 같은 자산을 두 선택이 사용하면 파일은 하나지만
  당시 선택 항목과 메타데이터는 각각 남긴다. mutable을 직접 참조하거나 해시만으로 병합하지 않는다.

보관 payload는 당시 여섯 그룹, 공통 고정 여부·생성 정보, 반복 회차/공통 문맥,
체크리스트의 ID/순서/문구/체크/완료 시각을 포함한다. 전체 업무일지와 알림 delivery는 복제하지 않는다.
알림 규칙·실행 상태는 이 묶음의 복원 대상이 아니며 `당시 알림을 복원하지 않음`을 안내한다.
선택 파일의 이름·메모·역할은 현재 첨부 JOIN으로 다시 만들지 않는다.

### 4.3 이행·호환

- 0013 → 0014 → 0015 순서, 기존 이행 백업/확인 창을 재사용한다.
  구현 단위 3A에는 이력 테이블만 도입하고 3B 파일 모델을 미리 생성하지 않는다.
- 기존 업무의 과거 이력/묶음은 만들지 않는다. 파일 이동·재해시·원본 재지정도 하지 않는다.
- 이전 전체 백업은 준비 루트에서 지원되는 이행 후 검사한다. 운영 자료로 테스트하지 않는다.
- 새 DB를 구버전으로 여는 것은 기존 revision 검사로 차단한다. EXE만 바꿔 내리는 다운그레이드는 금지한다.

## 5. 중요 시점 보관 명령

### 5.1 선택과 입력

- 이름 기본 제안은 `업무 보관 1`, `업무 보관 2`이며 자유 이름을 허용한다.
  같은 이름도 별도 보관이다. 내부 ID/시각으로 구분하고 실패 때 순번을 소비하지 않는다.
- 출처는 **같은 업무의 현재 첨부/개별 보관본**이다. 기본 파일 선택은 0개,
  현재 페이지 100개 이하/선택 전체 최대 100개, 페이지 간 ID 선택 유지로 한다.
  초과 선택을 조용히 자르지 않고 해제 안내를 한다. 외부 파일/보기 cache를 직접 선택하지 않는다.
- 현재 첨부는 기존 수동 순서, 개별 보관본은 기존 보관 시각/ID 순으로 조회한다.
  선택은 클릭 순서와 무관한 `(종류, ID)` 집합으로 직렬화한다. 당시 위치/선택 파일 순서는
  별도로 캡처하며 읽기 핸들 확보용 자산 ID 순서 때문에 사용자 파일 순서를 바꾸지 않는다.
  순서를 바꿔 페이지 경계가 달라지면 selector를 갱신하되 이미 체크한 ID는 유지한다.
- 0개일 때 버튼을 `업무 정보만 보관`, 파일 선택 시 `선택 N개와 함께 보관`으로 표시한다.
  파일 복사 실패를 0개 성공으로 바꾸지 않는다. 문서의 미저장 내용은 포함하지 않는다.
- 결과메모 등 열어 둔 기록 창의 미저장 초안은 자동 저장하지 않는다.
  초안이 있으면 `돌아가서 저장` / `DB에 저장된 내용만 보관`을 명시적으로 선택하게 한다.
  캡처 입력은 항상 DB에서 읽으며 위젯 값을 worker에서 읽지 않는다.
- 파일을 선택했을 때만 `선택 문서를 저장하고 닫았습니다` 확인을 요구한다.
  확인은 안정적인 파일 읽기 검사를 대체하지 않는다. 0개일 때는 이 확인을 표시하지 않는다.

### 5.2 전체 확정 절차

1. job_id/선택 종류·ID/이름/범위를 검증한다. 알려진 동일 명령 영수증이면 기존 결과를 반환한다.
2. 짧은 파일 gate에서 출처 상태/경로를 확인하고 고유 자산 ID 순으로 사용 예약을 확보한다.
   gate 밖에서 같은 순서로 쓰기/삭제 공유를 허용하지 않는 보호 읽기 핸들을 **모두** 확보한다.
   일부 잠금/누락이면 이미 확보한 자원도 해제하고 전체 실패한다.
3. 핸들이 유지된 상태에서 짧은 DB read_snapshot으로 업무/회차/체크리스트/선택 메타데이터를 읽는다.
   캡처 시각, 공통/회차 최신 이력 ID, 값/항목 ID/metadata revision 지문을 토큰으로 저장한다.
4. 부모 snapshot 저널에 승인 요청/출처/예정 자산·경로를 먼저 fsync한다.
   mutable은 새 frozen으로 스트리밍 캡처한다. 기존 frozen은 고정 크기/해시를 검증하여 재사용한다.
   선택한 내용 동일 자산의 검증은 한 번 수행하되 선택 항목은 빼지 않는다.
5. 모든 준비 파일/출처 검증 후 짧은 `gate → DB write_unit_of_work` 안에서 토큰을 재확인한다.
   관련 이력 ID가 바뀌었으면 값이 되돌아왔어도 재보관을 안내한다. 체크리스트/선택 파일 값·ID·revision도 비교한다.
   불필요하게 다른 업무/다른 회차/선택하지 않은 파일·전체 이력을 토큰에 넣지 않는다.
6. 안전한 새 경로에 파일을 공개하고 한 트랜잭션으로 새 자산·묶음·모든 파일 행·확정 영수증을 저장한다.
   보호 핸들과 사용 예약은 이 확정까지 유지한다. 파일이 없는 보관도 같은 정보 토큰을 최종 확인한다.
7. 커밋 뒤에만 성공을 표시하고 해당 업무의 타임라인을 갱신한다. 핸들/예약/worker 자원을 모두 해제한다.

캡처 대상 정보가 복사 중 바뀌면 성공하지 않는다. 다른 업무 작업과 알림은 계속 사용할 수 있다.
상태 토큰은 task.updated_at 하나가 아니라 관련 실제 값과 식별자다. 캐시 갱신만으로 실패시키지 않는다.
체크리스트가 잠시 바뀌었다가 같은 값/ID로 돌아온 경우에는 최종 값 지문 기준이며,
그 모든 중간 편집 이력을 추적한다는 의미는 아니다.

### 5.3 기존 2차 엔진과의 경계

- SnapshotService는 한 부모 작업/한 heavy slot/한 DB 확정이다.
  `DocumentLifecycle.create(VERSION)`/`AttachmentDocumentService.execute`를 파일별로 반복 호출해
  부분 완료 보관본을 먼저 만들지 않는다.
- Windows 보호 읽기, 스트리밍 복사·해시·flush, 안전 경로 공개, 사용 예약은 2차 어댑터를 재사용한다.
  다중 캡처 storage는 확보된 읽기 핸들을 받으며 coordinator.job을 중첩 획득하지 않는다.
- `.operations/snapshot-<job_id>`에 format_version/operation_kind가 명시된 부모 저널을 둔다.
  기존 단일 문서/삭제 저널을 새 모양으로 재해석하지 않는다. 종류별 dispatcher가 복구를 분기한다.
- 같은 ID 재시도는 처음 승인한 요청/선택/토큰을 재검증한다.
  자료가 바뀌었으면 새 보관 명령으로 시작하며 예전 준비 내용을 현재 상태처럼 확정하지 않는다.

## 6. 저장 실패·종료 복구

| 경계 | 보존/재시작 동작 |
| --- | --- |
| 핸들/예약 확보·검증 실패 | 현재 자료 불변. 이름과 실패 이유를 안내, 다른 선택을 자동 제외하지 않음 |
| 준비 파일 일부 복사·취소 | 완료 묶음 없음. 해당 부모 작업의 준비 자료만 정리/보존 |
| 새 파일 공개 후 DB 실패/종료 | 새 공개 파일은 미확정 복구 자료. 기존/재사용 frozen은 삭제하지 않음 |
| 묶음 커밋 후 통지 전 종료 | 영수증과 모든 참조 확인 후 완료로 인식. 같은 명령이 묶음을 다시 만들지 않음 |
| 확정 후 저널 정리 실패 | 묶음은 유효. 정리 대기 별도 표시, 확정 자료를 지우거나 실패 보관으로 되돌리지 않음 |
| 저널 손상·범위/경로/지원 버전 불명 | 자료 보존과 해당 범위 보호, 임의 자동 등록/파일 삭제 금지 |

기존 `중단된 내부 작업`에 종류/선택 수/실패 파일을 표시하고 안전한 동일 명령 확인 동선을 연결한다.
미확정 snapshot 자동 재실행은 하지 않는다. 일반 시작은 제한된 후보 점검만 하고 전체 보관 해시를 돌리지 않는다.
확정/미확정 다중 자산의 복구와 recovery 분리 전체 백업은 같은 부모 작업의 소유 원장을 사용한다.

## 7. 화면·조회 동선

### 7.1 진입과 목록

- 기존 업무 기록 창 하단에 `이력·보관` 버튼 하나를 둔다.
  업무/달력 오른쪽 메뉴에서도 같은 업무·원래 회차 키로 연다. 주 화면 새 탐색 탭은 추가하지 않는다.
- 모델리스 창을 재사용하고 편집창/첨부창/알림보다 독점 우선순위를 요구하지 않는다.
- 일반 업무는 해당 업무 전체, 회차 기록에서 열면 `업무 공통 + 이 회차`가 기본이다.
  `모든 회차` 조회는 명시적으로 전환한다. 색뿐 아니라 범위를 문자로 표시한다.

```text
이력·보관 · 예산 검토                 [현재 상태 보관…]
범위: 업무 공통 + 이 회차    종류: 전체    [기간 ▾]
------------------------------------------------------
10.09(금) 16:10  [중요 보관] 팀장 검토 전 · 파일 2개
10.09(금) 15:40  [변경] 설명·일정 · 업무 공통
10.09(금) 14:00  [변경] 결과메모 · 이 회차
10.09(금) 13:55  [기준] 이력 기록 시작
                         세로 스크롤 / 한 줄 요약
------------------------------------------------------
이 페이지 4건       [비교에 추가] [선택 2시점 비교]
                                              [닫기]
```

표시는 예시다. 당시 전체 설명/파일 정보를 아래에 자동 펼쳐 목록 높이를 줄이지 않는다.
선택 요약은 최대 두 줄이고 더블클릭/Enter로 별도 읽기 전용 상세를 연다.
0건에는 `아직 기록된 변경·보관이 없습니다. 기존 과거 변경은 소급 기록되지 않습니다`를 안내한다.

### 7.2 중요 보관 입력

```text
현재 상태 보관
보관 이름 [팀장 검토 전_______________________________]
저장된 업무 정보·결과메모·체크리스트를 함께 보관합니다.
파일 종류 [현재 첨부 ▾]                선택 2개 / 최대 100
------------------------------------------------------
[✓] 일반    검토안.xlsx
[✓] 원본    제출서식.hwp
[ ] 작업본  수정 중.hwp                 세로 스크롤
------------------------------------------------------
[✓] 선택 문서를 저장하고 닫았습니다
                [선택 2개와 함께 보관] [취소]
```

추가 페이지가 있을 때만 페이지 이동을 제공한다. 파일명은 한 줄/가운데 생략/전체 이름 tooltip이다.
진행은 처리 파일/전체 수, 취소를 표시한다. 닫기/취소는 worker 취소 요청이며 자원을 강제 폐기하지 않는다.

### 7.3 상세와 비교

- 변경 한 항목은 실제 변경 전 → 후, 기준/생성은 당시 상태, 중요 보관은 당시 정보/선택 파일이다.
- 중요 보관 파일은 `보기`, `선택 저장…`, `새 작업본…`을 제공한다.
  파일 여러 개는 폴더 한 번 선택해 저장한다. 묶음의 일부 파일만 삭제하는 메뉴는 제공하지 않는다.
- 과거 내용/파일명·메모·체크 상태는 읽기 전용이다. 파일 열기는 검증된 보기 사본이다.
- 설명/메모의 `텍스트 복사`는 가능하다. 현행 편집창의 입력을 자동 덮거나 상태/알림을 복원하지 않는다.
- `비교에 추가`로 최대 두 ID를 고정하고 페이지 이동에도 유지한다.
  기본 비교값은 두 항목의 after/보관 payload다. 현재 상태를 고르면 한 DB 스냅샷의 값/조회 시각을 명시한다.
- 업무 공통끼리 또는 같은 원래 회차끼리 비교한다. 서로 다른 회차나 공통 vs 회차 선택은 거절하고 범위 변경을 안내한다.
- 상태/날짜는 값의 차이, 자유 문장은 실제 문구의 차이만 표시한다.
  `예산 100만원` → `예산 100(천원)`을 같은 금액이라고 판단하지 않는다.
- 넓은 창은 전/후 두 열, 좁은 창은 전/후 세로 두 영역으로 한다. 키보드/스크롤로 전체 내용을 읽는다.
- diff 계산은 worker에서 수행한다. 초기 highlight 예산은 양쪽 합계 100,000자/10,000줄/0.2초다.
  초과/대폭 재작성 때는 `변경 강조 생략`과 원문을 표시한다. 원본 저장 내용을 잘라 보관하지 않는다.
  내부 문서 의미 비교나 모든 긴 글의 즉시 강조를 약속하지 않는다.
- 비교 중 선택 자료가 삭제/복원 세대 변경되면 오래된 결과를 적용하지 않고 재선택한다.

## 8. 타임라인·대량 자료·메모리

- 같은 DB read_snapshot에서 history와 snapshots의 **요약 컬럼만 UNION ALL** 한다.
  기준 시각은 자동 이력 recorded_at, 중요 보관 captured_at이다. 확정 시각은 상세에 별도로 표시한다.
- 정렬/커서 키는 `(기준 시각 UTC, 종류 rank, INTEGER id)` 내림차순으로 고정한다.
  종류 rank는 history=0/snapshot=1이며 시간 동률에도 겹치지 않는다. 페이지당 50+1행만 읽는다.
- 이전/다음 페이지를 사용하고 한 페이지면 영역을 숨긴다. 빈 마지막 페이지는 직전 유효 페이지로 돌아온다.
  보이는 리스트에는 50행만 유지하며 클릭할 때마다 50,000건을 메모리에 누적하지 않는다.
- 범위/종류/기간 변경은 첫 페이지로 초기화한다. 최초에는 기간 제한 없이 최신 기록을 보여준다.
  기간의 끝날은 사용자 시간대 다음날 0시의 배타 경계로 변환한다.
- 열린 동안 늦은 결과는 요청 토큰과 데이터 세대로 구분한다. 첫 페이지는 갱신하고 과거 페이지는
  `새 기록 있음`을 표시해 사용자의 위치를 갑자기 이동시키지 않는다.
- 시스템 시계가 거꾸로 바뀌면 시각순과 명령 실행순이 다를 수 있다.
  ID/command_id와 실제 저장 시각을 유지한다. 시각 정렬을 법적 순서/인과관계 증명으로 설명하지 않는다.
- 한 번에 상세 두 항목/파일 한 페이지만 가져온다. 단일 원문의 크기에 따른 비용까지 0이라고 하지 않는다.
  현행 설명/결과메모에는 별도 길이 상한이 없으므로 대형 원문 표시·복사·비교는 별도 스트레스 검사한다.
  새 기능 때문에 기존 문구를 자동 잘라내거나 새 저장 한도를 조용히 적용하지 않는다.
- 고정 파일 바이너리를 SQLite BLOB/GUI 리스트에 넣지 않는다. 파일 작업은 기존 bounded heavy slot,
  스트리밍 버퍼와 취소/알림 응답성 기준을 재사용한다.
- 초기 검색은 범위·기간·종류·변경 그룹 필터다. 설명 전체의 FTS 검색/다른 업무 전체 검색은
  별도 확인 없이 추가하지 않으며 기존 업무/업무일지 검색과 혼동되는 검색창을 두지 않는다.

## 9. 삭제·보존·백업의 필수 연결

### 9.1 snapshot_files는 실제 보존 참조

다음은 0015 적용과 같은 구현 단위의 필수 변경이다. 새 FK 허용 목록만 추가하고 끝내지 않는다.

- `database/file_references.py`의 ORM/sqlite 허용 목록, asset_reference_count,
  asset_paths_for_task에 snapshot_files/소유 snapshot을 포함한다.
- 삭제 repository의 선택 자산·선택 밖 참조·업무 소유 조회와 orphan 판정에도 같은 연결을 반영한다.
- 원본/작업본/개별 보관본 삭제 뒤 묶음 참조가 있으면 frozen 파일이 남는다.
  snapshot 참조만 있는 자산도 백업/사용량/무결성 검사에서 빠지지 않는다.
- 출처 attachment/version ID가 없어져도 파일을 열고 외부 저장하고 새 작업본을 만들 수 있어야 한다.
  당시 provenance 이름을 현재 이름 JOIN으로 대체하지 않는다.

### 9.2 묶음/업무 삭제

- 이 절의 **업무 이력 삭제 범위 승인과 백업/복원 연결은 0014/3A부터** 적용한다.
  이력을 먼저 CASCADE로 지우고 3B에서 나중에 확인창을 붙이는 상태로 진행하지 않는다.
  0015/3B에서는 같은 계약에 묶음과 파일 개수를 추가한다.
- 묶음 하나는 오른쪽 메뉴 `이 보관 삭제…`로만 명시적으로 삭제한다.
  묶음 이름·파일 행 수·실제 삭제/공유 유지 수를 확인하고 기존 격리 → DB 확정 → 정리를 재사용한다.
- 자동 이력은 항목별 편집/삭제나 기간·개수 자동 정리를 제공하지 않는다.
- 휴지통에서는 이력/묶음 조회·복사·외부 저장만 허용한다. 새 보관/작업본 생성/묶음 삭제는 먼저 업무 복원 후 한다.
- 자동 이력 두 항목은 같은 command_id여도 서로 다른 scope면 별도 저장·표시한다.
  휴지통의 읽기 전용과 선택된 범위를 상세/파일 명령에도 전달하여 메뉴만 비활성화하는 보호로 끝내지 않는다.
- 업무 영구 삭제 계획에 이력·묶음·파일 수를 추가하고 `보관본·업무 이력·중요 보관까지 함께 삭제`를 확인받는다.
  남기려면 업무 영구 삭제를 취소하고 휴지통에 보존한다. 업무일지는 기존 연결 해제/보존을 유지한다.
- 2차 단일/선택 삭제 command 직렬화·request 지문은 유지한다.
  기존 include_versions 필드는 호환을 유지하되 새 업무 삭제에서는 보관자료 전체 승인으로 해석하고
  실제 새 계획 fingerprint와 새 확인 문구를 반드시 확인한다.
- 새 plan/완료 기록에는 history_count/snapshot_count/snapshot_file_count를 추가한다.
  완료 payload는 version=2, 기존 version=1은 새 개수를 0으로 읽는다. per-asset 영수증은 기존 계약을 유지한다.
- 구형 미확정 삭제 저널은 새 이력/묶음 삭제 허가로 승격하지 않는다.
  확정 전 파일은 복구하고 새 범위 확인을 받는다. 이미 확정된 구형 삭제는 영수증대로 정리한다.
  모르는 target/저널 버전은 보존한다. 새 snapshot 대상은 명시적으로 분기하고 task로 fallback하지 않는다.

### 9.3 열기·외부 저장·전체 백업

- 공통 FileReference에 snapshot_file 종류/ID를 추가한다. 기존 필드/단일/다중 외부 저장 요청은 유지한다.
  DocumentSource/작업본 명령도 snapshot_file을 읽기 전용 출처로 지원하고 독립 mutable 작업본만 만든다.
- 실제 전체 백업의 DB·자산 목록·FK/manifest 검증·table_counts/지원 revision에 새 모델을 연결한다.
  같은 frozen bytes는 한 번 넣고 모든 참조/이력/묶음 payload를 보존한다.
- 현행 전체 백업 형식 3의 자산/DB 구조를 유지할 수 있지만 **새 스키마까지 지원한다는 검증**이 필요하다.
  새 archive 레이아웃을 임의로 만들거나 과거 형식 호환을 깨지 않는다.
- 미확정 snapshot 준비 자료는 정상 묶음이 아니라 recovery 영역이다.
  복원 뒤 자동 등록/보관 명령 재실행하지 않는다. 변경 보기 cache는 기존대로 전체 백업 대상이 아니다.

## 10. 모듈·화면 연결 계획

- Domain: 이력 범위/여섯 그룹의 읽기 전용 값, snapshot 정보/파일 항목, 안정적인 scope 키.
- Application: task_mutations, task_history, task_snapshots. 명령/조회/비교/캡처를 분리한다.
- Infrastructure: task_history_repository, task_snapshot_repository, snapshot_storage,
  0014/0015 migration, 기존 file_references/deletion/backup/internal recovery의 확장.
- Presentation: task_history_dialog, task_snapshot_dialog, history_compare_dialog.
  공통 밝은 스타일과 기존 queued OperationWorker/수명 관리 방식을 사용한다.
- MainWindow/TaskRecordDialog는 업무 ID/원래 회차/읽기 전용 상태만 전달한다.
  UI에서 SQL/물리 삭제/전체 파일 해시를 직접 수행하지 않는다.
- 변경 확정 신호는 task_id와 관련 scope/이력·묶음 ID다. 열려 있는 목록은 필요한 범위만 재조회한다.
  다른 창의 미저장 설명/결과메모를 갱신 신호로 덮어쓰지 않는다.

## 11. 구현 순서와 게이트

### 3A. 자동 변경 이력 + 조회/비교

1. 0014와 serializer/범위·명령 receipt, 트랜잭션 실패 회귀를 먼저 준비한다.
2. 새 업무/편집/상태/결과메모/회차/알림 처리 경로를 같은 명령 경계로 연결한다.
3. 이력 목록·한 항목 전후·두 시점 비교를 연결한다. 기록만 쌓이는 상태로 완료하지 않는다.
4. 업무 영구 삭제의 이력 범위 승인과 새 이력/receipt 전체 백업·복원을 같은 단위로 연결한다.
5. 영향 UI/알림·회차 회귀, 대량 이력 조회/메모리, 이행/전체 백업 복원을 검사하고 사용 확인한다.

### 3B. 중요 시점 묶음 + 통합/보존

1. 3A 사용 확인을 반영하되 본 공통 계약을 바꾸면 먼저 관련 설계를 갱신한다.
2. 0015와 참조·삭제·백업·복원 경계를 먼저 같이 연결한다.
3. 다중 안정 캡처/부모 저널/복구/읽기 전용 상세와 혼합 파일 외부 저장·새 작업본을 연결한다.
4. history+snapshots 통합 목록/비교를 검증한다. 명령 실패·강제 종료·공유 참조 보존을 필수 게이트로 한다.

3차를 이 두 내부 구현 단위로 나누되 이번에 양쪽의 연결 계약까지 설계한다.
설계 요청에서는 구현하지 않았고 이후 별도 구현 요청으로 양쪽을 연결했다.
사용 확인과 커밋/배포는 각각 별도 실행 단계다.

중단된 전체 검사를 통과로 계산하지 않고 필요한 안전 검사 미완료 상태에서 배포하지 않는다.

## 13. 설계 점검 결과와 남은 결정

- 승인 범위 유지: U12/U13/U14, 자동 삭제/전체 복원/새 외부 연동을 추가하지 않았다.
- 중복 방지: 설명/결과메모 입력은 기존 그대로이며 일지·체크 변경 이력을 자동 복제하지 않는다.
- 2차 재사용: 파일 자산·보호 읽기·cache·외부 저장·격리/복구·전체 백업을 통합하고 별도 보관 저장소를 만들지 않는다.
- 구현 위험: 모든 업무 변경 경로의 scoped 트랜잭션, 새 보존 참조의 모든 소비자 연결,
  다중 캡처 부모 저널, Qt worker 종료/늦은 결과 보호가 핵심이다. UI만 추가해서 완료하지 않는다.
- 공통 정책 변경 없음: 최대 선택·페이지 크기·payload/revision·UI 문구는 기존 승인 방향의 상세 결정이다.
  참조 목록/새 schema 적용과 단일 저널 호환은 구현 시 한 변경 단위로 검증한다.
- 필수 추가 사용자 결정은 현재 없다. 3A/3B 각각 사용 확인 때 버튼 위치·비교 표현·기본 보관 이름을 조정할 수 있다.
  이력 보존 기간 제한, 역사적 본문 전체 검색, 자동 현재 내용 복원은 별도 요청 전까지 추가하지 않는다.

# 한 업무의 여러 알림과 요일 표시 설계

설계일: 2026-10-06. 상태: 소스 구현·자동 검증 완료, 배포 전. 개수 제한과 오늘/달력 미리보기를 포함한다.
사용자 자료·버전·배포 파일·GitHub 공개는 이번 구현 요청에서 변경하지 않는다. 검증 기록은 `phase-reports/multiple-reminders-weekday.md`에 남긴다.

## 1. 목적과 확정 범위

업무는 하나만 등록하고 그 업무에 서로 다른 날짜·시각의 알림을 여러 개 연결한다.
알림을 늘리기 위해 업무를 복제하지 않는다. 모든 화면에서 사람이 읽는 날짜에는 한국어 요일을 함께 표시한다.

- 날짜·시각 직접 지정이 알림 추가의 기본 방식이다.
- 시작·종료 기준 알림도 같은 목록의 항목으로 관리한다. '기본 알림'과 '추가 알림'을 별도 계층으로 만들지 않는다.
- 새 업무의 기존 기본값인 시작 시각 알림 하나는 유지한다. 사용자는 변경·삭제하거나 더 추가할 수 있다.
- 업무 하나당 알림 규칙은 최대 20개로 제한한다. 기존 초과 자료는 자르지 않고 보존한다.
- 오늘 탭에서 오늘 울릴 알림을 바로 확인하고, 달력에서도 알림이 있는 날짜와 날짜별 예약을 확인한다. 업무의 일정일과 알림일은 독립이다.
- 업무 목록은 한 줄을 유지한다. 추가 알림 때문에 업무 등록창이 길어지거나 Tab 순서가 복잡해지지 않게 한다.
- 확인·재알림은 선택한 알림에만 적용하고, 업무 완료·취소·휴지통은 해당 업무의 알림 전체에 적용한다.
- 매시 알림의 대상 시간·기본 활성화·기록 처리 규칙은 변경하지 않는다. 날짜 표시가 있는 부분만 공통 요일 표시를 사용한다.
- 체크리스트 순서, 알림 수동 순서, 반복 업무 생성, ICS 알림 내보내기, 클라우드 동기화는 추가하지 않는다.
- 프로그램 종료 중의 정시 발생을 보장하지 않는다. 실행 중 발생과 기존 놓친 알림 복구 정책을 유지한다.

## 2. 현재 코드와 수정 근거

| 현재 구조 | 설계 판단 |
| --- | --- |
| reminders가 task_id로 업무에 여러 행을 연결 | 한 업무에 여러 알림을 저장할 기반이 이미 있다. |
| relation은 start/end/absolute, absolute_at과 offset_minutes 지원 | 날짜 직접 지정과 일정 연동을 기존 모델로 처리한다. |
| reminder_deliveries는 알림 ID·회차·예정 시각별 발생과 확인·재알림을 저장 | 각 알림을 독립 처리하고 기존 중복 방지 키를 유지한다. |
| 편집창은 시작·종료 선택칸을 각각 하나씩 노출하고 나머지는 숨겨 보존 | 모든 알림을 사용자가 보고 편집하는 목록으로 교체한다. |
| schedule_type=none에서 알림을 전부 버림 | 일정 없는 업무도 날짜 직접 지정 알림을 등록·보존할 수 있게 바꾼다. |
| 주 창이 업무를 저장한 뒤 알림을 별도로 저장 | 실패 시 일부 저장을 방지하는 통합 저장 명령이 필요하다. |
| 규칙 저장은 같은 identity의 ID를 보존하지만 스케줄을 매번 초기화 | 변경하지 않은 규칙·발생 이력·미룬 시각은 재작성하지 않는다. |
| 알림창의 완료 처리는 선택한 delivery 하나만 화면에서 제거 | 완료된 업무/회차의 다른 표시 중 알림도 즉시 정리한다. |
| 날짜 형식이 여러 화면에 흩어지고 일부 지정 알림은 UTC를 그대로 출력 | 공통 표시 함수와 날짜 입력의 읽기 전용 요일을 도입한다. |
| 오늘/달력의 업무 조회는 업무 일정일을 중심으로 함 | 일정이 미래인 업무의 오늘 알림도 별도 예약 조회로 가져온다. |
| next_fire_at 캐시는 각 규칙의 다음 한 번을 저장 | 월 전체 미리보기는 읽기 전용 발생 계산과 저장 이력을 합쳐 조회한다. 캐시 하나로 미래 월을 판단하지 않는다. |

수정 예상은 중간 이상 규모다. 새 알림 편집 UI, 통합 저장, 알림창 동기화와 날짜 표시에 더해
날짜 범위별 예약 조회·오늘 미리보기·달력 표시가 필요하다. DB와 기존 발생 계산/처리 엔진은 재사용한다.
이 설계는 새 DB 열·테이블을 요구하지 않는다. 첨부 수동 순서의 0011 업그레이드와는 별개의 변경이다.

## 3. 사용자 화면

아래 날짜·요일은 2026년 예시다. 알림 목록은 실제 발생 시각순으로 자동 정렬하고 수동 순서 기능은 두지 않는다.

### 3.1 업무 등록·수정

```text
+--------------------------------------------+
| 새 업무                                    |
| 제목   [보고서 제출                      ] |
| 설명   [                                 ] |
| 일정   [2026-11-05 (목)] [09:00]            |
|        [ ] 종일                            |
| 알림   설정 3개                 [설정...]  |
|        다음: 10월 16일(금) 09:00            |
| [ ] 종료·반복 등 추가 설정 보기            |
|                            [저장] [취소]   |
+--------------------------------------------+
```

- 기존 시작 알림·종료 알림 행은 제거하고 알림 요약 한 행으로 합친다. 종료 시각과 반복의 추가 설정은 유지한다.
- 요약의 `설정 N개`는 목록의 규칙 개수이며 남은 발생 횟수가 아니다. 사용 안 함 항목이 있으면 별도로 안내한다.
- `다음`은 아직 처리하지 않은 미래 예약/재알림 중 가장 빠른 실제 시각이다. 현재 떠 있는 알림은 '확인할 알림 있음'으로 구분한다.
- 예약이 소진되어도 규칙이 자동 삭제되지는 않는다. `설정 3개 · 다음 예약 없음`처럼 남은 알림으로 오해하지 않게 표시한다.
- 반복 업무는 `반복 알림 설정 N개`로 표시한다. 무한한 미래 회차 전체의 개수를 표시하지 않는다.
- 일정 없음이어도 알림 행은 보인다. 날짜 직접 지정만 사용 가능하며, 기준 일정이 없는 start/end는 만들 수 없다.

### 3.2 알림 목록과 항목 편집

```text
+--------------------------------------------+
| 알림 설정 · 보고서 제출                    |
| > 10.16(금) 09:00 · 날짜 지정 · 예정        |
|   10.26(월) 14:00 · 날짜 지정 · 예정        |
|   11.04(수) 09:00 · 날짜 지정 · 예정        |
| [추가...] [수정...] [삭제]                  |
|                            [적용] [취소]   |
+--------------------------------------------+

+--------------------------------------------+
| 알림 추가                                  |
| 방식   [날짜·시각 직접 지정             v] |
| 날짜   [2026-10-16 (금)]                    |
| 시각   [09:00]                             |
|                            [추가] [취소]   |
+--------------------------------------------+
```

- 방식 선택에는 날짜 직접 지정·시작 기준·종료 기준을 둔다. 시작/종료 기준 선택 때만 간격 입력을 표시한다.
- 기준 방식은 `기준 시각`, `10분 전`, `1일 전` 등 빠른 선택과 일/시간/분 간격 입력을 제공한다. 실제 예정 날짜·요일·시각을 반드시 미리 보여준다.
- 날짜 직접 지정에는 일수 제한이 없다. 기준 간격은 기존 전후 30일 범위를 유지한다. 그보다 먼 예약은 직접 지정으로 안내한다.
- 목록 선택 후 공통 수정·삭제 버튼을 사용한다. 선택 없음이면 비활성화하고, 더블클릭은 해당 알림 수정이다.
- 상태는 예정·미확인·재알림·확인함·지난 예약·사용 안 함을 구분한다. 반복 규칙은 '다음 회차 예정'과 현재 미확인/재알림을 함께 안내한다.
- `적용`은 편집창의 임시 초안에 반영할 뿐 DB에 저장하지 않는다. 업무의 `저장`이 최종 저장이다. 어느 단계든 취소하면 그 단계의 변경을 버린다.
- 주 창에서 바로 알림 설정을 열면 목록의 마지막 버튼은 `저장`이다. 업무 일정은 그대로 두고 동일한 저장 명령으로 알림만 저장한다.
- 알림이 많으면 목록 내부 스크롤과 총 설정 개수를 표시한다. 항목마다 날짜 입력칸을 펼치거나 버튼을 반복하지 않는다.
- 설정 창에는 `설정 3 / 최대 20개`를 표시한다. 한도에 도달하면 추가 버튼을 비활성화하되 기존 항목 수정·삭제·취소는 계속 가능하다.

### 3.3 일반 업무 목록·선택 상세·알림창

```text
전체 업무
--------------------------------------------------
O 11.05(목) 09:00 · 보고서 제출       [진행] [...]
O 11.06(금) 14:00 · 자료 확인         [진행] [...]
--------------------------------------------------
선택 업무: 보고서 제출
알림 설정 3개 · 다음 10.16(금) 09:00 [알림 설정...]
```

- 일반 업무 행별 `알림 3` 배지는 첫 구현에서는 넣지 않는다. 설정 개수/남은 횟수 혼동과 좁은 창의 잘림을 피한다.
  단, 오늘 알림 영역과 달력 날짜별 표시는 기본 노출한다. 업무를 선택하기 전에는 알림을 알 수 없는 설계로 만들지 않는다.
- 목록/달력 오른쪽 메뉴에 `알림 설정...`을 추가한다. 달력에서는 선택 회차가 아니라 업무 원본의 규칙을 편집한다는 안내를 표시한다.
- 달력 셀에는 요일을 반복하지 않는다. 기존 요일 헤더를 유지하고 하단 선택 날짜를 `11월 5일(목)`으로 표시한다.
- 알림창은 기존처럼 한 창에 여러 항목을 모은다. 같은 업무라도 예정 시각이 다른 알림을 각각 선택·처리할 수 있다.
- 알림창에는 업무 제목, 실제 알림 날짜·요일·시각, 날짜 지정/시작 기준/종료 기준의 이유를 보여준다. 중복되거나 긴 설명은 선택 상세로 보낸다.
- 예정/재알림 상세를 보는 행위는 날짜·필터·스크롤·선택을 초기화하지 않는다.

### 3.4 오늘 탭의 알림 미리보기

```text
오늘 · 10월 16일(금)

오늘 알림 · 총 3건                         [전체 보기]
------------------------------------------------------
09:00  보고서 제출  · 일정 11.05(목)           확인함
14:00  자료 검토    · 일정 10.30(금)           예정
16:30  계약 확인    · 일정 11.02(월)           재알림
------------------------------------------------------

기존 오늘 업무 목록
...
```

- 오늘 화면에 들어오면 기본으로 보인다. 별도 사이드바 탭이나 예정/완료 등 상태별 하위 탭을 만들지 않는다.
- 업무의 시작/종료가 오늘인지와 무관하게 알림 날짜가 오늘이면 표시한다. 일정 없는 업무의 직접 지정 알림도 포함한다.
- 업무 검색·상태·중요도·고정/첨부 필터와 독립이다. 업무 검색 때문에 알림도 조용히 사라지지 않는다.
  필터 사용 중에는 `알림은 업무 필터와 무관하게 표시`를 간결하게 안내한다.
- 한 행의 왼쪽 시각은 실제 알림/재알림 시각이다. 원래 업무의 일정은 `일정 11.05(목)`처럼 별도 표기한다.
  일정 없는 업무는 `일정 없음`으로 표시한다. 원래 일정과 알림 시각을 같은 의미로 섞지 않는다.
- 같은 업무의 다른 예약은 별도 행으로 보이지만 업무 레코드는 복제하지 않는다. 기존 오늘 업무 목록의 업무 총 개수에도 알림 행을 더하지 않는다.
- 상태는 예정·미확인·재알림·확인함·완료·시각 지남(발생 기록 없음)·다른 날로 미룸을 구분한다.
  확인함/완료는 흐리게 표시하되 그날의 목록에는 남긴다. 아직 발생하지 않은 예약을 확인된 것으로 추정하지 않는다.
- 시각순으로 정렬한다. 기본 스크롤/미리보기 시작은 가장 이른 미확인/아직 울리지 않은 알림에 맞추고,
  확인한 이력만 많은 경우 앞으로 울릴 알림이 미리보기 밖에 숨지 않게 한다. 갱신 때 기존 선택은 가능한 범위에서 유지한다.
- 기본 미리보기는 최대 3행이며 낮은 창에서는 2행까지 줄일 수 있다. `총 12건 · 3건 표시`와 `9건 더 보기`처럼 숨은 항목 수를 명시한다.
  첫 몇 행만 보여주고 마지막인 것처럼 보이게 하지 않는다. 전체 보기에서는 같은 날짜의 전체 목록과 스크롤을 제공한다.
- 좁은 폭에서는 업무의 원래 일정만 선택 상세로 옮긴다. 알림 시각·업무 제목·상태·총 개수/더 보기는 숨기지 않는다.
  기존 업무 목록의 최소 표시 공간을 보존하고 필요한 경우 콘텐츠 스크롤을 사용한다. 달력/업무 화면 전체를 스크롤 불가능한 고정 높이로 만들지 않는다.
- 알림이 없으면 `오늘 예약된 알림이 없습니다` 한 줄만 표시한다. 업무가 없지만 알림은 있는 경우 전체 화면을 '업무 없음' 안내로 덮지 않는다.
- 한 번 클릭은 선택/상세, 더블클릭은 업무 기록을 연다. 오른쪽 메뉴/공통 동작으로 알림 보기·설정에 접근한다.
  미래 예약은 발생한 delivery가 없으므로 알림창의 확인/재알림 처리를 억지로 실행하지 않는다. 변경/삭제하려면 규칙 설정으로 이동한다.

### 3.5 달력의 날짜별 알림 표시

```text
+----------------------+
| 16                   |
| 기존 업무 일정       |
| 알림 3건             |
+----------------------+

10월 16일(금) · 업무 1개 · 알림 3건      [목록 확대]
------------------------------------------------------
[업무]  10:00  회의
[알림]  09:00  보고서 제출 · 일정 11.05(목) · 확인함
[알림]  14:00  자료 검토   · 일정 10.30(금) · 예정
[알림]  16:30  계약 확인   · 일정 11.02(월) · 재알림
------------------------------------------------------
전체 4행 · 아래 항목은 스크롤로 확인    [기록][첨부][...]
```

- 업무 일정은 기존 일정일/기간대로 표시한다. 알림은 날짜 셀의 별도 `알림 N건` 표시로 추가한다.
  알림이 있다는 이유로 업무 시작일/종료일을 이동하거나 같은 업무 일정 막대를 복제하지 않는다.
- 업무 일정이 없는 날에도 알림이 있으면 `알림 N건`을 표시한다. 예시의 보고서 제출은 11월 5일 일정이면서 10월 16일에 알림 표시가 있다.
- 날짜별 알림은 업무 검색/필터와 독립적으로 기본 표시하고 그 의미를 안내한다. 검색 결과의 업무 일정만 가져와 사전 알림을 누락시키지 않는다.
- 셀의 업무 일정 개수와 알림 건수는 합치지 않는다. 글자 크기를 줄여 넣거나 새로운 알림 막대로 기존 일정 막대를 모두 밀어내지 않는다.
  낮은 셀에서는 기존 일정 미리보기 대신 `업무 N개 · 알림 M건`으로 축약하고 선택 날짜 목록에 전체 항목을 제공한다.
- 달력 셀의 알림 개수 클릭은 그 날짜를 선택하고 하단 목록의 첫 미처리/예정 알림으로 이동한다. 규칙 수정창이나 발생 알림창을 자동으로 띄우지 않는다.
- 하단은 기존 하나의 스크롤 목록/목록 확대를 재사용한다. 업무 행과 알림 행을 `[업무]`/`[알림]`으로 구분하며 새 하위 탭이나 두 개의 별도 작은 목록을 만들지 않는다.
- 업무 행은 기존 일정순으로 먼저, 알림 행은 실제 시각순으로 이어서 표시한다. 날짜 제목의 `업무 N개 · 알림 M건`과 총 행/스크롤 안내로 숨은 알림을 알린다.
- 같은 업무가 업무 행과 알림 행에 각각 나오는 것은 서로 다른 날짜별 정보 조회이며 새 업무 생성/업무 총 개수 증가가 아니다.
- 한 번 클릭은 해당 업무/예약 상세, 더블클릭은 업무 기록이다. 기록·첨부 버튼은 알림 행에서도 원본 업무에 연결한다.
  회차가 명확한 상대 알림만 해당 회차 기록으로 연결하고 직접 지정은 임의 회차를 추정하지 않는다.
- 오른쪽 메뉴/하단 `...`에서 `알림 보기·설정...`을 제공한다. 알림 행의 원래 업무 수정/완료와 알림 규칙 수정/삭제를 명확히 구분한다.
- 하단 목록은 실제 데이터 행 최소 3행 공간을 유지한다. 긴 날짜/총 개수 때문에 버튼이 잘리면 기존 공통 메뉴로 축약하고,
  빈 행/별도 알림 패널을 더해 목록 높이를 줄이지 않는다. 색상뿐 아니라 행 유형·상태 텍스트로 구분한다.
- 업무 완료 뒤 미래 알림은 제거하되 그날 이미 발생/처리한 이력은 흐리게 조회할 수 있다. 휴지통/영구 삭제 자료는 일반 달력 목록에서 제외한다.

### 3.6 규칙 개수와 날짜별 알림 건수

| 표시 | 의미 |
| --- | --- |
| 설정 3 / 최대 20개 | 업무에 저장된 규칙 수. 지난/비활성 규칙도 포함하며 delivery 수와 무관하다. |
| 오늘/달력 알림 N건 | 해당 날짜의 실제/예정 알림 항목 수. 서로 다른 규칙/회차는 각각 센다. |
| 업무 N개 | 기존 업무 일정 수. 알림 행은 업무 개수에 포함하지 않는다. |
| 총 N행/더 보기 | 현재 날짜 목록의 업무 행 + 알림 행. 선택 데이터가 더 있다는 안내다. |

같은 규칙/회차/원래 예정 시각의 예약과 delivery는 한 항목으로 합친다. 검사 직전에 '예정'과 발생 뒤 '미확인'을 동시에 두 행으로 세지 않는다.
같은 날 여러 번 미룬 것은 별도 규칙/새 업무가 아니라 그 항목의 상태/실제 시각 변경이다.
날짜별 N건에는 그날 확인/완료한 항목이 포함되므로 남은 울림 횟수와 같다고 안내하지 않는다. 남은 예약은 상태와 실제 시각으로 확인한다.

재알림을 다음 날로 미루면 원래 날짜의 항목은 `다음 날로 미룸`과 이동된 시각으로 표시하고, 새 날짜에는 `재알림`으로 표시한다.
이는 한 알림의 두 날짜 조회 참조이지 두 번 울리는 예약이 아니다. 미래 발생 횟수나 설정 규칙 개수를 두 번 늘리지 않는다.
지난 알림이 다음 날 복구 발생한 경우에도 원래 예정과 실제 발생 시각을 구분해 보여준다.

## 4. 날짜 직접 지정과 일정 연동

| 상황 | 날짜 직접 지정 | 시작·종료 기준 |
| --- | --- | --- |
| 업무 일정 이동 | 알림은 원래 날짜·시각 그대로 | 미발생 예약을 바뀐 일정에 맞춰 계산 |
| 일정 없음으로 변경 | 그대로 보존 | 해당 기준을 제거해야 저장 가능 |
| 종료 시각 제거 | 그대로 보존 | 종료 기준 항목 제거/변환 선택 안내 |
| 종일/시간 일정 전환 | 그대로 보존 | 새 기준 시각과 실제 예약 미리보기 |
| 반복 업무 | 지정 날짜에 한 번만 발생 | 각 회차의 시작·종료를 기준으로 발생 |

기준을 없앨 때 관련 규칙을 숨겨 두거나 조용히 삭제하지 않는다. 영향받는 항목과 '제거/날짜 직접 지정으로 변환/돌아가기'를 보여주고,
변환하면 현재 계산된 실제 시각을 사용한다. 지난 시각은 새 미래 날짜를 지정해야 한다.
종일 일정의 DB 종료는 마지막 날 다음 날 00:00(배타적 종료)이라는 기존 의미를 유지한다.
종료 기준 알림도 그 경계를 기준으로 계산하고 실제 시각을 미리 보여준다. 표시용 마지막 날짜를 계산 기준으로 몰래 바꾸지 않는다.
기존 종일 시작 당일 09:00 규칙도 보존하고 시간 일정의 단순 +9시간과 잘못 같은 이름으로 표시하지 않는다.

## 5. 예약 검증과 처리 규칙

### 5.1 최대 20개 제한

- 한 업무에 저장하는 start/end/absolute 규칙을 합쳐 최대 20개다. 사용 안 함과 지난 규칙도 개수에 포함한다.
- 반복 규칙 하나는 1개다. 반복으로 생성되는 발생과 delivery 이력, 재알림 횟수는 이 제한에 포함하지 않는다.
- 새 업무의 기본 시작 알림도 20개 안에 포함한다. 20개 상태에서 추가는 막고 수정·삭제는 허용한다.
- UI뿐 아니라 애플리케이션 저장 명령/기존 규칙 저장 경로에서도 실제 DB 기준으로 검증한다. 두 창이 각각 추가해 한도를 넘기지 않도록 같은 쓰기 트랜잭션에서 확인한다.
- 이미 20개 초과 규칙이 있는 기존 업무는 절대 자르지 않는다. 제목/기존 항목 수정·삭제는 허용하고,
  20개 이하로 정리하기 전 새 규칙 추가는 막는다. 조회·백업·복원·알림 발생 자체는 계속 지원한다.
- 여러 화면/규칙/이력에 대한 20개 제한이 아니라 업무별 규칙 제한이다. 한도 안내 때문에 기존 알림이 사라지거나 확인한 이력이 자동 삭제되지 않는다.

### 5.2 예약 검증과 알림 처리

- 동일 identity의 규칙은 중복 저장하지 않는다. 서로 다른 방식이 동일한 실제 시각으로 겹쳐도 저장 전에 알려준다.
- 일회성 업무에서는 같은 실제 시각의 활성 예약을 하나로 정리하도록 요구한다. 비활성 기존 항목을 자동으로 다시 켜지 않는다.
- 반복 규칙과 날짜 지정의 겹침은 가까운 다음 발생을 검사해 안내한다. 무한한 미래를 UI에서 전개하거나 계산하지 않는다.
- 새 직접 지정 알림의 과거 날짜·시각은 거절한다. 현재 분은 허용하고 기존 검사 주기에 따라 발생함을 안내한다.
- 새 기준 규칙의 유효한 미래 발생이 없으면 저장 전에 알린다. 기존 지난/확인한 규칙은 그대로 보존·표시할 수 있다.
- 새로 추가/시각 변경한 예약은 현재 분부터 스케줄을 계산한다. 기존 저장된 알림의 놓친 발생 복구와 구분해 최근 과거를 갑자기 새 알림으로 만들지 않는다.
- 단순 제목/설명 변경은 알림 ID, next_fire_at, schedule_initialized, 확인 이력, snoozed_until을 초기화하지 않는다.
- 여러 알림을 각각 미루면 모두 보존한다. 목록은 가장 빠른 재알림만 요약하고 상세에서 나머지를 확인할 수 있게 한다.
- PC 재시작/표시 실패 시 기존 복구 범위 안의 알림은 개별 이력을 유지해 한 알림창에 모은다. 같은 업무라는 이유로 가장 최근 것만 남기거나 조용히 버리지 않는다.

| 사용자 처리 | 적용 대상 |
| --- | --- |
| 이번 알림 확인 (기본) | 선택 delivery만 확인. 업무 상태와 다른 예약은 유지. |
| 다시 알림 | 선택 delivery만 지정 분 뒤로 이동. 다른 예약은 유지. |
| 업무 대기로 | 업무를 대기로 변경하고 선택 알림을 처리. 기존 정책처럼 다른 예약은 유지. |
| 업무 완료/취소/휴지통 | 해당 업무의 모든 예정·재알림·팝업 처리 항목을 제외. 완료한 실제 이력은 오늘/달력에서 읽기 전용 조회 가능하며 휴지통 자료는 제외. |
| 반복 회차 완료/건너뛰기 | 같은 task_id + occurrence_start만 정리. 다른 회차는 유지. |
| 특정 알림 삭제/시각 변경 | 그 규칙의 현재 미확인/재알림을 정리하고 다른 규칙은 유지. |

반복 업무의 absolute 알림에는 회차 식별자가 없으므로 가까운 회차를 추정해 완료하지 않는다.
이 항목에서는 `업무 전체 완료…`로 범위를 명시하고 확인을 받는다.
회차가 명확한 start/end 알림은 `이번 회차 완료…`로 표시한다. 원본 반복 업무 전체 완료와 구분한다.
일반 업무도 `업무 완료…`로 범위를 명시하며 모든 완료 동작은 남은 알림 중단 범위를 확인받는다.
`이번 알림 확인`을 파란색 기본/Enter 동작으로 먼저 배치하고 다시 알림을 같은 행에 둔다.
업무 완료·업무 대기는 별도 보조 행에 둔다. 확인창은 항상 위의 비차단 창이고 기본 선택은 취소다.
같은 알림의 확인창을 중복 생성하지 않으며, 확인 중 완료 범위가 변경되면 낡은 동의로 처리하지 않는다.
완료 범위의 FIRED/SNOOZED delivery는 같은 저장 단위에서 COMPLETED로 마무리한다.
취소·휴지통·건너뛰기로 해제하는 미처리 delivery는 ACKNOWLEDGED로 종료한다. 업무를 복원하거나 다시 진행으로 바꾸어도
이전에 닫은 알림창/재알림이 자동으로 되살아나지 않으며, 이후의 유효한 예약만 기존 정책에 따라 처리한다.

## 6. 저장·상태 보존·동시성

### 6.1 통합 저장 명령

UI는 업무 초안, 기존 알림 ID, 원본 규칙 스냅샷, 추가/수정/삭제 의도를 애플리케이션 계층의 저장 명령에 전달한다.
TaskDraft/ReminderRuleInput은 값 표현을 유지하고 ID와 편집 의도는 별도 명령 타입으로 분리한다.

1. 저장 버튼 중복 실행을 막고 날짜·기준·중복을 검증한다.
2. DB 쓰기 트랜잭션에서 현재 업무/규칙을 다시 읽는다. 없거나 휴지통이면 저장을 거절한다.
3. 편집 시작 뒤 업무/규칙이 다른 창에서 수정되었으면 충돌을 안내하고 초안을 보존한다. 오래된 화면으로 덮어쓰지 않는다.
4. 같은 트랜잭션에서 업무와 규칙 변경, 관련 delivery 정리, 필요한 다음 발생 계산을 수행한다.
5. 어느 단계든 실패하면 모두 롤백한다. '업무는 저장됨/알림은 실패' 상태를 만들지 않는다.
6. 커밋 뒤에만 저장 완료를 알리고 창·목록·알림을 갱신한다. UI 갱신 실패를 DB 저장 실패로 오인해 재저장하지 않는다.

SQLAlchemy 작업 단위를 도입해 업무 저장소와 알림 저장소가 같은 세션/트랜잭션을 사용하게 한다.
화면에 SQL을 넣거나 이미 커밋한 업무를 나중에 되돌리는 방식으로 원자성을 흉내 내지 않는다.
기존 단독 조회·빠른 등록·업무 기록 저장 등의 경로는 별도 유지하며 새 저장 명령에 무관한 기능을 전면 재작성하지 않는다.

### 6.2 규칙의 차이만 반영

- 미변경 항목: 기존 ID·enabled·다음 발생·이력을 보존한다. 알림 발생/확인 자체는 편집 충돌로 보지 않고 최신 상태를 따른다.
- 시각/기준 변경 항목: 규칙 ID를 유지하고 미래 스케줄만 재계산한다. 이전 미확인/재알림은 acknowledge 처리로 종료하고 이미 처리한 이력은 보존한다.
- 새 항목: 새 ID와 미래 스케줄을 생성한다. 변경 결과가 동일해 중복이 되지 않는지 다시 검증한다.
- 삭제 항목: 알림창 제거에 필요한 ID를 수집한 뒤 삭제한다. 현재 FK CASCADE처럼 해당 규칙의 delivery도 제거되므로 이 설계는 삭제한 알림의 영구 감사 이력 보존을 보장하지 않는다.
- 알림 규칙 삭제는 업무·체크리스트·업무일지·첨부 삭제와 무관하다. 삭제 항목에 미확인/재알림이 있으면 그 예약도 취소됨을 알려준다.
- 기준 일정 변경은 관련 상대 규칙만 재계산한다. 직접 지정과 무관한 규칙의 재알림은 보존한다.
- 이전에 처리한 동일 ID/예정 시각은 기존 fire_key로 재발생을 막는다. 단순 수정만으로 이미 확인한 시각을 다시 울리지 않는다.

### 6.3 알림창과 편집창

- 현재 열려 있는 알림은 delivery_id로 식별한다. 처리 뒤 선택 항목만 제거하거나, 완료/삭제 범위에 포함된 다른 항목도 함께 제거한다.
- 일반 목록의 완료/취소/휴지통과 규칙 편집에서도 같은 정리 경로를 호출한다. 발생 엔진에서 새 알림만 막고 화면의 오래된 알림을 방치하지 않는다.
- 클릭 직전에 DB 상태를 확인한다. 이미 다른 창에서 처리/삭제된 항목은 최신 상태로 정리하고 '찾을 수 없음' 오류를 반복하지 않는다.
- DB 저장/발생 검사가 끝나기 전에 반환된 후보도 표시 직전에 활성 상태를 재확인해 완료·삭제 직후의 오래된 후보를 띄우지 않는다.
- 발생 검사 중 규칙이 바뀌었다면 오래된 계산으로 next_fire_at을 덮어쓰지 않는다. 스케줄 저장은 예상 규칙/이전 스케줄과 현재 값을 비교하는 조건부 갱신을 사용하고, 달라졌으면 최신 규칙으로 다시 검사한다.
- 확인/재알림의 상태 변경도 트랜잭션에서 현재 delivery·규칙·업무 상태를 재확인한다. 오래된 클릭이 완료/삭제된 알림을 다시 SNOOZED로 만들지 않는다.
- 업무 편집/새 알림 설정 창은 ApplicationModal로 전체 앱의 알림을 막지 않는다. 주 창 소유의 비모달 창 + finished/accepted 처리 방식으로 연결한다.
- 같은 업무의 편집창은 재사용하고 새 업무 작성창도 중복 생성하지 않는다. 알림 설정 중 알림창/매시 알림창을 실제 마우스로 처리할 수 있어야 한다.
- 자식 알림 편집은 부모의 초안에만 적용한다. 부모 취소/종료 시 자식과 초안을 함께 정리하고, 알림 때문에 미저장 내용/포커스/선택을 초기화하지 않는다.
- 자식 설정/항목 편집이 열려 있는 동안 부모의 중복 설정 열기와 저장은 잠시 중지한다. 부모의 기준 날짜가 변하면 자식의 실제 예정 미리보기도 갱신한다. 독립 알림창의 입력을 막는 방식으로 부모를 잠그지 않는다.

### 6.4 오늘/월/선택 날짜의 읽기 전용 예약 조회

- `ReminderPreviewQuery`는 화면 시간대, 로컬 날짜 범위, 현재 시각, 페이지/검사 예산을 받는다.
  `ReminderPreviewItem`은 규칙 ID·업무 ID·회차·원래 예정·현재 유효 시각·delivery ID(있으면)·상태를 반환한다.
- 항목 정체성은 `(reminder_id, occurrence_start, original_scheduled_at)`이다. 업무 ID만으로 여러 알림/회차를 합치지 않는다.
  조회에서는 기존 fire_key와 같은 의미를 쓰지만 delivery/중복 방지 키를 새로 저장하지 않는다.
- 오늘 범위는 화면 시간대의 오늘 00:00 이상~다음 날 00:00 미만이다. 월 조회는 달력에 실제 보이는 앞뒤 달 날짜를 포함한 최대 42일 범위다.
  업무의 일정 범위/업무 검색 결과가 아니라 알림의 실제 발생 범위로 조회한다.
- directly 지정은 absolute_at 인덱스/범위 조회, 상대 규칙은 기준 날짜와 전후 30일 간격을 반영한 후보 조회를 사용한다.
  종료 기준은 ends_at을 기준으로 가져와 긴 기간 업무의 시작일이 범위 밖이라는 이유로 누락하지 않는다.
- 반복은 기존 발생 계산과 같은 시간대/offset 의미로 조회 범위에 해당하는 회차만 계산한다. 이미 완료/건너뛴 회차와 비활성/취소 업무는 예정에서 제외한다.
  next_fire_at이 첫 회차만 가리킨다고 나머지 월의 알림을 숨기지 않는다. 일정일이 다음 달이어도 이번 달의 사전 알림을 찾아야 한다.
- 범위별 예상 발생과 저장 delivery/재알림을 정체성으로 합쳐 상태를 만든다. 오늘 시각이 지났으나 delivery가 없으면 `시각 지남 · 발생 기록 없음`이지 확인함/실제 발생이 아니다.
- 과거 날짜는 저장된 실제 delivery를 중심으로 조회한다. 현재 수정된 규칙으로 과거의 실제 발생 이력을 만들어내지 않는다.
  PC가 꺼져 발생 이력이 없다면 '저장된 알림 이력 없음'으로 표시한다. 미래 월은 '현재 규칙 기준 예정'이며 실제 발생 보장이 아니라는 의미를 유지한다.
- 오늘은 원래 예정일이 오늘인 항목과 유효 재알림/복구 발생일이 오늘인 항목을 합친다.
  다른 날로 미룬 원래 항목은 이동된 날짜를 표시하되 오늘 다시 울릴 예약으로 간주하지 않는다.
- 규칙을 삭제하면 현재 FK cascade에 따라 그 규칙의 실제 이력도 사라질 수 있다. 날짜별 알림 목록을 영구 업무일지/감사 이력처럼 안내하지 않는다.
- 미리보기는 poll_due를 호출하거나 claim/acknowledge/next_fire_at 쓰기·복구·알림창 발생을 실행하지 않는다.
  달력을 다음 달로 넘겨 보는 행위가 알림을 소비하거나 조기에 발생시켜서는 안 된다.
- 월은 날짜별 개수 집계/간결한 표시만, 오늘/선택 날짜는 세부 항목을 페이지로 조회한다. 저장 이력·업무를 묶음 조회해 N+1을 피한다.
- 대량/사용자 정의 반복은 기존 검사 예산을 따르는 취소 가능한 배경 조회로 처리한다. 월/날짜/시간대가 바뀌면 이전 요청 결과를 버린다.
  예산 때문에 집계가 끝나지 않았으면 `집계 중` 또는 `알림 N+`와 추가 조회를 표시하며, 앞의 몇 건을 전체 개수인 것처럼 확정하지 않는다.
- 저장·확인·재알림·완료·휴지통·복원 후 오늘/월 집계/선택 날짜를 함께 무효화하고 필요한 범위만 다시 조회한다.
  정상 검사, 날짜 자정 변경, 시간대/PC 시각 변경, 앱 재시작도 반영한다. 기존 날짜·선택 정체성·스크롤·미저장 입력은 유지한다.
- 전체 보기/달력의 알림 행도 비모달이다. 현재 발생 알림창과 매시 알림의 마우스 입력을 막지 않는다.

## 7. 요일 표시 규칙

요일은 DB에 저장하지 않고 date에서 계산한다. OS 언어와 무관하게 월·화·수·목·금·토·일의 한국어 고정 매핑을 사용한다.
datetime은 화면이 사용하는 시간대로 변환한 다음 날짜와 요일을 계산한다. date 전용 업무일지 값은 시간대로 이동하지 않는다.

| 위치 | 표준 표현 |
| --- | --- |
| 날짜 입력 | `[2026-11-05] (목)` |
| 상세/설정 전체 날짜 | `2026-11-05(목) 09:00` |
| 한 줄 목록 | `11.05(목) 09:00` |
| 선택 날짜/페이지 제목 | `11월 5일(목)` |
| 종일 | `11.05(목) · 종일` |
| 기간 | `11.05(목)~11.07(토)` + 필요한 시각 |
| 재알림 | `10.26(월) 14:00` / 긴 상세는 연도 포함 |

- 입력칸은 기존 QDateEdit의 연·월·일 편집을 유지하고 내부에 읽기 전용 한국어 요일을 표시한다. 요일은 따옴표 리터럴로 표시해 네 번째 편집 구간이나 별도 포커스가 생기지 않는다. 기존 칸 밖 QLabel 방식은 사용 확인 후 제거했다.
- 날짜·요일·화살표가 함께 보이도록 실제 글꼴에 맞는 최소 폭을 확보한다. 글꼴/스타일 변경 시에도 다시 계산한다.
- dateChanged로 즉시 갱신한다. 잘못 입력한 중간 문자열에서 요일을 따로 추정하지 않고 유효한 QDate 값만 사용한다.
- 같은 날 시각만 보여주던 행/캘린더 셀에는 날짜를 억지로 중복하지 않는다. '오늘(화)' 등 제목/선택 상세에서 날짜·요일을 제공한다.
- 종일 기간의 마지막 표시 날짜는 기존처럼 배타적 종료에서 하루를 빼 계산한다. 00:00 경계의 다음 날 요일을 마지막 날인 것처럼 출력하지 않는다.
- 다년/연도 경계는 상세에 연도를 항상 표시하고 짧은 행에서는 툴팁/선택 상세로 전체 날짜를 제공한다.
- 시각과 요일의 시간대는 일치해야 한다. 특히 UTC→Asia/Seoul 변환으로 날짜가 바뀌는 야간 시각을 검사한다.
- 휴일 여부나 출근일 판정은 하지 않는다. 금요일은 공휴일이어도 '(금)'이며 요일 표시만으로 빨간 휴일 표시를 새로 만들지 않는다.

### 7.1 적용 위치

첫 구현의 완료 범위는 사람이 보는 날짜를 가진 다음 화면 전체다.

- 업무 편집의 시작일·종료일·반복 종료일, 알림 설정의 날짜와 예정 시각.
- 업무 목록·선택 상세·기간 표현·오늘 제목·휴지통 삭제 시각·재알림 안내.
- 업무 알림창과 날짜가 포함된 매시 알림 안내.
- 달력 선택 날짜 제목과 선택 업무 상세. 기존 요일 헤더와 셀의 날짜 숫자는 유지.
- 업무 기록의 날짜 입력·업무일지 목록/검색 기간/선택 상세.
- 첨부 검색 날짜 입력·검색 결과의 첨부 날짜, ICS 내보내기 기간 입력, 데이터 관리의 백업 날짜 안내.

Excel/ICS의 기계용 날짜, DB 값, 검색 비교, 파일명, 로그·무결성 검증·백업 매니페스트에는 요일 문자열을 붙이지 않는다.
첨부 수동 순서·일지의 검색 단위·기존 캘린더 첫 요일·기간 필터의 포함/제외 의미도 바꾸지 않는다.

공통 날짜 함수는 date, timezone-aware datetime을 구분하며 날짜 표시 로직에 Qt 객체/SQL을 섞지 않는다.
Qt 입력 도우미는 별도 UI 어댑터로 둔다. 날짜 문자열을 다시 파싱해 날짜/알림을 저장하지 않는다.
알림/재알림 요약은 현재 화면의 업무 ID에 대해 묶음 조회한다. 업무마다 SQL을 반복하거나 전체 DB/무한 반복 회차를 펼치지 않는다.
오늘/월 예약 조회는 업무 목록의 ID로 범위를 제한하지 않는다. 업무 목록 밖의 미래/일정 없는 업무도 알림 날짜 기준으로 가져온다.
목록 페이징·기존 알림 검사 예산/캐시·데이터 관리·백업 형식은 유지한다.

## 9. 호환성과 제외 범위

- 기존 알림 하나·start/end 둘·사용자 정의/비활성/absolute 여러 개를 모두 목록에 불러온다. 편집창을 열었다 닫는 것만으로 DB를 다시 쓰지 않는다.
- 백업은 기존 DB와 이력을 포함하므로 같은 형식으로 사용한다. 재시작·백업 복원 뒤에도 모든 활성 예약과 재알림을 유지한다.
- 기존에 표시되지 않던 absolute가 일정 없음 업무에 있어도 삭제하지 않고 관리 가능하게 한다.
- ICS는 현재처럼 일정만 내보낸다. OfficeFlow에서 여러 알림을 설정해도 ICS/외부 캘린더로 알림을 자동 전달하지 않는다.
- 첨부 수동 순서의 미커밋 변경은 보존한다. 이번 설계는 프로그램 버전·EXE·설치본·ZIP·Git 커밋·GitHub 공개를 변경하지 않는다.
- 삭제한 알림의 영구 감사 이력, 알림별 결과 메모, 알림 템플릿, 묶음 편집, 다른 업무 간 알림 복사는 제외한다.

## 11. 구현 순서와 완료 조건

1. 공통 날짜/요일 함수·입력 도우미, 20개 검증·규칙 편집 명령·상태 전이·날짜 범위 미리보기의 실패 테스트.

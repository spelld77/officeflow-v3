# 후속 개선 1차 상세설계

작성일: 2026-10-08. 상태: 1차 구현·개발 환경 검증 및 사용자 사용 확인 완료.
실제 결과와 미검증 환경: [1차 구현·검증 보고](26-follow-up-phase-1-results.md).

상위 기준: [전체 공통설계](24-follow-up-common-design.md),
요구 목록: [후속 개선 목록](23-follow-up-improvements.md).
이 문서는 1차의 화면·데이터·서비스·실패 처리·검증·구현 순서를 정한다.
상세설계 작성 요청은 코드 변경을 포함하지 않았다. 후속 `다음단계 진행` 요청으로
1차 코드 구현/격리 검증을 진행했다. 당시 실제 사용자 DB/첨부, 버전, 배포물, 커밋·GitHub 업로드는 변경하지 않았다.
이후 사용 확인 완료와 별도 사용자 요청에 따라 로컬 커밋 및 2차 상세설계를 진행한다.

## 1. 1차 범위와 사용자에게 생기는 변화

| 요구 | 1차 완료 시 동작 |
| --- | --- |
| U2 | 업무/회차 완료와 알림 확인 이력을 구분. 이미 열린 알림 설정창도 실제 상태 갱신 |
| U4 | 편집한 첨부의 실제 크기와 최근 확인 상태 제공. 정상 편집을 손상처럼 경고하지 않음 |
| U3 | 파일 하나를 오른쪽 클릭 → 다른 이름으로 저장 → 위치/이름 선택 → 독립 사본 생성 |
| U6 | 한 업무의 여러 첨부 선택 → 폴더 선택 → 기존 파일을 덮어쓰지 않고 일괄 저장 |
| U8 일부 | 첨부 정리 화면에서 파일 내용을 열어 보고 외부 저장 후 필요하면 별도로 삭제 |
| U10/U11 | 실패 시 자료 보존, worker/알림 독립성, 밝은 테마와 좁은 창 검증 |

이번에 하지 않는 것: U1 일정/알림 행 통합, 처리필요 기준 변경, 원본 지정/작업본/보관본,
보기 캐시, 첨부 메모, 업무 변경 이력/중요 시점 묶음, 업무자료 자동 정리/일괄 영구 삭제,
여러 업무 검색 결과의 일괄 저장. 보기 캐시는 공통설계 7.4에 따라 2차에 포함한다.
파일 저장 버튼은 내부 자료의 이동/삭제/새 첨부 등록을 수행하지 않는다.

## 2. 현재 코드 확인과 변경 지점

| 확인한 현재 동작 | 1차 변경 |
| --- | --- |
| `ReminderPreviewItem.status`는 표시 문자열이며 업무 상태와 섞이지 않음 | 실행 범위 상태와 알림 상태를 별도로 전달하고 공통 포맷 사용 |
| 미리보기 delivery 조회에는 해당 회차 상태가 직접 포함되지 않음 | 필요한 회차 상태를 같은 조회 스냅샷에서 일괄 확보 |
| 열린 설정창 동기화는 delivery만 갱신 | 편집 초안과 별개의 실제 업무/회차 실행 상태도 갱신 |
| 달력 알림 건수는 해당 날짜의 전체 미리보기 행 수 | 유효 알림 수와 처리 이력을 구분 |
| `Attachment.size_bytes/checksum`은 최초 첨부 정보 | 최초 정보는 유지하고 최근 성공한 실제 관측 정보 추가 |
| 기준 해시 없는 파일을 검사하면 최초 해시를 새로 채움 | 과거 기준 없음과 지금의 관측값을 분리 |
| 중복 추가 판단은 최초 해시 인덱스 조회 | 실제 저장 내용이 같은 후보만 중복으로 판정 |
| 기록창 첨부 목록은 단일 선택, 열기/검사/해제/삭제 버튼 | 여러 선택과 외부 저장 추가, 드문 행동은 더보기로 정돈 |
| 정리 목록은 복원/영구 삭제 중심 | 선택 항목 열기와 외부 저장 추가 |
| 사용량의 중복 계산은 DB 체크섬 기반 | 오래된 정보는 중복 확정이 아닌 최근 확인 기준 후보로 안내 |

기존 `TaskSaveService`의 업무+알림 저장 트랜잭션, 첨부 순서,
삭제 격리/복구, 백업 manifest 검증, 알림 스케줄러의 발생/재알림 규칙은 보존한다.

## 3. 화면 상세 동작

### 3.1 업무 기록창의 첨부 탭

기존 첨부 탭을 사용한다. 주 창에 새 관리 탭을 추가하지 않는다.

- 상단: `파일 선택 (여러 개)`, 기존 `위로 / 아래로`.
- 목록: Ctrl/Shift 복수 선택. 파일 이름·최근 확인 크기·확인 상태의 간결한 행.
- 상세: 한 개 선택 시 최초 정보/최근 확인 시각/현재 빠른 확인 정보를 표시.
  여러 개 선택 시 선택 수와 확인된 크기 합계 표시. 모르는 크기를 0으로 더하지 않는다.
- 하단: `열기`, `다른 이름으로 저장…` 또는 `선택 N개 저장…`, `더보기`.
- 더보기: `파일 정보 확인`, `연결 해제`, `파일 삭제`. 기존 순서의 맨 위/맨 아래 이동은 오른쪽 메뉴에 유지.
- 설명: `편집 후 저장한 내용이 사본에 포함됩니다. 미저장 내용은 포함되지 않습니다.`
  `외부 저장은 내부 첨부를 삭제하지 않습니다.`는 도움말/결과에서 안내한다.
- 기존 안내의 `원본을 앱 관리 폴더에 복사`는 `선택한 파일을 앱 관리 폴더에 복사`로 정돈한다.
  2차의 보호 역할인 원본과 일반 가져오기 출처를 혼동시키지 않는다.

| 선택 상태 | 열기 | 외부 저장 | 검사·해제·삭제·수동 순서 |
| --- | --- | --- | --- |
| 없음 | 비활성 | 비활성 | 비활성 |
| 한 개 | 해당 파일 열기 | 표준 파일 저장 대화상자 | 단일 항목에만 기존 동작 |
| 여러 개 | 비활성 | 표준 폴더 선택 후 일괄 저장 | 비활성. 복수 선택이 일괄 삭제 허가가 되지 않음 |
| 휴지통 업무 | 읽을 수 있으면 허용 | 허용 | 해제/삭제/순서 변경은 읽기 전용 정책 유지 |

캐시된 누락 상태만으로 영구히 열기/저장을 막지 않는다. 선택 항목의 빠른 재확인으로 상태를 갱신하고
실제 읽기 시에도 다시 확인한다. 빠른 재확인 중 버튼을 잠시 비활성화하고 상태를 표시할 수 있다.
알림을 처리하거나 다른 업무를 보는 동작은 파일 작업 때문에 차단하지 않는다.

### 3.2 오른쪽 메뉴와 선택 유지

- 선택된 파일에서 오른쪽 클릭: 기존 다중 선택을 유지한다.
- 선택되지 않은 파일에서 오른쪽 클릭: 그 파일 하나를 선택한다.
- 단일 선택 메뉴: `열기 / 다른 이름으로 저장… / 파일 정보 확인 / 순서 이동 / 연결 해제 / 파일 삭제`.
- 복수 선택 메뉴: `선택 N개 저장…`만 실행 가능한 파일 행동으로 제공한다.
- 더블클릭은 해당 한 파일 열기다. 복수 선택한 파일들을 한꺼번에 열지 않는다.
- 새로고침 후 살아 있는 선택 ID들과 스크롤을 보존한다. 삭제된 ID만 선택에서 제거한다.
- 파일 작업 시작 시 선택 목록을 고정한다. 도중에 선택을 바꿔도 진행 중 작업의 대상은 바뀌지 않는다.

### 3.3 다른 화면의 연결

- 첨부 검색: 단일 결과에 `다른 이름으로 저장…` 제공. 기존 단일 선택/페이지 조회 유지.
  여러 업무의 검색 결과를 동시에 내보내는 UI는 추가하지 않는다.
- 달력/오늘/업무일지: 기존 첨부 보기 동선으로 첨부 탭을 열어 같은 저장 기능을 사용한다.
  각 화면에 독립적인 파일 복사 구현이나 추가 버튼을 여러 개 만들지 않는다.
- 데이터관리 → 첨부 정리: `열기 / 다른 이름으로 저장… / 더보기(복원·영구 삭제)`.
  정리 목록은 단일 선택을 유지한다. 같은 업무의 여러 파일은 해당 업무 첨부 탭에서 저장한다.
- 작업 결과: 완료 수/실패 수/미처리 수와 `폴더 열기`, 실패/미처리 `다시 시도`를 제공한다.
  문서 자동 열기, 내부 삭제 버튼과의 자동 연결, 외부 저장 증빙 시스템은 만들지 않는다.

### 3.4 좁은 창·Tab·테마

- 핵심 버튼 세 개 중심으로 배치하고 드문 행동을 더보기에 넣는다. 강제 고정 폭으로 잘리지 않게 한다.
- 긴 이름은 목록에서 생략 표시하되 툴팁/상세에서 전체를 읽을 수 있다.
- 파일 상태는 색상만으로 구분하지 않는다. `수정됨`, `확인 필요` 등 글자를 함께 사용한다.
- 기본 Tab 순서는 파일 추가 → 목록 → 열기 → 저장 → 더보기 → 창 닫기다.
  순서 이동 버튼은 사용 가능한 경우 자연스러운 기존 위치를 유지한다.
- 공통 밝은 테마를 탭 본문·viewport·메뉴·상세·진행/결과 창까지 적용한다.
  추가 진행 창은 NonModal이고 최소화/창 닫기/알림 처리와 충돌하지 않아야 한다.

## 4. U2: 알림 실행 상태와 편집 초안 분리

### 4.1 읽기 모델

알림 미리보기의 기존 식별 키 `(reminder_id, original_occurrence_start, scheduled_at)`를 유지한다.
`status` 문구 자체를 합쳐 판단하지 않고 다음 의미를 별도 읽기 데이터로 둔다.

- 실행 범위 상태: 진행/대기, 업무 완료/취소/보관/휴지통, 이번 회차 완료/건너뜀/취소.
- 알림 상태: 예정, 시각 지남·발생 기록 없음, 미확인, 재알림, 확인함, 완료 처리, 대기 처리, 다른 날로 미룸.
- 현재 유효 알림 여부: 실제 실행 범위와 알림 상태에서 계산한 boolean.
- 회차 ID/원래 발생 시각, 예정/발생/재알림 시각은 현재처럼 따로 유지한다.

실행 데이터는 `ReminderRuntimeState`(실제 업무, 원래 회차별 상태, delivery, 읽기 시각)로 전달한다.
각 편집창은 `update_runtime_state`를 받아 초안 계산과 독립적으로 표시한다.
실제 업무/회차 ID는 저장된 식별자를 사용한다. 미리보기를 위해 만든 임시 `Task`의 ID 없음 때문에
저장된 실행 이력의 범위를 놓치지 않는다.

해당 delivery의 회차 상태는 원래 회차 키로 일괄 조회하거나 LEFT JOIN한다.
미리보기 날짜 근처의 닫힌 회차만 찾는 방식으로 과거/먼 미래 회차를 잘못 판단하지 않는다.
각 행에서 `TaskService`를 호출하는 N+1 조회는 금지한다.
범위/예산은 기존 1~42일, 결과 한도/중단 여부 계약을 보존한다.

### 4.2 표시와 건수

| 실제 범위 | 알림 처리 | 표시 예 |
| --- | --- | --- |
| 진행 중 | 예정 | `예정` |
| 진행/대기 | 재알림 | `재알림 10.08(목) 15:10` |
| 업무 완료 | 이미 확인함 | `업무 완료 · 알림 확인함` |
| 업무 완료 | 완료 처리된 delivery | `업무 완료 · 알림 처리됨` |
| 이번 회차 완료 | 이미 확인함 | `이번 회차 완료 · 알림 확인함` |
| 업무 취소/보관 | 과거 이력 | 실제 업무 상태와 기존 알림 처리 상태를 함께 표시 |

- 완료 때문에 아직 발생하지 않은 예약을 달력에 새 이력 행으로 만들지 않는다.
  알림 설정/요약에는 `업무 완료 · 이후 알림 중단`을 표시한다.
- 오늘 요약은 `확인할/예정 N건 · 처리 이력 M건`으로 구분한다.
  같은 업무의 여러 알림을 한 행으로 합치지는 않는다(U1 보류).
- 달력 날짜 칸의 `알림 N`은 현재 유효한 예정·미확인·재알림 수다.
  날짜 아래 목록/전체 보기에는 과거 처리 이력을 유지하고 유효 수와 이력 수를 따로 표시한다.
- `시각 지남 · 발생 기록 없음`은 울릴 예정이라고 단정하지 않고 별도 확인 필요 상태로 센다.
  미리보기 조회가 알림을 새로 발생시키거나 누락 복구를 수행하지 않는다.
  확인 필요가 있으면 오늘/날짜 아래 요약에 `발생 기록 확인 필요 K건`을 추가하고
  유효 알림/처리 이력에 중복 합산하지 않는다. 달력 날짜 칸에서는 `알림 확인 필요`로 구분한다.
- 다른 날 재알림의 원래 날짜 표시는 이동 이력이다. 실제 유효 수는 재알림 날짜에만 포함한다.
- 일부 조회이면 각각 확인된 수임을 알린다. `0건`을 전체 없음으로 오해시키지 않는다.
- 모든 문구/건수/회색 처리는 한 상태 포맷/판정 함수를 사용한다.
  기존 문자열의 `is_pending` 판정 앞에 `업무 완료` 문구만 붙이는 수정은 하지 않는다.

### 4.3 열린 창의 갱신

기존 `_task`/편집 기준값을 실제 상태 갱신용으로 덮어쓰지 않는다.

1. 업무/알림 처리 커밋 후 해당 업무의 실행 상태 갱신을 요청한다.
2. 실제 업무 상태, 관련 회차 상태, delivery들을 동일한 읽기 시점에서 가져온다.
3. `TaskEditorDialog`와 `ReminderSettingsDialog`에 별도의 runtime 상태로 전달한다.
4. 실제 상태 배너/실행 이력/다음 실제 예약 요약만 갱신한다.
5. 제목/설명/일정/상태 선택/알림 규칙의 미저장 입력, 선택 행, 스크롤, 열린 하위 규칙 창은 보존한다.

업무가 완료된 뒤 편집 초안에 진행 상태가 남아 있어도 `예정`을 실제 예약처럼 표시하지 않는다.
초안의 날짜/규칙 계산은 `미저장 설정 미리보기`로 구분한다. 새 업무는 실제 저장 상태가 없으므로
미리보기만 사용한다. 실제 상태가 바뀌었어도 기존 저장 충돌 검사는 유지한다.
자동 갱신이 저장 기준을 최신 값으로 바꿔 완료된 업무를 무심코 재개하게 해서는 안 된다.

갱신은 열린 업무 ID를 모아 중복 조회를 피하고 결과 세대 번호로 오래된 응답을 버린다.
완료/재개/대기/휴지통/복원/회차 완료·되돌리기와 알림 확인/재알림에서 연결한다.
주기 조회는 보완 수단이며 버튼 처리 후 다음 타이머까지 기다려야만 보이는 구조로 만들지 않는다.
알림 창의 완료/확인 기능, 다음 회차 예약, 다중 알림 최대 20개는 변경하지 않는다.

## 5. U4: 최초 정보와 최근 관측 정보

### 5.1 1차 스키마

기존 `attachments.size_bytes/checksum`은 최초 첨부 정보로 유지한다.
다음 nullable 관측 컬럼을 추가한다. 실제 migration은 구현 때 생성하며 예상 이름은
`0012_attachment_observation`이다. 최신 head가 달라지면 그 시점 head에 연결한다.

| 컬럼 | 타입/기본 | 의미 |
| --- | --- | --- |
| `observed_size_bytes` | INTEGER / NULL | 마지막 성공한 전체 내용 확인의 실제 크기 |
| `observed_checksum` | VARCHAR(64) / NULL | 같은 확인에서 계산한 SHA-256 |
| `observed_mtime_ns` | INTEGER / NULL | 그 내용 확인 시 수정 시각 힌트 |
| `observed_at` | UTC datetime / NULL | 성공한 내용 관측 시각 |
| `last_check_status` | VARCHAR(32) / NULL | 마지막 검사 결과. 아래 상태값 |
| `last_checked_at` | UTC datetime / NULL | 성공/오류 검사를 마지막으로 시도한 시각 |

관측 네 컬럼은 한 번의 성공한 읽기 결과로 함께 저장한다. 크기만 새로 바꾸고 해시는 옛값을
같은 시점의 정보처럼 남기지 않는다. `mtime_ns`는 힌트이며 동일 내용/미수정을 증명하지 않는다.
SHA 관측 후보 조회용 `(task_id, observed_checksum)` 인덱스를 추가한다.
상태값은 domain enum으로 제한하고 관측 크기/SHA/UTC의 유효성은 기존 검증 방식을 확장한다.

| 상태값 | 화면 | 의미 |
| --- | --- | --- |
| NULL | `내용 미확인` | 과거 데이터/아직 검사하지 않음 |
| `unchanged` | `첨부 당시와 같음` | 현재 관측값이 최초 기준과 같음 |
| `modified` | `첨부 후 수정됨` | 현재 내용과 최초 기준이 다름. 손상 판정 아님 |
| `no_baseline` | `내용 확인됨 · 최초 기준 없음` | 현재 읽기 성공, 과거 해시를 알 수 없음 |
| `missing` | `파일 누락` | 현재 파일 없음 |
| `unavailable` | `확인 불가` | 잠금/권한/읽기 오류 등 |
| `changing` | `저장 중 · 다시 확인` | 검사 중 내용/경로가 바뀜 |

`확인 중`, `다시 확인 필요`는 화면/요청 상태로 계산한다. 오류 메시지 전문을 DB에 계속 쌓지 않는다.
missing/error 결과에서는 이전 성공한 관측값을 지우거나 그 값을 현재 내용처럼 표시하지 않는다.
사용자 취소는 오류로 저장하지 않고 기존 완료 관측과 검사 상태를 유지한다.
파일 존재를 읽기로 확인한 성공 결과는 `missing_at`도 함께 해제한다.
접근 거부를 파일 없음으로 바꾸지 않는다. DB에 저장된 과거 누락 표시는 현재 검사 오류와 구분한다.

새 첨부는 가져온 크기/해시를 최초 정보와 최초 관측으로 함께 기록할 수 있다.
관측 시각/파일 특성은 최종 관리 파일을 확인해 연결한다. 기존 첨부는 migration 때 전부 NULL을 유지한다.
디스크를 훑어 모든 파일을 검사하거나 old 값을 지금의 관측값으로 소급하지 않는다.
기준 해시가 없을 때 현재 해시를 `checksum`에 채우는 기존 verify 동작은 중단한다.

### 5.2 조회·감지 시점

- 목록 표시/검색은 DB 메타데이터로 즉시 구성한다. 전체 파일 해시는 계산하지 않는다.
- 첨부 탭을 활성화하거나 돌아올 때 보이는 항목을 worker에서 빠르게 stat 확인한다.
  요청을 합치고 화면을 떠나면 오래된 결과를 버린다. GUI에서 동기 파일 탐색하지 않는다.
- 빠른 확인의 현재 크기/수정 시각은 화면용 표본이다. 성공한 SHA 관측 컬럼과 혼합 저장하지 않는다.
  바뀐 힌트가 있으면 `현재 크기 … · 내용 다시 확인 필요`로 표시한다.
- `파일 정보 확인`을 실행하면 선택 한 파일의 안정적인 전체 해시/크기를 관측한다.
  이때 `수정됨`은 정상적인 작업 파일 편집일 수 있다고 안내한다.
- 외부 저장/중복 판별 과정에서 성공한 안정적인 읽기 결과도 관측 갱신에 활용한다.
  같은 파일을 직후 UI 갱신 때문에 다시 해시하지 않는다.
- 타이머로 모든 첨부를 검사하거나 모든 외부 문서 편집기를 감시하지 않는다.
  외부 프로그램에서 저장 후 돌아왔다는 사실만으로 내용 동일 여부를 확정하지 않는다.

관측 저장은 첨부 ID/예상 경로/요청 세대와 현재 연결을 확인한다. 더 최신 결과를 옛 결과로 덮지 않는다.
repository의 `update_observation_if_current`는 예상 관측 버전(직전 관측/검사 시각)과 경로를 조건으로 갱신한다.
GUI 요청 번호만으로 서로 다른 창/worker의 DB 갱신 순서를 보호했다고 간주하지 않는다.
중간에 해당 첨부가 삭제/교체되면 관측 갱신은 폐기한다. 성공한 외부 저장 자체를 DB 관측 저장 실패 때문에
실패로 바꾸지는 않는다. `사본 저장 완료 · 첨부 정보 갱신은 다시 확인 필요`로 분리한다.
관측 갱신은 업무 변경/결과메모가 아니며 향후 자동 이력을 발생시키지 않는다.

### 5.3 중복 추가 판별

1. 새 출처를 기존 방식으로 안전하게 준비 복사하여 실제 크기/해시를 얻는다.
2. 같은 업무의 활성 첨부 후보를 페이지/worker로 확인한다. 해제/다른 업무 파일은 현재 중복 방지 대상이 아니다.
3. 최초/최근 해시 인덱스는 우선 후보를 찾는 용도로만 사용한다. 나머지 후보의 현재 크기도 확인한다.
   옛 크기만으로 현재 같을 수 있는 파일을 제외하지 않는다.
4. 실제 크기가 같은 후보의 현재 내용을 안정적으로 읽는다. 현재 해시가 같을 때만 중복으로 확정한다.
5. 짧은 게이트/DB 구간에서 후보가 여전히 활성 연결이고 확인한 파일임을 재확인한 뒤 등록/중복 결과를 결정한다.
   후보 읽기 보호는 최종 판단까지 유지한다. 긴 해시 계산은 게이트/DB 쓰기 밖에서 한다.

오래된 `A` 해시를 가진 첨부가 실제로 `B`로 편집되었으면 새 `A`는 추가할 수 있고
새 `B`는 현재 `B`를 읽어 확인했을 때 중복으로 판정한다.
검사 불가 후보를 동일 내용으로 추정하여 새 파일을 버리지 않는다. 해당 경우 새 첨부 등록은 허용하되
`일부 기존 파일의 중복 확인 불가`를 결과에 알린다. 취소 시 새 준비 파일만 정리한다.
새 작업본 만들기와 내용 중복은 2차에서 별도 명령으로 구분하며 이 API를 그대로 강제 적용하지 않는다.

### 5.4 사용량·검색·백업 소비자

- 검색/첨부 목록의 저장된 크기 표시는 `최근 확인 크기`, 없으면 `첨부 당시 크기`로 구분한다.
  빠른 stat가 있는 화면은 실제 표본 크기를 우선 보여준다.
- 데이터관리 사용량의 물리 크기는 기존 파일 inventory의 stat 결과를 사용한다.
  연결/해제 용량도 읽을 수 있는 파일은 그 실제 크기를 반영하고 미확인/누락 수를 구분한다.
- 중복 용량은 최신 관측 기준 후보일 뿐 파일 삭제 근거가 아니다. 전체 해시 검사를 자동 추가하지 않는다.
  `최근 확인 기준 중복 후보`라는 문구와 미확인 수를 사용한다. 예전 checksum만의 확정 집계는 제거한다.
- 백업은 최초/관측 정보가 달라도 현재 파일을 독립적으로 복사해 manifest를 검증한다.
  관측 해시를 백업의 실제 해시 대신 쓰지 않는다. 최초 해시가 없는 파일도 백업한다.
- metadata 검색 인덱스는 file name/task title 범위를 유지한다. 관측값 갱신으로 FTS 전체 재생성을 하지 않는다.

## 6. 파일 참조·읽기·사용 예약

### 6.1 서비스 데이터 계약

Application 경계의 DTO를 마련한다. 아래 이름은 구현 시 코드명으로 사용할 기준이다.

| 계약 | 핵심 데이터 |
| --- | --- |
| `FileReference` | kind=attachment/orphan, 첨부 ID 또는 검증 가능한 관리 상대 경로 |
| `ResolvedFileReference` | 실제 경로, 표시 이름, 업무/첨부 ID, 내용 종류, 기준 정보 |
| `FileObservation` | 실제 크기/SHA/파일 특성/관측 시각/검사 결과 |
| `ExportRequest` | 선택 참조의 고정 목록, 단일/일괄 모드, 선택 대상 경로/폴더 |
| `ExportItemResult` | 참조, 실제 출력 이름/경로, 캡처 시각, 성공/실패/미처리/확인 필요, 원인 코드 |
| `ExportBatchResult` | 각 결과, 작업 ID, 취소 여부, 출력 폴더 |

1차의 attachment resolver는 기존 행/저장소를 읽는 어댑터다. 2차에는 자산 원장/보호 파일 경계를
이 어댑터 아래에 연결한다. 화면/외부 저장 API는 원장 교체에 따라 다시 구현하지 않는다.
orphan은 일반 파일 경로를 임의 전달하는 탈출구가 아니다. 관리 루트 내부의 정리 항목만 허용한다.
2차 이후에는 새 보관 자산/작업 저널/캐시를 고아 파일로 오인하지 않도록 resolver와 inventory를 함께 확장한다.

### 6.2 안정적인 읽기

- 외부 저장/최종 중복 확정은 선택 파일에 쓰기/삭제 공유를 허용하지 않는 읽기 핸들을 확보한다.
  잠금 실패 시 저장하고 문서를 닫은 뒤 다시 시도하도록 안내한다.
- 기존 checksum의 before/after 파일 특성 비교도 유지한다. 경로 교체/예상치 못한 변경은 실패로 처리한다.
- 내용 확인만 하는 verify는 기존 안정성 검사도 재사용하되 상태를 변경/확인 불가로 구분한다.
  OS 보호를 확보하지 않은 검사를 절대적인 시점 동결과 동일하다고 안내하지 않는다.
- 자료를 읽고 준비 사본의 검증을 끝내면 외부 저장의 출처 보호를 해제할 수 있다.
  사용자 덮어쓰기 확인을 기다리는 동안 출처 편집을 계속 막지 않는다.
- Win32 공유 모드의 보장은 핸들이 살아 있는 동안이다. 회사 보안/파일시스템이 이를 지원하지 않으면
  안전한 복사에 성공한 것으로 간주하지 않는다. 우회나 단순 shutil 복사 fallback을 하지 않는다.
  근거: [CreateFileW 공유 규칙](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew).

### 6.3 앱 내부 예약

공통 파일 조정자를 생성자/부트스트랩에서 공유 주입한다. 숨은 전역 작업자/DB session을 추가하지 않는다.
예약 키는 정규화된 관리 상대 경로이며, 추후 자산 ID를 해석하는 경계에서도 같은 파일 보호를 사용한다.

- 짧은 기존 파일 게이트에서 출처를 재조회하고 사용 예약을 등록한다.
- 파일 읽기/복사 동안 예약은 유지하지만 게이트는 풀어 둔다.
- `delete_file`, 관리 고아 파일 삭제, 업무 영구 삭제는 예약을 서비스 단계에서 검사한다.
  UI 버튼만 막는 방식으로 다른 삭제 경로를 놓치지 않는다.
- 업무 영구 삭제는 DB CASCADE **전에** 현재 첨부/해제 경로의 예약을 확인한다.
  DB만 먼저 지우고 열린 파일 삭제 실패를 뒤늦게 발견하는 흐름을 허용하지 않는다.
- 최종 검사+DB 삭제는 짧은 동일 게이트 안에서 처리한다. 실패한 사용자 명령은 DB 연결을 유지한다.
- 종료/취소/예외마다 finally로 핸들/예약을 해제한다. 예약 때문에 장기 고아 상태를 만들지 않는다.
- 물리 파일을 없애지 않는 순서/관측 갱신은 가능하다. 출처 연결이 바뀌면 관측의 최종 저장 조건으로 처리한다.
- 가져오기 중 아직 DB 등록 전인 새 파일도 작업 예약으로 구분한다.
  긴 중복 판별 동안 이를 정리 목록의 삭제 가능한 고아 파일로 노출하지 않는다.

큰 파일 복사 때문에 게이트를 길게 잡거나 DB 트랜잭션 안에서 해시를 계산하지 않는다.
알림 상태 변경은 파일 작업 큐에 넣지 않는다.

## 7. U3/U6: 외부 저장 구현 계약

### 7.1 경로·이름·설정

- 단일: `QFileDialog.getSaveFileName` 계열의 Windows 표준 저장 UI.
  기본 이름은 목록의 `original_name`, 확장자는 실제 출처 형식으로 유지한다.
- 복수: 표준 폴더 선택. 선택 순서는 현재 첨부 수동 순서와 같고 출력 과정이 내부 순서를 바꾸지 않는다.
- 확장자 누락은 기본 확장자를 붙인다. 이미 입력한 같은 확장자는 다시 붙이지 않는다.
  다른 확장자는 파일 형식 변환이 아님을 안내하고 원래 확장자를 유지하도록 이름을 정정한다.
- Windows 예약 이름/금지 문자/끝 공백·마침표/길이/폴더 오류를 확인한다.
  일괄 저장의 잘못된 표시 이름은 안전한 이름을 제안해 변경 사실을 결과에 표시한다. DB 표시 이름은 바꾸지 않는다.
- 원본과 같은 경로/동일 물리 파일(hardlink 포함), 데이터 루트 내부, 보기 캐시, 백업 관리 폴더는 출력 대상으로 거절한다.
- 선택 폴더는 실제 접근 결과로 확인한다. 네트워크/보안 접근 실패를 정상 저장으로 표시하지 않는다.
- `AppSettings.attachment_export_directory: str | None`에 마지막 성공한 폴더만 기록한다.
  없거나 접근 불가하면 사용자 문서 폴더 등 안전한 기본 위치로 되돌린다. 설정 손상은 이 필드만 무시한다.
  오래된 설정 파일은 기본값으로 읽고, 이 필드 오류 때문에 전체 기존 설정을 초기화하지 않는다.
- 외부 파일들과 자동 동기화할 연결/영수증 DB는 만들지 않는다.

### 7.2 준비 복사와 새 파일 공개

1. 선택 참조와 대상 폴더를 고정하고 사용 예약/읽기 보호를 확보한다.
2. 대상과 같은 폴더에 앱 소유의 고유한 임시 파일을 배타 생성한다.
3. 출처를 1 MiB 청크로 읽어 복사하고 SHA/크기를 계산한다. 진행 통지는 최대 약 10회/초로 제한한다.
4. 준비 파일을 flush/fsync하고 독립적으로 크기/해시를 확인한다. 읽기 결과와 다르면 공개하지 않는다.
5. 사용 예약/출처 보호를 해제하고 준비 파일에서 최종 공개 절차를 수행한다.
6. 공개가 확인된 뒤에만 성공 결과를 반환한다. 문서는 자동으로 열지 않는다.

새 이름 공개는 덮어쓰기 없는 Windows 파일 rename/move 연산을 사용한다.
`exists()` 뒤 무조건 `os.replace()`하는 패턴은 금지한다.
Windows `os.rename`은 대상이 이미 있으면 실패하므로 새 출력의 충돌 방지 기반으로 사용할 수 있다.
다른 OS에서 같은 호출의 덮어쓰기 의미를 그대로 가정하지 않는다.
근거: [Python 3.12 os.rename/os.replace](https://docs.python.org/3.12/library/os.html#os.rename).

파일시스템/보안 제품이 검증/공개를 거절하면 실패다. final 경로를 먼저 빈 파일로 만들고
나중에 본문을 채워 완료 파일처럼 보이게 하는 구현은 하지 않는다.

### 7.3 단일 덮어쓰기

덮어쓰기 확인은 한 번만 제공한다. native 대화상자의 확인과 앱 확인이 중복되지 않도록 조정한다.
짧은 확인창은 준비된 내용과 실제 덮어쓸 파일 이름/폴더를 보여준다.

- 선택 시/교체 전에 기존 대상의 안정적인 파일 식별·내용 지문을 확인한다.
  확인 후 바뀌었으면 교체하지 않고 새 대상에 대한 재확인을 요청한다.
- 기존 파일을 지운 뒤 복사하지 않는다. 검증된 준비 파일의 교체에
  복구용 기존 파일을 남길 수 있는 Windows `ReplaceFileW` 어댑터를 사용한다.
- 복구 파일 경로를 항상 지정하고 오류를 무시하는 ACL/보안 옵션은 사용하지 않는다.
  대상 폴더/플랫폼이 안전한 교체를 제공하지 않으면 다른 이름 또는 다른 폴더를 안내한다.
- 교체 후 실제 출력과 보존된 이전 대상도 확인한다. 최종 확인과 교체 사이에 외부 프로그램이
  대상을 바꾼 경쟁이 발견되면 정상 성공으로 숨기지 않는다.
- 일반 복사/취소/잠금 실패에서는 기존 대상이 그대로 남는다.
  Windows의 부분 교체 오류나 재시작 시에는 원경로 상태부터 점검한다.
  복구할 수 있으면 되돌리고, 자동 복구가 안전하지 않으면 이전/새 파일을 모두 보존해 위치를 안내한다.
- 취소는 교체 직전까지 적용한다. 교체/복구 중에는 `안전하게 마무리 중` 상태로 끝낸다.
  공개에 성공한 파일을 취소 때문에 삭제하거나 실패한 것으로 되돌리지 않는다.

`ReplaceFileW`에는 오류 종류별로 파일이 다른 이름에 남는 경우가 있으므로
`실패하면 언제나 원경로가 그대로`라는 가정을 하지 않는다.
근거: [Microsoft ReplaceFileW 오류·복구 파일 문서](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew).
이 처리는 공통설계의 기존 대상 보존 원칙을 구현하는 세부 규칙이다.
외부 프로그램의 동시 변경/플랫폼 오류까지 완전한 파일시스템 트랜잭션으로 보장한다고 안내하지 않는다.

### 7.4 여러 파일 저장

- 기존 폴더 파일과 이번 선택 사이의 이름 충돌을 대소문자 구분 없이 처리한다.
- `보고서.xlsx`, `보고서 (1).xlsx`, `보고서 (2).xlsx`처럼 확장자 앞에 번호를 붙인다.
- 준비 파일 공개 때 다른 앱이 같은 이름을 만들면 덮어쓰기 없는 공개가 실패하도록 하고 다음 번호로 재시도한다.
  충돌 재시도 횟수에 상한을 두고 비정상 경쟁은 실패 항목으로 보고한다(기본 100회).
- 파일 하나 실패해도 취소가 아니면 다음 파일을 시도한다. 같은 폴더의 공간/접근 불가가 계속되면
  나머지는 미처리로 종료하여 동일 오류를 반복하지 않는다.
- 완료 파일은 남긴다. 실패/미처리만 재시도하되 다시 참조/이름/실제 저장 내용을 확인한다.
- 재시도는 새 작업이다. 그 사이 편집된 파일의 새 내용이 저장될 수 있음을 안내한다.
- 결과는 `3개 저장 · 1개 실패 · 1개 미처리`처럼 정확하게 표시한다.
  자동 변경된 이름과 원래 목록 이름을 대응시킨다. `폴더 열기`로 저장 장소를 확인한다.
- 여러 파일의 정확한 동일 시점 자료를 만드는 기능은 아니다. 그 요구는 3차의 중요 시점 묶음이다.

### 7.5 외부 작업 저널·중단 복구

내부 파일 확정 영수증 테이블은 2차에 도입한다. 1차 외부 저장은 SQLite에 출력 파일을 등록하지 않는다.
대신 데이터 루트의 전용 외부 저장 작업 저널에 작업 ID/정확한 임시·출력·복구 경로/검증값/진행 상태를 남긴다.
문서 본문/인증 정보는 넣지 않는다. 입력값을 문자열 명령으로 만들어 shell에 전달하지 않는다.

- 준비 복사: 기존 출력/관리 출처는 손대지 않는다. 강제 종료 후 남은 준비 파일은 완료 파일이 아니다.
- 새 파일 공개 후 통지 전: 출력 검증값으로 공개 여부를 확인한다. 무조건 다시 복사하여 번호 사본을 늘리지 않는다.
- 덮어쓰기 직전/직후: 저널과 복구 파일을 보고 양쪽 자료를 보존하고 완료/복구 필요를 구분한다.
- 복구/정리 대상은 앱 소유·경로·파일 식별/검증값이 확인된 정확한 파일뿐이다.
  그 뒤 사용자가 수정한 출력/복구 파일은 자동 삭제/교체하지 않는다.
- 재시작 시 사용자 폴더를 임의로 훑거나 덮어쓰지 않는다. 미완료 작업을 알리고
  실제 외부 파일 변경/삭제가 필요한 복구는 사용자 확인 후 안전하게 진행한다.
- 성공 확인 후 임시/교체 복구 파일 정리 실패는 별도의 `정리 확인 필요`로 남긴다.
  이미 성공한 사본 저장을 실패로 표시하거나 파일을 다시 출력하지 않는다.
- 유효하지 않은 저널은 자동 삭제 지시로 실행하지 않는다. 미분류 상태로 보존하고 안내한다.

이 저널은 독립 외부 파일의 장기 관리/백업 기록이 아니라 진행 중 파일 작업 복구 정보다.
완료/정리를 확인한 기록만 정리한다. 정리할 수 없는 복구 파일 위치는 사용자가 확인 가능하게 한다.

## 8. U8: 첨부 정리에서 확인 후 보관

- 해제 첨부: 등록된 표시 이름으로 열기/외부 저장 가능. 내부 연결은 복원하지 않아도 된다.
- 고아 파일: 실제 저장 이름을 기본 이름으로 사용한다. 원래 업무/사용자 파일명을 복원했다고 주장하지 않는다.
- 파일이 읽히면 열기/저장, 없거나 접근 거부면 실패 이유를 표시한다.
- 고아 참조는 읽기 직전 안전한 상대 경로/일반 파일/숨김 작업 영역 제외/등록 연결 여부를 확인한다.
  현재 일반 첨부로 다시 등록됐다면 올바른 attachment 참조로 재조회하거나 목록을 갱신한다.
- `열기/외부 저장`과 `복원/영구 삭제`는 별도 행동이다. 저장 성공 후 삭제를 자동 실행하지 않는다.
- 삭제 확인에는 `외부 저장 파일과 기존 백업은 삭제하지 않습니다`를 안내한다.
  사용 예약 중인 파일이면 DB/파일 삭제 전 보류한다.
- 후보 추천 알고리즘, 자동 삭제, 여러 정리 항목의 일괄 삭제를 새로 추가하지 않는다.
- 고아 파일 목록·정리 작업은 추후 자산/보관 모델의 공통 참조 해석을 사용하도록 경계를 유지한다.

## 9. Worker·화면 갱신·종료

- 검증/내보내기/가져오기 등의 큰 파일 작업은 공통 조정자의 큐에서 기본 한 개씩 수행한다.
  기존 worker를 모두 재작성하지 않고 같은 조정자에 등록/해제되게 연결한다.
- 큐에 대기 중인 작업도 취소 가능하다. UI 조회/알림 scheduler는 이 파일 작업 슬롯을 기다리지 않는다.
- 기존 `OperationWorker`/Qt queued signal/`finish_thread` 생명주기 원칙을 재사용한다.
- 진행 창은 NonModal. 겹치는 파일 변경 행동만 비활성화하고 업무 상태/알림 행동은 가능하게 한다.
- 첨부 관측 커밋 후 기존 `AttachmentService.subscribe`로 해당 업무 ID를 알린다.
  주 창/열린 첨부창/검색 화면은 필요한 메타데이터만 재조회한다. 관측 정보 때문에 현재 입력/검색어를 초기화하지 않는다.
  한 작업에서 여러 후보를 확인하면 변경 업무 ID를 합쳐 통지하고, 행마다 전체 목록을 연속 재조회하지 않는다.
- worker는 자체 session을 쓰고 GUI에 immutable DTO를 전달한다. 닫힌 창에는 결과를 적용하지 않는다.
- 선택/화면 전환 중 오래된 stat/verify/알림 조회 결과는 요청 세대 번호로 폐기한다.
- 파일 작업 중 창을 닫으면 취소를 요청하고 준비 파일 정리 후 닫는다.
  저장 완료 파일을 이미 만든 상태라면 결과/복구 정보를 남긴다. QThread 강제 종료는 하지 않는다.
- 앱 종료는 진행 작업을 안전한 구간까지 마무리한다. 예고 없는 프로세스 종료는 저널 복구로 다룬다.

## 10. 이행·백업·2차 연결

- 1차 DB 이행은 첨부 관측 컬럼/인덱스만 추가한다. 실제 파일 이동/변환/삭제는 없다.
- 기존 첨부 ID/최초 정보/순서/해제·누락 상태와 기존 알림 규칙/delivery는 유지한다.
- 업그레이드 전 기존 스키마 백업을 만들고 기존 schema guard를 유지한다.
  구현 검증은 격리한 v3 기존 스키마 DB와 첨부 fixture로 한다.
- 모든 새 관측 정보는 전체 백업의 DB에 포함되며 복원 후 첫 확인까지 `최근 확인`으로 취급한다.
  다른 PC의 파일 수정 시각이 달라졌다고 최초 정보/보관 내용이 손상됐다고 단정하지 않는다.
- 이전 백업 복원 → 스키마 업그레이드 → 첨부 조회/수정/외부 저장의 흐름을 시험한다.
- 새 DB를 구버전 코드로 직접 실행하지 않는다. 이전 버전으로 돌아가려면 해당 버전과
  업그레이드 전 전체 백업을 별도 데이터 루트에 함께 복원한다.
- 2차 자산 원장으로 넘어갈 때 관측 필드/최초 기준을 그대로 이행하고
  파일 참조·캡처·예약·외부 저장·정리 경계를 재사용한다.
- 2차의 frozen 참조는 역할별 열기/기준 검증을 resolver에 추가한다.
  지금부터 공개 UI/서비스가 단순 임의 절대경로에 의존하도록 만들지 않는다.
- 3차는 파일 관측/외부 저장을 사용자 업무 변경 이력으로 기록하지 않는다.

## 11. 구현 파일 지도

기존 경로는 `src/officeflow/` 기준이며, 신규 파일은 목표 경로다.

| 부분 | 기존/신규 작업 대상 |
| --- | --- |
| 알림 실행 읽기 모델·범위 조회 | `application/reminder_preview.py`, `infrastructure/database/reminder_repository.py` |
| 알림 상태 포맷·열린 창 runtime | `presentation/reminder_preview.py`, `reminder_settings.py`, `task_editor.py`, `main_window.py`, `month_calendar.py` |
| 첨부 관측·중복·예약 경계 | `domain/attachment.py`, `application/attachments.py`, `infrastructure/database/attachment_repository.py` |
| 관측 schema | `infrastructure/database/models.py`, 새 migration `versions/0012_attachment_observation.py`(구현 시 head 확인) |
| 파일 참조·외부 저장 명령 | 신규 `application/attachment_export.py` |
| 안정적 읽기·외부 파일 공개·복구 | `infrastructure/attachments/storage.py`, `coordination.py`, 신규 `infrastructure/attachments/export_storage.py` |
| 사용 예약/영구 삭제 연계 | `application/tasks.py`, `infrastructure/database/task_repository.py`, `infrastructure/backup.py`, 앱 조립 위치 `main.py` |
| 내보내기 worker·결과 동선 | 신규 `presentation/attachment_export.py`, 기존 `record_dialog.py`, `data_dialog.py`, `attachment_search_page.py`, `main_window.py` |
| 설정/작업 저널 위치 | `infrastructure/settings/store.py`, `bootstrap/paths.py` |
| 사용량/검색 읽기 모델·문구 | `infrastructure/backup.py`, `database/attachment_search_repository.py`, `application/attachment_search.py`, 관련 화면 |
| 도움말 | `docs/09-user-guide.md`, 내장 도움말 소스(구현 시 검색해 함께 변경) |

모듈 이름은 분리 책임을 고정하기 위한 기준이다. 파일 수를 맞추려고 단순 함수를 불필요하게 쪼개지 않는다.
기존 Excel/ICS `application/exporting.py`와 문서 파일 복사를 하나의 거대한 서비스로 합치지 않는다.
출력 파일의 결과 DTO/복구 경계는 기능 구현과 같은 변경 단위로 제공한다.

## 12. 실패 처리와 수용 기준

| 상황 | 사용자에게 보이는 결과 | 보존 조건 |
| --- | --- | --- |
| 첨부를 정상 편집하고 확인 | `첨부 후 수정됨`, 최신 크기/시각 | 최초 정보·수정된 파일 유지 |
| 최초 해시 없음 | 현재 확인됨, 최초 기준 없음 | 과거 기준을 꾸며 넣지 않음 |
| 검사/복사 중 파일 변경 | 저장 중/다시 시도 | 기존 관측·출처·기존 대상 유지 |
| 잠금/보안/권한 거부 | 해당 파일과 저장/닫기 또는 다른 위치 안내 | 우회/파일 삭제 없음 |
| 공간 부족 | 실패, 일괄 저장은 완료/미처리 구분 | 이전 파일/완료 출력 유지 |
| 같은 이름 여러 파일 | 번호 이름으로 성공 | 기존 폴더 파일 덮어쓰기 없음 |
| 공개 직전에 동명 파일 생성 | 번호 재시도 또는 재확인 | 새로 생긴 파일을 무조건 replace하지 않음 |
| 단일 덮어쓰기 오류/종료 | 복구 완료 또는 확인 필요·위치 안내 | 기존 내용/준비 내용의 안전한 보존 |
| 외부 저장 뒤 관측 DB 갱신 실패 | 저장 완료, 정보 재확인 필요 | 출력 파일을 지우지 않음 |
| 파일 사용 예약 중 영구 삭제 | 사용 중, 잠시 후 다시 시도 | DB 연결/관리 파일이 먼저 사라지지 않음 |
| 열린 창 중 업무 완료 | 실제 완료·알림 중단 표시 | 편집 입력/알림 규칙 초안 보존 |
| 반복 회차 완료 | 이번 회차 완료 표시 | 다른 회차의 알림 계속 유지 |

파일 해시 변경만으로 손상/삭제 필요를 판정하지 않는다.
저장 실패/부분 성공/정보 갱신 실패/정리 실패를 모두 같은 `실패`로 합치지 않는다.

## 13. 구현 후 필수 테스트 계획

### 13.1 자동 테스트

### 13.2 실제 화면·성능 확인

- Python 실행으로 첨부 편집 → 저장 → 외부 사본 저장 → 실제 파일 열어 내용 확인.
- 업무 완료/재알림을 파일 저장·정보 확인 중 처리해 화면 즉시 갱신과 알림 클릭 확인.
- 좁은 기록창/정리창/알림 설정창에서 버튼/이름/시각 잘림, Tab, 스크롤 확인.
- 영향 화면은 시스템 밝은/어두운 환경과 대표 배율 확인. 공통 레이아웃 변경 시 100/150/200% 점검.
  실제 확인하지 못한 환경은 결과에서 분리한다.
- 5,000건 업무 fixture의 목록/검색, 첨부 많은 단일 업무의 빠른 표시/취소,
  1 GiB 이상 파일 복사의 RSS 증가와 worker 종료 후 회수, 다중 저장 취소/재시도를 측정한다.
- 파일 크기에 비례해 메모리가 증가하지 않아야 한다. 작업 큐/진행 신호가 무제한 쌓이지 않아야 한다.
  알림 클릭/상태 변경이 긴 파일 게이트나 UI 동기 I/O를 기다리지 않는지 확인한다.
- 회사 보안 환경의 성공은 실제 회사 PC 확인 전까지 보장하지 않는다. 지원되지 않는 잠금/교체는 안전한 실패로 안내한다.

## 14. 1차 내부 구현 순서와 완료 게이트

1. 알림 runtime/회차 상태 읽기와 표시·건수·열린 초안 보호를 테스트와 함께 수정한다.
2. 관측 schema/domain/repository/verify·중복·사용량 소비자를 정돈한다.
3. 파일 참조/예약/읽기·출력 공개·중단 복구 서비스를 먼저 검증한다.
4. 단일 저장 → 같은 업무 복수 저장 → 검색/정리의 단일 저장 순으로 UI를 연결한다.
5. 전체 회귀/실패/화면/성능 확인과 도움말을 갱신하고 Python 실행 검증물을 사용자에게 전달한다.

위 순서는 1차 안의 구현 단위이며 전체를 다섯 차수로 다시 나누는 뜻이 아니다.
알림 표시 변경은 첨부 schema 없이 먼저 검증할 수 있지만 1차 완료는 위 범위가 함께 작동하는 상태다.

완료 조건:

- 승인된 범위 내 모든 사용자 흐름과 12절 실패 조건이 검증됨.
- 관련 unit/integration/UI 검사, Ruff, mypy 및 기존 회귀 검사 통과.
- 파일 작업 강제 종료/삭제 경쟁/단일 교체 복구에서 자료 보존 확인.
- 이전 데이터/백업과 새 데이터가 함께 동작하고 실제 사용자 데이터는 테스트에 쓰지 않음.
- 가독성/좁은 창/알림 독립성/큰 파일 메모리 실측과 미검증 환경을 기록함.
- 도움말·단계 보고에 구현 범위와 안전한 실패/복구 동선을 반영함.
- 1차 구현물 사용 확인 후 2차 상세설계로 진행. EXE/ZIP/커밋/업로드는 별도 요청 시 수행.

상위 공통 계약을 바꾸거나 범위를 확대해야 한다면 구현 전에 영향과 이유를 기록한다.
현재 추가 사용자 선택은 필요하지 않다. 이미 승인한 용어/동명 처리/보존 정책을 다시 묻지 않는다.

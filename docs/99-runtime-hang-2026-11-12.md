# 2026-11-12 3.0.18 실사용 응답 없음 조사

사용자 요청으로 10분 범위의 읽기 전용 조사를 수행했다. 현재 버전은 실행 폴더의 __version__과 로그에서
3.0.18로 확인했다. 실제 PID18812가 Responding=false이며 PID18700은 venv launcher다.

## 확인된 증거

- 비정지 Python 스택 3회가 일치한다. UI thread22620은 TaskRecordsDialog.event의
  super().event(event)(실제 배포본 record_dialog.py:2016)에서 반환하지 않는다.
- thread28320은 ReminderPreviewController → preview_deliveries → SQLAlchemy fetchall에 동일하게 머문다.
  세 번째 Python thread28796은 Python frame이 없다. OS 상태는 모두 대기이며 CPU도 거의 증가하지 않았다.
- 마지막 자원 표본 15:29:44 KST는 low_memory=false, 가용 물리 메모리 약6GB, 진행 파일 작업0이다.
  메모리 고갈의 직접 증거는 없지만 이 표본만으로 모든 자원 문제를 배제하지 않는다.
- Windows 대기 체인은 UI blocked 상태만 보여주고 소유 잠금/순환은 드러나지 않았다.
  native 스택은 프로세스 suspend OS731 오류로 실패했다. 내부 잠금 소유자/근본 원인은 미확정이다.
- 사용자는 달력에서 업무 작성 후 수정 버튼으로 제목을 바꾼 것 같다고 답했다. 재현된 사실은 아니다.
  소스에서 제목 저장 → _refresh_tasks → 열린 기록창 refresh_header와 알림 조회 갱신이 이어지는 경로를 확인했다.
- event override의 마지막 super 호출 위치이므로, 앞의 첨부/썸네일 예약 코드 자체를 범인으로 확정하지 않는다.
  SQL fetchall 동시 대기도 DB 잠금이 UI를 멈췄다는 증거로 단정하지 않는다.
- 11-10의 달력 setCurrentItem 대기와 관측 지점이 다르다. 기존 종료 교착이나 U40과 같은 원인이라고 단정하지 않는다.
- 별도로 어제 자동 백업 BackupError 로그가 반복돼 있다. 이번 정지와 연관성은 확인하지 않았다.

## 보존과 후속 단서

운영 DB/첨부/설정은 열거나 변경하지 않았고 프로세스를 종료/재시작하거나 코드를 주입하지 않았다.
진단 도구는 개발 폴더에만 잠시 준비했고 수집 후 제거한다. 증거는 artifacts/hang-2026-11-12/에 보존한다.
운영 앱의 해제/복구를 수행한 것은 아니다. 현재 요청은 조사이며 새 코드 수정·테스트·버전/배포/Git 작업은 없다.
다음 검토는 달력에서 업무 작성 → 업무 보기 수정 버튼 → 제목 저장 → 편집창/기록창 이벤트 전환과
알림 미리보기의 동시성으로 범위를 좁힌다. 정확한 이벤트 종류/native 잠금은 별도 증거가 필요하다.
기존 미커밋 U44 보관함 드래그는 보존했다.

## 사용자 종료 후 짧은 격리 재현 (2026-11-12)

사용자가 멈춘 앱을 종료하고 짧은 격리 재현을 요청했다. 15:51 KST부터 10분 이내로 조사했다.
실사용 실행 폴더 대신 dist의 정식 Python 3.0.18 ZIP을 이번 소유 임시 폴더에 추출해 import했다.
OFFICEFLOW_DATA_DIR을 자식 프로세스에 지정하고 AppPaths.root/실제 import 경로/버전을 검사한 뒤
합성 SQLite DB를 초기화했다. 운영 DB·설정·첨부·프로세스에는 접근하지 않았다.

- Windows Qt 창으로 달력의 작성 신호 → 새 업무 저장 → 업무 보기 → 수정 버튼 → 제목 변경/저장 →
  업무 보기 숨김/표시/활성화/닫기를 시험했다. 실제 마우스 좌표 입력이 아니라 신호와 버튼 click 호출이다.
- 알림 미리보기 없는 비교 실행 5회 완료.
- 미리보기 있는 초기 5회와 대기 방식 보완 후 5회도 화면 동작은 완료했으나, 조회 계측이
  repository 인스턴스에만 걸려 read_snapshot이 만드는 새 인스턴스의 호출을 놓쳤다.
  후자의 조회 실행 확인 assertion은 실패했다. 제품 정지나 DB 조회 실패가 아니며, 조회 미실행의 증거도 아니다.
  이 두 실행을 동시 조회 검증 성공으로 세지 않는다. QTest.qWait 대신 processEvents/time.sleep을 사용한
  보완은 시험 동시 실행 기회를 확보하기 위한 것이며 제품 수정이 아니다.
- 계측을 repository 클래스에 적용한 최종 실행은 합성 업무 20건과 알림 발생 이력 10건을 준비했다.
  위 흐름 5회, preview_deliveries 48회가 모두 반환했고 제목 저장/기록창 제목 반영/미저장 본문 보존을 확인했다.
  WindowTitleChange/Show/WindowActivate/WindowDeactivate/Hide 각각 10회 진입·반환을 기록했다.
  정상 종료했다. 근본 원인과 동일한 정지는 재현되지 않았다.
- 총 4개 자식 실행에서 UI 흐름 20회를 시도했으며, 제품 회귀 테스트 20개 통과로 주장하지 않는다.
  각 자식은 45초 faulthandler와 외부 55초 제한을 두었고 제한 종료는 발생하지 않았다.
  마지막 실행의 조회 횟수/소요 시간/환경은 artifacts/hang-2026-11-12/reproduction-summary.json을 따른다.

업무 보기의 현재 event override 자체나 제목 갱신이 항상 멈추는 것은 이번 조건에서 관측되지 않았다.
실사용 데이터 규모·장시간 사용·Excel과의 전환·보안 제품 개입은 재현하지 않았고,
계측 자체가 타이밍에 영향을 줄 수 있다. 따라서 원인 해결 또는 실사용 무재발 증거로 해석하지 않는다.

다음 개선 후보는 상시 대량 로그가 아니라 제한된 최근 이벤트 진입/반환 기록과 GUI heartbeat,
응답 정지 시 별도 감시 측에서 남기는 Python 스택이다. GUI 타이머만으로 정지 스택을 수집하는 구조는 피하고,
로그 상한/개인정보 미포함/정상 종료를 포함해 별도 설계한다. 이는 이번 제품 코드 구현/배포 승인이 아니다.
이번에는 진단 스크립트·작은 JSONL 증거만 보존하고 소유 합성 DB/추출본을 정리한다.

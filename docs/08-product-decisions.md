# 승인할 제품 결정

문서 상태: D1·D2 구현 완료, 나머지 사용자 승인 대기
목적: 구현 전에 행동이 달라질 수 있는 제품 규칙을 명확히 확정한다.

## D1. 빠른 등록의 기본 날짜

상태: Phase 2 적용

권장안: 현재 보고 있는 화면의 문맥을 따른다.

- 오늘 화면: 오늘의 시간 미정 업무
- 특정 날짜 화면: 선택한 날짜의 종일 업무
- 전체 업무 또는 전역 단축키: 일정 없는 업무

이 방식은 입력 횟수를 줄이면서 사용자가 보고 있던 문맥을 보존한다. 등록 직후 적용된 날짜를 토스트 메시지에 표시한다.

## D2. 여러 날 일정의 종료일

상태: Phase 2 적용

권장안: 화면에서 입력하는 종료일을 일정에 포함한다.

`9월 14일~17일`을 입력하면 네 날짜 모두 표시한다. 내부 DB에서는 안정적인 겹침 계산을 위해 18일 00:00을 배타적 종료로 저장한다.

## D3. 종일 일정의 기본 알림

권장안: 기본 알림 없음. 사용자가 알림을 켜면 시작일 오전 9시를 제안한다.

모든 종일 일정에 자동 알림을 넣으면 업무가 많은 날 알림 피로가 커질 수 있다. 제안 시각은 설정에서 변경할 수 있게 한다.

## D4. 놓친 알림 복구

권장안: 앱 시작 또는 절전 복귀 시 최근 2시간 이내의 놓친 알림만 한 번 묶어서 보여준다.

오래된 알림을 연속으로 표시하는 문제를 피하면서 가까운 업무는 놓치지 않게 한다. 유예 시간은 설정 가능하게 한다.

## D5. 삭제와 보관 기간

권장안: 업무 삭제는 30일간 보관함에 유지하고 이후 영구 삭제 후보로 표시한다. 첨부파일은 사용자가 영구 삭제를 승인할 때까지 자동 삭제하지 않는다.

DB 레코드와 실제 파일의 손실 위험이 다르므로 동일한 자동 삭제 정책을 적용하지 않는다.

## D6. 캘린더 드래그 편집

권장안: 최초 출시에서는 클릭 기반 생성·편집을 제공하고, 드래그 이동과 기간 늘리기는 안정화 후 추가한다.

드래그 편집은 편리하지만 월 경계, 반복 일정, 실수 복구와 실행 취소까지 함께 설계해야 한다. 핵심 기간 일정 표시를 먼저 안정화한다.

## D7. 기존 content의 제목 변환

권장안: 첫 번째 비어 있지 않은 줄의 최대 80자를 제목으로 사용하고 전체 원문은 설명에 보존한다.

내용 손실 없이 목록 가독성을 확보한다. 제목이 잘린 경우 마이그레이션 보고서에는 경고가 아니라 정보로 기록한다.

## D8. 기존 deadline 필드

권장안: 실제 사용자 DB의 값 패턴을 읽기 전용으로 분석하기 전에는 `ends_at`으로 자동 매핑하지 않는다.

`target_date`와 의미가 겹치거나 D-Day 표시용일 가능성이 있어 잘못 변환하면 일정 기간이 바뀔 수 있다. 샘플 분석 후 마이그레이션 규칙을 별도 ADR로 확정한다.

## 승인 방식

전체 권장안을 한 번에 승인하거나 특정 결정만 수정할 수 있다. 승인된 결정은 상태를 `Accepted`로 바꾸고 관련 요구사항과 테스트 케이스에 반영한다.

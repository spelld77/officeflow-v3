# 첨부 화면 공간·종류 필터·출처 구현·검증

2026-10-14 후속 요청으로 3.0.11 마감·배포를 진행한다. 최신 결과는 [62번 릴리스 체크리스트](62-release-checklist.md)를 따른다.

작성일: 2026-10-13. 대상: 공개 3.0.10 이후 개발 소스의 U23.
[60번 상세설계](60-attachment-space-and-source-design.md) 후 사용자 `구현 테스트해` 요청으로 반영했다.
상태: 구현·관련 자동 검증·Windows 시각 검증 완료. 사용자 사용 확인·배포는 아직이다.

## 1. 실제 반영

- 첨부 탭 상단을 추가/크기와 종류/보기 방식의 두 줄로 정돈했다. 파일 추가와 클립보드 이미지는 직접 접근한다.
  긴 업무 제목은 첨부 탭에서만 한 줄로 생략하고 전체 이름을 툴팁과 창 제목에 유지한다.
  아래는 한 줄 선택 요약과 열기/저장/보관함/더보기다. 정보·메모를 계속 여러 줄로 펼치지 않는다.
- `전체 파일 / 원본 / 작업본 / 일반`에 종류별 개수를 표시한다. 필터 중 `표시 / 전체`와 `전체 보기`가 나타난다.
  전체 0개와 선택 종류 0개를 구분한다. 새 창은 전체 보기로 시작하며 필터는 설정에 저장하지 않는다.
- 보이는 ID만 명령의 선택으로 쓴다. 필터로 사라진 ID는 저장·삭제·해제·이름/메모·출처 조회에서 제외한다.
  전체로 돌아가도 숨겼던 선택을 몰래 복원하지 않는다. 필터 중 순서 이동을 막고 전체 수동 순서는 그대로 유지한다.
  새 첨부가 생기면 전체 보기로 전환해 위치를 안내하며 새 파일들을 전부 자동 선택하지 않는다.
- 선택한 작업본의 직접 출처를 비동기로 표시한다. 원본/다른 작업본/보관본/중요 시점 파일/수정 보기 사본을 구분한다.
  현재 표시 이름, 생성 당시 이름, 실제 출처 삭제, 조회 실패를 따로 다룬다. 삭제된 출처 때문에 작업본을 삭제하지 않는다.
  보기 사본을 정상 정리한 경우를 출처 파일 삭제로 잘못 표시하지 않는다.
- `파일 정보…`는 별도 비모달 창이다. 같은 정보 창을 재사용하고 파일명·메모·현재/최초 정보·출처를 확인/복사한다.
  목록 선택을 바꿔도 열린 정보의 조회가 끝나며 그 결과가 다른 파일의 요약을 덮지 않는다.
  기존 파일 내용 검사 결과 창은 선택 변경 뒤에도 결과를 유지한다.
- `관련 파일 보기…`는 선택 파일 계열의 현재 첨부로 기존 보관함을 연다. 보관함 기본은 같은 계열의 보관본이다.
  유효한 단일 선택이 없으면 업무 전체 자료로 열고 범위를 명시한다. 계열이 없는 파일의 관련 조회는 비활성화한다.
- `넓게 보기 / 이전 크기`는 같은 업무 보기 창만 조절한다. 선택·스크롤·보기 방식·서비스를 유지하며 전체화면은 아니다.
  닫을 때 폭/높이를 기억하고 목록·달력·검색·알림·업무일지의 업무 보기 생성 경로에 전달한다.
  열린 다른 창을 강제로 바꾸지 않고 좌표·최대화 상태·필터는 저장하지 않는다.
- 작은 작업 영역에서는 창을 화면 안에 맞추고 첨부 본문에 세로 스크롤을 제공한다.
  시스템 다크 팔레트에서도 창/목록/스크롤 본문의 배경과 글자는 기존 공통 밝은 스타일로 표시한다.

## 2. 안전·호환·부하

- DB0016·전체 백업 v3 유지. 새 DB 이행, 첨부 내용/경로/순서/자산 구조 변경은 없다.
  표시를 위해 새 사본을 만들거나 해시를 계산하지 않는다. 기존 보존·외부 저장·삭제 저널·사용 예약을 그대로 쓴다.
- 새 설정 `record_window_width`, `record_window_height`는 nullable int, 200~8192 DIP다.
  잘못된 새 필드만 복구하고 기존 알림/백업 설정은 유지한다. 크기 저장은 최신 설정에 두 필드만 합친다.
  저장 실패는 비차단 안내이며 업무나 첨부 저장 실패로 표시하지 않는다.
- 출처는 한 worker를 재사용해 metadata만 조회한다. 실행 1개 + 최신 목록 대기 1개,
  명시적으로 연 정보 창용 대기 최대 1개다. 종료 시 안전하게 끝날 때까지 기다리고 강제 thread 종료는 하지 않는다.
  업무/ID/revision/generation 토큰으로 오래된 응답을 걸러낸다. 목록용 결과 캐시는 현재 선택 1개다.
- 잘못된 JSON, boolean/실수 ID, 과도한 payload, 타 업무/계열, 비활성 자산은 `출처 확인 불가`로 처리한다.
  읽는 동안 DB를 고치거나 파일 손상으로 단정하지 않는다.
- 사진 캐시 32 MiB/64개·보이는 이미지 요청·기존 썸네일 크기 계약은 그대로다.
  전체 첨부 metadata 조회 범위는 기존 방식이며 이번 필터가 대규모 첨부 페이지화의 대체는 아니다.

## 3. 검증 중 보완

- Windows 기본 렌더링에서 최소 창의 다섯 번째 행 하단이 몇 픽셀 잘렸다.
  기본 글꼴을 줄이거나 테스트를 완화하지 않고 목록 최소 높이와 도구 영역 여백을 조정했다.
- 정보 창 조회 중 목록 선택을 바꾸면 이전 요청이 병합되어 정보가 `출처 확인 중`으로 남았다.
  정보 창의 요청을 별도 고정하고 같은 창을 재사용해 해결했다. 현재 목록으로 늦은 결과가 새어 들어오지 않는다.
- 메모는 상시 선택 요약 대신 파일 툴팁/정보 창에서 확인한다. 기존 테스트도 새 표시 계약을 확인하도록 갱신했다.
  원본에서 바로 보관본 생성/같은 내용 중복 첨부를 금지하는 기존 정책은 그대로이며 테스트 fixture만 그 정책에 맞췄다.

## 5. 테스트 자료와 다음 단계

이번 테스트의 임시 fixture 20개 폴더, 약 484.55 MiB를 정확한 소유권·경로·reparse 부재 확인 후 정리했다.
`.test-tmp`에 남은 임시 폴더는 0개다. 합성 fixture는 테스트로 다시 만들 수 있으며 사용자 자료는 삭제하지 않았다.
1 GiB 스트리밍 fixture를 반복하지 않았고 작은 합성 파일을 사용했다. XML·소형 시각 캡처는 남긴다.
사용자 DB/첨부/로그·기존 다른 작업 폴더·배포물은 정리 대상이 아니다.

사용 확인은 프로젝트 루트의 `run-officeflow-dev.cmd`를 더블클릭한다.
개발용 `.local-data`를 사용하며 기존 설치/Python 배포 실행 폴더는 자동 교체하지 않는다.
먼저 원본 3개+작업본 2개가 있는 업무에서 종류 필터·출처·넓게 보기·다중 저장/삭제 범위를 확인한다.
공개 버전은 계속 3.0.10이다. EXE/설치본/ZIP 재생성·버전 변경·커밋·GitHub는 별도 후속 요청 때 진행한다.

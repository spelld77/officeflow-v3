# 후속 개선 2차 삭제·재시작 복구 기반 구현 보고

날짜: 2026-10-09. 선행: [내부 생성 기반](29-follow-up-phase-2-internal-operations-progress.md).
기준: [공통설계](24-follow-up-common-design.md) 9절과 [2차 상세설계](27-follow-up-phase-2-design.md) 8·11절.
상태: **삭제 실행기 backend와 시작 복구 연결을 구현한 중간 단위**. 2차 전체 완료가 아니다.
기존 첨부/업무 삭제 버튼은 아직 새 실행기로 전환하지 않았다. 생성/보관/보기 cache 메뉴도 아직 미연결이다.
운영 DB·첨부, 버전 3.0.7, EXE/ZIP, Git 커밋·GitHub는 변경하지 않았다.

## 1. 실제 구현한 범위

- `AttachmentDeletionService.plan/execute/recover`: 첨부 항목, 개별 보관본, 휴지통 업무의 삭제 API.
  논리 첨부/보관본 개수, 유지 보관본, 물리 삭제/다른 참조로 유지할 자산, 연결 해제할 업무일지 개수를 반환한다.
  앱 내 사용 예약/중단 보호 범위와 충돌하면 기다리지 않고 거절한다. 외부 파일 잠금은 실행 때 판정한다.
- 확인 지문을 실행 직전과 단일 DB 확정 transaction 안에서 재계산한다.
  이름·메모·순서·역할·해제 상태·휴지통 상태·참조/범위가 바뀌면 기존 확인으로 삭제하지 않는다.
  관측값 갱신만으로 확인을 무효화하지 않는다. 논리 출처 링크는 내용 보존 참조로 계산하지 않는다.
- 업무 영구 삭제는 휴지통에서만 허용한다. 보관본이 있으면 `include_versions`의 별도 범위 확인이 필요하다.
  단일 첨부 삭제는 보관본/독립 작업 파일/원본 지정 때 남긴 이전 편집 파일을 함께 지우지 않는다.
  업무일지는 기존 FK의 SET NULL로 연결만 해제하고 내용은 유지한다.
- 단일 heavy job과 배타적 삭제 의도 예약을 사용한다. 새 읽기/생성/백업 pin은 영향 경로에서 거절한다.
  파일 격리/복구는 파일별 짧은 gate이며 DB 쓰기 transaction 밖이다.
- `DeletionFileStorage`: `.trash/delete-<job>/delete-plan.json`에 명령·지문·정확한 자산/원경로를 기록한다.
  파일마다 `<asset>.state.json`에 identity/준비 상태를 flush/fsync 후 원자적으로 기록하고 격리한다.
  전체 N파일 저널을 N번 다시 쓰지 않는다. 준비·누락 기록과 실제 이동 사이 중단을 복구할 수 있다.
- Windows 독점 읽기/DELETE 핸들로 동일 파일을 확인하고 `ReplaceIfExists=False`인 핸들 이동 API로 격리한다.
  DB 확정 전 격리 파일의 독점 핸들을 자산 ID 순으로 확보하여 커밋까지 유지한다.
  경로 stat 후 핸들을 해제해 다른 파일이 끼어들 수 있는 구간을 만들지 않는다.
  링크/junction/reparse·하드링크·경로 이탈·소유 불명은 실패/보존하며 강제 삭제 fallback은 없다.
- DB 확정은 `논리 연결 제거 + 참조 없는 자산 pending_delete + 부모/자산별 삭제 영수증`을 함께 커밋한다.
  공유 자산은 active/원경로를 유지한다. pending_delete에 새 내용 보존 참조를 연결하는 것은 기존 trigger가 막는다.
  자산별 영수증은 부모 job/asset으로 만든 UUID5 PK와 작은 payload다.
  후처리마다 부모의 전체 N자산 JSON을 다시 파싱하는 비용을 피한다. 부모 영수증은 재시도 결과용으로 유지한다.
- 확정 전 오류/취소는 이미 격리한 파일을 원래 위치로 복구하고 논리 항목을 유지한다.
  원경로에 새 파일이 있으면 덮어쓰지 않고 양쪽을 보존한다. 참조/FK/저널을 확인 못하면 복구도 보류한다.
- 확정 후에는 영수증·현재 참조/상태·정확한 파일 identity를 확인한 동일 독점 핸들로 물리 정리한다.
  실제 bytes가 정리된 자산 행만 제거한다. 실패 시 pending_delete/저널을 남기며 논리 항목을 되만들지 않는다.
- `finished.json`은 파일 복구/삭제 완료 뒤 작은 상태 기록을 지우는 도중 종료에 대응한다.
  모르는 보조 파일/저널 임시 파일은 재귀 삭제하지 않고 확인 대상으로 보존한다.
  마지막 저널 자체가 누락/손상된 폴더는 안전한 완료로 추정하지 않고 보호한다.
- 같은 명령 ID의 재시도는 확정된 결과를 돌려준다. 다른 입력으로 재사용할 수 없고 새로 생긴 동명/동 ID 항목을 지우지 않는다.

## 2. 시작·백업 경계

- 정상 시작은 `.trash`와 `delete-` job 유무를 먼저 확인한다. 전체 자산 경로 set/모든 파일 해시를 만들지 않는다.
  유효 저널의 경로만 보호한다. 시작 preflight에서는 per-file state JSON/실제 출처 파일을 읽지 않는다.
- preflight는 최대 100개 job/선정 예산 2초다. 모르는 형식/손상/overflow는 파일 I/O를 보호하지만
  업무 입력·알림 UI까지 비활성화하지 않는다. 큰 단일 저널 파싱 완료 시간까지 2초를 보장한다는 뜻은 아니다.
- 실제 `build_application`에 새 삭제 preflight를 연결했다. 주 창 구성 뒤 기존 복구 worker에서
  삭제 영수증/참조에 따라 복구·후처리를 하고, 내부 생성 완료 확인과 결과를 합쳐 표시한다.
  종료는 worker 취소/안전 완료 이후 DB engine을 해제하는 기존 계약을 따른다.
- 구형 삭제 복구기는 `delete-` 폴더를 처리하지 않는다. 구형 이름 추측으로 새 격리 파일을 정리하지 않는다.
- recovery 분리 백업이 완성되기 전의 **임시 fail-closed 정책**을 유지한다.
  새 삭제 job 또는 DB의 pending_delete 자산이 남으면 정상 전체 백업 성공을 거절한다.
  저널 폴더가 없어졌다는 이유로 pending_delete를 백업에서 조용히 제외하지 않는다.
  기존 정상 백업을 삭제하거나 이를 성공 백업으로 위장하지 않는다.

## 3. 자동 검증

새 검사 34개: `test_attachment_deletion.py` 33개와 `test_deletion_recovery_startup.py` 1개.

- 현재 파일 삭제/영수증/동일 명령 재실행, 원본 삭제 후 보관본·이전 편집 파일/출처 payload 유지.
- 동일 frozen 자산의 다른 보존 참조로 실제 파일 유지, 마지막 참조 삭제 때만 정리.
- 휴지통 전용 업무 삭제, 보관본 범위 확인 필수, 업무일지 내용 유지/연결 해제.
- 오래된 확인, 격리 이후 새 참조/DB 실패/취소의 원상 복구.
- 여러 파일 중 두 번째 잠금 실패 시 첫 번째도 복구하고 DB 항목 유지.
- 읽기 pin/삭제 의도 충돌, commit_guard 중 실제 Windows 쓰기/경로 삭제 거절.
- 지원하지 않는 추가 asset FK 거절, pending_delete의 새 참조 거절.
- 누락 파일·첨부 없는 업무의 명시적 삭제, 하드링크 거절, 모르는 보조 파일 보존.
- 원경로 충돌 시 두 내용 보존, post-commit purge 실패 시 pending 상태/다음 시작 후처리.
- 파일별 원장 비용, 시작 시 per-file state 조회 없음, preflight overflow 보호.
- 구형 복구의 새 job 무시, job/저널 누락 pending 자산의 전체 백업 성공 거절.
- 파일 작업 중 다른 gate/DB 쓰기가 사용 가능, 실제 앱 시작에서 worker와 입력 독립.

실제 자식 프로세스를 `os._exit(75)`로 종료한 **9지점**을 별도로 검사했다:
저널 기록 / identity 준비 / 파일 이동 / 전체 격리 / DB 커밋 직전 /
DB 커밋 직후 / bytes 정리 / 자산 행 제거 / 파일별 상태 기록 정리.
확정 전에는 원경로·논리 자료를 복구하고, 확정 후에는 영수증에 따른 후처리·재시도 중복 방지를 확인했다.
예외 주입만으로 강제 종료를 대신하지 않았다.

최종 소스 전체 검사: **792 passed, 113.47초**, 제외/skip 없음.
관련 삭제·시작 복구·기존 데이터 보호 묶음은 83개가 통과했다.
전체 검사에는 기존 1 GiB 외부 저장/내부 생성 메모리 검사도 포함한다.
Ruff `src tests` 전체 통과, mypy **94개 소스** 통과, `git diff --check` 통과.
격리 pytest 루트는 `.test-tmp/phase2-deletion-final`이다. 생성 데이터/캡처/측정 스크립트는 Git 제외 경로다.

## 4. 실측·화면 확인

격리된 5,000 업무·50,000 첨부 **메타데이터** fixture로 측정했다. 운영 자료를 읽지 않았다.

| 측정 | 결과 |
| --- | --- |
| 삭제 pending 없는 preflight, 30회 중앙값 | 0.018 ms |
| 단일 첨부 삭제 계획, 7회 중앙값 | 2.672 ms |
| 전체 앱 구성부터 첫 UI event 처리, Windows 100% 단일 실행 | 684.951 ms |

첫 알림 엔진 준비 시간/복구 완료 시간/정리 완료 시간을 이 수치로 대체하지 않는다.
50,000 실제 파일의 전체 삭제 처리량이나 모든 파일 잠금 환경을 측정한 것은 아니다.
파일별 처리량/대량 job backlog 성능은 사용자 메뉴·cursor 연결과 함께 추가 검증해야 한다.

실제 Windows Qt renderer에 dark base/검은 글자 palette를 주입하고
760×560 logical px, 100%에서 기존 복구 상태 표시를 캡처·확인했다. 글자 대비/잘림 문제는 없었다.
새 창/테마/레이아웃은 추가하지 않았다. OS 시스템 테마 전환, 여러 모니터, 150%/200%를 이번 단위에서
다시 실측한 것은 아니며 이전 검사와 구분한다. 기능 UI 검사와 렌더링 확인은 별도로 수행했다.

## 5. 아직 남은 것과 다음 연결 순서

1. 새 삭제 계획/범위 확인과 worker를 기존 첨부·데이터관리·휴지통 버튼에 연결한다.
   현재 `AttachmentService.delete_file`, `TaskService.delete_permanently`와 경로 tuple 후처리는 기존 방식이다.
   이 보고서를 기존 모든 버튼의 안전 삭제 전환 완료로 읽지 않는다. 원본/보관본 생성 메뉴도 계속 미노출이다.
2. 공통 열기·보기 cache 재사용/변경 검사·작업본 보존/버리기/보관함·역할 표시를 완성한다.
3. 미확정 생성/손상 원장·범위 불명의 비차단 확인 UI와 job cursor/backoff/추가 배치 동선을 완성한다.
   현재 복구 worker 한 요청은 최대 20 job이다. 초과분은 보호/대기로 남으며 자동 backlog 완료를 주장하지 않는다.
   overflow 보호의 해제·재점검도 후속 범위다. 구형 무저널 `.trash` 처리는 아직 시작 시 기존 흐름이다.
   확정 후의 대량 파일 후처리/복구를 취소 가능한 작은 배치로 이어가는 작업도 추가로 정돈해야 한다.
   현재 확정 전 취소는 기존 파일 복구를 마무리하며, 확정 후에는 한 job의 안전 후처리를 마무리한다.
4. recovery 분리 전체 백업/복원, cache generation, 사용량/일반 정리와 대량 자료 검증을 완성한다.

2차의 사용자 흐름과 전체 백업/복원이 완결되기 전에는 2차 완료·배포 가능으로 판정하지 않는다.

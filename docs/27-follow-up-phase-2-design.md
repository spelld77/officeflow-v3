이 문서 작성은 운영 DB/첨부 변경, GitHub 업로드, EXE/ZIP 재생성을 포함하지 않는다.

## 1. 범위와 설계 결정

2차는 U5 원본/작업본, U7 개별 보관본, U9 첨부 메모와 이를 지탱하는 자산 원장,
안전한 생성·삭제·복구·보기 캐시·전체 백업/복원을 하나의 완결된 흐름으로 구현한다.
1차의 단일/다중 외부 저장, 실제 내용 관측, 짧은 파일 게이트와 작업 예약을 재사용한다.

| 결정 | 2차 정책 |
| --- | --- |
| 기존 첨부 | 수정 가능한 일반 첨부로 유지. 기존 파일을 이동하거나 자동 원본 지정하지 않음 |
| 원본 지정 | 지금 디스크에 저장된 내용을 독립 고정 파일로 복사. 성공 후 같은 첨부 ID를 원본으로 전환 |
| 이전 편집 파일 | 새 ID의 해제 첨부로 보존. 기존 외부 편집기 저장 경로도 버리지 않음 |
| 작업본 | 일반 첨부·원본·작업본·보관본에서 생성 가능. 새 독립 편집 파일이며 자동으로 열지 않음 |
| 보관본 | 일반 첨부/작업본의 현재 저장 내용을 사용자가 수동 고정. 자유 이름과 선택 메모 |
| 원본/보관본 열기 | 고정 관리 파일이 아니라 검증된 보기용 사본만 연결 프로그램에 전달 |
| 메모 | 파일별 선택 입력. 파일 내용과 업무 결과메모/일지에 영향 없음. 자동 상속/검색은 제외 |
| 외부 저장 | 현재 첨부와 선택 보관본을 함께 저장 가능. 외부 사본은 독립 파일이며 자동으로 열지 않음 |
| 삭제 | 현재/해제 첨부·보관본·진행 작업의 참조를 확인. 내용 보존 참조가 있으면 물리 파일 유지 |
| 임시 사본 정리 | 앱 소유·미수정·미사용을 확인한 항목만 정리. 수정/사용 불명은 보호 |

이 단계에 넣지 않는 것: U1 달력/알림 행 통합, 처리필요 기준 변경, U12~U14 자동 이력/업무 묶음,
문서 편집마다 자동 버전 생성, 원본 보호 해제/덮어쓰기, 여러 업무 사이의 파일 공유,
외부 설명 TXT, 첨부 메모 검색·자동 상속, Git 내장, 클라우드·회사 보안 우회.
원본과 보관본에서 다시 보관본을 복제하는 기능은 추가하지 않는다. 이전 내용부터 작업하려면 작업본을 만든다.

### 1.1 1차 피드백 반영과 공통 계약

사용자가 1차 사용을 확인했고 추가 수정 요청 없이 다음 설계를 승인했다. 외부 저장 방식은 유지한다.
2차에서는 1차의 `FileReference`를 확장해 모든 화면이 동일한 열기·검사·저장 정책을 사용하게 한다.
관측값은 고정값이 아니며, 외부 저장 성공은 내부 삭제 허가가 아니라는 원칙을 유지한다.

공통 계약의 범위/보존 정책 변경은 없다. 캐시 정리의 수치와 사용 종료 판정, 실제 스키마/서비스,
화면 배치, 백업 형식은 이 문서에서 구체화한다. 3차의 테이블은 미리 설치하지 않는다.

## 2. 대표 사용 흐름

1. 서식 첨부 → 오른쪽 메뉴 `원본으로 지정…` → 저장/닫기 안내와 확인 → 원본 배지 표시.
   처음 가져온 때가 아니라 **지정할 때 저장된 내용**을 고정한다.
2. 원본 선택 → `작업본 만들기…` → 이름 확인 → 같은 업무에 새 작업본 생성.
   폴더 선택창은 나오지 않는다. 이후 `열기`로 편집하고 일반 저장한다.
3. 작업본에서 `보관본 만들기…` → `팀장 검토 반영 v2`와 선택 메모 → 고정 보관본 생성.
   기존 작업본은 계속 편집 가능하다. 저장할 때마다 자동 보관본이 생기지는 않는다.
4. `보관본 보기`에서 v2 선택 → `작업본 만들기…` → 새 작업본 B 생성.
   작업본 A와 이후 v3는 바뀌지 않으며, 업무 상태/일정/알림도 되돌아가지 않는다.
5. `파일 함께 저장…` → 원본·작업본·필요한 보관본 선택 → 폴더 선택 한 번 → 외부 독립 사본.
6. 원본을 1시·2시·다음 날 다시 열면 미수정 사본을 재사용한다. 첨부 항목은 늘어나지 않는다.
   정리되어 없으면 다시 만든다. 수정한 보기 사본은 덮어쓰거나 자동 삭제하지 않는다.

## 3. 화면과 입력 상세

### 3.1 기존 첨부 탭

새 사이드바/업무 관리 탭을 추가하지 않는다. 일반 첨부의 기본 동선은 1차와 같다.

```text
첨부 3개 · 보관본 4개                         [파일 선택…]
┌─────────────────────────────────────────────────────────┐
│ [원본]   신청서.hwp                         고정됨       │
│          2026년 개정 서식                               │
│ [작업본] 신청서 - 작성.hwp                  수정됨       │
│          원본: 신청서.hwp · 보관본 4개                   │
│          금액 확인 필요                                │
│          참고자료.xlsx                     내용 미확인  │
└─────────────────────────────────────────────────────────┘
선택 파일의 크기·최근 확인·출처·메모
[열기] [다른 이름으로 저장…] [더보기 ▾]
```

- 일반 첨부는 굳이 `일반` 배지를 매번 붙이지 않는다. 원본/작업본 배지는 글자와 함께 표시한다.
- 메모가 없으면 빈 줄을 만들지 않는다. 목록에는 한 줄 미리보기, 전체 메모는 선택 상세/편집창에서 본다.
- 파일명은 생략 표시와 전체 툴팁을 제공한다. 고정 검증값/실제 경로/출처를 행에 모두 늘어놓지 않는다.
- 원본의 `열기`는 `보기`로 바뀌며 더블클릭도 같은 보기 정책이다.
- 보관본 개수는 업무 전체/선택 문서 계열을 구분한다. 보관본을 첨부 개수나 기존 `첨부 있음`에 더하지 않는다.
  현재 첨부 0개라도 `보관본 N개`를 통해 남은 자료를 조회할 수 있다.
- 기존 수동 순서는 현재 첨부끼리만 유지한다. 보관본은 생성 시각/ID 순이며 이동 버튼 대상이 아니다.
- 목록 새로고침은 첨부/보관본 종류와 ID로 선택을 복원한다. 작업 도중 선택이 바뀌어도 명령 대상은 고정된다.

### 3.2 단일 선택 오른쪽 메뉴

| 행동 | 일반/작업본 | 원본 | 보관본 |
| --- | --- | --- | --- |
| 열기/보기 | 관리 편집 파일 열기 | 보기용 사본 | 보기용 사본 |
| 다른 이름으로 저장… | 현재 저장 내용 | 고정 기준 확인 후 복사 | 고정 기준 확인 후 복사 |
| 작업본 만들기… | 허용 | 허용 | 허용 |
| 원본으로 지정… | 허용 | 제공하지 않음 | 제공하지 않음 |
| 보관본 만들기… | 허용 | 제공하지 않음 | 제공하지 않음 |
| 메모 편집… | 허용 | 허용 | 허용 |
| 보관본 보기… | 같은 계열 | 같은 계열 | 보관함 안에서 조회 |
| 연결 해제/첨부 항목 삭제… | 허용 | 허용, 다른 참조 안내 | 보관본 삭제…로 구분 |

메뉴 순서는 열기/보기 → 외부 저장 → 작업본/보관본/원본 지정 → 메모/보관 조회 → 파일 정보 → 순서 → 해제/삭제다.
복수 선택 메뉴는 외부 저장만 제공한다. 복수 선택이 일괄 내부 삭제/원본 지정 허가가 되지 않는다.
기존 삭제 문구는 `첨부 항목 삭제…`로 구체화하고 확인창에서 실제 삭제/유지 파일 수를 설명한다.

휴지통 업무는 조회·보기·외부 저장만 허용한다. 원본 지정/작업본 생성/보관/메모 수정은 차단한다.
해제 첨부는 정리 화면의 보기·외부 저장·복원·명시적 삭제 정책을 유지한다.
새 업무 자료로 재사용하려면 먼저 해제 첨부를 복원한다. 임시 캐시를 원본으로 지정하지 않는다.

### 3.3 생성·메모 입력창

- 원본 지정: `현재 저장 내용을 고정합니다. 문서를 저장하고 닫아 주세요.`와 이전 편집 파일 보존 안내.
  확인 전에 장시간 파일 핸들/DB 트랜잭션을 잡지 않는다. 같은 ID/이름/순서/메모를 유지한다.
- 작업본: `파일 이름` 한 칸. 제안은 `이름 - 작업본.확장자`, 동명 제안에는 `(2)` 등 번호.
  파일 이름 1~500자, 확장자를 보존하며 경로 구분자/Windows 금지 이름은 거절한다.
  같은 표시 이름 자체는 금지하지 않지만 사용자가 구분할 기본 이름을 제안한다.
- 보관본: `보관 이름`(1~200자)과 선택 `메모`(0~2,000자). 기본 이름은 계열별 `보관본 N`.
  N은 이전 보관 순번을 사용하며 삭제된 번호를 재사용하지 않는다. `v2.0`을 자동 증가하지 않는다.
  같은 이름도 별도 ID/시각으로 구분하고 기존 보관본을 교체하지 않는다.
  입력창을 연 뒤 다른 보관이 먼저 확정되더라도 사용자가 작성한 이름은 바꾸지 않는다. 실제 순번은 별도 값이다.
- 메모 편집: 최대 2,000자, 빈 문자열로 지울 수 있음. 일반/원본/작업본/보관본 각각 독립 저장.
  작업본/보관본 생성의 메모 기본값은 비어 있다. 출처 메모를 몰래 상속하지 않는다.
- 초기에는 기존 첨부나 생성된 보관본의 이름을 바꾸는 별도 기능을 추가하지 않는다.
  보관 이름을 잘못 정했다면 올바른 이름으로 새로 보관하고 필요하면 기존 항목을 명시적으로 삭제한다.
- 새 파일의 최초 정보는 실제 생성 내용으로 기록한다. 기존 첨부의 최초 정보는 원본 지정으로 소급 변경하지 않는다.

작업 결과는 모델리스 창/인라인 상태로 표시한다. 실패 후 입력 이름/메모를 유지하고 재시도한다.
생성 성공 시 새 항목 선택, 원본 지정 시 같은 항목 선택을 유지한다. 문서는 자동으로 열지 않는다.

### 3.4 보관본 조회와 혼합 일괄 저장

`보관본 N개`/`보관본 보기…`는 기존 첨부 탭에 연결된 보관함 창을 연다.
기본 필터는 선택 문서 계열이고 `이 업무 전체`로 바꿀 수 있다. 출처가 삭제된 계열도 전체 조회에서 남는다.
최신 50개씩 조회하며 보관 이름·파일명·시각/요일·선택 메모를 보여준다.
`보기 / 다른 이름으로 저장… / 더보기(작업본 만들기·메모·삭제)`와 Ctrl/Shift 선택을 제공한다.

첨부 탭 더보기의 `파일 함께 저장…`는 **한 업무의** 현재 첨부와 보관본을 고르는 창이다.
종류/계열 필터, 100행 페이지, 현재 페이지 선택/해제, 선택 개수를 제공한다.
페이지 밖 선택은 종류/ID로 유지하고 제출 전에 범위/존재를 다시 검사한다.
`전체 선택`이라고 표시하면서 보이지 않는 수천 항목을 임의 선택하지 않는다.
선택 후 1차 외부 저장 결과창을 재사용한다. 실패/미처리만 재시도하며 완료 파일은 다시 만들지 않는다.

보관본의 외부 기본 이름은 `출처파일명 - 보관이름.확장자`다. Windows 안전 이름 변환과 길이 제한,
동명 자동 번호를 1차 서비스에 위임한다. 목록의 보관 이름/원래 파일명은 변환 결과로 덮어쓰지 않는다.
폴더 선택/마지막 저장 폴더 기억은 외부 저장에만 적용한다. 내부 작업본 생성에 폴더 선택을 넣지 않는다.

### 3.5 다른 화면·테마·키보드

- 달력/오늘/업무일지는 기존 첨부/기록 동선으로 새 정책을 이용한다. 별도 파일 복사 코드를 만들지 않는다.
- 첨부 검색은 현재 첨부 검색 범위를 유지하고 원본/작업본 역할을 표시한다. 보관본/메모 검색은 추가하지 않는다.
  검색 결과 원본 열기 역시 직접 관리 경로가 아니라 보기용 사본이다.
- 데이터관리 정리에서는 해제 첨부, 미분류 파일, 미완료 내부 작업, 보기 임시 파일을 혼합하지 않는다.
  고정 자산을 기존 고아 파일로 오판하는 경로를 없앤다.
- `첨부 저장 폴더 열기`는 고정 파일을 편집용으로 찾도록 유도하지 않게 일반 편집 영역 안내로 바꾼다.
  원본/보관본의 직접 탐색기 선택 기능은 제공하지 않는다. 관리 경로를 숨기는 것이 OS 접근 통제는 아니다.
- 기존 밝은 테마를 창·본문·viewport·메뉴·입력 팝업·선택/비활성 상태에 명시적으로 적용한다.
  600×450 logical px의 좁은 창은 스크롤/가변 레이아웃으로 핵심 버튼에 접근 가능해야 한다.
- 생성 입력의 Tab은 이름 → 선택 메모 → 생성 → 취소다. 일반 업무 등록의 Tab 흐름은 바꾸지 않는다.
  파일 작업/보기 안내는 전체 주 창이나 알림 팝업을 막는 ApplicationModal 창으로 만들지 않는다.

## 4. 실제 데이터 모델

하나의 Alembic revision `0013_attachment_assets`를 계획한다.
선행 revision은 `0012_attachment_observation`이다. 이 문서에서 migration 파일을 생성/실행하지 않는다.
실제 파일 경로의 권위는 `file_assets` 한 곳으로 옮기며 자산 ID는 UUID hex(32), 업무/첨부/보관본 ID는 기존 정수 규칙이다.

### 4.1 테이블과 핵심 컬럼

| 테이블 | 핵심 컬럼/제약 |
| --- | --- |
| `file_assets` | `id`, `kind` mutable/frozen, `state` active/pending_delete, `relative_path` UNIQUE, `stored_name`, `created_at`, `fixed_size_bytes`, `fixed_checksum`, `frozen_at`, 1차의 관측 6컬럼, `missing_at` |
| `document_families` | `id`, `task_id` FK CASCADE, `created_at`, `next_version_number`(초기 1). 내용 소유자가 아니라 계열 조회용 |
| `attachments` 확장 | 기존 ID/업무/표시명/최초 크기·해시/생성·해제·순서 + `asset_id` FK RESTRICT NOT NULL UNIQUE, `family_id`, `role` general/original/work, `memo`, `metadata_revision`, 선택 출처 ID/당시 출처 payload |
| `attachment_versions` | 정수 ID, 업무/계열 FK, `asset_id` FK RESTRICT, `label`, `suggestion_number`, 당시 `original_name`, 독립 `memo`, `created_at`, `metadata_revision`, 선택 출처 ID/당시 출처 payload |
| `file_operation_receipts` | `job_id` PK, `operation_kind`, `committed_at`, `payload_version`, 완료 항목/자산 ID의 JSON. 사용자 이력 테이블이 아니라 재실행 중복 방지용 |

- `attachments.asset_id`의 UNIQUE는 한 자산에 현재/해제 첨부가 중복 소유권을 갖지 못하게 한다.
  frozen 자산은 추후 묶음 파일 등 **다른 참조 테이블**에서 공유할 수 있다.
- mutable 자산은 일반/작업본 첨부 하나가 소유한다. original 역할과 보관본은 frozen만 참조한다.
  일반/작업본에 frozen을 연결하거나 mutable을 보관본에 연결하는 명령은 거절한다.
- `file_assets`에는 업무 CASCADE를 두지 않는다. 자산 FK는 참조가 남은 물리 삭제를 제한한다.
  역할/자산 kind·state 일치는 명령 트랜잭션과 DB trigger로 함께 방어한다.
- frozen의 fixed 크기/SHA-256/확정 시각은 필수이고 mutable의 fixed 값은 NULL이다.
  경로/kind/fixed 값은 확정 이후 내용 교체 명령으로 수정하지 않는다. 최근 검사 결과만 갱신할 수 있다.
- `metadata_revision`은 이름/메모/역할/자산/해제/순서 등 사용자 메타데이터 변경마다 증가한다.
  빠른 stat/내용 관측 변화는 이 번호를 올리지 않는다. 작업별로 관련 값도 캡처 지문에 포함한다.
- 출처 ID는 해당 첨부/보관본 FK SET NULL이며 당시 출처 payload(version 1)는 이름·ID·역할·계열·시각을 보존한다.
  출처 삭제를 파일 보존 참조 삭제와 혼동하지 않는다. 부모가 없어도 남은 보관본에서 새 작업이 가능하다.
- `memo`는 empty string 기본값. 최초 크기/해시는 첨부 항목의 역사적 기준이며 자산 관측/fixed 값과 구분한다.
  원본 지정으로 같은 첨부 ID를 유지해도 최초 첨부 내용으로 되돌아간 것처럼 표시하지 않는다.
- 계열 FK와 업무 ID의 일치는 트랜잭션/trigger로 검사한다. 다른 업무 자료를 동일 계열에 연결하지 않는다.
  출처 컬럼은 `source_attachment_id`/`source_version_id`이며 둘을 동시에 설정하지 않는다.

### 4.2 인덱스·조회·3차 경계

자산 경로 UNIQUE, 첨부 자산 UNIQUE, 첨부 `(task_id, detached_at, sort_order, id)`,
첨부/보관본 `(family_id, created_at, id)`, 보관본 `(task_id, created_at, id)`와 각 자산 FK 인덱스를 둔다.
해시 후보 인덱스는 자산의 최근 관측 SHA-256/fixed SHA-256에 둔다. 목록은 JOIN 메타데이터만 조회한다.
최초 해시로 새 파일을 버리는 방식으로 되돌리지 않는다.

보관본은 업무 공통 자료다. 반복 업무의 한 회차 완료로 삭제하거나 회차마다 복제하지 않는다.
메모/출처/보관본 도입이 회차별 체크리스트나 자동 이력을 미리 구현하는 것은 아니다.
3차의 `snapshot_files.asset_id`가 동일 frozen 원장을 참조할 수 있게 참조 조회 인터페이스를 둔다.
실제 snapshot 테이블/이력은 3차에 추가하며 미지의 테이블을 조용히 무시하고 삭제하는 어댑터는 금지한다.
등록된 참조 조회 제공자와 자산을 가리키는 실제 DB FK 목록이 일치하는지 검사한다.
지원하지 않는 추가 참조가 있으면 삭제/정리/완전 백업은 거절하여 파일을 보존한다.

### 4.3 저장 위치

- 기존 mutable 파일: 지금 상대 경로 그대로.
- 새 작업본: 기존 UUID 분산 경로 `<앞2자>/<다음2자>/<uuid>.<ext>`.
- 새 원본/보관본: `attachments/frozen/<앞2자>/<다음2자>/<asset_uuid>.<ext>`.
- 내부 작업: `attachments/.operations/<job_id>/journal.json`과 준비 파일.
- 삭제 격리: 기존 `.trash`를 유지하고 저널에 자산 ID/작업 ID/정확한 경로 추가.
- 보기 사본: `data-root/cache/attachment-views/<generation>/<cache_id>/표시파일명`.
  중앙 자산 원장/일반 고아 파일 범위와 분리한다. 파일당 별도 원자적 cache JSON을 사용한다.

표시 이름을 내부 경로로 사용하지 않는다. 전체 경로와 파일 identity를 확인하고 reparse/junction/symlink,
하드링크·경로 이탈·관리 영역 혼동을 거절한다. frozen/작업본을 하드링크로 연결하지 않는다.

Application에 파일 캡처·자산 참조·DB 명령의 Protocol을 둔다. Windows API/JSON/SQL 구현은 Infrastructure다.
서비스의 반환값은 immutable DTO이며 ORM 객체나 열린 session을 GUI에 보내지 않는다.
heavy job 자리는 가장 바깥의 명령/백업 조정자가 한 번만 확보한다. 내부 캡처·검증 서비스가 같은
Semaphore를 다시 확보하여 교착시키지 않는다. 읽기 pin과 배타적 삭제 의도 예약을 구분하며 서로 충돌하면 대기 대신 안내한다.
`FileReference`의 보관본 ID와 cache ID는 종류별로 검증한다. 임의 관리 경로를 frozen 열기 우회 수단으로 받지 않는다.
고아 해석은 자산/참조/미확정 작업까지 확인해야 하며, `attachments` 한 테이블의 등록 여부만 검사해서는 안 된다.

기존 `path_for_open`은 frozen 관리 경로를 반환할 수 없게 바꾼다. 모든 호출자를 공통 worker 기반
`prepare_open(reference)`으로 이행하며 editable은 지금 파일, frozen은 검증된 cache 경로를 반환한다.
기존 `unlink` 반환 경로/성공 메시지도 고정 경로를 편집용으로 노출하지 않도록 수정한다.
원본 내용 불일치를 1차의 일반 `첨부 후 수정됨` 관측 업데이트로 승인/기준 교체하지 않는다.
지연된 관측 결과 적용은 현재 asset ID/kind와 최근 검사 토큰을 조건부 비교한다.
원본 전환 전 일반 파일의 결과가 새 frozen 자산에 쓰이거나 새 고정 기준을 바꾸지 않도록 회귀 검사한다.

### 5.1 명령 API와 트랜잭션 경계

계획 API의 핵심 입력/결과는 다음과 같다. 정확한 Python 구현은 이 계약에 맞춰 다음 단계에서 추가한다.

- `designate_original(attachment_id, expected_revision, job_id, cancel_requested)` → 기존 원본 첨부/보존한 해제 ID/새 asset ID.
- `create_work_copy(source: FileReference, filename, job_id, cancel_requested)` → 새 Attachment.
- `create_version(source: FileReference, label, memo, job_id, cancel_requested)` → 새 AttachmentVersion.
- `update_memo(reference, memo, expected_revision)` → 같은 종류의 최신 메타데이터. 파일 캡처/복사 없음.
- `versions_page(task_id, family_id, cursor, limit=50)` → 요약 페이지. 상세 메모/출처는 선택 시 지연 조회.
- `prepare_open(reference, cancel_requested)` → 경로·editable/view_copy 구분·사용 토큰·안내 DTO.
- `plan_delete(target)` / `execute_delete(plan_fingerprint, job_id)` → 삭제/유지/후처리 상태 DTO.
- `files_for_backup(db_snapshot)` → 참조 자산/복구 자료의 배치 조회. live DB와 스냅샷 목록을 혼합하지 않음.

사용자 메타데이터 명령은 expected_revision의 CAS를 사용한다. 파일 명령은 서버 조회로 만든 출처 지문도 최종 비교한다.
Infrastructure에 명령 확정용 unit-of-work를 두어 자산·첨부·계열 순번·보관본·영수증을 한 session/transaction에서 저장한다.
기존 repository의 각각 별도 `transaction()`을 여는 메서드를 연달아 호출하고 전체 원자성을 주장하지 않는다.
입력 확인/파일 준비는 밖에서 하고, `finalize_create`/`finalize_delete` 같은 단일 확정 진입점만 DB 쓰기를 가진다.

## 6. 파일 생성·DB 확정·취소

### 6.1 공통 프로토콜

1. 짧은 조회로 출처/계열/업무 상태/메타데이터 revision과 요청 입력을 확인하고 작업 ID를 발급한다.
   작업 ID별 선택 지문을 기록한다. 같은 ID의 요청 입력이 다르면 재시도 아닌 오류다.
2. 단일 heavy job 자리를 취소 가능하게 기다린다. 출처 자산 pin과 보호 읽기 핸들을 확보한다.
   DB 쓰기 트랜잭션/전역 파일 게이트를 잡은 채 대기·해시·복사하지 않는다.
3. 검증된 저널에 새 자산 ID, 정확한 준비/공개 경로, 출처 지문을 atomic JSON/flush로 기록한다.
4. 1 MiB 스트리밍으로 준비 파일 생성·SHA-256·flush/fsync·독립 재검증을 수행한다.
   frozen 출처는 이 읽기 결과가 fixed 기준과 같아야 한다. 미저장 문서 내용은 캡처할 수 없다.
5. 짧은 `파일 게이트 → DB transaction` 순서로 출처/소유/업무 휴지통/캡처 지문을 재확인한다.
   새 경로는 기존 파일을 덮어쓰지 않고 공개한다. 충돌은 실패로 보존하며 다른 파일을 교체하지 않는다.
6. 자산·첨부/보관본·계열 순번·원본 전환·영수증을 같은 트랜잭션에서 확정한다.
   source pin과 보호 읽기 핸들은 이 확정까지 유지한다. 오래된 화면 초안으로 다른 값을 덮어쓰지 않는다.
7. DB 커밋 후 성공/갱신을 통지하고 저널을 정리한다. finally에서 핸들·pin·job slot을 해제한다.

캡처 지문에는 관련 역할/자산/계열/표시명/순서/메모/해제 상태와 task.deleted_at를 넣는다.
task.updated_at나 파일의 수정 시각만으로 동일 상태라고 판단하지 않는다.
다른 업무의 알림 확인, 무관한 제목 편집, 최근 관측 결과만으로 이 명령을 실패시키지 않는다.
취소는 확정 직전까지 허용한다. 확정 구간에 진입한 취소는 커밋 결과를 확인하여 이미 완료면 완료로 알린다.

### 6.2 원본 지정의 특수 트랜잭션

- 같은 첨부 ID가 새 frozen 자산을 참조하고 role=original이 된다. 이름/메모/순서/계열은 유지한다.
- 이전 mutable 자산을 참조하는 **새 해제 첨부 행**을 함께 생성한다.
  최초/관측 정보와 기존 general/work 역할·계열·출처를 보존하고 전환 시각에 detached 처리한다.
  UNIQUE 소유권을 위반하지 않게 기존 연결 변경 후 새 해제 행을 생성한다.
- 이전 파일을 자동 삭제하지 않는다. 외부 편집기가 예전 경로로 나중에 저장해도 새 원본은 바뀌지 않는다.
- 전환 도중 source 상태가 바뀌거나 DB가 실패하면 원래 첨부/편집 파일은 그대로다.
  공개된 새 frozen은 성공 원본으로 표시하지 않고 복구 대상으로 남긴다.

### 6.3 작업본/보관본과 중복 판별

작업본 생성은 명시적 복제이므로 일반 가져오기 중복 규칙으로 거절하지 않는다.
같은 계열에 새 첨부 ID·독립 mutable 자산을 생성하고 현재 첨부 순서의 끝에 추가한다.
출처의 메모는 상속하지 않는다. 출처 ID/당시 이름으로 관계만 표시한다.

보관본은 새 frozen 파일/새 보관 ID로 만든다. 일반/작업본의 역할·파일 경로를 바꾸지 않는다.
명시적으로 같은 내용/이름을 다시 보관해도 이전 보관본을 덮어쓰거나 자동 삭제하지 않는다.
계열 보관 순번은 확정 트랜잭션에서만 증가한다. 실패/취소가 번호를 소비하지 않는다.
같은 작업 ID 재시도는 이미 확정된 항목을 반환한다. 사용자가 새 보관을 요청하면 새 작업 ID다.

일반 파일 추가의 현재 내용 기반 중복 검사에는 현재 frozen 원본도 후보로 포함할 수 있다.
그 기준 검증이 실패하면 같은 파일이라고 단정하여 새 파일을 버리지 않는다.
보관본·해제 파일만 같다는 이유로 일반 첨부 등록을 막지 않는다. 기존 중복 정책의 범위를 명시적으로 유지한다.

## 7. 고정 파일 검증과 보기용 캐시

### 7.1 고정 기준과 열기

원본/보관본의 보기·외부 저장·작업본 생성·백업은 읽은 실제 크기/SHA-256을 fixed 기준과 비교한다.
`고정 내용 확인됨 / 보관 후 변경됨 / 누락 / 확인 불가 / 확인 중`을 일반 편집 파일 상태와 구분한다.
불일치한 파일은 보존하지만 정상 원본/보관본으로 열거나 내보내지 않는다. 기준 해시를 실제 값으로 덮어쓰지 않는다.
무결성 이상일 때는 검증된 백업/외부 사본 확인을 안내한다. 자동 원본 교체/손상 복구를 약속하지 않는다.

보기 요청은 source pin → 안정적 source 검증 → 등록 cache 확인/준비 → 검증된 cache 경로 반환 순서다.
목록을 여는 것만으로 모든 원본/보관본을 해시하지 않는다. 현재 요청한 파일을 worker에서 처리한다.
외부 프로그램의 실행 성공 여부는 GUI에서 받고, 실행 전에 cache 사용 토큰을 기록한다.
cache의 실제 표시 파일 이름은 1차의 안전 이름/길이 제한 함수를 사용한다. 전체 이름은 UI/원장에 남긴다.

cache JSON에는 형식 버전, cache ID, 데이터 generation, source asset ID/fixed 기준,
실제 cache 상대 경로/파일 identity/생성 SHA-256·크기, 생성·최근 열람 시각,
사용 토큰과 상태, 사용 종료 확인 시각을 둔다. 출처가 없어져도 수정 cache의 외부 저장은 가능해야 한다.
JSON/경로가 불명확하면 앱 소유로 추정하여 지우지 않는다. 이 원장은 보안 인증서나 악의적 변조 방지 수단은 아니다.

### 7.2 재사용과 수정 발견

- 미수정 cache가 있으면 source fixed 기준과 cache 생성 기준을 모두 검증한 뒤 같은 사본을 재사용한다.
  파일 이름/표시명만으로 재사용하지 않는다. 재열람은 첨부/작업본 항목을 추가하지 않는다.
- 삭제된/누락된 cache는 원본 검증 후 다시 만든다. 고정 source가 불일치하면 과거 cache가 있어도 정상 열람 성공으로 처리하지 않는다.
- cache가 수정되었으면 `보기용 사본에 수정 내용이 있습니다. 원본에는 반영되지 않습니다.`로 보호 표시한다.
  `수정 사본 저장…`과 필요시 저장 후 `파일 선택`으로 다시 첨부하는 동선을 안내한다.
  외부 저장만으로 내부 작업본을 자동 등록하거나 원본을 갱신하지 않는다.
- 수정된 사본을 원본 내용으로 덮어쓰지 않는다. 다시 원본을 보려면 별도 cache를 생성할 수 있으나
  아래 상한/보호 규칙을 따른다. 잠금/미확인 cache도 새 파일로 계속 밀어내며 쌓지 않는다.
- 정상 재사용 가능 cache는 자산당 1개다. 이전 수정/미확인 사본은 보호 항목으로 별도 유지한다.
  같은 자산에 보호 사본 2개가 있으면 세 번째 생성 대신 저장/사용 종료 확인을 안내한다.
  기존 자료는 지우지 않으며 외부 저장/정식 작업본 생성 같은 명시적 대안은 계속 제공한다.

### 7.3 미사용 판정: 잠금이 없다는 것만으로 충분하지 않음

파일 핸들 공유 규칙은 핸들이 열린 동안의 쓰기/삭제 충돌을 막는다. 문서의 모든 사용 상태를 보여주는 것은 아니다.
특히 외부 프로그램 실행 요청이 성공했다는 사실이나 잠금 검사 성공만으로 문서 종료를 확정하지 않는다.
근거: [CreateFileW 공유 모드](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew).
개별 편집기의 동작을 추측하여 안전하다고 판정하지 않는 것은 이 설계의 보수적인 정책이다.

2차의 일반 연결 프로그램 실행에서는 개별 문서 종료를 확실하게 추적하지 않는다.
따라서 다음 상태를 사용한다.

| 상태 | 재사용 | 자동 정리 |
| --- | --- | --- |
| 아직 열지 않음/열기 실패, 내용 정상 | 검증 후 가능 | 기간/상한 조건과 독점 검증 통과 시 가능 |
| 열기 요청 후 종료 미확인 | 내용 검증이 되면 가능 | 불가. 앱 재시작/시간 경과만으로 해제하지 않음 |
| 사용자가 문서 닫음을 확인, 내용 정상 | 다시 열면 사용 중으로 전환 | 독점 검증 후 가능 |
| 수정됨/출처 불명/검사 실패 | 정상 미수정 사본으로 재사용하지 않음 | 불가. 명시적 저장/정리만 |

`데이터 → 첨부 정리 → 더보기 → 보기 임시 파일 관리…`에서 선택 사본의
`문서를 닫았습니다`를 확인하고 미수정 항목을 정리 대상으로 돌릴 수 있게 한다.
매번 열 때 확인창을 강제하지 않는다. 오래된/상한 초과 항목이 있을 때만 관리 상태를 알린다.
수정된 사본은 이 확인만으로 자동 삭제하지 않으며 `외부 저장` 또는 별도 `수정 사본 삭제…` 확인이 필요하다.
외부 저장 성공도 삭제 허가가 아니다. 이 방식은 완전 무인 정리보다 보존을 우선한다.
추후 문서별 종료를 확실히 추적할 수 있는 연결 프로그램 지원이 생기면 판정기를 추가하되
현재의 불확실한 항목을 모두 사용 종료로 소급 처리하지 않는다.

### 7.4 정리 시점·상한·경쟁 보호

- 유효기간: **마지막 열람 후 7일**. 초기 크기 기준: **일반 cache 512 MiB**, 개수 기준: **100개**.
  둘 중 하나를 넘으면 사용 종료가 확인된 미수정 항목부터 오래된 순으로 정리한다.
- 한 번 요청한 큰 파일 하나가 512 MiB를 넘으면 필요한 보기 사본 1개를 허용하고 초과 상태를 알린다.
  상한은 보호 사본 강제 삭제 기준이 아니며 수정/사용 불명 파일을 포함한 실제 용량도 따로 보여준다.
- 스키마 준비/내부 복구 후 시작 검사, 새 cache 생성 전, 실행 중 30분 간격으로 후보 검사를 예약한다.
  종료 시 전체 파일 정리는 하지 않는다. 알림이 파일 검사 때문에 기다리지 않게 한다.
- 한 번에 최대 20개 후보를 고르며 후보 선정/메타데이터 검사 예산은 2초다.
  선택한 파일의 전체 해시는 worker에서 완료까지 수행한다. 2초마다 해시를 처음부터 취소하여 큰 파일이 영원히
  검증되지 않는 구조로 만들지 않는다. 사용자의 파일 명령/종료 요청이 오면 취소·보류할 수 있다.
  파일별로 단일 heavy job 자리를 반환하며 다음 후보 실행 전에 사용자 요청을 우선한다.
  자리가 없으면 백그라운드 cache 검사는 보류하며, 미완성 해시를 성공 검증처럼 재사용하지 않는다.
- 앱 내 gate/pin과 사용 토큰을 다시 확인한 후, Windows의 독점 읽기/삭제 권한 핸들로
  **동일 파일을 해시 확인한 채 핸들을 유지하여** 정리한다. 검증 핸들을 닫고 경로만 다시 삭제하는 경쟁을 만들지 않는다.
  핸들 기반 변경 API를 사용하며 오류/보안 거절 시 보존·보류한다. 경로 기반 강제 삭제 fallback은 없다.
- `SetFileInformationByHandle`와 삭제 disposition의 지원/권한 조건은 별도 구현 테스트 대상이다.
  근거: [SetFileInformationByHandle](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-setfileinformationbyhandle),
  [FILE_DISPOSITION_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_disposition_info).
  이는 앱 소유 미수정 cache에만 쓰며 원본/보관본/작업본의 영구 삭제는 8절 절차를 사용한다.
- 등록된 정확한 cache 파일만 대상으로 한다. 편집기가 만든 lock/임시/복구 파일과 모르는 파일은 자동 삭제하지 않는다.
  빈 폴더도 모르는 항목이 있으면 남긴다. cache 관리 전체 폴더를 재귀 삭제하지 않는다.

cache는 정식 백업 대상이 아니다. 수정된 사본은 외부 저장/재첨부가 필요함을 관리창과 백업 안내에 표시한다.
cache 상태/자동 정리 실패가 앱 시작/알림 스케줄러를 중단시켜서는 안 된다.

## 8. 참조 기반 삭제·해제·정리

### 8.1 삭제 계획과 명령

살아 있는 보존 참조는 현재/해제 첨부와 보관본이다. 휴지통 업무도 포함한다.
3차에서 묶음 파일 참조가 추가되면 동일 조회/계획에 합친다. 출처 추적 링크와 cache는 자산 내용 보존 참조가 아니다.
source pin/진행 작업/백업 pin은 삭제를 막는다. 사용 중이면 UI를 기다리게 하지 않고 재시도를 안내한다.

삭제 계획은 논리 항목·보관본·삭제 가능 자산·참조로 유지할 자산·사용 중/불명 항목·업무일지 영향 개수를 제공한다.
사용자 확인 후 최종 gate/transaction 안에서 지문과 참조를 재계산한다. 바뀌었으면 다시 확인받는다.

- 첨부 해제: 첨부 행과 자산을 남긴다. 메모/역할/계열도 유지하며 정리 화면에서 복원 가능하다.
- 첨부 항목 삭제: 해당 첨부만 삭제. 보관본은 별도 보관 자료이므로 같이 지우지 않는다.
  `작업본 1개 삭제 / 보관본 4개 유지`처럼 명시한다. source ID는 비우되 당시 출처 정보는 남긴다.
- 보관본 삭제: 선택 보관본만 삭제. 그 frozen 자산을 다른 자료가 참조하면 물리 파일 유지.
- 원본 삭제: 원본 항목만 삭제. 작업본/보관본은 독립 파일이라 유지된다.
  원본 지정 때 보존한 이전 편집 파일도 별도의 해제 첨부이며 자동으로 삭제하지 않는다.
- 업무 휴지통 이동/복원: 현재/해제 첨부·보관본·메모·계열 모두 유지한다.
- 업무 영구 삭제: 휴지통에서만 허용. 기본 업무/첨부 확인 외에 보관본까지 삭제한다는 범위를 확인한다.
  보관본을 남기려면 삭제를 취소하고 휴지통 상태로 둔다. 주인 없는 별도 보관함으로 옮기지 않는다.
  현재 업무일지의 연결 해제/보존 규칙과 외부 독립 사본은 바꾸지 않는다.

업무 삭제가 계열/사용자 항목을 CASCADE로 지우더라도 `file_assets`를 CASCADE로 지우지 않는다.
`TaskRepository.delete_permanently`의 기존 경로 tuple 기반 동작을 삭제 계획/영수증 방식으로 바꾼다.
원본/작업본이 모두 삭제된 계열에 보관본이 남으면 보관함 전체 조회와 그곳의 작업본 생성 동선이 계속 동작해야 한다.

### 8.2 격리·DB 확정·후처리

1. 삭제 범위/참조/예약을 gate에서 확인하고 저널에 자산·항목 ID/원경로/격리경로를 기록한다.
   대상에는 배타적인 삭제 의도 예약을 건다. 다른 생성/열기/백업 명령은 이 예약을 확인해 재시도를 안내한다.
2. 삭제 가능한 파일만 앱 소유 격리 위치로 이동한다. 기존 파일 공유/경로 identity/실제 잠금을 검사한다.
   일부 격리가 실패하면 DB 항목을 지우지 않고 이미 격리한 파일을 복구한다. 복구 불가 자료는 보존/경고한다.
   여러 파일의 격리/복구는 짧은 파일별 gate 구간으로 수행한다. 전체 복사/해시/사용자 확인을 gate 안에서 하지 않는다.
3. 짧은 DB 트랜잭션에서 해당 논리 참조 제거, 참조 없는 자산의 state=pending_delete, 삭제 영수증을 함께 확정한다.
   다른 참조가 있는 자산은 active 상태/원경로를 유지한다. pending_delete 자산에는 새 참조를 생성할 수 없다.
4. DB 확정 후 worker에서 격리 파일을 정리한다. 다시 참조/identity를 확인하고 완료된 자산 행만 삭제한다.
   물리 정리 실패는 pending_delete/저널로 남기며 완료 사용자 항목을 다시 만들거나 다른 파일을 지우지 않는다.

DB 확정 전 중단은 남은 참조에 따라 원경로로 복구한다. 같은 경로가 새 내용으로 생겼으면 덮어쓰지 않는다.
DB 확정 후 중단은 영수증과 참조를 확인해 후처리한다. 이전 `.trash` 저널도 전체 자산 목록으로 판정한다.
삭제되지 않은 연결을 경로 목록만 보고 물리 삭제하는 후처리 경로를 남기지 않는다.

### 8.3 고아/미분류 자료

자산 원장에 등록된 파일, 미완료 내부 작업, 격리 자료, cache는 일반 고아 목록에서 제외한다.
active 자산에 참조가 없더라도 단순 고아로 자동 삭제하지 않고 일관성 확인 대상으로 남긴다.
미분류 기존 파일은 기존 내용 확인/외부 저장/명시적 삭제 동선을 유지하되 작업/frozen 영역의
미등록 파일은 일반 파일 삭제로 우회하지 않고 복구 점검 대상으로 분리한다.
완료 날짜·용량·해시가 같다는 이유로 첨부/보관본을 자동 삭제하지 않는다.

## 9. 전체 백업·복원

### 9.1 형식 3과 수집 계약

현재 코드의 백업 형식은 2다. 2차 새 백업은 **format_version=3**으로 한다.
SQLite DB, 설정, 참조된 모든 active 자산, 별도 미분류/격리/미완료 복구 자료를 구분해 담는다.
manifest의 파일 항목은 상대 경로·실제 크기/SHA-256·category(asset/recovery)·선택 asset ID를 가진다.
`attachments` 한 테이블의 경로 집합만으로 완전성을 판단하지 않는다.

1. 내부 복구 상태를 확인하고 DB online backup의 짧은 일관된 캡처를 만든다.
   gate에서 해당 DB 스냅샷의 필요한 자산 경로를 예약하고 settings의 짧은 사본을 준비한다.
2. 게이트/DB 쓰기를 풀고 파일별 보호 읽기·독립 복사·해시를 worker에서 수행한다.
   현재처럼 긴 복사 전체를 전역 gate 안에서 실행하는 경로를 이 단계에서 제거한다.
3. frozen은 fixed 기준과 같아야 한다. mutable은 지금 내용으로 복사하며 최초 해시 변화가 실패 이유가 아니다.
4. 스냅샷의 모든 보존 참조, 실제 manifest, FK, 역할/kind, 파일 크기/해시를 검사하고 ZIP을 확정한다.
   모든 pin/파일 핸들은 finally에서 해제한다. 백업 큐 대기와 복사는 취소 가능해야 한다.

필요한 자산의 누락/불일치/잠금/불안정 읽기는 **정상 전체 백업 실패**로 반환한다.
기존 정상 백업은 유지하고 자동 백업 성공 시각/보존 정리를 진행하지 않는다. 앱/알림은 계속 작동한다.
원래 누락 자료를 허용했던 기존 형식 1/2 백업은 복원 시 그 경고를 유지하며 새 완전 백업으로 위장하지 않는다.
불완전 진단 백업을 새로 만드는 별도 기능은 이번에 추가하지 않는다.

pending_delete/미분류/격리 자료는 live 자산으로 위장하지 않고 recovery 목록에 구분해 보존한다.
확실하게 읽을 수 없는 필요한 복구 파일도 조용히 제외하지 않고 실패/확인 필요를 알린다.
cache·외부 사용자 폴더·외부 저장 저널이 가리키는 출력 파일은 포함하지 않는다.
수정 cache가 있으면 정식 자료가 아닌 임시 내용이며 먼저 저장할 필요가 있음을 안내한다.

### 9.2 복원과 새 PC 이동

- 형식 1/2는 legacy 첨부 경로로 검증 후 지원 스키마까지 이행한다. v2.6 import는 복원하지 않는다.
- 형식 3은 자산/참조/역할/계열/메모/보관본/영수증과 frozen fixed 기준을 검증한다.
  archive 중복 경로·경로 이탈·필수 파일 누락·형식/스키마 초과·FK 불일치면 루트 교체 전에 중단한다.
- 별도 준비 위치에서 현재 소스의 migration/전체 검증을 수행한 뒤 기존 복원 트랜잭션으로 교체한다.
  실패하면 기존 DB/첨부/설정을 사용하며 이전 루트 복구 가능성을 유지한다.
- recovery 자료는 별도 `recovery/<restore_id>`로 복원하고 사용자 확인 대상으로 표시한다.
  미완료 작업을 정상 첨부로 연결하거나 백업 속 미확정 명령을 현재 데이터에 자동 재실행하지 않는다.
- 복원 후 cache generation은 새 UUID다. 이전 cache는 외부 편집이 남을 수 있어 자동 삭제하지 않는다.
  관리창에서 이전 자료로 구분하고 수정 사본 저장/사용 종료 확인 동선을 남긴다.
- DB만 옮기면 실제 파일이 따라가지 않는다. 다른 PC 이동은 전체 백업/복원을 안내한다.
  원본·작업본·보관본의 실제 내용과 역할/메모/계열이 함께 복원되는 검사를 완료 조건으로 둔다.

## 10. 기존 DB 이행과 호환

1. 시작 단계에서 지원 가능한 revision과 필요 용량을 확인한다. 새 스키마를 구버전 소스로 여는 것은 기존처럼 차단한다.
2. `pre-attachment-assets-*.db` online 보호 사본을 검증한 뒤 revision 0013을 수행한다.
   자동 migration은 DB 구조/메타데이터만 바꾼다. 파일 전체 복사/이동/해시는 하지 않는다.
3. 기존 현재/해제/휴지통 첨부 각각에 mutable 자산/독립 문서 계열을 연결한다.
   첨부 ID/순서/표시명/최초 크기·해시/해제 시각과 실제 상대 경로를 그대로 유지한다.
   1차의 관측 6컬럼과 missing_at는 같은 값으로 자산에 옮긴다. role=general, memo는 빈 문자열이다.
4. 기존 첨부의 stored_name/relative_path/관측 컬럼은 자산 원장으로 옮기고 첨부에서 제거한다.
   Domain/API의 호환 필드는 JOIN projection으로 반환하며 독립 경로 컬럼을 계속 갱신하지 않는다.
5. SQLite attachments 재구성 시 인덱스/FK와 기존 `attachment_search` FTS5/trigger를 명시적으로 재생성·재검증한다.
   새 테이블/매핑/backfill/재구성은 하나의 원자적 DB migration으로 다룬다.
6. row 수·첨부 ID/이름/순서·자산/계열 매핑·FK·검색 결과를 검사한다. 중단/실패 시 보호 DB를 남기고
   파일은 변경하지 않는다. 부분 이행 상태를 정상 시작으로 인정하지 않는다.

이행 전 경로 중복/자산 소유 불명/잘못된 역할 등 기존 정보가 일관되지 않으면 임의 병합/파일 복사로
교정하지 않고 보호 사본과 문제 식별을 남긴 채 이행을 중단한다. 실제 내용 해시를 과거 기준으로 채우지 않는다.
그 문제를 안전하게 고치는 별도 이행 절차가 필요하면 구현 전 계획을 보완한다.

SQLite/Alembic의 실제 transaction 경계는 fixture와 별도 프로세스 중단으로 확인한다.
명령이 반환했다는 것만으로 migration 원자성을 검증했다고 하지 않는다.
다운그레이드로 보관본을 버리는 migration은 제공하지 않는다. 구버전으로 되돌릴 때는 이전 프로그램과
업그레이드 전 전체 백업을 별도 데이터 루트에 복원한다. DB 보호 사본만으로 이후 첨부 수정까지 복구할 수는 없다.

실제 운영 DB는 구현/자동 테스트에 쓰지 않는다. 사용 확인 전 격리된 기존 스키마 fixture/전체 백업으로 검증한다.

## 11. 재시작 복구·오류·종료

### 11.1 내부 작업 저널

내부 저널은 형식 버전·작업 ID·종류·선택 지문·출처 asset ID·예정 새 ID·정확한 상대 경로·파일 identity·
준비 검증값·단계·DB 영수증 키를 가진다. 출처 원본 내용을 JSON/로그에 넣지 않는다.
저널을 임시 JSON에 써서 flush/fsync 후 교체하고 내용/경로/소유를 검사한다.
1차의 `external-file-operations` 저널은 별도 규칙으로 계속 처리한다. 내부/외부 복구를 섞지 않는다.

| 중단 지점 | 재시작 처리 |
| --- | --- |
| 준비 복사 도중 | 해당 작업의 DB 미확정과 소유를 확인. 완성 여부 불명 파일은 보존/점검 |
| 준비 완료, 공개 전 | 성공 항목을 만들지 않음. 같은 출처가 현재와 같으면 명시적 재시도, 아니면 새 명령 |
| 새 파일 공개 후 DB 미확정 | 원본/작업본 연결은 이전 상태. 새 파일은 참조/영수증 확인 후 복구 대상 표시 |
| DB 커밋 후 통지 전 | 영수증/실제 참조/파일 검증으로 이미 완료를 인식. 동일 작업 중복 생성 금지 |
| 삭제 격리 후 DB 미확정 | 살아 있는 참조를 확인하고 원경로 복구. 경로 충돌이면 보존/점검 |
| 삭제 DB 확정 후 purge 실패 | pending_delete/참조/정확한 격리 경로를 다시 확인한 후 후처리 |
| 저널 손상/경로 이탈/모르는 형식 | 자동 삭제/재실행하지 않음. 자료 보존과 위치/사유 안내 |

스키마와 자산 조회가 준비된 후 내부 복구를 먼저 수행하고, cache/고아 정리를 시작한다.
사용자의 문서 명령을 복구 과정에서 새 작업 ID로 자동 다시 실행하지 않는다.
미확정 공개 파일/소유 불명 자료는 `데이터 → 첨부 정리 → 중단된 내부 작업 확인…`에서 확인한다.
확실한 삭제 후처리와 검증된 준비 파일 정리를 제외한 불확실한 삭제는 사용자의 명시적 판단을 받는다.
복구 판단/정리 실패는 프로그램 시작 실패가 아니라 자료 보호 경고다. DB 자체가 안전하게 열리지 않으면 별도 시작 오류다.

### 11.2 실패 메시지와 종료

- 미저장/공유 잠금: `문서를 저장하고 닫은 뒤 다시 시도해 주세요.` 기존 내용 유지.
- 고정 불일치: `보관 후 내용이 변경되었습니다. 기준을 바꾸지 않았습니다. 백업/사본을 확인해 주세요.`
- DB/메타데이터 충돌: `첨부 정보가 변경되어 확정하지 않았습니다. 새로고침 후 다시 시도해 주세요.`
- 공간/권한/보안 거절: 파일 이름과 작업 단계를 알리고 성공으로 표시하지 않음. 우회 실행 안내 없음.
- 이미 완료된 작업: 새 항목을 만들지 않고 기존 결과로 연결.
- 취소/부분 후처리: 기존 출처/보관 내용은 유지하며 완료 여부와 남은 복구 자료를 구분.

짧은 생성/삭제 확정만 gate를 사용하고 긴 작업은 worker다. 같은 범위 변경은 pin/지문으로 거절하며
다른 업무 입력·알림 확인/완료는 계속 동작한다. 갱신은 기존 초안·체크리스트 입력·알림 설정을 덮어쓰지 않는다.
창 닫기/앱 종료는 취소 요청 후 안전한 worker 마무리를 기다린다. `QThread.terminate`/강제 핸들 종료는 사용하지 않는다.
프로세스가 외부에서 강제 종료되면 종료 전 팝업을 보장할 수 없으며 저널/복구로 대응한다.

## 12. 검증 계획과 완료 조건

아래는 **2차에 실행할 검사**이며 이 문서 작성으로 통과한 것이 아니다.
1차 기준점 재검사(700 통과/1 GiB 1개 제외)는 [1차 보고](26-follow-up-phase-1-results.md)에 별도 기록했다.

### 12.1 도메인·DB·기존 데이터

- 이름/메모 공백·길이·한글·확장자·금지 이름, 역할/kind/state 조합, 잘못된 출처/다른 업무 계열.
- mutable 소유 UNIQUE, frozen 기준 불변, 모든 asset FK RESTRICT, source FK SET NULL과 출처 payload 보존.
- 기존 0012/이전 지원 스키마: 현재/해제/휴지통/이미 수정된 파일/최초 해시 없음/누락/관측 상태.
  ID·이름·순서·경로·현재 bytes·최초 정보·관측값 유지, 일반 첨부로 이행, 메모 기본값.
- SQLite 재구성/검색 trigger·FTS5·외래키, 경로 충돌 이행 거절, 반복 실행, 새/옛 전체 백업 복원 이행.
- migration 중 실제 별도 프로세스 중단 후 재시작, 원자성/원본 파일 불변, 구버전/미래 스키마 차단.

### 12.2 사용 흐름·파일 보호

- 최초 A→외부 편집 B→원본 지정: 원본=B. 최초 기준=A 유지, 이전 mutable=B가 해제 상태로 남음.
- 기존 외부 편집기가 이전 경로에 C를 저장해도 원본=B 유지. 잠금 실패가 일반 복사 fallback으로 통과하지 않음.
- 원본/일반/작업본/보관본에서 새 작업본 생성과 독립 편집. 같아도 명시적 복제 허용, 자동 문서 열기 없음.
- 작업본 A의 v2/v3 보관 후 A 수정, v2→작업본 B 생성: v2/v3/A 유지, 업무 상태/알림 불변.
- 자유 보관 이름/같은 이름/같은 내용, 실패 순번 미소비, 명령 ID 재시도 중복 금지.
- 메모 편집/빈 값/출처 미상속/백업 보존, 원본 내용 수정 없음, 열린 메모창 CAS 충돌과 입력 유지.
- 모든 보기 경로(record/search/data/달력 연결)에서 frozen 관리 경로가 외부 편집기에 전달되지 않음.
- frozen 내용 변경/누락/읽기 거절: 보기·외부 저장·작업본·백업 실패, fixed 기준 유지, 실제 자료 보존.
- 일반 중복 판별, 출처 링크 삭제, 역할/메모/순서 변경 중 캡처 충돌, 알림 처리 중 진행 작업 상태 유지.

### 12.3 캐시

- 1시/2시/재시작 열람에서 미수정 사본 재사용, 삭제 후 재생성, 첨부 개수 변화 없음.
- source 검증 실패 시 정상 cache로 우회하지 않음, cache identity/내용 변경·JSON 손상·경로 이탈.
- 잠금 없음/앱 재시작/7일 경과만으로 종료 미확인 사본을 삭제하지 않음.
- `문서를 닫았습니다` 확인 후에도 실제 잠금/수정/재열람이 있으면 정리하지 않음.
- source 삭제 후 수정 cache 외부 저장, 보호 사본 상한, 큰 단일 파일 상한 예외, 실제 용량/보호 개수 표시.
- timer 후보/20개/2초 예산·취소·Windows handle 기반 삭제 경쟁·API 거절·회사 보안 잠금의 실패 보존.
- 미등록 editor 임시 파일/하드링크/reparsepoint는 재귀 정리하지 않음. restore generation과 이전 cache 보호.

### 12.4 삭제·백업·실제 강제 종료

- 원본/작업본 삭제 후 보관본 조회·새 작업·메모·저장 가능, 원본 지정 이전 해제 파일 별도 유지.
- 해제/복원/휴지통/업무 영구 삭제 범위 재확인, 같은 asset의 다른 참조/사용 예약이 물리 삭제 차단.
  3차 연결을 모사한 별도 FK fixture도 삭제 계획 누락 시 거절되는지 검사.
- 참조 확인 이후 새 참조 생성 경쟁, 부분 격리 실패, DB 실패 복구, 원경로 재생성 충돌, purge 실패 재시작.
- 실제 Windows 자식 프로세스를 복사 중/공개 직후/DB 커밋 전·후/격리 후/삭제 확정 후에 중단하고 재실행.
  기존 출처 불변·정확한 성공/미확정 판정·영수증·중복 없음·다른 자료 삭제 없음 확인.
- 1차 외부 단일/혼합 일괄 저장 회귀, 원본/작업본/보관본 동명·일부 실패·취소·실패만 재시도.
  내부 삭제/복원/백업 이후에도 외부 독립 파일은 그대로.
- 형식 3 전체 백업/새 PC 격리 복원에서 bytes·고정 기준·메모·계열·보관 순번·참조·영수증 일치.
  일부 누락/frozen 불일치/손상 ZIP/잠금/공간/중간 교체 실패, 형식 1/2의 기존 경고 유지.
- 미분류/격리/미확정 자료가 복구 영역으로 남고 자동 정식 등록/명령 재실행되지 않음.

### 12.5 UI·응답·메모리

- 첨부/보관함/혼합 저장/메모/cache관리/복구 창의 밝은 테마, 선택/비활성/메뉴/viewport 대비.
  실제 Windows 렌더러, 100%·150%·200% 배율, 좁은 창/긴 한글 이름·메모·요일·스크롤·핵심 버튼 접근.
- 오른쪽 클릭 선택 유지, Ctrl/Shift·페이지 밖 선택·선택 수, 보관본 50행/혼합 100행 페이지,
  삭제된 출처 계열 조회, 부모창/입력 초안 보존, 모델리스 진행/종료/알림 우선순위 회귀.
- 5,000 업무·50,000 첨부/다량 보관본 metadata fixture: 첫 조회/선택 상세/필터 응답과 페이지별 메모리 실측.
  목록 표시만으로 전체 bytes 해시/모든 보관본 ORM 객체 적재를 하지 않는 것을 검사한다.
- 별도 프로세스 1 GiB 생성/검증/외부 저장/백업 경로를 검사한다. 바이너리 처리만의 peak RSS 증가
  32 MiB 미만을 초기 회귀 목표로 두며 데이터 행 개수 비용과 구분한다. 실제 결과/측정 환경을 보고한다.
- 장시간 큐/취소·재시도/캐시 후보 검사 후 핸들/pin/session/worker 해제, 오류 후 다음 알림·업무 작업 계속 동작.
  UI 스레드 긴 I/O/전역 게이트 장시간 점유를 테스트/실측으로 찾아낸다.

### 12.6 완료 게이트

## 13. 구현 순서와 변경 단위

다음은 **다음 구현 요청 때 수행할 내부 순서**다. 부분 완료를 배포/운영 전환 단계로 해석하지 않는다.

1. 자산/계열/보관/영수증 도메인·revision 0013·기존 첨부 JOIN 어댑터·전체 참조 조회.
   이행/FK/FTS와 기존 일반 첨부 동작의 회귀 검사를 먼저 만든다.
2. 보호 캡처/내부 저널/명령 ID·삭제 계획/격리 복구 및 자산 기반 백업 수집 경계를 구현한다.
   자료 생성 API를 연결하기 전에 기존 자료를 빠뜨리지 않는 백업/정리 기반을 마련한다.
3. 원본 지정·작업본·보관본·메모, 공통 열기와 보기 cache/혼합 저장/보관함 UI를 연결한다.
   원본 관리 경로 직접 열기 호출자를 모두 교체하고 관련 실패/UI 검사를 함께 수행한다.
4. 형식 3 백업/복원·이전 형식·미분류 복구/cache generation·사용량 표시를 완성한다.
   실제 프로세스 중단·대량 자료·전체 회귀·Windows 가독성 검사를 수행하고 결과 문서를 작성한다.
5. 개발 실행으로 사용 확인을 받은 뒤 3차 상세설계에 피드백을 반영한다.
   버전 변경·EXE/ZIP·GitHub 릴리스는 별도 요청 전까지 하지 않는다.

## 14. 설계 점검과 다음 단계

- 승인된 U5/U7/U9와 공통 계약에 맞게 일반 편집 파일과 frozen 파일을 분리했다.

- 보관본의 부모가 삭제되어도 조회/재작업 가능하며 삭제/백업/고아 판정이 같은 참조 원장을 사용한다.

- 메모는 업무 설명/결과메모/일지와 구분하고 이름 자유 입력은 버전 번호 체계를 강요하지 않는다.
- 1차의 외부 저장을 재사용하며 3차 묶음도 같은 frozen 참조를 사용할 수 있게 경계를 준비한다.
- 실제 API/DB 원자성·외부 편집기/회사 보안 동작은 설계만으로 검증 완료라고 하지 않는다.

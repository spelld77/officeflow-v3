# 개발 및 품질 지침

## 1. 개발 방식

기능을 화면 단위가 아니라 완결된 사용자 흐름 단위로 개발한다. 예를 들어 `업무 등록`은 버튼만 만드는 것이 아니라 입력 검증, 도메인 규칙, DB 저장, 목록 갱신과 테스트까지 한 번에 완료한다.

각 기능은 다음 순서를 따른다.

1. 사용자 시나리오와 수용 기준 작성
2. 도메인 규칙과 데이터 변경 검토
3. 실패 테스트 작성
4. 최소 구현
5. 통합 및 UI 테스트
6. 접근성·성능·오류 메시지 확인
7. 문서와 변경 기록 갱신

## 2. 코드 규칙

- Python 코드는 타입 힌트를 기본으로 한다.
- UI 문자열, 색상, 크기를 비즈니스 로직에 넣지 않는다.
- SQL을 View 또는 ViewModel에서 실행하지 않는다.
- 전역 mutable 상태와 숨은 싱글톤을 사용하지 않는다.
- 한 함수가 저장, 파일 복사, 팝업 표시를 동시에 담당하지 않는다.
- 빈 `except`와 `except: pass`를 금지한다.
- 날짜 문자열 비교 대신 명시적인 date/datetime 타입을 사용한다.
- 모든 파일 경로는 `pathlib.Path`로 처리하고 사용자 데이터 루트 기준 상대 경로를 선호한다.
- 데이터 변경에는 명시적인 트랜잭션을 사용한다.

자동 검사 도구는 formatter, linter, type checker, test runner 역할을 분리하고 CI와 로컬에서 같은 명령을 사용한다. 정확한 버전은 프로젝트 부트스트랩 시 lock 파일에 고정한다.

## 3. 테스트 전략

### 단위 테스트

- 기간 유효성 및 날짜 겹침
- 지연·진행 중 계산
- 상태 전이
- 반복 일정 발생과 예외
- 알림 중복 방지 키
- 이미 이전한 데이터의 원본 ID 보존

### 통합 테스트

- repository CRUD와 트랜잭션 롤백
- DB 스키마 업그레이드와 다운그레이드 가능 범위
- 첨부파일 복사 실패 시 DB 롤백
- 백업 생성과 복원
- Excel·ICS 내보내기 결과

### UI 테스트

- 빠른 등록부터 목록 표시까지
- 검색·필터 조합과 초기화
- 기간 일정 등록과 캘린더 표시
- 완료·대기·다시 알림 흐름
- 창 크기와 DPI 변경 시 핵심 컨트롤 접근 가능 여부

### 테마·가독성 공통 기준 (2026-10-08 사용자 합의)

- 현재 밝은 UI를 기본으로 유지한다. 사용자 요청 없이 다크 테마 지원을 새로 추가하지 않는다.
- 새 화면은 처음부터 `presentation/theme.py`의 공통 밝은 스타일을 적용한다.
  Windows의 밝은/어두운 테마와 섞여 글자가 보이지 않는 상태를 방지한다.
- 글자색과 실제 배경색을 함께 확인한다. 일반·선택·비활성·오류 상태도 포함한다.
- 창뿐 아니라 내부 본문·스크롤 viewport·달력·드롭다운·오른쪽 메뉴·연결 팝업의
  스타일 적용 누락을 확인한다. 동일 문제는 가능하면 공통 스타일 또는 공통 생성 방식에서 해결한다.
- 내용에 따라 표시/숨김을 설정하는 자식 영역은 부모를 먼저 지정한 뒤 `setVisible/show`를 실행한다.
  부모 없는 위젯이 초기화 중 별도 창으로 잠깐 표시되지 않는지 창 생성의 Show 이벤트도 확인한다.
- 기존 `tests/ui/test_theme.py`, `tests/ui/test_task_editor_theme.py`의 회귀 검사 방식을 재사용한다.
  색상 검사만으로 잘림이나 실제 렌더링까지 확인했다고 간주하지 않는다.
- 매 변경마다 전체 화면·모든 배율을 반복 검사하지 않는다. 새 화면은 해당 화면과 연결 팝업,
  일반 기능 수정은 영향을 받은 화면을 중심으로 자동 검사 및 실제 화면/캡처를 확인한다.
- 공통 테마·공통 레이아웃 변경 또는 릴리스 때는 대표 화면을 밝은/어두운 시스템 환경과
  100%, 150%, 200% 배율에서 점검한다. 좁은 창에서 접근·가독성·잘림도 확인한다.
- 수행한 검증과 수행하지 못한 환경을 구분해 기록한다. 사용자 확인만을 가독성 검증으로 대신하지 않는다.

### 회귀 테스트 fixture

- 0건, 50건, 5,000건 데이터셋
- 하루 일정, 기간 일정, 시간 미정, 반복 업무
- 월 경계, 연도 경계, 윤년, 일광절약시간 시간대
- 누락 첨부파일과 손상된 설정 파일

## 4. 품질 게이트

기능 완료 조건은 다음과 같다.

- 수용 기준이 자동 테스트 또는 명확한 수동 검증으로 확인되었다.
- 새 코드의 타입 검사와 정적 검사가 통과한다.
- 실패 경로와 사용자 오류 메시지가 구현되었다.
- 데이터 변경이 있으면 마이그레이션과 롤백/복구 전략이 있다.
- UI 변경은 위 테마·가독성 공통 기준에 따라 영향 범위를 점검했다.
  공통 UI 변경 및 릴리스는 대표 화면의 100%, 150%, 200% 배율 검증을 포함한다.
- 관련 설계 문서와 사용자 도움말이 갱신되었다.
- 사용자 데이터나 민감 정보가 로그와 테스트 fixture에 포함되지 않는다.

## 5. Git 작업 규칙

- 기본 브랜치는 항상 실행 가능한 상태를 유지한다.
- 기능별 짧은 브랜치와 작은 커밋을 사용한다.
- 커밋은 `feat`, `fix`, `refactor`, `test`, `docs`, `build` 범주를 사용한다.
- 스키마 변경과 이를 사용하는 코드는 같은 변경 단위에 포함한다.
- 생성된 DB, 로그, 백업, 첨부파일, 빌드 결과는 Git에 포함하지 않는다.
- 릴리스 태그 전 마이그레이션, 새 설치, 기존 설치 업그레이드를 각각 시험한다.

## 6. 보안과 데이터 안전

- 비밀번호와 토큰을 평문 설정 파일이나 DB에 저장하지 않는다.
- 파일 열기는 사용자가 직접 연결한 경로만 대상으로 한다.
- 첨부파일 이름을 경로로 그대로 사용하지 않고 안전한 내부 이름으로 저장한다.
- 실제 삭제 전에는 앱 데이터 루트 내부인지 확인한다.
- 자동 정리 기능은 기본적으로 미리보기와 복구 가능한 이동을 제공한다.
- 백업은 SQLite online backup API 또는 안전한 스냅샷 절차를 사용한다.

## 7. 릴리스 검증

- 깨끗한 Windows 환경에서 설치와 제거
- 이미 이전한 v3 데이터 조회·수정·검색과 기존 백업 복원
- 트레이에서 숨기기와 복원
- 재부팅 후 자동 시작 옵션
- 장시간 실행 후 알림 중복 여부
- 네트워크 드라이브 및 존재하지 않는 첨부 경로 처리
- 백업에서 복원 후 데이터 개수 비교
- 설치 프로그램과 실행 파일의 버전 표시 일치

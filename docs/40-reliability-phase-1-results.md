## 실제 반영

### 백업 상태

- 자동/수동 시도와 최근 성공·실패·취소를 `backup-health.json`에 원자적으로 보존한다.
  실패를 로그에만 남기던 부분을 주 창의 `백업 확인 필요`와 데이터 화면의 상세로 연결했다.
- 확인은 표시만 내리고 최근 실패 기록을 남긴다. 재실패는 다시 안내한다.
  재시도·취소가 미확인 실패를 숨기지 않으며 같은 종류의 성공으로 해소한다.
- 종료된 실행의 진행 중 기록은 완료 미확인이다. 다른 창의 대기 취소가 실행 중인 시도를
  덮어쓰지 않도록 상태 저장의 활성 시도와 heavy-job 소유 구간을 구분했다.
- 기록 파일 읽기/쓰기 실패도 별도 안내한다. 실제 정상 백업을 삭제/실패로 위장하지 않는다.
  공개/검증 성공 뒤 오래된 자동 백업 정리만 실패하면 백업 성공 + 정리 확인 필요다.
- 상태 파일은 복원 백업 대상에서 제외한다. 백업 형식 v3·스키마 0015·보존 정책은 유지한다.

### 자료 검사

- `데이터 → 자료 검사`에서 명시적 시작/취소와 결과 목록을 제공한다.
  현재·해제 첨부/원본/작업본/개별 보관/중요 보관 파일과 휴지통 자료를 포함한다.
- 읽기 전용 SQLite 연결의 100개 keyset 페이지와 시작 ID/rowid/생성 시각 상한을 사용한다.
  공유 자산을 한 번씩 검사하고, 파일 해시 중 DB 연결을 유지하지 않는다.
- Windows 보호 읽기 핸들·기존 경로 검증·파일별 pin·1MiB SHA-256 읽기를 사용한다.
  파일 전후 특성/원장 변경, 누락, 잠금·복구 보호, 고정 기준과 중요 보관 기준을 구분한다.
- 일반 파일의 정상 편집 가능 변경을 frozen 변경과 구분한다. 기준 없음은 손상으로 표시하지 않는다.
- 전체 건수 요약과 상세 최대 500개를 분리한다. 누락·고정 기준 문제가 정상 편집 정보에
  밀려 숨겨지지 않도록 우선 표시한다. 취소는 부분 결과이며 완료 팝업은 만들지 않았다.
- worker 결과는 queued 전달, 진행 신호는 약 100ms 단위로 제한한다.
  검사/창 종료 시 취소 후 native thread join과 핸들/사용 예약 해제를 확인했다.

### 종료 진단

- 앱 실제 진입점에서 주 스레드/일반 Python 스레드 미처리 예외 hook과 native fault 기록을 설치한다.
  Python 예외의 메시지/locals/업무 텍스트가 아니라 종류와 코드 위치만 새 진단 로그에 남긴다.
- GUI의 비차단 `오류 기록 확인`은 다른 일시적 상태 메시지로 없어지지 않는다.
  기존 비정상 종료 안내와 데이터 탭의 `진단 폴더 열기`로 확인 동선을 연결했다.
- native 기록은 빈 정상 실행 기록으로 이전 fault를 밀어내지 않으며 현재+이전 2개를 유지한다.
  embedding/test host의 기존 faulthandler는 교체하지 않는다. 정상 종료에서 소유 핸들/hook을 해제한다.
- 별도 감시 프로세스·자동 재시작·회사 보안 우회·강제 종료 전 메시지 보장은 추가하지 않았다.

## 검증

Windows / Python 3.12.4 / PySide6·Qt 6.11.2, 격리된 pytest 임시 프로필 사용.

| 검사 | 결과 |
| --- | --- |
| 전체 단위·통합 | 676개 통과, 192.91초 |
| 전체 UI | 331개 통과, 182.05초 |
| 마지막 대기 취소 보호 보완 후 관련 단위·통합·UI·기존 성능 | 90개 통과, 24.36초 |
| Ruff | 전체 소스/검사 통과 |
| mypy | 소스 118개 통과 |
| diff 공백 검사 | 통과 |

전체 회귀 1,007개와 마지막 관련 90개는 중복 합산하지 않는다.
마지막 검사는 새 대기 취소 보호 검사, 모든 새 기능 검사, 기존 백업/데이터/주 화면과 성능 5개를 포함한다.

검증한 실패/경계:

- 상태 실패의 재실행 유지, 안내 확인·재실패·성공, 중단/취소, 손상 상태 JSON,
  상태 기록 권한 오류, 정상 공개 후 오래된 백업 정리 실패, 다른 시도의 대기 취소.
- 공유 original/version/snapshot 자산 중복 검사 방지, snapshot-only·해제·휴지통 자료,
  정상 편집·누락·고정 변경·원장 불일치·실제 열린 쓰기 핸들·중단 보호·기준 없음.
- 원장 변경·시작 이후 파일 추가 제외, 경로 탈출 거절, 파일/DB 바이트 불변,
  625개 결과의 페이지/500개 상한, 뒤늦은 심각 문제 우선 표시.
- 5MiB 실제 파일의 1MiB 읽기 단위·중간 취소·pin 해제, 작업 중 GUI 타이머 작동/안전 종료.
- 예외 비공개 값 로그 제외·hook 복원, 격리 자식 프로세스의 실제 `os.abort()` fault 기록과 이전 로그 회전.

## 가독성

Windows 한글/Segoe UI 글꼴을 로드하고 Qt offscreen에서 밝은/어두운 palette × 100/150/200%의
6조합, 각 백업/검사 화면을 500×480 논리 크기로 렌더했다. 검사 본문/목록의 밝은 실제 픽셀을 검사하고
대표 100/200% 어두운 palette 및 200% 밝은 화면 PNG를 직접 확인했다.
캡처: `artifacts/reliability-visual/`(Git 제외).

첫 캡처에서 목록의 dark 배경과 안내 문구 높이 압박을 발견하여 viewport 색과 styled background를
명시하고, 간결한 설명·요약/상세 분리·최소 목록 높이·작은 창의 외부 스크롤로 수정한 뒤 재검사했다.
실제 OS 테마/배율 설정을 변경한 live desktop 검사로 부르지 않는다.

## 미검증/범위 제외

회사 DRM·보안 종료 정책, 실제 HWP/Excel 편집기, 장기간 실행과 모든 강제 종료 원인 확보는 미검증이다.
일반 파일 관측/고정 기준을 자동 갱신하지 않았으며 검사 결과로 자료를 자동 복구/삭제하지 않는다.
검사 결과는 파일별 확인 시점의 상태이며 그 뒤 편집까지 보장하지 않는다.
OS 파일 읽기/DB 잠금 응답이 느리면 취소·종료에도 시간이 걸릴 수 있다.

기존 U16 문서 변경을 보존했다. 운영 `%LOCALAPPDATA%/OfficeFlow`와 `.local-data`를 검사에 사용하지 않았다.
버전 3.0.8·운영 DB/첨부·기존 배포물·Git 커밋·GitHub는 변경하지 않았다.
제외한 보기 사본 추가 백업 안내, 2차 검색/백업 선택 저장, 3차 일정/알림 묶음 UI는 구현하지 않았다.
소스 도움말/지침/후속 목록만 최신 동작과 다음 차수 경계에 맞춰 갱신했다.

다음 게이트: `run-officeflow-dev.cmd`의 개발본에서 데이터 관리의 백업 안내/자료 검사 사용 확인.
이 실행은 개발 프로필 `.local-data`를 사용하며 실행 시 일반 저장/백업 동작이 발생할 수 있다.
사용 확인 뒤 2차 상세설계로 진행하며 커밋/배포는 별도 승인 범위다.

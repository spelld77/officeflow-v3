# 후속 개선 2차 내부 생성·중단 보호 구현 보고

날짜: 2026-10-09. 선행 상태: [첫 구현 단위](28-follow-up-phase-2-progress.md).
기준: [2차 상세설계](27-follow-up-phase-2-design.md) 6·11·13절.
상태: **2차 진행 중, 사용자 메뉴/보기 사본/새 삭제 프로토콜까지의 전체 완료가 아님**.
후속 단위: [삭제·재시작 복구 기반](30-follow-up-phase-2-deletion-progress.md).
이 문서의 검사/남은 목록은 내부 생성 단위를 마쳤을 때의 기록이며 최신 삭제 범위는 후속 보고를 따른다.
운영 DB·첨부와 버전 3.0.7, 배포 EXE/ZIP, Git 커밋/GitHub는 변경하지 않았다.

## 이번 구현

- `AttachmentDocumentService`와 명령 DTO: 원본 지정·독립 작업본·수동 보관본의 내부 생성 API.
  GUI 메뉴에는 아직 노출하지 않는다. 보관본에서 새 작업본도 생성할 수 있다.
- 출처 보호 읽기 + 1 MiB 복사/해시 + flush/fsync + 준비 파일 독립 재검증.
  출처 핸들/사용 예약을 DB 확정까지 유지한다. 복사/해시는 DB 쓰기 transaction이나 전역 gate 밖이다.
- 내부 `.operations/<job_id>/journal.json`: atomic JSON, 정확한 준비/공개 경로·명령 지문·출처/자산 ID·
  단계·파일 identity/검증값. 모르는 형식/경로/추가 파일은 보존한다.
- 준비 파일을 독점 핸들로 검증하고 같은 핸들의 `FileRenameInfo`로 공개한다.
  `ReplaceIfExists=False`이며 충돌 파일을 덮어쓰지 않는다. 핸들은 DB 커밋까지 유지한다.
  공개하지 않은, 완성·소유가 확인된 준비 파일의 실패 정리는 같은 독점 핸들의 삭제 disposition을 사용한다.
  경로 기반 강제 삭제 fallback은 없다. 부분 복사/공개 후 실패/판정 불가는 보존·점검 대상으로 남긴다.
- 출처의 역할/자산/계열/이름/메모/순서/출처 정보/revision/해제·휴지통 상태를 재검사한다.
  자산·첨부/보관본·계열 순번·원본 전환·확정 영수증을 **하나의 DB transaction**으로 저장한다.
  무관한 업무 제목/알림 상태나 최근 파일 관측은 이 캡처 지문에 넣지 않는다.
- 원본 지정은 같은 첨부 ID/표시명/메모/순서/최초 정보를 유지한다. 현재 저장 내용만 새 frozen으로 고정하고,
  이전 mutable 자산의 소유권은 새 해제 첨부 행으로 함께 보존한다. 이전 편집 경로는 지우지 않는다.
- 작업본은 새 독립 mutable 파일/첨부, 보관본은 새 frozen 파일/보관 항목이다.
  이름 중복이나 같은 내용 때문에 명시적 생성 요청을 버리지 않는다. 메모는 몰래 상속하지 않는다.
  보관 순번은 성공 transaction에서만 증가하며 실패가 번호를 소비하지 않는다.
- 동일 명령 ID/동일 입력은 확정 영수증의 기존 결과를 반환한다. 다른 입력은 거절한다.
  생성 결과가 이후 편집/삭제/누락되어도 같은 명령으로 다시 생성하지 않는다. 현재 상태를 별도 경고한다.

## 시작·동시성·백업 보호

- coordinator에 읽기 pin과 충돌하는 배타적 삭제 의도 예약 API, 재시작 후 보호 범위를 추가했다.
  새 삭제 계획/격리/DB pending_delete/영수증 실행기로 기존 삭제를 교체한 것은 **아직 아니다**.
- 시작 preflight는 내부 pending 영역만 확인한다. 아무 pending도 없으면 DB 조회/해시/전체 첨부 경로 적재를 하지 않는다.
  기본 최대 100개·2초의 후보/metadata 예산이며 초과·손상·범위 불명은 파일 I/O를 보수적으로 보호한다.
  보호된 경로의 열기·pin·물리 삭제·일반 고아 정리를 차단한다. 업무 조회/입력·알림 엔진 전체를 막지 않는다.
- 첫 창 구성 뒤 Qt worker가 최대 20개를 확인한다. 실제 영수증·자산/논리 연결·내용 검증이 일치하는
  **이미 완료된 생성 작업**의 정확한 기록만 정리한다. 미확정 명령을 자동 재실행/등록/삭제하지 않는다.
  종료는 worker 취소/안전 마무리 후 DB owner를 해제한다. `QThread.terminate`를 쓰지 않는다.
- 한도 밖 pending/손상 기록/미확정 공개 파일에 대한 cursor 점검·명시적 사용자 복구 UI는 남은 작업이다.
  정상 캐시의 후보 인덱스나 새 삭제 복구 worker를 구현했다고 해석하지 않는다.
- 정상 확정된 새 자산은 기존 형식 3 전체 백업 수집에 포함된다. 실제 생성 자료의 새 PC 격리 복원을 검사했다.
  미확정 내부 자료의 별도 recovery 목록 수집/복원이 완성되기 전의 **임시 안전 게이트**로,
  내부 pending 자료가 있으면 전체 백업을 실패로 반환한다. 이를 조용히 제외해 성공으로 표시하지 않는다.
  기존 정상 백업은 남으며 자동 백업 성공/보존 개수 정리를 진행하지 않는다.

## 검증 결과

- 전체 자동 회귀 **758개 통과**, 103.37초. 제외/건너뜀 없음.
  Ruff 전체 src/tests 통과, mypy 91 source files 통과, `git diff --check` 통과.
- 이후 내부 1 GiB 생성의 peak 상한을 설계 목표인 **32 MiB**로 엄격하게 둔 관련 재검사도 **2개 통과**(6.36초).
  재검사 내부 생성은 1.797초/peak 증가 2,150,400B였다. 아래 첫 실측과 별도 실행이다.
- 실제 Windows 핸들의 공유 잠금, 독점 공개/준비 파일 정리, 하드링크 출처 거절, 대상 충돌 보존.
- 원본 지정 당시 내용/이전 편집 경로 보존, 작업본 독립 편집, 같은 이름의 v2/v3 보관,
  이전 보관본에서 새 작업본, 최초 정보/메모/출처 당시 이름 유지와 명령 중복 방지.
- 이름/메모/순서/해제/휴지통 변경 중 캡처 충돌, DB 영수증 삽입 실패의 전체 DB rollback,
  준비/공개 자료 보존, 미확정 자료의 고아 오판·불완전 백업 성공 방지.
- 실제 별도 프로세스의 `os._exit(74)`로 7개 경계를 중단했다:
  저널 기록 / 복사 중 / 준비 완료 / 공개 직후 저널 갱신 전 / 공개 기록 후 / DB commit 직전 / DB commit 후.
  재시작의 범위 보호·DB 확정 판정·완료 요청 재시도 중복 없음·출처 보존을 확인했다.
  이는 아직 새 삭제 격리/삭제 commit의 실제 프로세스 중단 검사를 대신하지 않는다.
- 실제 생성한 원본/작업본/보관본/이전 해제 파일/메모/계열/출처/영수증의 전체 백업과 새 격리 루트 복원.
- Qt offscreen 회귀: 첫 창 구성 후 worker 실행, 긴 점검 중 업무 입력/GUI timer 응답,
  취소 후 worker 완료 이전 DB owner 해제 방지. 기존 알림/업무 회귀도 전체 검사에 포함했다.
  회사 보안 제품·모든 외부 편집기에서의 장시간 사용/전원 장애는 검증하지 않았다.

### 스트리밍·시작 실측

격리된 자식 프로세스에서 1 GiB 파일을 실제 생성/검증/DB 확정했다.
첫 관련 실행의 결과(디스크 cache 등의 영향을 받는 개발 PC 실측):

| 항목 | 값 |
| --- | --- |
| 내부 보관본 생성·재검증·DB 영수증 | 1.938초 |
| 내부 생성 peak RSS 증가 | 2,138,112B (약 2.0 MiB) |
| 내부 생성 작업 후 RSS 증가 | 462,848B |
| 기존 외부 저장 스트리밍 | 2.984초, peak 증가 2,162,688B |

5,000 업무/50,000 첨부 **metadata** fixture의 정상 pending 없음 preflight는 7회 중앙값 **0.021ms**였다.
실제 문서 50,000개 생성/전체 백업이나 cache 50,000개 정리의 결과는 아니다.
Windows Qt renderer에서 주 창 구성·초기 이벤트까지 100% 839.499ms / 150% 580.733ms / 200% 541.047ms였다.
배율별 한 번 측정이며 다른 실행 조건/디스크 cache가 섞일 수 있다. 배율의 성능 우열/시간 보장으로 해석하지 않는다.
알림 엔진 준비 시간/새 삭제 복구 완료/일반 cache 정리 완료는 아직 별도로 실측하지 않았다.

새 화면은 추가하지 않았다. 좁은 760×560 logical px의 기존 창/새 상태 메시지를
어두운 QPalette + Windows renderer에서 100%·150%·200%로 캡처해 실제 글자 대비와 상태 문구를 확인했다.
OS 자체 테마 전환/다중 모니터 모든 조합은 미검증이다.

## 이어서 할 작업

1. 첨부/보관본/업무 영구 삭제의 계획·지문·범위 확인, 배타 의도 예약·격리·pending_delete·삭제 영수증과 복구 실행기.
   legacy `.trash`와 새 작업의 대상별 worker/후처리·cursor, 미확정 파일의 명시적 복구 확인 동선을 연결한다.
2. 내부 recovery 자료를 분리해 수집/복원하는 전체 백업 계약을 완성하고 임시 백업 차단 게이트를 대체한다.
3. 고정 파일 보기 cache·변경 표시·작업본 보존/버리기와 공통 FileReference를 완성한 다음
   원본/작업본/보관본 메뉴·보관함·혼합 외부 저장 UI를 연결한다. 직접 관리 frozen 파일 열기 우회는 허용하지 않는다.
4. 7일 수명/후보 인덱스·사용 종료 확인·cache generation/상한, 대량/중단/가독성 검사 후 사용자 사용 확인.

내부 생성 API가 있다는 이유로 2차 전체 완료나 실제 운영 전환 단계로 넘어가지 않는다.

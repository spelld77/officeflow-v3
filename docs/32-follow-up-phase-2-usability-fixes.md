# 후속 개선 2차 사용성 오류 수정

날짜: 2026-10-09. [2차 전체 보고](31-follow-up-phase-2-results.md) 이후 사용자 확인에서 발견한 오류의 수정 기록.
버전 3.0.7 유지. 운영 DB·첨부·기존 수정 사본을 변경하거나 자동 삭제하지 않았다.
EXE·설치 파일·ZIP 재생성, Git 커밋/원격 업로드는 하지 않았다. 3차 구현도 시작하지 않았다.

## 1. 발견한 문제와 수정

### 다중 선택 순간 종료

- 실제 Windows Qt renderer의 격리 자료에서 긴 한글 이름을 가진 여러 파일의 선택/해제를 반복했다.
  기존 구현은 이벤트 처리 중 native Qt abort 또는 응답 정지로 재현됐다. Python traceback만으로
  Qt 내부의 정확한 원인을 단정하지 않으며 파일명 길이 자체가 원인이라고 판단하지 않는다.
- 선택 상태 확인을 비활성화한 대조 검사에서는 같은 반복이 정상 종료됐다.
  클릭마다 생성/종료하던 상태 확인 QThread를 창이 소유하는 worker 하나로 재사용하도록 변경했다.
- 선택/보이는 항목 최대 100개만 확인한다. GUI에서 파일 전체를 읽지 않고 취소·세대 검사는 유지한다.
  QSignalBlocker로 행 상태 변경 중 선택 재진입을 막는다. idle/busy 모두 창 종료 전에 취소·합류한다.
- native Windows 검사를 별도 자식 프로세스 자동 테스트로 추가했다.
  다중 선택 80회, 창 재생성, idle 종료, busy 취소 종료를 검사하며 abort가 pytest 부모를 종료하지 않게 한다.

### 수정 사본을 남기고 원본 유지

- 사본 목록의 내용 확인/닫음 확인 후 refresh가 선택을 지웠다. 다음 보존 클릭이 무반응인 원인이었다.
  선택 ID·현재 행·스크롤을 유지하고 첫 진입 때 수정된 사본을 우선 선택한다.
- 이름 입력과 `편집기에서 저장하고 문서를 닫았습니다` 체크를 저장 창으로 모았다.
  체크 전에는 저장을 막고 제출 때 backend의 token·실제 파일 잠금·내용을 다시 검증한다.
- 수정 내용은 독립 작업본으로 저장한다. 원본 bytes는 변경하지 않는다.
  보존 후 원본 재열람은 원본 내용이고 작업은 새 작업본에서 이어간다.
- 첨부 목록의 `수정본 있음`에서 `수정본 저장…`을 바로 제공한다.
  사본이 정리된 자산에도 `none` 결과를 보내 이전 변경 표시가 남지 않게 했다.
  검사 한도로 확인하지 못한 사본은 확인 불가이지 미수정으로 단정하지 않는다.

### 목록 과밀·스크롤·선택 상세

- 긴 파일명과 여러 줄 메모가 있는 600×540 창에서 기존 목록 viewport가 50px까지 줄어드는 것을 재현했다.
- 첨부/보관본/사본은 `종류 | 파일명 | 짧은 상태`의 한 행이다.
  긴 이름은 가운데 생략하여 확장자를 남기고 전체 내용은 tooltip/정보/메모 창에서 본다.
- SHA-256·처음 이름·전체 메모는 별도 읽기 전용 `정보` 창으로 분리했다.
  기본 선택 상세는 최대 두 줄이고 `보관함` 버튼을 하단 한 줄에 합쳤다.
  긴 정책 설명은 안내/tooltip으로 옮겼다. 파일 수·다중 선택 수를 표시한다.
- 목록 최소 높이는 180 logical px이며 밝은 배경/파란 손잡이의 명시적 세로 스크롤을 제공한다.
  행 그리기는 행/viewport 안으로 제한한다.
- 초기 수정 캡처에서 QWidget 최소 높이가 레이아웃 여유를 넘어 목록과 요약이 겹치는 것도 발견했다.
  위쪽 중복 설명/패딩을 줄이고 실제 좌표 비중첩 검사와 좁은 창 캡처로 재확인했다.

## 2. 검증

운영 프로필을 사용하지 않고 ignored `.test-tmp`와 임시 테스트 자료만 사용했다.
아래 수정 전 실패 및 중간 미완료/환경 제한 실행은 통과 결과로 계산하지 않는다.

- 수정 전 회귀 3개가 실패하는 것을 확인했다: 확인 후 선택 해제, 저장 창의 문서 닫음 체크 부재,
  긴 메모/이름에서 목록 높이 부족. 이 항목을 실제 저장 버튼 동작까지 자동 검사한다.
- 별도 native Windows 선택 스트레스 250회 정상 종료. 상태 확인 비활성 대조 40회도 정상 종료.
- 수정 후 사용성·테마·기록 창 관련 검사 26개 통과 / 18.15초.
- 전체 회귀 첫 재검사 841개 통과 / 186.96초.
  화면 추가 보완 뒤 전체 검사에서 반복 업무 공유 안내 2건·빈 목록 안내 1건의 회귀를 발견했다
  (838 통과 / 3 실패). 문구를 복구한 뒤 관련 34개 / 22.70초 및 **최종 전체 841개 / 180.94초** 통과.
- 최종 화면 상태의 별도 native Windows 250회 선택 스트레스도 다시 정상 종료했다.
- Ruff 전체 검사 통과. mypy 101개 소스 파일 오류 없음. 문서 링크·도움말 내부 이동·`git diff --check` 통과.
- 실제 Windows renderer: 기본 밝은 palette 100%, dark Window/Base 및 검은 Text palette 주입 조건의
  100%·150%·200%, 좁은 500×540 창 100%·200%에서 7화면씩 42개 캡처했다.
  첨부 단일/다중 선택, 정보, 사본, 수정본 저장 비활성/활성, 보관함을 포함한다.
  대표 캡처를 직접 확인하고 선택 전후 목록 높이·스크롤 범위·버튼 접근·목록/요약 좌표를 별도로 검사했다.
- 22개 파일 fixture의 단일 선택 목록 viewport: 600×540와 500×540에서 171~172 logical px.
  약 5행이며 창을 높이면 목록도 늘어난다. 다중 선택·정보 창 때문에 긴 메모가 목록을 밀어내지 않는다.
- 캡처/실행기는 `.test-tmp/usability-reviewed-*`와 `.test-tmp/attachment-usability-visual.py`에 있으며 배포 파일이 아니다.
  전체 검사에서만 생성한 대용량 fixture는 확인 후 정리하고 캡처·재현 실행기는 남긴다.

회사 보안/DRM, 실제 한글/Excel 편집기의 잠금·미저장 버퍼, 시스템 테마 live 전환, 장시간 운영 전체를
이번 검사로 검증했다고 하지 않는다. 문서 종료는 추측하지 않고 사용자 확인과 보호된 파일 접근을 함께 사용한다.

## 3. 사용자 재확인

프로그램을 종료한 뒤 저장소의 `run-officeflow-dev.cmd`로 다시 실행한다. 공개 EXE/ZIP에는 아직 이 수정이 없다.

1. 여러 첨부를 Ctrl/Shift로 선택·해제하고 `선택 N개 저장…`을 사용한다.
2. 원본 열기 → 편집기에서 수정/저장/닫기 → 첨부 목록의 `수정본 저장…`을 선택한다.
   이름과 문서 닫음 체크 후 저장한다. 원본은 그대로이고 새 작업본에 변경 내용이 있는지 확인한다.
3. 긴 이름/메모의 첨부를 선택하고 `정보`를 연다. 목록은 한 줄과 스크롤을 유지하는지 확인한다.
   중요한 파일의 영구 삭제나 운영 자료 교체로 시험하지 않는다.

## 4. 추가 사용 확인: 파일 정보 결과·열기 완료 창

2026-10-09. 사용자 추가 확인에서 다음 두 문제를 수정했다. 파일/보존 정책·DB 스키마는 변경하지 않는다.

- `파일 정보 확인` 결과를 목록 아래 요약 QLabel에만 표시해 자동 파일 상태 확인/선택 갱신이 덮어썼다.
  검사 결과와 해당 파일 정보를 별도 읽기 전용 모델리스 창으로 표시한다.
  닫기 전까지 내용을 유지하고 다른 파일 선택/자동 상태 갱신이 결과를 바꾸지 않는다.
  검사 오류도 같은 창에서 유지한다. 사용자가 취소한 검사는 별도 결과 창을 열지 않는다.
- 파일 열기는 공통 FileActionController의 수동 완료 안내를 사용하여 매번 `완료했습니다` 창이 남았다.
  열기에만 `close_on_success`를 사용한다. 연결 프로그램 전달이 성공하고 native worker 종료/합류가
  끝나면 진행 창을 자동으로 닫고 기존 파일 정보/선택 상세를 성공 문구로 덮지 않는다.
  준비 실패·연결 프로그램 실패·경고는 자동으로 닫지 않는다. 다른 저장/삭제 작업의 완료 확인은 유지한다.
- 수정 전 각각 회귀 검사가 실패하는 것을 확인했다: 정보 확인 후 유지되는 정보 창 없음,
  열기 성공 뒤 완료 창 잔존. 수정 후 관련 **114개 / 35.67초** 통과.
  결과/오류 유지, 일반·원본·보관본 열기 3회씩, 실패 안내, 다른 작업 완료/경고,
  확인 취소·부모 종료·알림 상호작용·native Windows 다중 선택 회귀를 포함한다.
- 실제 Windows renderer와 dark Window/Base·검은 Text 주입 조건의 100%·150%·200%에서
  정보 창 유지·열기 성공 20회씩·실행 실패 창 유지를 확인하고 캡처했다.
  외부 편집기 실행은 대체 함수로 검증했으므로 실제 회사 DRM·편집기 동작 검증으로 간주하지 않는다.
  캡처는 ignored `.test-tmp/feedback-visual-*`에 있다.
- Ruff 전체·mypy 101개 소스·`git diff --check` 통과. 이번 추가 수정은 관련 범위 검사이며
  위 841개 전체 검사는 앞선 2차 수정 시점의 결과다. 운영 데이터·배포 파일·Git 커밋/원격 업로드는 변경하지 않았다.

## 5. 추가 사용 확인: 원본 지정 해제·변경 버리기

2026-10-09. 사용자가 요청·승인한 두 항목을 공통/2차 설계 갱신 후 구현했다.
설계와 검증 상세는 [원본 해제·사본 버리기 보완](33-original-release-and-view-discard.md)에 기록한다.

- 원본 해제 메뉴가 없던 문제: 검증한 원본을 독립 일반 파일로 전환한다.
  같은 첨부 ID/이름/메모/순서/기존 관계를 유지하고 이전 고정 내용은 보관함에 남긴다.
- 변경 버리기의 확인창이 닫음 상태를 갱신하지 않던 문제: 선택 사본을 worker에서 먼저 관측하고
  같은 확인창에서 문서 닫음을 확인한다. 별도의 닫음 확인/작업본 생성 후 삭제를 요구하지 않는다.
- 승인 뒤 파일 변경/재열람·잠금·편집기 임시 파일 등 기존 보존 조건은 유지한다.
  내용 변경 시 확인창을 새로 열도록 안내하고 원본/작업본/보관본에는 사본 삭제를 적용하지 않는다.
- 전체 회귀 879개 및 마지막 추가 검사 24개, Windows 밝은/어두운 palette와 3개 배율 확인 완료.
  운영 자료·배포물·커밋/업로드는 별도이며 현재 수정은 개발 소스에서 재시작 후 확인한다.

## 6. 추가 사용 확인: 보관함 페이지·여러 파일 삭제

2026-10-09. [상세설계·검증 결과](34-document-paging-and-multiple-delete.md)를 따른다.

- 한 페이지 보관함에서 불필요한 이전/다음 영역을 숨기고 실제 추가 자료가 있을 때만 페이지 이동을 제공한다.
  첫/마지막 페이지 경계를 막고 삭제로 빈 마지막 페이지가 되면 직전 유효 페이지로 돌아온다.
- 현재 첨부 다중 선택에서 삭제가 비활성화되던 문제, 보관함에서 현재 항목 하나만 삭제하던 문제를 수정했다.
  Ctrl/Shift 선택 전체를 한 번 확인하고 공통 격리/복구 엔진의 한 DB 트랜잭션으로 삭제한다.
  선택 밖의 보관본과 공유 파일 참조를 유지한다. 확정 전 잠금/취소/충돌/DB 실패는 선택 전체를 보존한다.
- 보관함의 외부 저장용 체크는 삭제와 구분한다. 확인창에서 실제 대상 이름·종류와 개수를 표시한다.
  체크된 다른 페이지 파일은 강조 선택 삭제에 자동 포함하지 않는다.
- 기존 단일 삭제 저널 형식·지문, 운영 자료·DB 스키마·배포·Git 커밋/원격 업로드는 변경하지 않는다.

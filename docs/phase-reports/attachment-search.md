# 첨부파일 검색 구현·검증 보고서

- 검증일: 2026-10-01
- 기준: OfficeFlow 3.0.2 개발 소스, 스키마 `0010_attachment_search`
- 변경 범위: 파일명 검색 구현·기존 검색 연동·사용자 도움말·테스트
- 배포: 구현 검증 단계에서는 배포물을 변경하지 않았으며 이후 사용자 요청으로 3.0.3 배포 진행.
  배포 검증은 `../14-release-checklist.md`에 기록한다.

## 구현 내용

상단 검색 대상의 `첨부파일`을 선택하면 현재 업무 탭의 상태·날짜·고정 필터와 독립된
전체 기간 파일 검색으로 전환한다. 완료·보관·취소 업무도 포함하고 휴지통·연결 해제 파일은
기본 제외한다. 원래 파일명의 부분 문자열을 2글자부터 검색하고 여러 단어는 같은 파일명에서
모두 일치해야 한다. `%`, `_`, 따옴표도 문자 그대로 처리한다. 문서 본문·셀·OCR은 범위 밖이다.

- 파일 종류, 첨부일, 휴지통·정리 대기 포함 옵션.
- 선택 파일 열기, 더블클릭·Enter, 연결 업무와 선택 첨부 관리.
- 휴지통 업무는 읽기 전용, 정리 대기는 기존 첨부 정리로 이동.
- 기존 업무·캘린더·업무일지 검색에도 파일명 조건을 OR로 결합하되 기존 보기 범위 유지.
- 업무 목록의 일치 표시·툴팁과 상세·오른쪽 버튼 메뉴의 일치 파일 바로 열기.
- 250ms 입력 지연, 워커 하나와 최신 대기 요청 하나, 오래된 응답 무시.
- 50개씩 keyset 조회, 최대 500행 유지 후 구간 이동. 표시 개수/더 있음만 안내하며
  별도 전체 파일 개수 쿼리는 실행하지 않음.
- 검색·첨부 관리 중 알림 조작, 모델리스 창의 가져오기 취소·종료 대기.
- 낮은 창에서 기존 사이드바 메뉴의 세로 여백 축소.
- SQLite 오류 로그의 바인딩 값 숨김, 파일 검색 워커는 검색어·파일명을 로그에 기록하지 않음.

## 데이터 안전

기존 DB에는 SQLite 온라인 보호 사본을 만든 뒤 색인을 추가한다. 보호 사본 위치는
사용자 데이터의 `data/schema-backups/pre-attachment-search-*.db`다. 첨부 실물은 변경하지 않으며
보호 사본은 DB만 포함하므로 기존 `.ofbackup` 전체 백업을 대체하지 않는다.
여유 공간을 먼저 확인하고 색인 생성은 SAVEPOINT로 실패 시 롤백한다. 다음 실행에서 재시도한다.
시작 실패는 메시지로 안내하고 단일 실행 잠금을 해제한다.

추가·파일명 변경·영구 삭제의 색인 동기화는 DB 트리거로 처리한다. 연결 해제·휴지통 이동·복원은
검색 시 메타데이터 상태를 판정한다. 검색 시 실물 파일을 순회하거나 체크섬을 다시 계산하지 않는다.
실물 누락은 기존 표시를 사용하고 실제 열기 단계에서 경로와 접근을 다시 확인한다.

## 자동 검증

최종 전체 테스트 결과:

- `mypy src`: 69개 소스 파일 통과.
- 전체 자동 테스트: **260개 통과**, 75.89초, 코드 커버리지 83%.
- 150% 배율 첨부 검색 UI 테스트: 15개 통과.
- 200% 배율 첨부 검색 UI 테스트: 15개 통과.
- 격리된 데이터 경로의 `--smoke-test`: 정상 종료(코드 0).
- 760×560, 960×640, 1280×800에서 한국어 글꼴로 화면 캡처·버튼 폭·위치·메뉴 높이 확인.
- 기존 DB 백필·보호 사본·파일명 변경·삭제 트리거, 강제 색인 실패 후 롤백/재시도,
  디스크 부족 시 원본 보존, 예전/최신 백업 복원 및 첨부 바이트 보존 확인.
- v2.6 가져오기 후 파일명 검색, 기존 업무일지·캘린더 검색 범위 회귀 확인.
- 검색 실행 중 취소 후 다음 조회 정상, 빠른 입력의 최신 결과 보장, 단일 워커,
  500행 제한·이전/다음 구간, 파일 누락·삭제·연결 프로그램 열기 실패, 알림 동시 조작 확인.
- 첨부 복사 중 종료 시 취소 완료·스레드 종료 및 닫힌 창의 지연 콜백 차단 확인.

테스트는 격리된 임시 DB·합성 첨부파일만 사용했다. 실제 사용자 DB·첨부는 변경하지 않았다.

## 성능 측정

환경: Windows, Python 3.12.4, 이 개발 PC의 로컬 디스크. 업무 5,000건·첨부 메타데이터
50,000건을 새 DB에 생성했다. 각 항목은 첫 조회 이후 20회 반복했으며 디바운스·화면 렌더링은
쿼리 시간에 포함하지 않는다. OS 콜드 캐시나 저사양·네트워크 드라이브 성능을 보장하지 않는다.

| 조회 | 첫 조회 ms | 중앙값 ms | p95 ms |
|---|---:|---:|---:|
| 없는문서 (결과 없음) | 7.37 | 3.52 | 3.59 |
| 견적서 (3글자, 드문 일치) | 4.65 | 4.52 | 4.59 |
| 보고서 (3글자, 흔한 일치) | 4.71 | 4.51 | 4.56 |
| 보고 (2글자, 흔한 일치) | 1.11 | 0.57 | 0.64 |
| 견적 (2글자, 드문 일치) | 10.59 | 10.21 | 10.45 |
| 최근 파일 | 0.92 | 0.50 | 0.57 |
| 기존 업무 목록 보고서 검색 (전체 건수 계산 포함) | 83.54 | 77.02 | 77.76 |

- 보호 사본 작성 + 초기 색인 생성: 0.19초.
- DB 크기: 16,314,368 → 24,125,440바이트, 증가 7,811,072바이트 (약 7.45 MiB).
- 500개 결과를 유지한 Python 할당 메모리: 293,073바이트, 피크 319,065바이트 (약 0.30 MiB).
  프로세스 전체 RSS·Qt 네이티브 메모리·SQLite 캐시·장기 실행 메모리 증가는 이번 수치에 포함하지 않는다.
  따라서 전체 검색 기능의 추가 RSS가 20 MB 이하라고 확정하지 않는다.
- 이 합성 데이터에서 3글자 첫 페이지 p95 300ms, 2글자 p95 1초 목표 충족.

재현용 명령은 **존재하지 않는 새 DB 경로**로 실행한다. 기존 DB를 대상으로 하면 중단하도록 보호했다.

```powershell
.\.venv\Scripts\python -m officeflow.tools.benchmark_attachment_search artifacts/new-attachment-benchmark.db --runs 20
```

## 사용자가 확인할 부분

개발 소스는 `run-officeflow-dev.cmd`로 실행한다. 이 실행기는 별도 `.local-data`를 사용한다.
실사용 데이터로 시험할 때는 먼저 `.ofbackup`을 보관하고 실사용 실행기를 사용한다.
기존 3.0.2 ZIP·설치파일에는 이 변경이 포함되지 않으므로 3.0.3 배포본을 사용한다.

실제 Excel/PDF/Word 연결 프로그램 실행과 회사 보안 제품의 허용 여부는 PC 정책에 따라 다르므로
자동 테스트에서는 OS 열기 요청을 대체해 경로·성공/실패 처리만 검증했다. 설치형·ZIP 재패키징,
GitHub 업로드, 이전 버전으로 다운그레이드, 실제 업무 데이터의 장기 부하 시험은 이번 범위에 포함하지 않았다.

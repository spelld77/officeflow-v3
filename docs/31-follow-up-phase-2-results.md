날짜: 2026-10-09. 기준: [공통설계](24-follow-up-common-design.md), [2차 상세설계](27-follow-up-phase-2-design.md).

## 1. 완성한 사용자 흐름

- 기존 첨부는 일반 편집 파일로 유지한다. 자동 원본 지정·파일 이동·최초 정보 재작성은 하지 않는다.
- 첨부 탭의 오른쪽 메뉴/더보기에서 원본 지정, 새 작업본, 보관본 남기기를 제공한다.
  원본 지정은 지정 시 저장된 내용을 독립 고정 파일로 보존하고 이전 편집 파일도 해제 목록에 남긴다.
  원본 지정 뒤 같은 첨부 ID·이름·메모·순서를 유지한다.
- 일반 첨부/원본/작업본/보관본에서 새 작업본을 만든다. 새 내부 파일이며 기존 파일을 덮어쓰지 않고 자동으로 열지 않는다.
  기본 이름은 `이름 - 작업본.ext`, 동명이면 번호를 제안한다. 표시 이름 중복 자체는 허용한다.
- 일반/작업본의 저장된 내용을 수동 보관한다. 자유 보관 이름과 선택 메모를 사용하고 번호는 별도 순번으로 관리한다.
  실패 때 순번을 소비하지 않고 같은 명령 ID 재시도는 중복 파일/항목을 만들지 않는다.
- 보관함은 선택한 문서 계열 또는 업무 전체를 조회한다. 부모 첨부가 삭제된 계열도 업무 전체에서 조회할 수 있다.
  보관본은 50개, 현재 첨부는 100개씩 keyset 조회한다. 당시 파일명/출처와 현재 출처 이름을 구분한다.
  긴 메모는 목록/선택 상세에서 요약하고 메모 창에서 전체를 편집한다. 시각/요일도 표시한다.
- 현재 첨부/보관본을 체크해 함께 외부 저장한다. 종류·계열·페이지를 바꿔도 체크를 유지하고 현재 페이지 선택/해제를 제공한다.
  기존 단일/여러 파일 저장의 덮어쓰기 확인·동명 번호·실패만 재시도를 재사용한다.
  보관본 외부 기본 이름은 당시 파일명에 보관 이름을 붙인다. 외부 사본은 자동으로 열거나 내부에 재등록하지 않는다.
- 이름 변경은 표시 이름만 바꾸며 실제 UUID 경로·ID 연결·원본 내용·작업본 자체 이름·당시 보관 정보는 유지한다.
  파일별 메모는 독립 정보이며 업무 설명/완료 요약/일지로 자동 입력하거나 출처에서 상속하지 않는다.

## 2. 고정 파일과 보기 사본

- 기록 창, 검색의 파일 열기, 데이터관리의 해제 파일 열기, 보관함 보기를 공통 열기 정책으로 연결했다.
  원본/보관본의 관리 경로는 외부 편집기에 전달하지 않는다. source 고정 크기/SHA-256을 확인한 뒤 독립 사본을 연다.
  좋은 cache가 있어도 고정 source의 누락/변조를 숨기지 않는다.
- 미수정 사본은 재열람/재시작 때 재사용한다. 첨부 개수에 더하지 않으며 정시/재시작 알림을 만들지 않는다.
  생성이 끝나지 않은 사본을 정상 문서로 판정하거나 자동 작업본으로 보존하지 않는다.
- 첨부 목록의 보이는/선택 항목만 worker로 확인해 저장된 사본 변경을 표시한다.
  포커스 복귀·목록 열기/선택 시 확인하며 오래된 목록 세대/복원 세대의 결과는 적용하지 않는다.
- 첨부의 `보기 사본 확인/보존…` 또는 데이터 → 첨부 정리 → 보기 사본에서 내용 확인, 닫음 확인,
  작업본 보존, 변경 버리기, 선택 미수정 정리, 외부 저장을 제공한다.
- 작업본 보존은 원본이 아니라 사본의 저장된 현재 bytes를 캡처한다. 독립 작업본의 DB 확정 후에만 선택 사본을 정리한다.
  이후 다시 저장된 변경이 있으면 남겨 두며 다음 명시적 보존은 새 작업본을 만든다. 중복 클릭은 같은 결과를 두 번 만들지 않는다.
- last_used 7일 경과 + 사용자가 닫음 확인 + 정상 내용 검증 + Windows 독점 핸들 확보가 모두 통과할 때만 자동 정리한다.
  수정본·종료 미확인·이전 복원 사본·잠금/미분류 editor sidecar는 자동 삭제하지 않는다.
- 미수정 생성 상한은 100개/512MiB, 해당 source 보호 사본 2개면 추가 생성을 제한한다.
  사본이 없는 경우 단일 큰 파일을 허용한다. 확인된 용량/변경·준비 수와 제한을 관리 화면에 표시한다.
- JSON이 각 사본의 소유 원장이고 SQLite는 후보 인덱스다. 손상 인덱스는 보존 후 제한 배치로 재구성한다.
  20개/2초 후보 예산, 취소/후순위 heavy slot, 실패 후보 다음 시도 지연을 사용한다.
  확인 불가인 첫 후보도 due를 갱신하여 뒤 후보가 굶지 않는다.
- 삭제 승인 원장은 별도로 먼저 fsync한다. bytes 삭제 후 중단됐으면 남은 metadata 정리만 복구한다.
  bytes가 남아 있으면 승인 원장이 있어도 자동 삭제를 재실행하지 않는다. 경로/identity/내용/사용 token/sidecar를 재확인한다.

## 3. 삭제·중단 보호·전체 백업/복원

- 첨부, 보관본, 해제 첨부, 휴지통 업무의 영구 삭제를 같은 삭제 계획/저널/worker로 연결했다.
  삭제 확인에 연결·보관본·실제 삭제/다른 참조 유지 수를 표시하고 업무 삭제의 보관 범위를 별도로 승인받는다.
  오래된 계획/예약된 파일/미지원 자산 FK는 거절한다. 휴지통만으로 파일을 없애지 않는다.
- 파일 격리 → 단일 DB 확정/영수증 → 참조 없는 bytes 정리 순서다. 확정 전 취소는 복구를 마무리한다.
  확정 후 정리 및 재시작 복구는 파일 사이 취소를 확인하고 남은 자료를 다음 점검까지 보존한다.
- 시작 시 제한된 원장 점검으로 보호 범위를 먼저 확보한다. 첫 화면/알림 타이머 준비 뒤 일반 정리한다.
  내부/삭제 cursor는 tick당 20 후보, 하나의 job을 처리하고 slot을 양보한다. 새 pending도 주기적으로 제한 재탐색한다.
  실패 job은 뒤로 미루고 같은 경고를 매초 반복하지 않는다.
- 중단된 내부 작업 확인 창에서 미확정/손상 자료를 보여준다. 확정 자료만 자동 마무리한다.
  미확정 생성은 사용자 클릭으로 같은 명령/출처/bytes/영수증을 다시 검증해 재시도할 수 있다.
  모르는 파일을 자동 등록·삭제하거나 다른 명령으로 재생성하지 않는다.
- 전체 백업 형식 3: DB·설정·정식 자산과 recovery 복구 자료를 별도 archive namespace로 보존한다.
  고정 자산을 해시 검증하고 유효한 삭제 격리 bytes도 일관되게 보존한다. 필요한 bytes/소유 정보 누락은 성공으로 표시하지 않는다.
  일반 고아 파일은 미분류 recovery이고 cache는 제외한다. 형식 1/2 및 종전 분리 전 형식 3도 검증한다.
- 복원 시 recovery는 `데이터 루트/recovery/복원 ID`에 격리하며 정식 첨부로 승격하거나 명령을 재실행하지 않는다.
  이전 cache는 확정 전까지 이전 루트에 유지하고 복원 확정 후 새 루트에 보존한다. 복원 transaction별 새 generation은 재시작에도 동일하다.
  복원 전 자료가 누락/고정 불일치이면 기존 정책의 pre-restore-preserved 폴더로 보존한다.

## 4. 구현 조정과 검증에서 고친 문제

- cache 위치는 `attachments/cache/attachment-views`로 정했다. 같은 보호 캡처 어댑터를 재사용하면서
  자산·일반 고아·첨부 사용량·전체 백업의 대상에서는 명시적으로 제외한다. 공통 계약의 비첨부/비백업 원칙은 같다.
- 기존 보관함에 현재 첨부 종류 전환과 체크 보존을 넣어 별도의 중복 저장 화면을 만들지 않았다.
- 미확정 bytes를 명령으로 자동 재실행하지 않는 원칙을 유지한다. 확인 창은 목록/동일 생성 명령 재검증이고 모르는 자료 삭제 기능은 아니다.
- Qt worker 완료는 bound Slot/QueuedConnection으로 GUI 스레드에서 처리한다. 종료된 위젯에 늦은 결과를 적용하지 않는다.
  native 스레드 종료/소유권 해제도 확인하며 부모/DB 폐기 전에 취소·종료를 기다린다.
- 백그라운드 점검 타이머는 부모 창이 소유하고 종료 시 정지한다. 반복 실행의 GUI 스레드 처리·종료 뒤 재시작 방지를 검사했다.
  검증 과정에서 일부 전체 검사 실행의 native Qt 종료가 발생해 위젯·스레드·타이머 수명을 보완했다.
  이후 최종 전체 검사 두 번과 완료/창 닫기 반복 검사에서 재현되지 않았다. 모든 장시간/회사 환경을 보장하는 결과는 아니다.
- 실제 dark system palette 캡처에서 새 QListWidget viewport가 검게 남는 문제를 발견해 명시적 배경/선택/전경을 보완했다.
  QPlainTextEdit도 밝은 스타일/Tab 이동을 지정했다. 긴 상세가 좁은 창을 밀어내지 않게 요약/별도 메모 편집으로 분리했다.

## 5. 검증 결과

최종 검증은 격리 자료를 사용했다. 중간 실패/중단 결과를 통과로 계산하지 않는다.

- 전체 회귀: **835 통과 / 150.32초**. 종료 위치를 추적하는 진단 실행기로 실행했다.
- 일반 조건 재검사: **835 통과 / 157.26초**. 별도 진단 hook 없는 `python -m pytest`로 확인했다.
- Ruff 전체 검사 통과. mypy **100개 소스 파일 오류 없음**. `git diff --check` 통과.
- 설계/완료 문서 링크, 사용자 도움말 필수 내용/내부 이동 링크, QA 자료의 Git 제외를 확인했다.

- 관련 생성/삭제/보기/복원/Qt 사용 흐름의 통합 및 UI 검사를 실행했다.
- 실제 자식 프로세스 강제 종료: 스키마 이행, 생성 공개/확정 경계, 삭제 격리/확정/정리,
  cache 작업본 보존 3경계, cache 정리 3경계, 복원 cache 이동 후 generation 공개 전/후.
  재시작 후 기존 파일 불변·영수증·중복 방지·불명 자료 보존을 검사한다.
- 같은 stat의 내용 변경, 열린 protected handle, 재열람 token, editor sidecar, source 삭제 후 보관본 재작업,
  이전 generation cache 외부 저장, 50,000 후보에서 첫 실패 20개 뒤 다음 20개 진행을 검사했다.
- 실제 Windows Qt renderer에 dark Window/Base와 검은 Text palette를 주입했다.
  기록/보관함/cache/복구/작업본 생성/보관 생성/메모 7화면을 100%·150%·200%에서 숨김 캡처했다.
  요청 크기는 600×450 logical px, 기존 기록 창은 기존 최소 높이 때문에 600×540이다.
  기능 자동 검사와 실제 렌더링 가독성 확인은 구분한다. 최종 QA 캡처는 `.test-tmp/phase2-current-visual-*`에 있다.

### 성능·큰 파일 실측

Windows / Python 3.12.4 / PySide6 6.11.2. 격리 fixture이며 운영 DB를 사용하지 않았다.

| 검사 | 실제 결과 |
| --- | --- |
| 5,000 업무 + 50,000 첨부 metadata의 첫 화면 | 562.906ms |
| 같은 fixture의 알림 타이머 준비 | 563.835ms, active 확인 |
| 5,000 업무 + 50,000 첨부 + 50,000 보관본의 첫 50행 조회 | 14.974ms, SQL 1회 |
| 같은 fixture의 다음 50행 30회 | 중앙값 1.173ms / 최대 2.262ms |
| 선택 보관본 상세 | 2.899ms |
| 1GiB 외부 사본 | peak RSS 증가 2.04MiB / 3.141s |
| 1GiB 내부 고정 캡처 | peak RSS 증가 2.05MiB / 1.765s |
| 1GiB 고정 source 검증 + 보기 사본 | peak RSS 증가 0.85MiB / 2.375s |
| 1GiB 전체 백업 + 검증 | peak RSS 증가 5.70MiB / 8.312s |

행 개수 fixture는 metadata 성능이며 50,000 실제 문서를 열거나 전체 bytes를 백업한 측정이 아니다.
알림 준비 시간은 타이머 활성 시각이지 운영 알림의 실제 수신 SLA가 아니다.
1GiB는 별도 실제 Windows 프로세스에서 처리하고 파일 크기/정상 출력까지 확인했다. 모두 32MiB 증가 목표 이내다.
QA 실행기/프로필/캡처는 ignored `.test-tmp`에 남으며 릴리스 포함 파일이 아니다.

## 6. 사용자 확인과 남은 단계

1. 개발 실행 `run-officeflow-dev.cmd`로 확인한다. EXE/배포 ZIP은 이번 소스를 아직 포함하지 않는다.
   이 실행기는 저장소의 `.local-data`를 사용한다. 최초 실행은 해당 DB의 0013 이행을 진행하므로 먼저 전체 백업을 권장한다.
2. 테스트용 서식을 첨부해 원본 지정 → 작업본 편집 → 자유 이름 보관 → 이전 보관본에서 새 작업 → 혼합 외부 저장을 확인한다.
3. 원본의 보기 사본을 편집/저장/닫은 뒤 변경 표시와 수정본 저장… → 문서 닫음 체크 → 저장을 확인한다.
   원본을 다시 열면 원본 내용이며 새 작업본은 별도 목록 항목인 것을 확인한다.
4. 첨부 이름/메모와 남은 보관본 조회, 전체 백업/새 테스트 프로필 복원을 확인한다.
   중요한 운영 파일 삭제로 테스트하지 않는다. 운영 전에는 기존 앱의 전체 백업을 남긴다.

회사 보안/DRM과 실제 한글·Excel 편집기, 외부 저장장치 장애, 다중 모니터·시스템 테마의 live 전환은 미검증이다.
편집기 미저장 버퍼/문서 종료를 추측하지 않고 닫음 확인을 요구한다. 수정 cache와 이전 generation은 전체 백업에서 제외되므로 별도 보존해야 한다.
파일 유실 가능성을 절대 0으로 보장하는 것이 아니라 검증 실패·불명 상태의 보존/중단을 기본값으로 삼았다.
사용 확인 후 3차 상세설계(U12/U13/U14)를 진행한다. U1·외부 Git 연동·버전/배포/원격 업로드는 별도 요청 전까지 유지한다.

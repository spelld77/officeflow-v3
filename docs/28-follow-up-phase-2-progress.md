# 후속 개선 2차 첫 구현 단위 보고

날짜: 2026-10-09. 기준: [2차 상세설계](27-follow-up-phase-2-design.md).
상태: 2차 구현 진행 중. 이 보고는 첫 변경 묶음이며 **2차 전체 완료/사용 확인/운영 적용/배포가 아니다**.
버전은 3.0.7을 유지하며 실제 사용자 DB/첨부, EXE/ZIP, 커밋/GitHub는 변경하지 않았다.
이후 진행은 [내부 생성·중단 보호 구현 보고](29-follow-up-phase-2-internal-operations-progress.md)를 따른다.
아래 남은 작업은 첫 구현 단위 당시 상태이며, 최신 범위와 검사 결과는 29번 보고에서 구분한다.

## 이번 반영 범위

- revision 0013: 파일 자산·문서 계열·보관 참조·작업 영수증 원장을 설치한다.
  기존 현재/해제/휴지통 첨부는 일반 편집 첨부로 이행한다. 자동 원본 지정이나 실제 파일 이동/해시는 하지 않는다.
  ID/순서/최초 이름·크기·해시/관측값/경로/내용을 유지한다. 초기 migration이 최신 첨부 ORM을 설치하여
  옛 revision을 건너뛰지 않도록 실제 초기 첨부 스키마를 명시했다. 0013의 테이블 정의도 미래 ORM과 분리했다.
- 실제 경로와 관측은 자산 원장에서 관리하고 기존 일반 첨부 API는 JOIN으로 같은 정보를 반환한다.
  참조 검사에 현재/해제 첨부와 보관본을 포함한다. 지원하지 않는 추가 자산 FK가 있으면 삭제/백업을 거절한다.
  고정 파일의 경로/크기/해시와 최초 이름·보관 당시 정보를 DB trigger로 보호한다.
- 일반 첨부의 `이름 변경…`, `메모…`: 오른쪽 메뉴/더보기에서 편집한다.
  이름 본문만 수정하고 확장자는 유지한다. 실제 경로·최초 이름은 그대로이며 검색/외부 저장 기본 이름을 갱신한다.
  파일별 메모는 선택 입력(최대 2,000자), 목록 한 줄 미리보기와 선택 상세에 표시한다.
  메모 검색/자동 상속/업무일지 자동 입력은 하지 않는다. 저장 실패 시 입력을 유지하고 revision 충돌은 거절한다.
  휴지통/해제 첨부는 복원 후 편집한다. 파일 작업 중 변경 버튼은 비활성화한다.
- 백업 형식 3의 자산 수집 기반: 별도 보관 참조만 남은 파일도 포함하고 고정 크기/해시를 확인한다.
  필요한 파일의 누락/고정 불일치를 성공으로 표시하지 않는다. legacy 형식 1/2의 경고는 유지한다.
  큰 파일은 보호 읽기로 독립 복사하며 전역 게이트는 DB 캡처/사용 예약의 짧은 구간에만 사용한다.
  압축 중 출처가 바뀌어도 확보한 독립 사본은 유지한다. 무거운 복사는 단일 작업 큐를 따른다.
- 복원 전 자료가 이미 누락/고정 불일치인 경우: 정상 백업의 복원을 막지 않되 이전 루트를 별도로 보존한다.
  지원 스키마/연결/DB 무결성 확인 후에만 허용하며 다른 실패를 우회하지 않는다.
  `backups/pre-restore-preserved-<id>`는 정상 백업이 아니며 자동 삭제/보존 개수 정리의 대상이 아니다.
- 정상 시작의 삭제 복구 확인에서 `.trash`가 없으면 DB/전체 파일 경로를 읽지 않는다.
  실제 저널이 있으면 해당 경로/내부 이름만 조회하며 전체 첨부 경로 set을 만들지 않는다.
  DB를 읽을 수 없으면 격리 자료를 보존하고 실패를 알린다.

## 검증

- 최종 전체 회귀: **730개 통과**, 88.87초. 1 GiB 스트리밍 검사도 포함했으며 제외/건너뜀은 없다.
  이 실행은 실제 내부 생성/보기 cache 기능까지 검증한 것이 아니라 현재 구현한 소스와 기존 기능의 회귀 검사다.
  직전 이름/메모·기록·첨부 검색·자산 관련 검사 60개도 통과했다.
- Ruff/mypy 통과 (88 source files). 기존 일반 첨부·검색·순서·완료/알림·백업/복원 회귀를 포함한다.
- 진짜 0012/0010/0009 스키마 fixture를 생성해 이행한다. 새 보관 자료를 버리는 downgrade로
  옛 DB를 모사하지 않는다. 새/기존 설치, 해제/누락/편집 후 저장 자료와 최초 기준 유지 검사를 한다.
- 이행의 세 경계에서 실제 자식 프로세스를 `os._exit`로 즉시 종료했다.
  DB 전부 롤백/기존 파일 보존/재실행 후 중복 없는 이행을 검사했다. 내부 생성/삭제 저널의 강제 종료 검사는 아직 아니다.
- 보관 참조만 남은 고정 파일의 유지·전체 백업/격리 복원, 출처 삭제 후 과거 payload 유지,
  이름/메모 CAS, 최초 이름/보관 capture 수정 거절, 변조 고정 파일의 외부 저장 거절을 검사했다.
  원본/보관본은 이 검사용 ORM fixture일 뿐 실제 생성 UI가 구현되었다는 뜻이 아니다.
- 현재 파일 누락/변경 상황에서 정상 백업 복원·이전 추가 파일 보존과 보존 폴더 이동 직후 중단/재시작을 검사했다.
- Windows Qt renderer 캡처: 좁은 340px 창, 어두운 QPalette, Qt 배율 100%/150%/200%의 이름/메모 창.
  실제 캡처를 확인했고 배경/글자 대비와 저장/취소 버튼 접근을 검사했다. OS 테마 자체의 전환이나
  모든 화면/모니터 조합은 검증하지 않았다. 일반 자동 UI 회귀는 offscreen 검사다.

## 대량 자료 실측

이 개발 PC의 격리 metadata fixture(5,000 업무, 50,000 첨부). 실제 문서 50,000개를 만들거나
그 자료 전체를 백업한 결과는 아니다. seed 비용과 파일 읽기 비용을 아래 값에 섞지 않는다.

| 항목 | 실측 |
| --- | --- |
| 0012 → 0013 이행(보호 DB 포함) | 1.673초 |
| 한 업무의 첨부 metadata 10행, 7회 중앙값 | 0.669ms |
| 파일명 검색, 7회 중앙값 | 3.425ms |
| 정상 시작 삭제 복구 사전 확인, 7회 중앙값 | 0.684ms |
| 주 창 생성·초기 이벤트 처리 | 600.816ms |
| 기존 1 GiB 외부 저장 스트리밍 | 3.032초, peak RSS 증가 2,191,360B |

대량 시험 중 임시 ID 매핑의 무색인 조회와 SQLite batch 교체의 자기 FK 때문에
구 테이블 삭제가 반복 전체 검사로 느려지는 것을 발견했다. 매핑 색인과 자기 참조 staging table/rename으로 수정했다.
FK 검사를 끄지 않고 회귀 검사로 검색 계획·임시 자기 FK·최종 FK를 확인한다.
메타데이터 측정/외부 저장 측정은 새 내부 생성/cache/전체 백업의 대용량 검증을 대신하지 않는다.

## 아직 남은 2차 작업

1. 보호 캡처·내부 작업 저널/명령 ID/영수증 확정, 배타 삭제 예약·계획·격리 복구와 시작 시 보호 범위.
2. 원본 지정(이전 편집 파일 보존), 작업본·보관본 생성 및 조회/삭제 UI.
3. 공통 frozen 열기·보기 사본 재사용/변경 감지·작업본 보존/버리기·혼합 저장.
4. 7일 만료와 전용 후보 인덱스/제한 정리, cache generation/보호 사본 관리,
   미완료 내부 자료의 분리 백업/복원·사용량·대량/중단/가독성 검사.

공개 `원본 지정`/`작업본 만들기`/`보관본 보기` 메뉴는 아직 노출하지 않았다.
고정 관리 파일의 기존 직접 열기는 거절하도록 막았지만, 실제 보기 사본으로 여는 흐름은 아직 구현 전이다.
기존 일반 첨부는 계속 편집 가능하다. 이 부분 상태로 3차 상세설계나 릴리스/운영 전환을 진행하지 않는다.

개발 실행 시에는 0013을 적용하므로 기존 공개 코드로 DB를 다시 열지 않는다.
2차 전체 기능/실패 복구 검증 전에는 사용 확인을 위해 실제 사용자 자료로 자동 전환하지 않는다.

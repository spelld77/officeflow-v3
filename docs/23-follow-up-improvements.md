### 아직 부족한 설계와 보완 기준

- 기존 데이터: 기존 첨부는 일반 수정 가능한 첨부로 유지한다. 자동 원본 지정·내용 되돌리기를 하지 않는다.
  과거 업무 변경 이력은 소급하여 재구성할 수 없다. 도입 시/첫 변경 시 기준과 이후 기록을 구분한다.
- 공통 보존 모델: 작업본·개별 보관본·업무 묶음의 파일 관계와 삭제 영향을 명시한다.
  묶음이 사용하는 보관 파일을 작업본 삭제나 고아 파일 정리가 잘못 제거하지 않게 한다.
  정리 대상 판별·백업 목록·참조 유지 로직도 새 보관 모델에 맞춰 갱신한다.
- 반복 회차: 업무 공통 설명/서식과 회차별 결과메모/보관을 구분한다.
  서로 다른 회차를 합치거나 한 회차 완료/삭제로 다른 회차의 자료·알림을 잃지 않게 한다.
- 열린 문서: 원본 지정·복사·보관 중 외부 편집과 잠금을 다룬다.
  보기용 사본의 수정은 실제 보관본에 반영되지 않음을 안내하고, 외부 편집기의
  자체 `다른 이름으로 저장`으로 생긴 파일을 자동 연결했다고 오해하지 않게 한다.
- 기록 범위: 자동 이력에 들어갈 값, 업무일지와 결과메모의 차이, 수동 묶음의 포함 자료를 명시한다.
  내부 갱신 시각/알림 실행 정보 같은 기계적인 변화가 매번 사용자 이력을 만들지 않게 한다.
- 일관된 묶음: 보관 중 업무 내용과 파일이 바뀌면 여러 시점의 자료를 하나의 시점인 것처럼 확정하지 않는다.
  편집 중 자료의 저장 확인과 보관 완료 조건을 설계한다.
- 조회·비교: 긴 설명과 수백/수천 건의 이력을 전체 로딩하지 않는다.
  현재/과거 구분, 선택 시점 비교, 추가 불러오기, 실제 문구 보존을 수용 기준으로 둔다.
- 백업 호환: 새 스키마/보관 자료를 복원했을 때의 호환 범위와 이전 프로그램으로의 다운그레이드 제한을 안내한다.
  DB만 백업하면 첨부/보관 파일까지 보존되는 것처럼 안내하지 않는다.
- 화면 일관성: 원본·사본·작업본·보관본·묶음·외부 복사의 용어를 정돈한다.
  새로운 메뉴를 기존 첨부/기록 동선에 배치하고 좁은 창에서 목록과 메모가 과밀해지지 않게 한다.

### 사용자 확인 완료: 승인된 기준 1~6

승인일: 2026-10-08. 사용자가 1~6번 권장안에 모두 동의했다.
같은 사항을 다시 확인하지 않고 설계 기준으로 사용한다. 실제 삭제 시의 확인 대화상자는 유지한다.
이번 승인은 설계 선택에 대한 것으로, 기능 구현·커밋·배포·업로드 요청과는 구분한다.
기술 설계는 이 기준 안에서 진행하며 범위나 데이터 보존 정책을 바꾸어야 하면 별도로 확인한다.

1. 역할 명칭(U5/U7): UI를 `원본 / 작업본 / 보관본`으로 통일한다.
   수정 가능한 내부 사본은 `작업본`, 외부 복사는 `다른 이름으로 저장`으로 구분한다.
2. 동명 외부 저장(U6): 여러 파일 저장 시 기존 파일을 보존하고 자동 번호로 새 이름을 만들어 결과를 알린다.
   단일 저장의 명시적 덮어쓰기 확인은 유지한다.
3. 삭제 범위(U5/U7/U8/U13): 휴지통에서는 전부 보존한다.
   사용 중인 보관 파일은 연결 하나를 없앴다고 물리 삭제하지 않는다.
   업무 영구 삭제 시 보관 자료까지 없앨지는 삭제 범위와 영향 개수를 명시해 별도로 확인받는 정책으로 설계한다.
4. 자동 이력 범위·보존(U12): 초기 범위는 제목·설명·일정·중요도·상태·결과메모다.
   체크리스트 세부 변경/업무일지 편집 이력은 별도 검토한다.
   초기에는 자동 삭제하지 않고 필요한 범위만 조회한다. 보존 기간 제한은 나중에 사용자 선택으로 정한다.
5. 묶음 포함 범위(U13): 당시 기본 업무 정보·결과메모·체크리스트 상태·사용자가 선택한 첨부를 포함한다.
   전체 업무일지는 기본 복제하지 않는다. 반복 업무는 공통 자료와 보관 대상 회차를 함께 표시한다.
6. 묶음 실패 처리(U13): 선택한 첨부 일부가 복사되지 않으면 해당 묶음은 완료로 확정하지 않는다.
   실패 항목을 안내해 다시 시도한다. 사용자가 선택 범위를 바꿔 파일 없이/일부만 새로 보관하는 것은
   명시적인 새 선택으로 허용한다. 실패한 항목을 조용히 제외하지 않는다.

초기 구현에 필수 아닌 선택은 보류한다: 외부 설명 TXT 동봉, 첨부 메모 검색,
메모의 사본 상속, 여러 업무 검색 결과의 일괄 저장, 원본 교체/보호 해제의 편의 기능.
원본 교체는 기존 원본을 조용히 덮어쓰지 않으며 초기에는 새 원본 항목을 만드는 방향을 권장한다.

## U1. 일정과 알림의 중복처럼 보이는 표시

상태: 새 3차 상세설계·소스 구현·격리 테스트 완료, 사용자 사용 확인 전(2026-10-10).
아래는 개선 전 진단과 방향이며 최신 결과는 44번 보고를 따른다. 실제 알림 팝업의 묶기는 제외한다.

- 달력 날짜별 목록은 업무 일정과 알림을 별도 행으로 합쳐 같은 제목을 반복 표시한다.
- 오늘 화면은 오늘 알림과 업무 목록에 같은 업무가 각각 표시된다.
- 오늘 알림 및 전체 보기에서는 같은 업무의 여러 알림이 여러 행을 차지한다.
  한 업무가 미리보기 2~3행을 모두 차지하여 다른 업무의 알림을 밀어낼 수 있다.
- 알림 팝업에서도 제목은 반복되지만, 알림별 확인·재알림은 독립적으로 유지해야 한다.
- 일반 업무 목록에는 알림 행을 추가하지 않는다. 업무일지는 완료 항목과 기록을
  업무·반복 회차별로 묶고, 첨부파일 검색은 파일 단위 결과로 표시한다.

검토한 방향:

1. 달력·오늘 알림은 같은 업무·회차를 한 행으로 묶고 알림 개수와 다음 시각을 표시한다.
2. 펼치면 각 알림의 시각·상태를 확인한다. 서로 다른 반복 회차를 합치지 않는다.
3. 그날 일정 없이 알림만 있는 업무도 기본 노출한다.
4. 업무 개수와 알림 건수를 구분하고 부분 조회·전체 보기·스크롤 안내를 유지한다.
5. 오늘의 업무 목록을 알림 영역과 중복된다는 이유만으로 숨기지 않는다.
   업무 검색·필터와 알림의 독립성, 기록·첨부·알림 설정 연결을 보존한다.
6. 팝업을 묶더라도 선택한 알림만 확인·재알림하고 업무 완료와 명확히 구분한다.

근거: 달력의 `CalendarPage._refresh_day_list`, 오늘의 `ReminderPreviewWidget`,
주 창의 오늘 업무 목록 구성. 관련 UI 검사 3개 통과.

## U2. 여러 알림 도중 업무 완료 후 상태 구분

상태: 1차 구현·검증 및 사용자 사용 확인 완료. 아래 재현 결과는 개선 전 진단 기록이다.
현재 반영 범위와 제한은 [1차 구현·검증 보고](26-follow-up-phase-1-results.md)를 따른다.

확인 대상:

- 먼저 확인한 알림, 완료 시 미확인·재알림인 알림, 아직 울리지 않은 알림의 표시.
- 달력·오늘 알림·일반 업무 목록·알림 설정창의 업무 완료 상태 구분.
- 이미 열린 알림 설정창의 업무 상태가 완료 후 최신 상태로 반영되는지.
- 반복 업무는 회차 완료와 업무 전체 완료를 구분하고 다음 회차 알림을 보존하는지.

재현 결과:

1. 알림 3개를 설정하고 첫 알림을 확인한 뒤 두 번째 알림에서 업무를 완료하면,
   미리보기에는 첫 알림 `확인함`, 두 번째 알림 `완료`가 남는다. 양쪽 원본 업무 상태는
   완료이지만 알림 행에는 이를 별도 표시하지 않는다. 아직 발생하지 않은 세 번째 알림은
   미리보기에서 제외된다. 미확인·재알림 delivery는 완료로 처리되고 미래 발생은 중단된다.
2. 업무 목록에서 완료한 경우에도 이미 확인한 알림 이력은 `확인함`으로 남고,
   나머지 미래 예약은 표시하지 않는다. 일반 업무 목록은 업무 상태 `완료`를 표시한다.
3. 이미 열어둔 알림 설정창은 발생 이력만 갱신하고 업무 스냅샷을 갱신하지 않는다.
   따라서 실제로는 중단된 미래 알림이 `예정`으로 보일 수 있다. 저장되지 않은 편집 내용을
   보호하기 위한 갱신 방식에서 생긴 표시 버그다. 새로 열면 최신 업무 완료 상태로
   `업무 완료·취소 · 울리지 않음`을 표시한다.
4. 달력 업무 막대는 완료 시 회색, 날짜별 업무 행은 체크 표시로 구분한다.
   알림 행의 상태·날짜 칸 알림 건수는 업무 완료 여부/과거 이력과 미래 예약의 구분이 부족하다.

1차 구현의 기준이 된 개선 방향:

- 업무 상태와 알림 처리 상태를 분리하여 `업무 완료 · 알림 확인함`처럼 표시한다.
  과거 확인 이력을 모두 `완료`로 덮어쓰지 않는다.
- 미래 예약은 완료 후 울리지 않는다는 것을 업무 알림 요약/설정창에 명시한다.
  달력에 모든 중단 예약을 추가할지는 U1의 중복 표시 정돈과 함께 결정한다.
- 열린 편집창의 미저장 제목·일정·알림 규칙은 보존하면서 실제 업무/회차의
  최신 실행 상태를 별도로 반영한다. 완료 업무 재개와 반복 회차 완료도 함께 검증한다.
- 날짜 칸 및 요약 건수에서 예정 알림과 처리된 이력이 뒤섞여 보이지 않도록 정돈한다.

근거: `ReminderPreviewService`, `preview_targets`/`preview_deliveries`,
`ReminderSettingsDialog.update_delivery_states`, 주 창 `_synchronize_reminder_dialog`.
격리 DB에서 진단 3건 및 기존 완료·반복 회차 검사 2건, 총 5건 통과.
실제 사용자 DB·첨부·설정과 프로그램 소스·배포 파일은 변경하지 않았다.

## U3. 첨부파일을 다른 이름으로 저장

상태: 1차 구현·검증 및 사용자 사용 확인 완료. 아래 합의한 흐름을 구현했다.

목적: 내부 저장 폴더를 찾아 파일을 복사하고 이름을 바꾸는 과정을 없앤다.
서식 또는 작업 파일을 첨부로 보관하고, 필요할 때 수정본을 제출·전달용 사본으로 꺼낸다.

합의한 기본 동작:

1. 첨부 목록의 파일을 오른쪽 클릭하여 `다른 이름으로 저장…`을 선택한다.
2. 익숙한 Windows 저장 대화상자를 연다. 기본 파일명은 내부 저장 이름이 아니라
   첨부 목록에 표시되는 `original_name`이다.
3. 사용자는 저장할 폴더를 선택하고 `저장`을 누른다. 이름 변경은 선택 사항이다.
4. 보관 파일을 이동·변경하지 않고 현재 디스크에 저장된 내용을 복사한다.
5. 저장한 사본을 자동으로 열지 않는다. 별도의 `사본 만들어 편집` 기능은 추가하지 않는다.

함께 고려할 사항:

- 마지막 저장 폴더를 기억하고, 사라졌거나 접근할 수 없으면 다른 위치를 선택하게 한다.
- 확장자 누락·중복, 잘못된 파일명, 원본과 동일한 저장 경로를 안전하게 처리한다.
- 기존 파일 덮어쓰기는 확인받는다. 취소·복사 실패 시 기존 대상 파일을 훼손하지 않는다.
- 큰 파일 복사는 화면을 멈추지 않게 한다. 저장 중 파일 변경·잠금·보안 프로그램의
  접근 거부는 성공으로 표시하지 않고 안내한다. 보안 정책을 우회하지 않는다.
- 연결 문서 프로그램의 미저장 편집 내용은 가져올 수 없다. 먼저 저장하도록 안내한다.
- 완료 후 저장 위치를 알리고 선택적으로 `폴더 열기`로 저장한 파일을 선택해 보여준다.
- 외부 사본은 OfficeFlow 백업 대상이 아니며, 이후 외부 사본 수정은 첨부에 자동 반영되지 않는다.
  별도로 첨부하지 않으면 연결된 새 첨부도 생성하지 않는다.
- 첨부파일 검색에서도 동일 기능을 제공하는 방안을 검토한다.
- 여러 파일 일괄 저장은 이후 사용자 요청으로 U6에 추가했다.
  클립보드 파일 복사와 밖으로 드래그는 아직 범위에서 제외한다.
  메일·공문 시스템의 드래그/붙여넣기 지원은 별도 확인한다.

## U4. 첨부파일을 직접 수정하는 사용 흐름과 무결성·메타데이터 정돈

상태: 1차 구현·검증 및 사용자 사용 확인 완료. 아래 현재 동작은 개선 전 진단 기록이다.
최초/관측 정보 분리와 실제 내용 기준 중복 판별의 결과는 [1차 보고](26-follow-up-phase-1-results.md)를 따른다.

사용 흐름: 첨부로 보관한 작업 파일을 연결 프로그램에서 열어 수정·저장하고,
필요할 때 U3로 제출용 사본을 저장한다. 원본 서식을 별도로 보존하는 것은 필요할 때만
서식과 작업 파일을 나누는 방식으로 안내한다.

현재 확인된 동작:

- 첨부 시 외부 파일을 관리 저장소에 복사한다. `열기`는 그 관리 사본을 직접 연다.
  저장하면 관리 사본의 내용이 바뀌지만 처음 가져온 외부 파일은 별개다.
- 첨부 당시 체크섬과 크기는 외부 프로그램의 저장 후 자동 갱신되지 않는다.
- `무결성 확인`은 첨부 당시와 내용이 같은지 비교하므로 정상적인 편집도 `변경됨`이다.
  정상 편집과 손상 여부를 체크섬 차이만으로 구분할 수 없다.
- 내용 변경 경고 자체로 파일을 삭제·연결 해제하거나 열기·삭제를 차단하지 않는다.
- 동일 업무에 재첨부할 때의 중복 판별 및 사용량의 중복 내용 계산은 옛 체크섬을
  사용하므로 파일을 직접 수정한 뒤에는 부정확할 수 있다.
- 전체 백업은 현재 저장된 파일 내용으로 별도 체크섬을 계산한다. 기존 첨부 체크섬과
  다르다는 이유로 백업을 거부하지 않는다. 백업 중 변경·접근 실패는 별도로 감지한다.

개선 방향(구체 설계 필요):

1. 첨부를 수정 가능한 작업 파일로 사용하는 흐름을 지원하고 도움말에 명시한다.
2. `첨부 당시와 내용이 다름`과 `파일 손상`을 혼동하지 않도록 무결성 결과 문구를 정돈한다.
3. 최신 크기·변경 정보와 중복 판별을 실제 저장 내용에 맞게 관리한다.
   파일 변경 감지 시점·조회 비용·파일 잠금·저장 중 검사 방식을 함께 결정한다.
4. 변경될 때마다 최초 체크섬을 무조건 덮어쓰거나 변경 경고를 숨기지 않는다.
   최초 기준과 최신 확인 상태의 분리 또는 명시적인 수정본 갱신 절차를 설계한다.
5. U3는 오래된 크기/체크섬에 의존해 복사를 거부하거나 예전 내용을 복사하지 않는다.
   현재 저장된 파일을 안정적으로 복사하고 수정 중이면 재시도/안내한다.
6. 백업 생성 시점의 별도 검증과 복원 보호는 유지한다. 백업 검증을 없애지 않는다.
7. 이미 수정한 첨부도 보존한다. 갱신·변환을 이유로 파일을 삭제하거나 사용자의
   수정 내용을 되돌리지 않는다. 자동 덮어쓰기·문서 편집 자동화는 우선 추가하지 않는다.
   사용자가 명시적으로 보관하는 버전 기능은 이후 논의한 U7에서 별도로 검토한다.

근거: `AttachmentService.attach/path_for_open/verify`,
`SqlAlchemyAttachmentRepository.find_active_by_checksum`, 첨부 열기/검사 UI,
`BackupManager`의 현재 파일 사본·체크섬 검증과 데이터관리 정리 동작.
격리 DB/첨부 테스트 1건에서 수정본 유지·외부 원본 유지·메타데이터 불일치·
옛 체크섬 기반 중복 판별·수정된 현재 내용의 백업을 확인했다.
실제 사용자의 파일 상태는 직접 검사한 것이 아니므로 개별 파일의 정상 여부를 단정하지 않는다.

## U5. 원본 서식과 작성 사본의 구분·보호

상태: 원본/작업본·보기 사본을 포함한 [2차 구현·검증](31-follow-up-phase-2-results.md) 완료. 사용자 사용 확인 대기.
U3의 외부 사본 저장 및 U4의 수정 가능한 첨부 관리와 함께 설계한다.

사용자 요구:

- 사용자가 원본으로 지정한 첨부에 `원본` 표시를 한다.
- 원본에서 만든 업무용 작성 파일은 첨부 목록의 별도 항목으로 보관한다.
  처음 논의한 `사본` 배지는 이후 승인한 명칭 `작업본`으로 정돈한다.
- 원본으로 지정한 시점의 내용을 보존하며, 지정 이후에는 직접 수정하지 못하게 한다.

정리한 동작:

1. 일반 첨부는 기존처럼 작업 파일로 사용할 수 있다. 사용자가 명시적으로 지정한
   파일에만 원본 보호를 적용한다.
2. `원본으로 지정…` 시점에 디스크에 저장된 내용을 기준으로 고정한다.
   이미 편집한 파일을 지정했다고 최초 첨부 시점의 내용으로 되돌리지 않는다.
   연결 프로그램에서 미저장 내용을 먼저 저장하고 문서를 닫게 안내하며,
   복사/고정 중 파일 변경·잠금·실패 시 지정이 성공했다고 표시하지 않는다.
3. 원본은 표시뿐 아니라 보관 방식과 열기 경로로 보호한다. 원본의 실제 보관 파일을
   기존 `열기`처럼 편집 프로그램에 직접 전달하지 않는다. 원본 확인이 필요하면
   별도의 보기용 사본 등으로 열어 원본 보관 내용이 덮어써지지 않게 한다.
4. 원본 메뉴의 `작업본 만들기…`에서 파일명을 지정하면 같은 업무의 첨부 목록에
   새 작성 사본을 등록한다. 자동으로 열지 않으며 사용자가 사본을 열어 작성한다.
5. 작성 사본은 `작업본` 표시와 원본 연결 정보를 유지하고 자유롭게 수정·저장한다.
   사본에서 U3 `다른 이름으로 저장…`을 하면 외부 제출용 파일만 생성한다.
   외부로 꺼낸 파일은 다시 첨부하지 않는 한 첨부 목록 항목이 아니다.
6. 원본과 생성 직후 사본의 내용이 같아도 의도적인 사본 만들기는 중복 첨부 검사로
   거부하지 않는다. 일반 첨부의 중복 정책까지 무조건 해제하지 않는다.
7. 원본과 내부 작성 사본은 모두 전체 백업에 포함한다. 원본·사본 구분과 원본 연결도
   백업·복원 및 다른 PC 이동 후 유지한다. 현재 기능에는 없는 메타데이터이므로
   추가 스키마와 기존 자료의 안전한 이행을 설계해야 한다.
8. 표시된 원본 내용을 조용히 교체하거나 U4의 변경 정보 갱신으로 원본 기준을 덮어쓰지 않는다.
   원본 업데이트/보호 해제는 2차 범위에서 제외한다. 표시 이름 변경(U15)은 내용 변경/보호 해제가 아니다.

이후 논의한 용어·사용 흐름:

- 내부에서 수정하는 작성 사본은 설명·메뉴·배지에서 `작업본`으로 구분한다.
  사용자 승인으로 역할 명칭은 `원본 / 작업본 / 보관본`으로 통일했다.
- `작업본 만들기…`는 업무의 첨부 목록에 내부 파일을 만든다. 외부 폴더 선택창을 열지 않는다.
  원본뿐 아니라 U7의 보관본에서도 새 작업본을 만들 수 있다.
- 작업본을 연결 프로그램에서 열어 일반 저장하면 해당 작업본이 갱신된다.
  OfficeFlow의 `다른 이름으로 저장…`은 외부로 복사하는 별도 동작이다.
  마지막 저장 폴더를 보여주는 것은 이 외부 저장 대화상자에 해당한다.

2026-10-09 추가 논의 반영(2차 소스에 구현, 사용 확인 대기):

- 1시·2시·다음 날은 같은 원본을 다른 시점에 보는 예시다. 정시/재시작 알림을 만들지 않는다.
  미수정 보기 사본은 재사용하고 정리 후 필요할 때 재생성한다. 열람할 때마다 첨부 항목을 늘리지 않는다.
- 보기 사본의 저장된 내용이 생성 기준과 다르면 원본/보관본 행에 `보기 사본 변경됨`을 표시한다.
  `작업본으로 보존… / 변경 내용 버리기…`를 선택할 수 있고 외부 저장도 대안으로 유지한다.
  포커스 복귀·첨부목록/선택·명령 직전의 제한된 검사다. 외부 편집기의 저장 순간/미저장 버퍼를 감지한다고 하지 않는다.
- 작업본 보존은 변경 사본의 현재 bytes로 같은 업무의 독립 작업본을 만든다. 원본에서 다시 복사하지 않는다.
  원본은 그대로이고 정식 작업본은 백업 대상이다. 성공/검증 후 승인한 선택 cache를 안전하게 정리한다.
  실패/잠금/추가 변경이면 남기며 보존과 정리 결과를 분리한다. 작업본을 이어 수정하려면 새 작업본을 연다.
- 보존 뒤 원본을 다시 보면 원본 내용의 임시 사본을 사용/생성한다. 작업본을 다시 만들거나 자동으로 열지 않는다.
  외부 편집기에 열린 기존 cache가 자동으로 새 작업본 경로로 전환되는 기능은 없다.
- 미수정·미사용 cache는 기본 마지막 열람 후 7일 만료/다음 실행 후 제한된 자동 정리다.
  수정됨/사용 종료 불명은 기한만으로 삭제하지 않고 확인 목록·작업본 보존/버리기·생성 제한을 제공한다.
  만료 미수정 사본의 닫음 확인은 선택/일괄 처리할 수 있게 한다. 상세 상한/판정은 2차 설계 7절을 따른다.
- 시작 시 첫 화면/알림 준비와 일반 정리를 분리한다. 전용 cache 후보 인덱스·배치/cursor·실패별 재시도 지연을 둔다.
  기존 삭제 복구가 매 시작 전체 첨부 경로를 set에 적재하는 경로도 개선한다.
  필수 DB 이행/예약 복원/미확정 자료 안전 확인은 생략하지 않고 복구 중 파일 범위를 보호한다.
- 현재/최초 파일명과 기존 연결 자료의 처리 기준은 U15에 별도로 기록했다.

2차 설계·구현·검증의 확인 범위(회사 편집기/보안 환경은 별도 사용 확인):

- 원본 보기용 사본의 생성·재사용·정리 수명과 파일명, 회사 보안 프로그램과의 호환성.
- 이미 열려 있는 파일의 지정 방지 및 외부 프로그램 저장 방식에 대한 검증.
- 사본 기본 이름, 사본에서 다시 사본 생성, 원본 삭제·휴지통 시 연결 표시 정책.
- 좁은 창에서도 원본/사본 배지가 제목·첨부 순서 동작을 가리지 않게 표시한다.
- 파일 읽기 전용 속성만으로 완전한 보호를 보장하지 않는다. 보호된 보관본을
  일상 편집 경로에서 분리하고, 외부 변조가 발생하면 기준 체크섬으로 변경을 감지한다.
  탐색기 등으로 직접 변경하는 행위까지 절대 불가능하다고 약속하지 않는다.
- U4의 최신 크기/내용 관리 및 중복 판별 개선은 작성 사본과 일반 첨부에 여전히 필요하다.

## U6. 선택한 여러 첨부파일을 한 폴더에 일괄 저장

상태: 같은 업무의 현재 첨부 일괄 저장은 1차 구현·검증 및 사용자 사용 확인 완료.
원본/보관본까지의 대상 확장은 2차 소스에 반영했다. 보관함에서 현재 첨부/보관본을 혼합 체크해 저장한다.
U3의 단일 파일 사본 저장을 여러 파일 선택으로 확장한다.

목적: 업무 완료 후 사용자가 만든 외부 보관 폴더에 작업 파일들을 모을 때,
원본·작성 사본·선택한 보관 버전을 하나씩 저장하는 반복 작업을 없앤다.
별도의 ZIP 압축이나 전체 데이터 백업이 아니라 선택한 파일들의 외부 복사 기능이다.

기본 동작:

1. 첨부 목록에서 Ctrl/Shift 등으로 여러 파일을 선택한다.
   원본·작성 사본·보관 버전 기능이 추가되면 버전 항목도 명시적으로 선택할 수 있어야 한다.
2. 오른쪽 메뉴의 `선택 파일 저장…`으로 대상 폴더를 한 번 선택한다.
   단일 파일은 U3의 `다른 이름으로 저장…`을 유지한다.
3. 선택한 파일들을 목록의 표시 이름을 기준으로 그 폴더에 저장한다.
   내부 보관 파일명이나 저장소 하위 폴더 구조를 그대로 내보내지 않는다.
4. 프로그램 안의 첨부·원본·버전은 이동·삭제·덮어쓰지 않는다.
   외부 파일은 제출·보관용 복사본이며 이후 수정도 내부 자료에 자동 반영되지 않는다.
   내부 첨부/업무 삭제나 백업 복원도 이 외부 파일에 영향을 주지 않아야 한다.
5. 완료 후 성공·실패·건너뜀·취소 개수를 표시하고 `폴더 열기`를 제공한다.
   원본/사본/버전 중 선택하지 않은 항목을 임의로 추가하거나 제외하지 않는다.

함께 설계할 사항:

- `전체 선택`과 선택 개수·가능하면 실제 저장 용량을 표시한다. 큰 버튼을 파일마다 추가하지 않는다.
- 원본과 작업본, 여러 버전의 표시 파일명이 같거나 대상 폴더에 이미 파일이 있으면
  승인된 정책에 따라 기존 파일을 보존하고 자동 번호로 새 이름을 구분한다.
  구체 번호 형식과 결과 이름을 명확히 안내한다.
  명시적인 덮어쓰기 선택 없이 기존 파일을 바꾸지 않는다.
- Windows에서 사용할 수 없는 파일명·긴 경로·대상 폴더 접근 권한·공간 부족을 처리한다.
  관리 저장소 내부를 대상 폴더로 지정하는 것은 차단한다.
- 현재 저장된 내용만 복사한다. 미저장 편집 내용은 포함되지 않음을 안내한다.
  복사 중 변경·잠금·누락·보안 접근 거부를 감지하고 파일별 결과를 알린다.
- 여러 파일의 내용이 같아도 사용자가 선택한 원본/버전 파일을 중복 첨부 규칙만으로
  조용히 제외하지 않는다. 내부 보관과 외부 파일 복사의 의미를 구분한다.
- 백그라운드 진행·취소를 제공하고 성공한 파일 수를 표시한다.
  실패·취소 시 미완성 파일을 성공으로 남기지 않으며 기존 대상 파일은 보호한다.
  이미 정상 저장된 파일은 보존하고 남은 항목이 무엇인지 안내한다.
- 우선 한 업무의 첨부 목록을 대상으로 한다. 여러 업무의 첨부 검색 결과 일괄 저장은
  업무별 동일 이름 충돌과 선택 범위를 검토한 뒤 별도로 범위를 확정한다.
- 보관본/혼합 저장은 [2차 구현 보고](31-follow-up-phase-2-results.md)에 반영했다. 일괄 저장이 모든 수정 때의 자동 버전 생성이나
  자동 버전 삭제 정책을 추가하는 것은 아니다.
- 대량 첨부, 원본·사본·버전 동명, 기존 대상 파일 존재, 수정 중 문서,
  일부 누락/차단, 공간 부족, 중간 취소를 격리된 자료로 검증한다.

## U7. 작업 파일의 필요한 시점만 보관·보호하고 자유롭게 이름 붙이기

상태: UI·이름·생성·삭제·혼합 저장까지 [2차 전체 보고](31-follow-up-phase-2-results.md)에 반영했다. 사용자 사용 확인 대기.
원본 외에 보관본에서 작업본을 만드는 흐름을 사용자가 확인한 기존 기준을 유지한다.
U5의 원본 보호와 달리, 작성 중인 사본의 특정 시점 내용을 남기는 기능이다.

사용자 요구:

- 작성 사본을 계속 수정할 때 v1.0, v2.0 등 이전 내용을 구분해 보관할 방법이 필요하다.
- 보관한 버전도 실수로 수정되지 않게 하는 방안을 검토한다.
- 필요한 버전 여러 개를 선택하여 U6으로 외부 폴더에 함께 저장할 수 있어야 한다.

검토한 방향(제안):

- 평소에는 하나의 작업본을 수정하고, 필요할 때만 `보관본 만들기…`를 선택하는 방향이다.
  앞서 논의한 `버전으로 보관…`과 같은 목적이며 메뉴 문구는 구체 UI 설계 시 확정한다.
  외부 편집 프로그램에서 저장할 때마다 자동으로 버전을 만들지는 않는다.
- 입력은 `버전 번호` 전용 칸이 아니라 자유로운 `보관 이름` 한 칸으로 단순화한다.
  `v1.0`, `v2.0`, `초안`, `팀장 검토 반영`, `v2.0_팀장 검토 반영`을 모두 허용한다.
  번호형/설명형 등의 별도 모드를 선택하게 하거나 버전 번호를 필수로 요구하지 않는다.
- 기본 이름으로 `보관본 1`, `보관본 2` 등을 제안하고 자유롭게 고칠 수 있게 하는 안을 검토한다.
  `v2.0` 다음을 무조건 `v3.0`으로 정하지 않는다. 사용자가 `v2.1` 등을 선택할 수 있다.
- 보관 시각은 자동 기록한다. 다양한 이름을 사용해도 시간 순서를 알 수 있게 하며,
  이름 문자열만으로 생성 순서를 판단하지 않는다. 선택적인 설명은 U9와 연계한다.
- 보관 이름과 실제 저장 파일명은 구분한다. 이름 변경으로 파일 내용이 바뀌지 않으며,
  외부 저장 시 보관 이름을 반영한 안전한 파일명을 제안하는 방향이다.
- 보관 버전은 그 시점의 저장 내용을 별도로 고정하고, 확인할 때 실제 보관본을
  직접 편집 경로에 넘기지 않는 방식으로 보호한다. U5의 보호 한계도 동일하게 적용한다.
- 목록이 길어지지 않도록 작업 사본 아래에서 보관 버전을 펼쳐 보는 구성을 검토한다.
- 보관본을 만든 뒤에도 기존 작업본은 계속 수정할 수 있고, 보관본 내용은 변하지 않는다.
- v3.0 작업을 중단하고 v2.0부터 다시 작성하려면 v2.0에서 `작업본 만들기…`를 사용한다.
  기존 작업본이나 v3.0을 덮어쓰지 않고 새 작업본을 만든다. 불필요한 항목의 삭제는 별도 선택이다.
- 외부 `다른 이름으로 저장…`은 내부 보관본을 생성하거나 작업 대상을 자동 전환하지 않는다.
- 동명 보관본 표시, 새 작업본의 기본 이름·메모 연결, 삭제 확인, 백업·복원과 연결 관계는
  구현 전에 결정한다. 기존 첨부를 자동 변환하거나 오래된 버전을 자동 삭제하지 않는다.

사용성 기준:

- 한글·엑셀 등에서 편집하는 방식은 그대로이며 파일의 역할·이력 관리만 보완한다.
- 탐색기에서 이미 잘 관리하는 사용자에게 버전 관리나 메모 입력을 강요하지 않는다.
  변경이 잦거나 이전 내용을 보존할 필요가 있는 파일에만 선택적으로 사용한다.
- 내부 보관과 외부 폴더 복사는 별개임을 안내하여 보관본 생성이 독립 백업이라는 오해를 막는다.

## U8. 외부 폴더에 독립 보관한 뒤 내부 첨부를 안전하게 정리

상태: 사용자 목적 재정리. 기존 자료의 내용 확인/외부 저장 동선은 1차 사용 확인 완료.
자산·보관본·보기 캐시의 안전 정리/복구·시작 성능까지 [2차 전체 보고](31-follow-up-phase-2-results.md)에 반영했다.
U3/U6은 파일을 꺼내는 기능이고, 이 항목은 꺼낸 파일의 독립성과 내부 정리의 안전성을 다룬다.

우선 목적:

- 사용자는 중요한 파일을 자신이 만든 일반 Windows 폴더에도 직접 남기려 한다.
- OfficeFlow에서 실수로 삭제하더라도 별도로 저장한 파일은 남아 있어야 한다.
- 나중에 프로그램 없이 탐색기에서 폴더와 알아볼 수 있는 파일명으로 찾고 열 수 있어야 한다.
- 디스크 용량 절약이나 자동 정리 후보 추천은 주목적이 아니다.
  외부 폴더 자동 감시·복잡한 보관 상태 관리·의무적인 내보내기는 우선 추가하지 않는다.

기본 흐름:

1. U3/U6으로 필요한 파일을 사용자가 고른 외부 폴더에 일반 파일 그대로 복사한다.
2. 저장 위치와 파일별 성공/실패를 알려주고, 탐색기에서 확인할 수 있게 한다.
3. 내부 자료도 기본적으로 그대로 남긴다. 정리가 필요할 때 사용자가 별도로 선택한다.
4. 첨부/업무 삭제·백업 복원 시 외부 폴더의 파일을 삭제하거나 덮어쓰지 않는다.
   외부 파일은 OfficeFlow 전체 백업과 별개이며 사용자가 관리한다.

현재 정리 동작과 개선 검토:

- 업무 완료만으로 첨부를 삭제하지 않는다. 업무 휴지통 이동도 첨부를 보존한다.
- 첨부 `연결 해제`는 업무 목록에서 연결만 빼고 내부 파일을 남긴다.
  데이터관리의 첨부정리에서 복구하거나 영구 삭제할 수 있다.
- 첨부 `파일 삭제`와 휴지통 업무의 영구 삭제는 실제 내부 파일 삭제를 포함한다.
  내부 삭제 처리용 임시 보관은 Windows 휴지통이나 사용자용 되돌리기 기능이 아니다.
- 현재 첨부정리에서는 파일 열기·외부 사본 저장이 부족하다.
  삭제 전에 내용을 확인하고 U3/U6으로 보관할 수 있는 동선을 검토한다.
- 연결 해제와 실제 파일 삭제의 차이, 선택한 삭제 범위 및 되돌릴 수 없는 점을
  안내한다. 외부 저장 성공만으로 내부 파일을 자동 삭제하지 않는다.
- 날짜·완료 상태·같은 체크섬만으로 자동 삭제하지 않는다.
  반복 업무 첨부는 회차 사이에서 공유되므로 한 회차 완료를 삭제 근거로 삼지 않는다.
- 여러 첨부를 한 번에 내부 정리하는 기능은 필요성과 안전한 선택/확인 방식을
  별도로 검토한다. 일괄 외부 저장이 일괄 삭제까지 허용하는 것은 아니다.
- 내부 첨부를 삭제해도 기존 백업에는 파일이 남을 수 있음을 안내한다.
  첨부 정리가 이전 백업이나 외부 보관 파일까지 삭제하는 기능은 아니다.
- 2026-10-09: 시작 시 점검은 일반 업무/첨부 전체 스캔과 구분한다. 실제 pending 저널의 참조만 조회하고
  캐시 후보는 별도 인덱스에서 제한된 배치로 선정한다. 첫 화면/알림을 일반 정리 완료까지 기다리게 하지 않는다.
  필수 복구 안전 확인과 파일 범위 보호는 유지한다. 메타데이터 조회 속도만으로 시작 시간 검증을 대체하지 않는다.
- 이후 장기간 누적 용량·여러 업무의 정리 후보·읽을 수 있는 업무 자료 동봉은 아래 U16에서 별도로 검토한다.
  기존 U8의 외부 저장/내부 삭제 분리와 자동 삭제 금지 원칙을 유지한다.

## U9. 첨부파일별 선택적인 메모

상태: 일반 첨부의 선택 메모 편집/목록·선택 상세 표시를 구현하고 격리 검증했다.
원본/작업본/보관본 생성 이후 전체 흐름까지 연결했다. [2차 전체 보고](31-follow-up-phase-2-results.md).
외부 설명 TXT와 메모 검색/자동 상속은 계속 보류한다.

목적: 업무 전체의 결과메모/업무일지와 구분하여, 개별 파일의 용도·주의점·검토 상태 등을 남긴다.
예: `2026년 개정 서식`, `금액 확인 필요`, `10월 8일 제출한 파일`.

검토한 기본 동작:

- 첨부 오른쪽 메뉴의 `메모 편집…`에서 작성·수정한다. 입력은 선택 사항이다.
- 파일명 아래에 메모 한 줄을 표시하고 긴 내용은 별도로 확인하는 구성을 검토한다.
  메모가 없는 파일은 불필요한 빈 줄을 만들지 않는다.
- 파일 내용·확장자·이름은 바꾸지 않는다. 메모는 첨부 정보로 저장하고
  OfficeFlow 백업·복원 및 다른 PC 이동 시 유지한다.
- 원본/사본/보관 버전이 각각 다른 메모를 가질 수 있도록 관계를 설계한다.
  사본 생성 시 메모 복사 여부와 첨부 검색에 메모를 포함할지는 추가 결정한다.

외부 저장 시 추가 제안(미확정):

- U3/U6으로 일반 파일만 저장하면 프로그램 안의 메모가 파일 자체에 따라가지는 않는다.
- 필요할 때 `첨부파일 설명.txt`도 함께 저장하는 선택사항을 검토한다.
  기본은 파일만 저장하며 설명 파일을 자동으로 만들지 않는다.
- 설명을 함께 저장할 경우 실제 내보낸 파일명과 메모를 대응시키고,
  기존 설명 파일의 덮어쓰기·동명 충돌을 안전하게 처리한다.
- 업무 결과메모/일지를 첨부 메모로 자동 복제하거나 메모를 완료 조건으로 요구하지 않는다.

## U10. 첨부·작업본·보관본의 파일 보존과 실패 상황 검증

상태: 1·2차의 생성·삭제·보기 사본·전체 백업/복원 및 실제 프로세스 중단 검사를
[2차 전체 보고](31-follow-up-phase-2-results.md)에 기록했다. 회사 편집기/보안 환경의 사용 확인과
배포 검증은 별도이며, 이후 구현한 U12~U14에도 같은 보존 조건을 적용했다.
추가 검사 결과는 [3차 보고](36-follow-up-phase-3-results.md)를 따른다.

목적: 버전 관리의 편의보다 파일 보존을 우선한다. 정상 사용뿐 아니라 처리 도중의
강제 종료·저장 실패에서도 기존 원본·작업본·보관본을 잃지 않도록 한다.

현재 코드에서 다시 확인한 보호 장치:

- 첨부는 외부 파일을 이동하지 않고 내부 저장소로 복사한다.
- 임시 파일 복사를 마친 뒤 정식 경로로 확정한다. DB 등록 실패 시 새로 가져온 파일을 정리한다.
- 첨부 삭제는 임시 격리 후 DB 처리를 하고, DB 삭제 실패 시 파일을 복구하도록 되어 있다.
  완료된 영구 삭제를 사용자가 되돌리는 휴지통 기능과는 다르다.
- 새 전체 백업은 DB·정식 파일 자산·복구 자료를 구분해 담고 검증 후 확정한다.
  필요한 파일 누락/고정 내용 불일치이면 성공으로 확정하지 않는다. 종전 형식의 누락 선언은
  경고로 구분하며 백업에 없는 내용을 복구할 수 있다고 안내하지 않는다.

새 기능의 필수 보존 원칙:

1. 작업본/보관본 생성 실패는 기존 파일을 변경·삭제하지 않는다. 이름이 같다는 이유로 덮어쓰지 않는다.
2. 저장 중인 문서를 복사할 때 안정된 저장 내용인지 확인한다. 변경·잠금·접근 거부가 있으면
   실패 또는 재시도를 안내하며, 미완성 복사본을 정상 보관본으로 표시하지 않는다.
3. 실제 파일 확정과 DB 등록 사이에 종료되어도 재실행 시 상태를 확인할 수 있도록 설계한다.
   정리 과정에서 기존 자료를 추정하여 삭제하지 않고, 파일만 남거나 정보만 남은 상태를 안전하게 다룬다.
4. 이전 보관본에서 다시 작업할 때 새 작업본을 만들어 기존 작업과 모든 보관본을 보존한다.
5. 원본·보관본의 실제 파일을 일반 편집 경로에 넘기지 않는다. 보기용 사본 정리는
   실제 작업본이나 보관본 삭제와 분리한다.
   보기용 사본은 캐시로 재사용하고 미수정·미사용 항목만 안전하게 자동 정리한다.
   수정됨/사용 중/판정 불가 사본은 보존하며, 정리 시점과 상한은 2차 상세설계 7절을 따른다.
   공통 기준은 `24-follow-up-common-design.md`의 7.4절을 따른다.
6. 외부 저장은 복사만 수행한다. 내부 삭제·백업 복원은 외부 사본을 삭제하거나 덮어쓰지 않는다.
7. 원본·작업본·보관본과 역할·연결·보관 이름·시각·메모가 백업/복원 및 PC 이동 후 유지되어야 한다.
   기존 사용자 첨부를 변환할 때 이미 수정한 내용도 보존한다.

격리 자료로 확인할 필수 검사:

- 복사 중, 파일 확정 직후, DB 등록 전후에 강제 종료하고 재실행하여 기존 파일 보존을 확인한다.
- 공간 부족, 파일 잠금, 권한/보안 접근 거부, DB 저장 실패, 복사 중 문서 변경을 재현한다.
- 취소·반복 실행·동명 입력에서도 기존 내용을 덮어쓰지 않는지 확인한다.
- 보관본 생성 후 작업본을 수정해도 보관본이 바뀌지 않는지, 이전 보관본에서 새 작업을
  시작해도 원래 작업본과 이후 보관본이 남는지 확인한다.
- 실제 백업을 복원한 뒤 파일 내용과 연결 정보를 확인한다. 누락·손상 백업과 중간 복원 실패도 검사한다.
- 내부 첨부/업무의 삭제·복원 후 외부 폴더에 저장한 파일 내용이 그대로인지 확인한다.
- 정상 흐름 검사만 통과했다고 배포하지 않고 위 실패 상황의 보존 검사를 함께 통과시킨다.

보호 한계와 안내:

- 체크섬은 변경/불일치를 감지하는 수단이지 파일을 복구하는 수단은 아니다.
- 동일 PC에 원본·작업본·보관본을 여러 개 두는 것은 디스크 고장에 대비한 독립 백업이 아니다.
- 같은 디스크의 외부 폴더 사본은 프로그램 내부 삭제 실수에 대비할 수 있지만,
  디스크 고장까지 대비하려면 회사 정책이 허용하는 별도 저장 위치의 복사/백업이 필요하다.
- 외부 직접 삭제·디스크 손상·회사 보안 프로그램의 격리까지 절대 막는다고 보장하지 않는다.
  안전한 실패 처리, 이상 안내, 검증된 백업과 독립 사본으로 위험을 줄인다.

## U11. 새 UI의 테마·가독성 누락 방지

상태: 2026-10-08 사용자 요청으로 상시 개발 기준에 반영. 이번 작업은 지침 기록이며
프로그램의 테마 코드나 기존 화면을 변경한 것은 아니다.

- 새 화면부터 공통 밝은 테마와 글자/배경 쌍을 적용하고 내부 본문·팝업까지 확인한다.
- 매번 모든 환경을 검사하지 않고 변경 영향 범위에 비례하여 검증한다.
  공통 UI 변경과 릴리스에서는 대표 화면의 시스템 테마·배율·좁은 창 점검을 포함한다.
- 상세 기준은 `06-development-process.md`의 테마·가독성 공통 기준에 두고,
  저장소 `AGENTS.md`에서도 UI 작업 전에 이를 확인하도록 안내한다.

## U12. 업무 세부사항의 자동 변경 이력

상태: 사용자와 검토 후 개선 대상으로 추가. 수동 보관만 우선 제공하자는 중간 제안은
이후 사용자가 업무 세부사항의 잦은 변경을 고려하여 자동 이력과 수동 보관을 함께
추가하는 방향에 동의하면서 대체되었다. 초기 기록 범위와 자동 삭제하지 않는 정책은
사용자 승인으로 확정했다. 3차 소스 구현·격리 검증 완료, 사용자 사용 확인 전.
2026-10-09: [3차 상세설계](35-follow-up-phase-3-design.md) 2~4절·7~8절에 명령 단위/원자성/조회를 확정했다.
실제 반영 범위와 검사는 [3차 보고](36-follow-up-phase-3-results.md)를 따른다.

목적: 업무 내용을 수정한 뒤 무엇이 바뀌었는지 확인하고, 실수로 지운 내용을 찾는다.
현재 설명란은 계속 편집하는 곳이고, 이력은 과거 내용을 읽는 곳이다.
같은 설명을 사용자가 다시 작성하게 하지 않는다.

검토한 동작:

- 초기에는 제목·설명·일정·중요도·상태·결과메모 변경을 대상으로 한다.
  반복 회차별 결과메모의 연결은 구체 설계에서 정돈한다.
  체크리스트 세부 변경과 기존 업무일지 기록 편집 이력은 초기 범위에 포함하지 않는다.
- 입력하는 글자마다 저장하지 않는다. 실제 내용이 달라진 채 저장에 성공했을 때
  이전/새 내용과 변경 시각을 기록한다. 취소·저장 실패·내용이 같은 저장은 정상 변경 이력으로 남기지 않는다.
- 현재 내용을 덮어쓰는 작업과 이력 기록의 정합성 및 실패 처리를 함께 설계한다.
- 지난 내용을 확인하거나 복사할 수 있게 한다. 이전 설명을 현재에 반영할 때는
  명시적인 선택과 확인이 필요하며 현재 내용을 조용히 덮어쓰지 않는다.
- 기존 업무일지를 같은 내용으로 자동 복제하거나 체크리스트 완료 기록을 새로 만들지 않는다.
- 첨부의 모든 외부 편집 저장까지 자동 추적하거나 모든 저장에 보관본을 만들지는 않는다.
  파일의 특정 시점 보존은 U7/U13의 명시적인 보관 기능과 구분한다.
- 평소 업무 화면을 늘리지 않고 U14의 `이력·보관` 화면에서 확인하는 방향이다.
- 초기 자동 이력은 자동 삭제하지 않는다. 필요한 범위만 조회하는 방식으로 구현한다.
  과거 이력 검색과 대량 조회 방식은 추가 설계하며, 향후 보존 기간 제한은 별도 사용자 선택으로 정한다.
- 2026-10-09: 장기 자료 정리 후보 U16에 선택한 과거 이력 정리와 조회/비교 범위 안내를 기록했다.
  기록만으로 현재 자동 이력의 보존·삭제 정책을 변경하지 않는다.

## U13. 중요한 시점의 업무 내용·선택 첨부를 수동 묶음 보관

상태: 사용자가 중요한 시점에 직접 남기는 사용 흐름을 확인했고, U12와 함께
추가하는 방향에 동의했다. 포함 범위와 실패 처리/삭제의 공통 정책은 사용자 승인으로 확정했다.
구체 UI·저장 구조·삭제 확인 동작을 구현하고 격리 검증했다. 사용자 사용 확인 전이다.
2026-10-09: [3차 상세설계](35-follow-up-phase-3-design.md) 4~6절·9절에 저장/다중 캡처/참조·삭제·백업을 확정했다.
실제 반영 범위와 검사는 [3차 보고](36-follow-up-phase-3-results.md)를 따른다.

목적: `팀장 검토 요청 전`, `수정 지시 반영`, `최종 제출`처럼 중요한 시점의
업무 자료를 함께 남겨 나중에 당시 내용과 파일을 확인한다.
보관 자체가 제출 행위를 수행하거나 실제 제출 사실을 증명하는 기능은 아니다.
2026-10-09 사용 확인 보완: 보관 입력/보관 파일 목록의 연한 기본 체크박스를
20px 파란 테두리·명시적 체크 표시로 정돈하고 선택 안내를 추가했다.
체크 수/버튼 문구와 좁은 창·배율별 관련 검사는 [3차 보고](36-follow-up-phase-3-results.md) 10절을 따른다.

검토한 기본 흐름:

1. 사용자가 중요하다고 판단한 시점에 `이력·보관 → 현재 상태 보관…`을 선택한다.
2. 자유로운 보관 이름을 입력하고 보관할 첨부를 선택한다.
   기존 설명·결과메모는 당시 내용을 가져오며 별도 설명을 다시 작성하도록 요구하지 않는다.
3. 보관 이름·시각, 당시 기본 업무 정보·결과메모·체크리스트 상태,
   선택한 첨부의 실제 저장 내용을 고정한다. 문서 프로그램의 미저장 내용은 포함하지 않는다.
4. 이후 현재 업무나 작업 파일을 수정해도 보관 묶음은 바뀌지 않는다.
5. U14에서 과거 묶음을 열어 읽거나 필요한 파일을 U3/U6으로 외부 폴더에 저장한다.

설명·체크리스트·일지와 중복하지 않는 기준:

- 설명은 현재 업무 내용, 체크리스트는 현재 진행 여부, 묶음 보관은 당시 자료의 고정본이다.
  진행 여부만 표시할 목적이면 체크리스트로 충분하며 자료 보관을 필수 단계로 요구하지 않는다.
- 체크리스트의 당시 체크 상태를 참고용 읽기 전용 정보로 포함한다.
  보관 화면에서 체크를 바꿔 현재 체크리스트에 반영하지 않는다.
- 체크 완료마다 자동 보관하거나 보관 여부를 확인하는 체크 항목을 자동 생성하지 않는다.
- 보관할 때 같은 설명/메모를 업무일지에 새 기록으로 복제하지 않는다.
- 현재 업무는 계속 편집하고 과거 내용은 `이력·보관`에서만 확인하는 방향이다.
  과거 화면에는 보관 이름·시각과 현재 내용이 아니라는 표시가 필요하다.

자료 보존과 이전 내용 활용:

- 파일명/연결 정보만 보관하지 않고 선택한 파일의 당시 저장 내용을 보존해야 한다.
  일부 파일 복사 실패 시 해당 묶음을 완료로 확정하지 않고 실패 항목을 알려 재시도한다.
  사용자가 보관 범위를 명시적으로 바꿔 새로 보관할 수 있지만 실패 파일을 조용히 제외하지 않는다.
- 지난 설명은 명시적으로 가져오고, 보관 첨부는 새로운 작업본으로 만든다.
  과거 묶음을 열거나 내용을 가져왔다고 현재 업무의 완료 상태·일정·알림 실행 상태를
  통째로 과거로 되돌리지 않는다. 일정 수정이 필요하면 일반 편집 흐름에서 명시적으로 처리한다.
- 수동 보관 묶음은 자동 변경 이력의 보존 기간과 같은 기준으로 자동 정리하지 않는다.
  삭제 범위·확인·업무 영구 삭제와의 관계는 별도 설계한다.
- 묶음과 포함 자료/연결 정보를 전체 백업·복원 및 PC 이동 후 보존한다. U10 검증을 적용한다.
- U7의 개별 첨부 보관본과 같은 보존 기능을 활용하여 서로 독립된 두 버전 관리 기능으로
  구현하지 않는 방향이다. 공유된 보관 파일의 연결 해제/삭제 때문에 묶음 자료가 사라지지 않게 설계한다.

## U14. 자동 변경과 수동 보관을 한 흐름으로 보는 통합 이력

상태: 사용자가 `a → b → c → d`처럼 변화를 한눈에 보는 기능을 제안했다.
타임라인과 자유로운 문장 비교를 구현하고 격리 검증했다. 사용자 사용 확인 전이다.
2026-10-09: [3차 상세설계](35-follow-up-phase-3-design.md) 7~8절에 한 줄 목록/지연 상세/범위·비교·페이지를 확정했다.
실제 화면·조회·비교 검사 결과는 [3차 보고](36-follow-up-phase-3-results.md)를 따른다.

검토한 화면 방향:

- 업무 하나의 U12 자동 변경과 U13 중요 보관을 시간순 한 흐름에서 보여준다.
  가로로 끝없이 늘어놓지 않고 좁은 창에서도 읽을 수 있는 세로 이력을 기본으로 검토한다.
- 각 항목에 시각과 `내용 변경`/`중요 보관` 구분을 표시한다. 색상만으로 구별하지 않는다.
- 요약에는 바뀐 항목과 짧은 미리보기만 표시한다. 누르면 당시 전체 내용을 확인한다.
- 원하는 두 시점을 선택하여 비교하는 기능을 검토한다. 변경하지 않은 내용은
  기본적으로 접고 필요하면 문맥/전체 내용을 확인할 수 있게 한다.
- 정해진 값의 일정·상태는 `10월 15일 → 10월 18일`처럼 표시할 수 있다.
- 현재 상태도 과거와 구분한다. 평소 업무 화면에 모든 이력을 펼치지 않는다.
- 이력 증가 시 조회 범위·추가 불러오기 등을 설계하여 전체 이력을 매번 한꺼번에 읽지 않는다.

자유로운 설명·메모 비교의 정확성:

- 사용자가 `예산 100만원`을 `예산 100(천원)`으로 고칠 수 있으므로
  자유 문장을 구조화된 예산 필드처럼 자동 해석하거나 의미를 추정하지 않는다.
- 수정 전후의 실제 작성 문구를 보존하고 바뀐 부분을 강조한다.
  숫자가 같다고 같은 금액으로 취급하거나 단위·표현을 임의로 변환하지 않는다.
- 대폭 재작성은 억지로 간단한 화살표 요약으로 연결하지 않고 수정 전후 전체 문장을 보여준다.
  긴 글의 생략 부분과 주변 문맥을 확인할 수 있게 하여 미리보기를 전체 내용으로 오해하지 않게 한다.
- 한글·엑셀 첨부의 문서 내부 변경 비교는 우선 범위에 넣지 않는다.
  파일 추가/제외와 사용한 보관본을 표시하고, 당시 파일을 별도로 확인하게 한다.
  체크섬 차이를 문서 내용의 의미상 차이로 설명하지 않는다.

## U15. 첨부 표시 이름 변경과 기존 연결 자료 유지

상태: 일반 첨부의 표시 이름 변경, 현재 이름 검색/외부 저장과 최초 이름 보존을 구현하고 격리 검증했다.
원본/작업본 생성·보기 cache 연결과 이름 변경 시 출처 정보 보존을 검증했다. [2차 전체 보고](31-follow-up-phase-2-results.md).
첨부를 올린 뒤 마음에 들지 않는 이름을 고칠 수 있게 하되 파일/연결/과거 자료를 바꾸지 않는 기능이다.

정리한 동작:

1. 일반/원본/작업본 단일 항목의 오른쪽 메뉴 `이름 변경…`에서 이름 본문만 수정한다. 확장자는 고정한다.
   원본의 내용 고정과 표시 이름 변경은 별개다. 빈 이름/금지 이름·문자·경로/길이 오류를 검증한다.
2. 기존 `original_name`은 최초 파일명으로 보존하고 새 `display_name`을 현재 이름으로 사용한다.
   기존 자료는 동일 이름으로 이행한다. 목록/첨부 검색/외부 저장 기본 이름을 같이 갱신한다.
3. 실제 UUID 파일명/경로, asset·첨부·계열 ID, bytes/해시, 메모/수동 순서는 바꾸지 않는다.
   이름 변경 때문에 원본/작업본/보관본을 재생성하거나 외부 파일을 찾아 이름 바꾸지 않는다.
4. 원본 이름 변경 전에 만들어 둔 작업본의 자체 이름은 그대로다. 원한다면 해당 작업본도 별도로 변경한다.
   기존 보관본의 보관 이름·당시 파일명·내용·당시 출처 이름은 그대로 둔다. 보관 이름 변경은 이번 범위에 추가하지 않는다.
5. 연결은 문자열 이름이 아니라 안정적인 ID다. 현재 출처 요약에는 새 이름을 보여주되 상세에서는
   `현재 출처 이름 / 생성·보관 당시 출처 이름`을 구분한다. 출처가 삭제되면 당시 정보와 삭제 표시를 유지한다.
   3차 업무 묶음의 과거 이름도 현재 이름 JOIN으로 바꾸지 않는다.
6. 이미 열린 외부 문서/cache/외부 저장 사본의 물리 이름은 그대로다. 새로 만드는 보기 사본은 최신 이름을 제안한다.
   휴지통/해제 상태는 먼저 복원하고 이름을 변경한다. 일괄 이름 변경은 제외한다.

검증: 이름 변경 후 검색·외부 저장·전체 백업/복원, CAS 충돌/취소/동명·한글·긴 이름,
원본 변경 전 생성한 작업본·보관본 연결/과거 이름 보존, 열린 파일/cache 경로 불변을 2차 완료 조건에 포함한다.
상세 위치: [2차 설계](27-follow-up-phase-2-design.md) 3.7절·4절·10절·12절.

## U16. 장기 사용에 따른 업무 이력·첨부·보관·백업의 안전한 정리

기록일: 2026-10-09. 상태: 사용자 요청으로 후속 개선 후보에 기록. 상세설계·구현은 미진행.
이번 요청은 논의 내용 기록이며 프로그램/DB/운영 자료/버전/배포물/커밋/GitHub는 변경하지 않는다.
U8의 외부 저장/내부 정리와 U10 안전 계약을 재사용하며 U12/U13의 장기 보존 문제를 확장 검토한다.
현재 3.0.8의 개별 첨부·보관 삭제와 달리, 여러 업무의 후보 조회·업무 정보 동봉 외부 보관·
과거 자동 이력만 정리·DB 공간 축소를 한 동선으로 제공하는 기능은 아직 없다.

### 목적과 확인한 부담

- 1년 사용량이 작더라도 여러 해의 이력·작업본·보관 파일·전체 백업은 계속 누적된다.
- 자동 이력은 업무 정보의 변경 전/후를 저장한다. 매 변경마다 첨부파일을 복제하지는 않으나
  긴 설명을 자주 수정하면 DB가 커질 수 있다.
- 편집 가능한 파일을 중요 시점마다 보관하면 독립 고정 사본이 증가한다. 기존 같은 고정 자산은
  참조로 재사용하지만 내용 해시가 같은 모든 파일을 자동으로 중복 제거하는 것은 아니다.
- 용량뿐 아니라 백업·검증·복원 시간, 여러 보관본 중 필요한 자료를 찾는 어려움도 고려한다.
- 정식 자료와 안전 조건을 만족한 임시 보기 사본 정리를 구분한다. 원본·중요 보관은 만료 캐시가 아니다.

### 제안한 사용자 흐름

1. `데이터 → 오래된 자료 정리`에서 완료 후 경과 기간, 업무별 첨부/보관 용량,
   오래된 개별 보관본·중요 시점 보관을 기준으로 후보를 찾는다. 기간 `2년`은 예시이며 확정 기본값이 아니다.
   기간·완료·큰 용량은 후보 조건이지 삭제 허가가 아니다. 진행 중 업무·원본 파일은 기본 선택에서 제외한다.
   반복 업무의 한 회차 완료를 공통 첨부/다른 회차 정리 근거로 삼지 않는다.
2. 필요하면 원하는 외부 폴더에 업무별 독립 자료를 보관한다. 프로그램 없이 읽을 수 있는
   제목·설명·결과·일지 문서와 선택 첨부/보관 파일, 파일 목록·보관 이름·메모를 함께 저장하는 방향이다.
   외부 보관은 기본 권장 동선이며 강제하지 않는다. 전체 백업과 별개이고 앱의 자동 재가져오기/복원 약속은 아니다.
3. 외부 보관을 선택했다면 복사 완료와 내용 검증을 확인한 뒤 별도 내부 삭제 확인으로 진행한다.
   부분 실패/취소를 전체 보관 완료로 표시하지 않는다. 실패 범위의 삭제는 보류하고
   검증이 끝난 범위만 따로 정리할지는 상세설계에서 확정한다. 저장 성공을 자동 삭제 승인으로 해석하지 않는다.
4. 삭제 범위는 `선택 첨부·보관본만`, `선택 과거 자동 이력만`, `업무 자체 영구 삭제`로 구분한다.
   파일만 정리하면 현재 업무 정보·일지·선택하지 않은 보관 자료는 유지한다.
   업무 자체 영구 삭제는 기존 휴지통/보관 범위 승인과 업무일지 연결 해제·보존 정책을 따른다.
5. 최종 확인에는 실제 항목명·업무/회차·삭제/유지 자료 수·물리 파일의 실제 감소 가능 용량을 표시한다.
   공유 자산은 중복 계산하지 않고 다른 참조가 있으면 유지한다. 외부 보관 파일·기존 백업은 삭제 범위가 아니다.

### 보존·복구·성능 기준

- 자동 삭제는 기본 꺼짐이다. 원본·중요 보관·과거 이력을 오래됐다는 이유로 자동 폐기하지 않는다.
  후보 기본 선택/보호 표시/기간/자동화 도입은 구현 전에 별도 확정한다.
- 모든 파일 삭제는 기존 참조 계산·사용 예약·잠금·삭제 계획·저널·확정 영수증을 재사용한다.
  확인 이후 변경/새 참조/중단·불명 자료가 발견되면 보류/보존한다. 외부 폴더와 불명 파일을 임의 청소하지 않는다.
- 자동 이력 정리는 현재 업무·중요 보관을 바꾸지 않는다. 삭제한 기간에는 과거 조회/비교가
  불가능하다는 안내와 남은 이력의 시작 범위/기준을 제공한다. 최신 충돌 판정값·재시도 영수증은
  단순히 오래됐다는 이유로 함께 제거하지 않는다. append-only 계약/스키마 변경이 필요하면 공통·상세설계를 먼저 보완한다.
- 정리 전 보호 백업과 복구 동선을 설계한다. 전체 백업 복원은 현재 자료를 교체할 수 있으므로
  개별 자료 복구와 혼동하지 않는다. 보호 백업 자체의 보존 기간/개수도 별도 확정하여 무한 누적을 피한다.
- 내부 정리 후에도 기존 백업에 삭제한 자료가 남는다. 백업 정리는 별도 선택·범위 확인으로 제공하고,
  삭제하면 복구 가능한 과거 시점이 줄어드는 것을 안내한다. 기존 자동 백업 개수 제한/수동 정리를 재사용한다.
- DB 행 삭제만으로 DB 파일 크기가 즉시 줄어드는 것은 아니다. 공간 재사용과 실제 축소를 구분한다.
  DB 공간 정리는 매 시작이 아닌 별도 유지보수 후보이며 사전 백업·여유 공간·연결/작업 종료·
  중단 복구 및 완료 검증을 상세설계한다. 근거: [SQLite VACUUM](https://www.sqlite.org/lang_vacuum.html).
- 후보/용량 조회는 인덱스·페이지·제한 배치로 처리하고 시작 시 전체 파일 해시를 수행하지 않는다.
  외부 보관/삭제는 진행·취소를 지원하며 알림을 막지 않는다. DB 공간 정리는 별도 안전 시간에 수행한다.

### 권장 순서와 남은 결정

- 1단계 후보·용량·외부 보관과 선택 파일/보관 정리 → 2단계 과거 자동 이력 정리 →
  3단계 필요 시 DB 공간 축소. 새 차수 번호·일정·구현 승인은 아직 정하지 않았다.
- 상세설계 전 확정할 것: 후보 기간/최근 변경 기준, 기본 제외·보호 자료, 외부 문서 형식/동명 처리,
  정리 전 백업·복구 방법/보존 기간, 이력 기준점·영수증 유지, 복수 업무/반복 회차/부분 실패의 정리 경계.
- 실제 구현 시 공유 참조/외부 저장 검증 실패/열린 파일/강제 종료/변경 경쟁/큰 자료/백업 복원과
  밝은 테마·좁은 창을 격리 자료로 검사한다. 기록 자체를 구현·검증·배포 완료로 표시하지 않는다.

## U17. 외부 업무 폴더 바로가기

기록일: 2026-10-10. 상태: 사용 목적·첫 범위 합의와 화면 시안까지 검토. 상세설계·구현은 미진행.
오늘 배포하는 3.0.9에는 포함하지 않는다. 후속 요청 때 공통 계약 영향과 상세설계를 먼저 확정한다.

- 사용자가 직접 관리하는 외부 업무 폴더의 표시 이름·경로·순서만 저장한다.
  OfficeFlow 첨부 저장소/보기 캐시 등 내부 관리 폴더는 연결 대상에서 제외한다.
- 열기는 탐색기로 이동하는 동작이다. 외부 파일을 복사·이동·삭제·정리·감시하지 않는다.
  연결 삭제는 바로가기 정보만 제거하며 실제 폴더/파일에 손대지 않는다.
- 백업에는 연결 정보만 포함한다. 외부 파일 내용 보관이나 중요 시점의 파일 동결을 약속하지 않는다.
- 폴더/상위 폴더 이름 또는 위치 변경 시 기존 연결을 유지하고 `폴더 다시 지정`으로 경로를 바꾼다.
  열기 실패를 삭제/실제 이동으로 단정하지 않는다. 공유폴더의 접속/권한 문제일 수도 있다.
- 첫 UI는 기존 업무 기록 창의 폴더 탭과 목록/달력의 오른쪽 메뉴 접근을 검토한다.
  새 업무 등록 기본 Tab 이동이나 메인 화면 전체 개편은 하지 않는다. 좁은 창·밝은 테마 기준을 유지한다.
- 시작 시 모든 폴더 검사/전체 디스크 탐색/자동 경로 추적은 하지 않는다.
  같은 경로의 여러 업무 연결 변경과 상위 경로 일괄 변경은 필요 확인 후 별도 상세 결정이다.
- URL은 첫 범위에서 제외한다. 외부 파일 직접 연결도 보류한다.

### U16 추가 논의: 읽을 수 있는 업무 묶음과 경량화

2026-10-10 사용자 요청으로 후속 후보를 보완한다. 아직 구현·자료 정리·자동 삭제 승인이 아니다.

- 끝난 업무의 제목/설명/일정/완료 요약/체크리스트/업무일지와 선택 파일을 외부 폴더에 묶어 남긴다.
  예시 `업무내용.html + 첨부파일/ + 보관본/`은 탐색기/브라우저에서 앱 없이 읽는 용도다.
  실제 외부 문서 형식, 파일 링크, 안전한 이름과 충돌·출처/메모 표현은 상세설계에서 확정한다.
- 원본·작업본·개별 보관본·중요 시점 파일 중 선택/제외 범위를 명확히 표시한다.
  프로그램이 임의로 최종본을 결정하지 않는다. HTML은 사용자 문자열 이스케이프와 상대 파일 링크가 필요하다.
- 외부 저장은 내부 자료를 줄이지 않는다. `내보내기 → 복사·내용 검증 → 사용자 확인 → 별도 내부 정리`
  순서를 유지하며 부분 실패/취소를 삭제 허가로 사용하지 않는다.
- 파일만 정리한 뒤 업무 텍스트/검색과 `외부 보관됨·저장 폴더 위치`를 남기는 방향을 검토한다.
  외부 폴더를 옮겼다면 다시 지정한다. 자동으로 외부 자료를 추적/재가져오지 않는다.
  반복 범위, 공유 참조, 삭제 영수증과 현재/과거 파일 링크 보존은 U16 상세설계에서 먼저 확정한다.
- 업무 묶음은 사람이 읽고 사용하는 독립 사본이지 전체 백업/자동 재가져오기 파일이 아니다.
  전체 복원용 `.ofbackup`과 역할을 구분하고 실제 외부 폴더 백업은 사용자가 따로 관리한다.
- 파일 정리는 용량·백업·검증/복원 부담을 줄인다. 화면/메모리 경량화는 별도 실측이 필요하며
  자료 증가만으로 느려진다고 단정하거나 외부 내보내기로 화면 속도 개선을 약속하지 않는다.
- 우선 읽을 수 있는 묶음 내보내기를 구현/사용 확인한 뒤 내부 정리를 연결하는 방향이다.
  자동 이력 정리·DB 실제 공간 축소·백업 보존 정리는 기존 U16의 별도 단계/안전 기준을 유지한다.

### 이번 아이디어 비교에서 제외·보류한 후보

- 업무 복사/템플릿: 상황·환경이 매번 달라지고 입력량도 적다는 사용자 판단으로 제외한다.
- 스마트 목록/관련 업무 자동 추천/첨부 본문 검색: 당장 필요성이 낮아 보류한다.
  별도 요청 없이 새 목록/추천 모델/파일 본문 추출·외부 서비스는 추가하지 않는다.

## 별도 검토 메모: Git 활용과 기술 선택

상태: 활용 검토만 진행했다. Git의 실제 내장·로컬 저장소 연결·외부 업로드는 선택/구현하지 않았다.

- U12의 텍스트 변경 이력과 U13의 시점 묶음 보관에 Git의 개념을 활용하는 방향이 유용하다.
  사용자에게 Git 설치·커밋·브랜치 조작을 요구하지 않는 형태를 우선 검토한다.
- 두 기능은 Git 없이도 구현할 수 있다. Git 도입 자체가 파일 보존·백업을 보장하지 않으며
  DB/파일 정합성, 외부 편집 중 변경, 강제 종료 복구는 별도로 해결해야 한다.
- 실행 중인 SQLite DB 파일을 그대로 Git으로 관리하는 방식을 기본으로 삼지 않는다.
  데이터의 일관된 스냅샷과 현재 전체 백업/복원 절차를 유지한다.
- 업무자료를 개발 소스 저장소나 GitHub에 자동 업로드하지 않는다.
  로컬 이력 관리와 원격 전송은 별개이며 외부 전송에는 회사 정책 및 별도 사용자 선택이 필요하다.
- 코드·스크립트를 자주 사용하는 경우 기존 로컬 Git 저장소를 업무에 연결하거나
  Git 이력을 오프라인으로 옮기는 기능은 장기 후보일 뿐 현재 추가할 기능으로 확정하지 않았다.

## 별도 보류 메모: 회사 PC의 시간대 목록 파일 처리

- `tzdata`의 `zone.tab`, `zone1970.tab`, `zonenow.tab`이 회사 보안 프로그램에서
  암호화 처리된 것으로 사용자 보고가 있었다. 실제 제품 메시지·경로는 미확인이다.
- OfficeFlow의 시간 계산과는 별개의 시간대 목록이며, 세 파일의 읽기를 막은
  시험에서도 `Asia/Seoul` 계산은 정상이었다. 실제 시간대 데이터와 패키지 전체는 필요하다.
- 배포/설치에서 정확한 세 파일을 제외하는 것은 검토 후보일 뿐 확정하지 않았다.
  설치 후 삭제만으로 최초 설치 중 감지를 예방할 수 있는 것도 아니다.
- 회사 정책 확인 없이 보안 우회·확장자 위장·필수 시간대 데이터 삭제를 하지 않는다.
